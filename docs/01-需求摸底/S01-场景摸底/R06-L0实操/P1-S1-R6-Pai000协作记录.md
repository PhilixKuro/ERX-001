**② 重装踩到两个坑（Claude 在执行中发现）**

**提出者：** Claude

**⚠ 讨论中发现（两条，均已解决，且两条都该写进 docker/README.md）**：

**坑一：`bench reinstall` 在无 TTY 环境下必须显式传 `--admin-password`，否则 drop 完数据库才失败，且会连带丢掉 erpnext。** 首次执行 `bench --site erx.localhost reinstall --yes --db-root-password 123` 报 `EOFError`。成因经读源码确认：`frappe/commands/site.py:462-499` 的 `_reinstall()` 把 `admin_password=None` 原样传给 `_new_site()`，而 `frappe/utils/install.py:132` 的 `get_admin_password()` 是 `frappe.conf.get("admin_password") or getpass.getpass(...)`——站点 `site_config.json` 里**没有** `admin_password` 字段（`up.sh` 建站时经 `--admin-password` 传入、不落盘），而 `docker compose exec -T` 无 TTY，`getpass` 遂抛 `EOFError`。

**真正的代价不是失败本身，而是失败点的位置**：`_reinstall()` 先读旧库的 `get_installed_apps()`（第 478 行）拿到 `["frappe","erpnext"]`，然后 drop 库、按序装 app。它在**装完 frappe、装 erpnext 之前**死在密码提示上，此时 `installed_apps` 已被改写为 `["frappe"]`。故**第二次 reinstall 只会装 frappe**——它读的是已经被污染的 `installed_apps`。处置：reinstall 后须 `bench --site erx.localhost install-app erpnext` 单独补装。**正确的一次性命令是** `bench --site {site} reinstall --yes --admin-password admin --db-root-password 123`。

**坑二：`--bare` 里保存 `System Settings` 必须一并给 `language`。** 只设 `country` 与 `time_zone` 去 `save()` 撞 `MandatoryError: [System Settings, System Settings]: language`——该字段 `reqd=1`，而 reinstall 后其值为空。已在 `--bare` 段内加 `if not ss.language: ss.language = "en"` 兜底，中文由随后的 `set-locale.sh` 覆盖（它设 `System Settings.language` 与 `User.language` 两处）。

**结论：** 两坑均已解决，空站点起点已造出并经 16 项断言全数通过。两条都属"换机器/下次重装会重现"的平台性知识，**应回填 `docker/README.md`**（坑一尤其重要——它会让人以为 reinstall 成功了而实际丢了 erpnext）。

**根因是译名撞车**（实测 `frappe._()`）：

| 英文原名 | 译名 |
|---|---|
| `Accounts Receivable` | **应收账款** |
| `Debtors` | **应收账款** ← 与上行同 |
| `Accounts Payable` | **应付账款** |
| `Creditors` | **应付账款** ← 与上行同 |

英文模板里父子分别是 `Accounts Receivable`（组）与 `Debtors`（明细），**两个不同的词**；zh 译文把它们译成了同一个词，于是 `add_suffix_if_duplicate()` 给子节点追加了 `1`。

**故教材第三步现在写的"中文模板里该译名在科目树上出现两次，故第二个得 `1`"方向正确但不够准**——应改为"**父子两级的英文原名不同（`Accounts Receivable` / `Debtors`），但译名相同，故子节点被追加 `1`**"。这也使它从"科目表模板的怪癖"归位为**一条明确的翻译缺陷**：`Debtors` 应译「应收账款」而父级 `Accounts Receivable` 宜译「应收款项」或保留层级差异。并入 `SH-P1S1004`。

**这一条还有实操价值**：单据上选应收科目时，**要选带 `1` 的那个**（它才是 `account_type=Receivable` 的明细科目），不带 `1` 的是 group、不能记账。两者界面上只差一个数字，**极易选错**。

**方法修正（本步定下，取代第 4 步那份清单）**：凡要断言界面呈现，须满足**两个层级都有依据**：

| 层 | 要查什么 |
|---|---|
| 数据层 | 相关表的记录（`Desktop Icon` / `Workspace Sidebar` / DocType meta 的 `Tab Break`） |
| **渲染层** | **把数据变成界面的那段代码**（`boot.py` 的 `get_sidebar_items()`、`desktop_icon.py` 的 `get_desktop_icons()` 过滤、`list_view.js` 的视图选择） |

**且凡给数量断言（"共 N 个"）必须标注是哪一层的 N**，因为数据层的条数与界面显示数经过滤后普遍不等——本轮 `Desktop Icon` 36 条、顶层 9 条、实际显示远多于 9，三个数字全不一样。

**另定一条**：**用户报障时，先分清是"教材写错"还是"层级混淆"。** 本步若按字面把"首页有采购和销售两个选项卡"当成教材错误去改表单那节，会把对的地方改错。

**（二）`icon_type` 决定 hidden 是否向下传递**

`Desktop Icon` 的 `icon_type` 分布（实测）：`Link` 32 / `App` 3 / `Folder` 1。

| 图标 | icon_type | hidden | 子项是否显示 |
|---|---|---|---|
| `Accounting`（会计） | **Folder** | 0 | 显示（9 个子项） |
| **`ERPNext`** | **App** | **1** | **仍显示**——7 个 `hidden=0` 的子项照样在首页 |
| `Framework` / `Frappe Framework` | App | 0 | 显示 |

`ERPNext` 组下 9 个子项的 hidden 值（实测）：`客户关系`=1、`售后支持`=1，其余 7 个（`库存` `资产` `采购` `质量` `销售` `项目` `生产`）=0。

**故首页实际显示的图标数远多于"顶层 9 条"**，Claude 第零步那张"顶层只有 7 个"的表作废。

**（三）`desktop_icon.py:170-210` 的过滤逻辑**（读源码）

`get_desktop_icons()` 的 permitted 判据按 `icon_type` 分三路：`Folder` 恒 permitted；`App` 走 `check_app_permission()`；`Link` 则查 `bootinfo.workspace_sidebar_item` 里该 sidebar 有没有 item。最后一步过滤是 `not s.parent_icon or s.parent_icon in permitted_parent_labels`——**只看父图标是否 permitted，不看父图标的 hidden**。这就是 hidden 不向下传递的出处。

**（四）`create_desktop_icons_from_workspace()` 证明两套表确有关联**（读源码 `desktop_icon.py:231+`）

该函数遍历 `Workspace`（`public=1` 且排除 `Welcome Workspace`）为每条生成一个 `Desktop Icon`。**故 `Workspace` 不是死表，它是 `Desktop Icon` 的来源之一**——这解释了为什么两套表的条数接近（19 vs 32 中的一部分），也说明"`Workspace` 完全不管导航"的说法要放宽为"**它不直接渲染导航，但它是导航记录的生成源**"。教材段②那一节须据此修正。

## 本步分析：三个选项

**先厘清一件事**：用户说的"重写 UI 与路由"在 ERPNext 上有三种解法，代价与风险差别极大。**不宜用"要不要自建 App"这一个问题笼统裁决。**

| 选项 | 具体做什么 | 代价 | 风险 | 保留什么 |
|---|---|---|---|---|
| **A 只重整导航与译名**（不写前端代码） | 改 `Desktop Icon` + `Workspace Sidebar` 的记录（藏掉用不到的、按弹簧厂业务顺序重排、把入口按"接单→采购→生产→发货→收款"组织），补齐译名（`Translation` DocType 或自有 app 的 `zh.csv`）。**全部是配置，零前端代码** | **1-3 天** | 低。`standard=1` 记录是否被 `bench migrate` 覆盖**未实测**，须先验 | 全部原生表单与逻辑 |
| **B 自有 App 覆盖导航 + 自建少数高频页** | A 的全部，另加：用 `Page` 或独立 Vue 前端自建 **3-6 个高频作业页**（车间报工、领料、发货、收款），这些页直接调 `@frappe.whitelist` 方法。**其余 800 个 DocType 继续用原生表单** | **2-6 周**（视自建几个页） | 中。自建页要自己实现即时反馈；原生表单与自建页并存，**存在两套心智** | 原生表单作为"后台/少用功能"的兜底 |
| **C 全面重写 UI，以自有 UI 为唯一基准** | 自建完整前端（Vue + REST API v2 + `get_meta` 动态生成表单），原生 desk 只作管理后台 | **3-6 个月起**，且**持续维护成本**：上游 v17 改字段即要同步 | **高**。① 前端那套即时反馈逻辑（`transaction.js` 3410 行 + `taxes_and_totals.js` 1229 行）要重写一遍；② 193 个 Report 与 43 个 Print Format 全部脱离；③ 上游升级时自有 UI 与新字段失配，**而本项目的战略是跟着自有 fork 走 v16→v17**；④ **教材要重写两次**（先按自有 UI 写，UI 改一次又要改一次） | 仅服务端逻辑 |

**Claude 的推荐：A 先做，B 按实测需要追加，C 暂不做。** 五条理由：

## 本步分析：这套机制怎么建

**先给结论**：**它是一个"编排层"——外部发一条"执行某个步骤"的指令，它负责三件事：调服务端造/改单据、把界面导航到该单据、把该填的值填上。** 三件事分别对应上表的 1/2/3、4、1/2。

**架构形态（三层，与用户的三个用例对齐）：**

```
用例层：   演示脚本(现在)      MCP server(将来)      React 前端(将来)
                └──────────────────┴────────────────────┘
                                   ↓ 都调同一组接口
编排层：   自有 app 里的"流程编排 API"（本次要建的东西）
             · 定义流程：八步各是什么 DocType、从哪个上游 map 来、要填哪些值
             · 定义"下一步"：当前在哪一步 → 下一步是什么
             · 执行一步：调 whitelisted 方法造单 + 填值 + 推事件让界面跳转
                                   ↓ 只用官方接口
ERPNext：  REST v2 / run_doc_method / execute_doc_method / publish_realtime / 800 个 whitelisted 方法
```

**关键设计决定：编排层的"流程定义"存成数据，不写死在代码里。** 建一个自有 DocType（如 `Demo Flow` + 子表 `Demo Flow Step`），每步记：`doctype`、`上游来源`、`调哪个 make_ 方法`、`要预填哪些字段的什么值`、`下一步是谁`。**理由**：① 演示脚本要改顺序时改数据不改代码；② MCP 将来读同一张表即知道"这个系统有哪些可编排的流程"，这正是 MCP 需要的**能力自描述**；③ 与"ERPNext 里一切都是 DocType"一致，不引入异质机制。

**要用户裁决的一处：界面"自己动"怎么实现，两条路**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **甲 服务端推事件驱动** | 外部（或演示遥控器）调编排层 API → 服务端造好单据 → `publish_realtime` 推事件给该用户的浏览器 → desk 前端收到后 `frappe.set_route` 跳转并填值 | **真正的"外部操控"**：指令可以来自任何地方（手机、另一台机器、MCP、脚本），浏览器只是被动显示。**最接近"像放 PPT"**（可以拿手机当遥控器）。且这套推送通道 MCP 将来也要用（MCP 改了数据要让界面刷新） | 要装一段前端监听代码（自有 app 的 `app_include_js`，约百行）。realtime 依赖 socketio 在跑（本项目 9100 端口已配） |
| **乙 浏览器侧驱动** | 在 desk 里加一个"演示遥控"面板，点"下一步"由**前端**调编排层 API，拿到结果后前端自己跳转填值 | 不依赖 realtime；实现略简单 | **不是"外部操控"**——控制权仍在 desk 内部，MCP 与 React 前端复用不到"驱动界面"这部分（它们只能复用编排 API）。演示时必须在 desk 页面上操作 |

**Claude 推荐甲**，三条理由：① 用户明确说"**外部**操控"且"为 MCP 打基础"，而 MCP 是外部进程，只有甲的形态能被它复用；② 甲的前端那段监听代码是**一次性投入**，之后 MCP 与 React 都吃这个通道；③ "像放 PPT"的体验（拿手机点下一步、投屏上界面自己动）只有甲做得到。

**另一处要提醒的（不必现在定，但影响演示脚本）**：**自动填值的"合适的值"从哪来。** 两种来源混用：
- **从上游单据 map 来的**（客户、物料、数量、价格）——走 `make_*` 方法，服务端算好，**准确可靠**。
- **需要现场编的**（日期、批号、报工工时）——由流程定义里预设。**这类要小心 LG-062**：R3 已证明工序成本完全依赖真实报工工时，演示时若把工时填成几秒，毛利率会虚高 40 个百分点（R3 实测 68.8% vs 应为 28.8%）。**演示脚本里的报工工时必须预设成合理值**，否则客户会看到一个漂亮但错误的成本数字。

**工作量估**：编排层 + 流程定义 DocType + 甲的前端监听 + 一条八步流程的定义，**2-4 周**（比第 9 步 B1 的 3-7 天大，但它是长期资产而非演示一次性投入）。
