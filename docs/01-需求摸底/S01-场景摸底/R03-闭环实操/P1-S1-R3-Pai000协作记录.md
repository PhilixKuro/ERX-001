#### 第 3 步：建公司（环节 1）——暴露两处稿子偏差

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户按操作稿环节 1 建公司，报「在会计选项卡里能看到两个科目表模板选项，但看不到启用永续盘存」。Claude 首答判断该字段在「库存与制造」选项卡而非会计选项卡；用户复报「只看到库存与生产选项卡，里面同样没有启用永续盘存」。第二次取证才定位到真正原因。

**用户回答：** 两次报告——① 会计选项卡见两个科目表模板选项、无永续盘存；② 库存与制造选项卡内同样无永续盘存。随后报「已保存」。

**结论：**

- **操作稿环节 1 的字段顺序写错了。** `enable_perpetual_inventory` 所在的「库存设置」（Stock Settings）Section Break 带 `depends_on: eval:!doc.__islocal`，即**整节只在文档保存之后才显示**。稿子把它列进"保存前要填的字段表"是不成立的。该字段 `default='1'`，故保存时已生效，用户无需手动勾。
- **「科目表」是两个字段而非一个。** 稿子写成一行「科目表（Chart of Accounts）→ `Standard`」，实际是 `create_chart_of_accounts_based_on`（选 `Standard Template`）+ `chart_of_accounts`（选 `Standard`，`depends_on` 前者），要点两下。这正是用户看到"两个选项"的由来。
- 正确顺序：主表单四项 + 会计选项卡科目表两项 → **先保存** → 回到页面切库存与制造选项卡确认永续盘存。

**取证段（本步实做，全部可复现）：**

**① 字段位置与显示条件**

```python
m = frappe.get_meta('Company')
# 遍历 fields，按 Tab Break / Section Break 累积当前所在 tab 与 section
```

| 字段 | Tab | Section | 关键属性 |
|---|---|---|---|
| `company_name` / `abbr` / `default_currency` / `country` | （无 Tab，主表单顶部） | — | — |
| `create_chart_of_accounts_based_on` | Accounts | Chart of Accounts | Select，options = `Standard Template` / `Existing Company` |
| `chart_of_accounts` | Accounts | Chart of Accounts | `depends_on: eval:doc.create_chart_of_accounts_based_on==="Standard Template"` |
| `enable_perpetual_inventory` | Stock and Manufacturing | **Stock Settings** | Check，`default='1'`，`hidden=0`，`read_only=0`，自身无 `depends_on` |
| `default_inventory_account` / `stock_adjustment_account` / `stock_received_but_not_billed` / `valuation_method` | 同上 | 同上 | 同在该节内 |

**关键发现**：`Stock Settings` 这个 **Section Break 自身**带 `depends_on: eval:!doc.__islocal`。`__islocal` 是"文档尚未保存"标记，故该节连同其下五个字段在新建界面整块不显示；用户看到的「库存与制造」选项卡里只剩下方的 `Manufacturing` 节（`default_operating_cost_account` + 三个默认仓库）。这是 ERPNext 有意设计——这些字段填的是科目，而科目表在保存公司那一刻才生成。

#### 第 4 步：默认公司与多客户部署的机制问答，并查出菜单译名大面积不符

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户提三问。前两问是机制理解（非操作卡点），第三问是操作卡点。

**① 默认公司与单据公司的区别及各自用处**

**用户回答：** 提问，无裁决。

**结论（Claude 答，机制事实）：**
- **单据公司**（单据上的 `company` 字段）是业务数据，决定这笔业务记进哪套账——用哪棵科目表、哪些仓库、哪个成本中心，生成的 GL Entry / Stock Ledger Entry 归谁。在 PO / SO / Work Order / Stock Entry / BOM 上均为必填（R2 已查证）。
- **默认公司**（全局默认值）是 UI 便利 + 查询过滤器：新建单据时预填 `company`、列表与报表的默认筛选范围。本身不产生业务数据。
- **两者不一致时的坑**：单据上选了 A 公司但默认公司为空或为 B，则该单据上仓库/科目这类 Link 字段的候选值查询带着默认公司作条件，一条都查不到，而 Frappe 把"查不到候选"报成**「没有权限」**。这条坑 `docker/README.md` 有记，操作稿环节 1 也写了"别漏"。本步已查证当前全局默认公司为**空字符串**，故该步确为必做。

**② 跨公司隔离的含义；将来卖给多客户是否也按本流程新建公司、默认公司设哪个**

**用户回答：** 提问，无裁决。

**结论（Claude 答，机制事实 + 部署建议）：**

**① 同一 Site 多公司的意义**

**用户回答：** 提问，无裁决。

**结论（Claude 答，机制事实）：** 用于**同一客户拥有多个法人实体**、各自独立出财务报表但共享主数据与人员：集团下子公司各自报税；一个厂拆"生产公司"+"贸易公司"两个主体（中国为开票与税务常见）；跨境时国内厂 + 香港贸易公司（币种与科目表不同）。收益恰来自那条不对称——Item / Customer / Supplier 共享，故同一料号可在两家公司间调拨、做内部交易而不维护两份主数据；ERPNext 另有跨公司交易功能（A 卖给 B 自动生成对应单据）。用户的场景（多个不同客户）不属此类，因共享主数据从收益变成泄露。

**② 若不填默认公司就查不到候选值，是否每查不同公司都要改默认公司**

**用户回答：** 提问，并指出"听起来更麻烦了"。

**结论：** **用户的质疑成立，Claude 上一步的因果说过头了，本步更正。**

- **准确的机制**：默认公司为空**不产生权限错误**，只是不预填 `company`、不预筛列表。真正会报「没有权限」的是 **User Permission**（用户被限定只能访问某公司时访问别家的记录）。`docker/README.md:39` 记的是一个具体场景（演示单据在 `(Demo)` 副本公司名下而默认公司指主公司），不是"默认公司为空即查不到"的一般规律。上一步把两件事混成一条因果。
- **日常多公司切换不靠改默认公司**：① 单据上的 `company` 字段可直接改，仓库/科目等 Link 字段的候选过滤读的是**单据上的** company 而非全局默认；② 列表与报表有公司筛选器；③ 用户级另有 **Session Defaults** 比全局默认更细。
- **默认公司的意义**是省掉重复输入：单公司站点（用户将来的形态）一填永久受益；多公司站点填最常用那家、其余手改。它**不是权限边界**，权限走 User Permission。
- 本站点实测 `User Permission` **0 条**、仅一家公司，故该坑对当前环境不存在。设默认公司这一步**仍该做**（省事 + 验证它能存住），但它卡不住实操。

**③ 每个 Site 是否即 Frappe 里的一个独立 App；自定义 App 给多客户用是否要每客户复制一份**

**用户回答：** 提问，无裁决。

**结论：** **Site 与 App 正交——App 是代码，Site 是数据。不需要给每个客户复制自定义 App。**

装 app 到站点（`bench --site X install-app your_app`）做的是在该站点数据库里建该 app 的 DocType 表、跑其 patch，**不复制代码**。故一份代码、一处修改、所有客户站点同时生效（重启后）。客户间差异用配置解决（各站点自己的设置记录），差异大到配置解决不了时才考虑分支或做成可开关的模块。这正是 Frappe 生态能做 SaaS 的基础。

**④ 不同 Site 是否共享数据库、是否靠某个 site 字段区分**

**用户回答：** 提问，无裁决。

**⑤ 翻译能否非侵入或最小侵入改造（如替换翻译文件）**

**用户回答：** 同意把翻译改造加入延迟需求，**先做一版中国大陆通用翻译、再做一版弹簧行业标准专用翻译**，采用 Claude 提议的 **A+B 方案**。

**① 用户的 Routing 质疑成立，操作稿此处写得不好（第二处实质性改进，由用户发现）**

已查证 `Routing` **只有三个字段**：`routing_name` / `disabled` / `operations`（一张 `BOM Operation` 子表）。**无任何数量字段**，故其 `time_in_mins` 的含义不完整——它依赖"全厂共用同一 BOM 基准量"这条**隐含约定**。

ERPNext 的设计前提是"同一家工厂所有 BOM 用同一基准量"，此前提下 Routing 不需要数量字段（大家都按 1000 填，数天然可比），加了反而会出现"这条按 5000、那条按 1000"的混乱。**但该前提在实际中会漏**（弹簧按 1000 支合理、模具可能按 1 件），且它是"用约定代替字段"——约定靠人守，字段靠系统守。

**正确做法**：定一个基准量（1000 支），Routing 与 BOM 都按它填，中间不做换算。Claude 让用户在 BOM 里除 5 是多余步骤且是出错来源（忘改则 BOM 认为 1000 支要 520 分钟、成本虚高 5 倍）。

**② ⚠ 讨论中发现：`fixed_time` 字段存在，R1 与操作稿的"原生无固定工时"论断错了**

这是本步查证的最重要发现，详见取证段。**它使 D2 ⚠ 的判定须拆为两项**，并且是 R1 复核建议预警的"grep 未找到即推定缺口"这类误判的第一个应验实例。

**③ 同类软件的做法（行业通识，非本项目查证）**

用户设想的"Routing 写工序+用时+标准产量 + 固定工时"即 **MRP II 的标准工艺路线模型**，比 ERPNext 现状完整。标准模型把每道工序的工时拆两段：

| 时间类型 | 含义 | 随批量变 |
|---|---|---|
| **准备时间**（Setup Time） | 换模、调机、装炉、首件调试 | **不变** |
| **加工时间**（Run Time） | 每件实际加工 | 按件数线性 |

总工时 = 准备时间 + 单件时间 × 数量。回火表达为"准备 90 分 + 单件 0"；卷簧表达为"准备 20 分（换线调簧距）+ 单件 0.05 分"。SAP 的工艺路线有基准数量（Losgröße）加准备/机器/人工三种时间类型，Oracle 与 Dynamics 同为 setup + run time 结构；该模型在 MRP II 时代定型，因换型时间在多品种小批量生产中占比高，不建模则产能算不准。

**ERPNext 的 `fixed_time` 是该模型的简化版**——只有"固定"与"线性"两档、不能相加，故卷簧的"20 分换型 + 每支 0.05 分"表达不了，只能二选一。用户的二开方向由此得到确认，并分三层落地（见 `SH-P1S1005`）。

**④ 同一料号为何可有多张 BOM**（答用户质疑："配方"为何需要多张）

配方成立，但**同一产品可以有多种做法**。五种真实情形：替代料（65Mn 缺货改 70# 钢，料不同工艺同）；工艺升级并存（新买联合机把卷簧与磨端合一道，更快但只一台、产能不够时仍用老工艺）；自制 vs 外协（热处理自做含回火工序，外协则改为一项外协费用——R1 的 G 域）；不同批量的最优工艺（500 支手工上下料省调机时间，50000 支值得调自动送料机）；版本演进（客户改图纸，新旧并存，老订单按老 BOM）。`is_active` / `is_default` 两标记正为此：多张可同时 active，只有一张 default。

**⑤ 环节 6 的完整解释（答上一轮四个子问，此处记结论）**

| 子问 | 结论 |
|---|---|
| 3-1 那个 5000 在哪设置的 | **系统里没有 5000**。它只是"卷簧机 20-25 支/分钟 → 5000 支需 250 分钟"这个推算的中间量，算完即弃。Routing 无数量字段故系统不知道。**BOM 头部的 `quantity=1000` 才是第一个绑定数量的地方**，此后 50/18/36 才有确切含义 |
| 3-2 Components 数量为何要自己填 | 系统不知道"一支弹簧要多少线"——那是产品几何（线径/外径/圈数）决定的，ERPNext 不懂弹簧。它能做的是**按比例缩放**（填了 1000 支 8.68 kg，工单要 5000 支时自动算 43.4 kg），不是从零推导 |
| 3-3 工序时间为何要自己填 | 同理，系统不知道"一分钟能做几支"——那是设备能力。**BOM 的本质是承载工艺知识的载体，不是计算器** |
| 3-4 BOM 是一张单子还是以后都按它算 | **是配方，长期复用**。对比：BOM = 配方/工艺文件（长期）；工单 = 这一次生产的指令（一次）；采购单/发货单 = 这一笔交易（一次）。取 1000 为基准是因工时按整批填更直观（填 1 则工时为 0.05 分钟，看不出含义），且为制造业常规；**基准量不是限制，系统按比例缩放到任意数量** |

分工的一句话总结：**你负责"一支多少料、一分钟几支"（工艺知识），系统负责按比例换算、累加成本、跨单据传递（算术与记账）。** 这正是 R1 样板一说的"把老师傅心里的数落成公式"——数在老师傅脑子里时，工厂只有他知道、钢价变了不能快速重算、他退休知识就没了。ERP 项目最费时间的正是把这些数挖出来定下来，而非装软件。

#### 第 20 步：`物料凭证` 译名撞名、会计分录的非搜索入口、凭证与科目的概念讲解

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户提三件事：① 搜索 `Stock Ledger Entry` 看到的页面与在库存工作区点「物料凭证」看到的页面不一致，**已发生多次这类情况**，要求之后全量查询还有多少，尽量做到搜索进入与点击进入是同一页面；② 找不到除搜索以外进入会计分录的方式；③ 看不懂会计分录里那两个编号对应什么，要求讲解凭证、科目这类财务概念，以及它与库存里那个凭证的区别。

**结论：**

**① 页面不一致的根因是翻译撞名——这次是实在的数据问题，不是渲染问题**

| 英文 | 类型 | 中文译名 |
|---|---|---|
| `Stock Ledger Entry` | **DocType**（数据表） | **物料凭证** |
| `Stock Ledger` | **Report**（报表） | **物料凭证** |

**两个不同的东西译成同一个中文名。** 搜索进的是 DocType 的原始列表，工作区链接进的是报表（`link_type='Report'`、`is_query_report=1`）。故不是同一页面的显示差异，而是**本来就是两个东西**。报表那个才是给人看的（带筛选、排序、汇总），DocType 那个是原始记录且 `in_create=1`（不能手工新建，只能由单据产生）。

**这条归入翻译改造且属必改** —— 同名会持续造成困惑。用户要的"全量查询这类情况"并入 `SH-P1S1005`。

**② 会计分录的非搜索入口（两个）**

| 要看什么 | 入口 |
|---|---|
| 某张单据产生的分录 | 打开该单据 → 右上「菜单」→ **「会计凭证」**（`Accounting Ledger`） |
| 全部分录、按科目/日期筛 | 「财务报表」工作区 → **「会计总账」**（`General Ledger`，`Financial Reports` 下已有该 Link） |

**三个易混译名**：`Accounting Ledger` → 会计凭证；`General Ledger` → 会计总账；`GL Entry`（DocType）→ 总账分录。`GL Entry` 同为 `in_create=1`，**所有分录必须由单据产生**——这保证"账上每一笔都追得到一张业务单据"，无凭空数字。

**③ 财务概念讲解（DEC-010 定操作稿不含会计原理层，此处按用户要求就地补讲，正是 LG-010 记着的缺口）**

- **科目（Account）= 给钱分类的抽屉。** 本公司 95 个，建公司时按 `Standard` 模板生成，分五大类：资产（我有什么：`存货`/`现金`/`应收账款`）、负债（我欠什么：`应付账款`/`暂估库存`）、权益（老板投了多少、赚了多少）、收入（`销售`）、费用（`销货成本`/工资/电费）。科目是树状的，故能既看总数又看明细。
- **分录（Entry）= 一笔钱的两面。** 核心规则：每笔业务至少动两个科目，借方金额 = 贷方金额。**"借"与"贷"不是借钱/贷款的意思，纯粹是记账的左右两栏**，可理解成"左"和"右"。本例读法：仓库里多了 750 元货（资产增加），同时欠供应商 750 元（负债增加）。两边必须相等是因为钱不凭空出现——多了 750 存货，这 750 必来自某处（此处是"欠着"，若现金买则是"现金减少 750"）。这就是**复式记账**，五百年前威尼斯商人发明，至今通用，好处是**自带校验**（两边不等即记错）。
- **凭证（Voucher）= 产生这些分录的那张业务单据。** 分录里的 `voucher_type=Purchase Receipt`、`voucher_no=MAT-PRE-2026-00001` 即"这两行由该采购入库单产生"。**故"凭证"不是另一个东西，就是那张单据**——手工会计时代做完分录要附发票收据作凭据，ERP 里单据本身即凭据、分录自动生成。
- **库存那个"凭证"与会计这个"凭证"是同一个凭证，两套账各记一次**：

  | 账 | 记什么 | 表 |
  |---|---|---|
  | 库存账 | 数量与估值：+100 kg、单价 7.5、余额 100 | `Stock Ledger Entry` |
  | 会计账 | 借贷分录：存货 +750、暂估库存 +750 | `GL Entry` |

  两条记录的 `voucher_no` 同为 `MAT-PRE-2026-00001`。**为什么两套**：仓库管理员关心"还有多少公斤"（数量），财务关心"存货值多少钱"（金额）；而两套必须对得上（100 × 7.5 = 750 = 存货科目余额），这就是永续盘存的含义。手工进销存无此层，故月底须人工做"存货结转"。

**取证段：**

| 查证项 | 结果 | 复现 |
|---|---|---|

| Workspace 里指向它们的链接 | `Stock` 工作区的「物料凭证」是 `link_type='Report'`、`is_query_report=1`（指向 Report `Stock Ledger`）；另有「库存余额」同为 Report | `select parent,label,link_to,link_type,is_query_report from tabWorkspace Link where link_to in (...)` |

| 三个易混译名 | `Accounting Ledger`→会计凭证、`General Ledger`→会计总账、`GL Entry`→总账分录 | 同上 `_()` |
| `GL Entry` / `Stock Ledger Entry` 的 `in_create` | **均为 1**（不能手工新建） | `frappe.db.get_value('DocType', dt, 'in_create')` |
| `General Ledger` 的 Workspace 入口 | 在 `Financial Reports` 工作区 | 同上查询 |

**⑥ 关于永续盘存的成本构成（答第 22 步用户的价格问题，本步补答）**

**价格本身 Claude 未给准确数字**——该类软件定价按用户数/模块/代理商折扣浮动且时常变动，知识截止前的数据很可能不准，准确报价只能找代理商或看当期官网价目表。用户随后更正问的是"年费几千元"那一档。

**技术上"贵在哪里"**（不依赖具体价格）三处：

1. **倒序录单的重算**（最麻烦）：漏录一张更早日期的入库单，会改变 FIFO 队列，导致其后每一笔的估值与会计分录都要重算。ERPNext 用 `repost_item_valuation` 后台任务处理，还要应对重算失败、并发、队列堆积。便宜软件的做法是不支持倒序录单、或录了不重算（账就不准）。
2. **估值方法的完整实现**：FIFO 要维护队列（本例 `stock_queue=[[100.0,7.5]]`）、移动加权平均要每笔重算均价、批次/序列号要逐批追踪，各自的边界情况（负库存、零成本、退货冲回）一大堆。
3. **账实不符的诊断工具**：ERPNext 带四张诊断报表（`stock_and_account_value_comparison` / `stock_ledger_invariant_check` / `incorrect_stock_value_report` / `incorrect_balance_qty_after_transaction`）——**这些报表的存在本身说明该机制会出问题**，写自检工具也是成本。

**而用户问的"是不是需要亲自跟业务才能做好"——这才是真正的答案，判断成立**：软件有永续盘存功能 ≠ 工厂能用上永续盘存。它要求每笔物料移动都有单据且及时录入；做不到则车间领料不录单（系统认为料还在原料仓）、完工不录单（WIP 越积越多、成本核不出）、盘点差异不处理（账实差额越拉越大）。**这些不是软件能解决的，是车间流程与人的习惯。** R1 判 D3（在制品盘点）为 🔧 而非 ✅ 正是此理。故**卖永续盘存不是卖代码，是卖"帮工厂把单据流程建起来"**——这也是本项目第 ④ 阶段"定制专属业务逻辑与简单界面"的价值所在（那个"简单界面"是为了让 50 岁的卷簧工愿意点两下报工，R1 样板二 D2 的痛点）。**软件可复制，流程落地不可复制，后者才是收费依据。**

#### 第 24 步：★ 环节 13 讲解——机制与代码位置

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户提三问并报已提交（销售订单前的报价单）：① 分录金额是什么意思、"从库存估值差额算"又是什么意思、刚刚哪个操作导致了这点、有别的选择吗；② 如果暂估库存和实际应付不一致应该怎么处理；③ **如果做仓库到科目的映射，那些仓库专属科目是不是应该成为中国财税标准科目的子科目，然后父科目的表里会包含子科目的数据。**

**用户回答：** 上述三问 + 已提交。

**结论：**

**① 分录金额的两个可能来源，ERPNext 用后者**

| 来源 | 本例值 | 是什么 |
|---|---|---|
| 单据金额 | 750 | 采购入库单的 `grand_total` |
| **库存估值差额** | **750** | `Stock Ledger Entry.stock_value_difference` ← **ERPNext 用这个** |

本例两者恰好相等故看不出差别。**导致这点的操作是提交采购入库单**，系统按序做两件事：先按 FIFO 算库存（`stock_value` 0 → 750，差额 750），再读那个差额生成分录。

**什么时候两者会不等**（这才是该设计的意义）：运费。料钱 750 另有运费 50，运费要计入存货成本故库存估值差额为 800，分录是"借存货 800 / 贷暂估库存 750 / 贷运费暂记 50"。**若按单据金额记，存货只记 750，库存账说 800、会计账说 750，两账裂开。** ERPNext 处理运费用「到岸成本凭证」（Landed Cost Voucher），`make_gl_entries` 的参数里有 `via_landed_cost_voucher`。其他会不等的情形：FIFO 下退货（退哪一批什么价）、库存调整、跨期重算（`repost_item_valuation` 改了历史估值）。

**故"从库存估值差额算"的意义是让会计账跟着库存账走，而非各自算一遍——两账同源就不可能漂移。**

**别的选择**：只有"不开永续盘存"（`enable_perpetual_inventory=0`），那样库存只有数量账、不产生 GL Entry、月底人工做存货结转。建公司时它默认勾着，故本闭环走的是永续盘存这条路。

**② 暂估库存与实际应付不一致的三种成因与处理**

| 情形 | 处理 |
|---|---|
| **价差**（收货按 PO 单价 750，发票开 780） | 发票提交时自动把差额记入价差科目：借暂估库存 750 / 借价差 30 / 贷应付 780 |
| **数量不同**（收 100 发票开 105） | **不能靠发票调**，须先修库存：补一张收货单或让供应商重开票。**原则：实物的事用库存单据解决，金额的事用发票解决**，混着改会让两账裂开 |
| **货到票一直不到**（月末挂账） | 这不是"不一致"而是正常状态。暂估库存科目的余额即"已收货未开票"金额，代表**隐含负债**。查法：会计总账筛该科目；ERPNext 另有 Received Items To Be Billed 报表。本例余额为 0 因收货后立即开票，真实工厂该科目常年有余额 |

**③ ⚠ 用户的判断完全正确，且这是中国财税落地的一个具体入手点**

`Account` 是树形 DocType，**报表按树汇总**（父科目数字 = 全部子科目之和）。故正确结构是：

```
存货（is_group=1，不能直接记账）
├── 原材料 - HDS      ← 线材仓的科目
├── 在产品 - HDS      ← WIP 仓的科目
├── 库存商品 - HDS    ← 成品仓的科目
└── 废料 - HDS        ← 废料仓的科目
```

各仓库的 `account` 字段分别指向对应叶子科目。收益：资产负债表「存货」一行显示总数（自动汇总）、点开看得到各类明细、每个数都能追到具体仓库的库存流水。

**而这恰好对上中国会计准则**——存货类一级科目正是这么分的（1403 原材料、1405 库存商品、1411 周转材料、生产成本/在产品）。**ERPNext 的 `Standard` 模板是国际通用结构、不是中国科目表**，它只给 `存货` 一个笼统科目、下无细分。

**故第 ② 阶段"做中国大陆通用版"的一件核心事就是把科目表换成符合中国准则的结构**：① 一级科目按 1001/1002/1403/2202 编号体系重建；② 存货、应收应付、税金几类的子科目结构补齐；③ 各仓库、各税种映射到对应科目。**这不是二开而是配置**——科目表是数据（`Account` 记录）不是代码，ERPNext 支持自定义科目表模板。**难点不在技术在会计知识**，要一个懂中国准则的会计把科目表设计出来。

**本轮不做**：改科目表会让后面所有分录的科目名再变一次；它要跟一份完整的中国科目表设计（第 ② 阶段的活）；且现在单科目反而更容易看清机制（环节 18 会看到"借存货/贷存货"净额为零的分录，正好理解为何需要拆分）。**并入 `SH-P1S1001`（中国本地化），但把"子科目 + 父科目汇总"这个具体结构记下来，届时不必重新设计。**

#### 第 28 步：工单（环节 17）——排产算法实证，与"批量设置字段"的不对称

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户报三件事：① 修改了仓库默认值；② **工单的发料仓为什么不用填**；③ 工单已提交，但**第一次报错提示没填发料仓，设置了发料仓又取消后再度保存就没报错了，问这是 BUG 还是什么**。

随后用户追问：**"如果我不是清空而是更改的话，明细行会跟着更改吗。如果会的话，那清空前端和明细行也清空之间同步，不是更符合使用心智吗。至于改成空值后提交，靠现有验证机制应该能校验出来吧"**。

**用户回答：** 上述三项 + 对 Claude 方案的反驳。

**结论：**

**① 不是 BUG，是"批量设置字段"的正常行为，但命名与反馈确实有问题**

工单头部的 `source_warehouse` 是**批量设置字段**（一次性给所有明细行填仓库），真正生效的是**明细行**上的 `source_warehouse`。用户的操作序列恰好做对了：填头部 → 推送到明细行 → 清空头部 → **明细行的值留下**（清空头部不反向清明细）。第一次报错也是对的（那时明细行为空）。

ERPNext 里这类字段有好几个（`set_warehouse`、`set_from_warehouse`）。

**② ⚠ 用户的反驳成立，Claude 改判**

Claude 初判 A（只加提示：明细行一致时头部显示该值）优于 B（双向同步），理由是"批量清空是危险操作"。**用户指出两点化解了该顾虑**：① 改值会跟着改（已查证 `transaction.js` 的 `set_warehouse` handler 遍历 items 逐行赋值），**只有清空不跟着清，这个不对称才是困惑来源**；② 明细行为空时提交会被拦（用户第一次就被拦了），故"清空后提交"不会造成脏数据，最坏是报错后填回。

**改判：B（双向同步）优于 A。** 行为一致性本身就是防错，不一致才是错误来源；且校验层已兜住后果。按 B 记进 `SH-P1S1005`。

**③ 本轮附带的一个观察**：这类"看似小的交互不一致"比功能缺失更消耗信任——功能缺了用户知道要绕，行为不一致用户会怀疑自己记错了。用户本轮已撞上三个同类：手工建收货单选不了 PO、提交按钮不出现、清空不同步。

**取证段：**

**① 工单终态（提交后）**

| 字段 | 值 |
|---|---|
| 单号 / status | `MFG-WO-2026-00001` / `Not Started`（docstatus 1） |
| 头部 `source_warehouse` | **`''`（空）** |
| 明细行 `source_warehouse` | **`仓库 - HDS`** ← 这才是生效的 |
| 三个仓库 | wip `进行中 - HDS`、fg `成品 - HDS`、scrap `废料 - HDS` |
| `required_items` | `WIRE-65MN-2.0` **required_qty = 43.4** |
| 计划起止 | 09-20 19:09 → 09-21 04:09（9 小时） |
| `expected_delivery_date` | 2026-10-04（从 SO 带来） |
| 三个开关 | `skip_transfer=0`、`use_multi_level_bom=1`、`transfer_material_against='Work Order'` |

**43.4 = 8.68 × 5** —— BOM 是 1000 支基准、工单 5000 支，**系统按比例缩放**。

**② 工序时间被乘了 5 倍（`fixed_time` 机制的实证）**

| 工序 | BOM 里 | 工单里 | 计划开始 | 计划结束 |
|---|---|---|---|---|
| 卷簧 | 50 | **250** | 09-20 19:09 | 09-20 23:19 |
| 去应力回火 | 18 | **90** | 09-20 **23:29** | 09-21 00:59 |
| 磨端 | 36 | **180** | 09-21 **01:09** | 09-21 04:09 |

机制在 `work_order.py:1550`：`if not d.fixed_time: d.time_in_mins = flt(d.time_in_mins) * flt(self.qty)`。

**这个 250 恰好等于当初为算 BOM 而假设的"5000 支要 250 分钟"**——绕一圈回到原点，说明整套换算自洽。**而回火那 90 分钟现在是"18 × 5"线性算出来的**：若工单改 2000 支它会变 36 分钟而实际仍是 90。**等二开勾上 `fixed_time` 后这里会恒定显示 90。**

**③ 排产算法实证**

三个工序间隔均为 **10 分钟**（23:19→23:29、00:59→01:09），即 `mins_between_operations`。**R2 查证它当时是 0，实测为 10** —— 要么 v16 默认值是 10 而 R2 查错，要么系统在某处设了它。

算法（`work_order.py:1262-1287` 的 `set_operation_start_end_time`）：从 `planned_start_date` 起按 `operations` 顺序累加工时、前后之间加固定间隔。**没有优化、没有资源冲突消解、没有换型时间。** R1 样板三（C4 插单）说的"朴素顺排"就是这 26 行。

**④ 三张生产任务单自动生成**

| 单号 | 工序 | for_quantity | status | 预计时间 | time_required |
|---|---|---|---|---|---|
| `PO-JOB00001` | 卷簧 | 5000 | `Open` | 19:09-23:19 | 250 |

#### 第 31 步：生产任务单报工（环节 19）——计时器 bug 定位，与废品数未记

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**提出者：** 用户

**背景：** 用户报三件事：① **问题出在计时前手动动了工时记录**，于是导致计时器不正常；但认为这也是用户可能犯的错误、**依然需要修复**；另发现**只能记一次时**，不像 Claude 说的可以反复计时，要求查代码确认并简单说有没有必要增加反复计时功能；② 发现**把工时记录内容全部删掉后也无法重新计时，保存后计时选项又出现但是"停止计时"而不是"开始计时"，一切都很混乱**；③ 三个生产任务单均已完成，但**之前 `MFG-WO-2026-00002` 的三张生产任务单既无法提交也无法取消，一直是待处理状态**。

**用户回答：** 上述三项 + 选 A（废品数按 5000 走，不回改任务单）+ 指出漏记。

**结论：**

**① 反复计时原生就支持，Claude 此前说得不准确**

`job_card.js:670-673` 有**四个**按钮而非两个：`Start Job` / `Resume Job` / `Pause Job` / `Complete Job`。**"今天做一半明天做一半"的正确操作是「暂停」而非「停止」**：暂停 → `is_paused=1` → 下次显示「继续」→ append 新的 time_log 行。**故能多段计时，但入口是 Pause/Resume 这一对，不是反复点 Start。**

按钮显示条件（`:610-613`）：

```js
const should_show_start = (no_time_logs_yet || pending_qty_cycle_done || sub_operation_cycle_done) && !doc.is_paused;
```

**「开始」只在三种情况显示**：还没有任何 time_log、上一轮完成了还有剩余数量、子工序循环完成。**其余时候一律只显示 Pause/Complete。** 这解释了用户说的"只能记一次时"。

**故"增加反复计时功能"不必要——原生已有，是入口不明显（Pause 而非 Stop）。**

**② ⚠ 用户报的"删空后无法重新计时"是真 bug，根因定位到具体代码行**

`job_card.js:614-621`：

```js
const last_log_complete = time_logs?.length && time_logs[time_logs.length - 1].to_time;
const is_actively_running = !!(time_logs?.length && !last_log_complete && !is_on_hold && !doc.is_paused);
```

**它只看最后一行有没有 `to_time`，不检查该行是否为有效行。** 用户删空再保存后系统 append 了一个空行，于是：`time_logs.length=1`（不是"还没有 time_log"）→ 最后一行 `to_time` 为 None → `last_log_complete=false` → `is_actively_running=true` → **显示"停止计时"而非"开始计时"**。**系统认为正在计时，而那一行完全是空的。**

**且该空行残留在三张任务单上各有一个**（见取证段），**说明不是偶发、是每次操作都会产生**。

**判定：上游 bug，该修，两层修法**：

| 层 | 做法 | 侵入度 |
|---|---|---|
| 服务端防御 | `Job Card.validate` 的 hook 里删掉 `from_time` 与 `to_time` 皆空的行、重排 idx | **零侵入**（`doc_events` hook） |
| 前端根治 | `is_actively_running` 的判断加上"该行必须有 `from_time`" | 要改 js 或用 client script 覆盖 |

服务端那层即可解决用户遇到的全部症状。记进 `SH-P1S1006`。

**③ 孤儿任务单的正确处置是删除而非取消**

**③ ⚠ 用户的第 3 个判断成立——ERPNext 不做工序间数量传递，这是真缺口**

**④ 工艺损耗与工序废品是两套机制，业务上的区别（答用户后续追问）**

| | 工艺损耗（BOM 的 `process_loss_percentage`） | 工序废品（Job Card 的 `process_loss_qty`） |
|---|---|---|
| 在哪定 | BOM，**事前** | Job Card，**事后** |
| 性质 | 计划值、标准损耗 | 实际值、这一批真实发生的 |
| 业务含义 | "这个产品按工艺**注定**损失 5%" | "这一批**实际**废了多少支" |
| 弹簧厂例子 | 每卷线材切头切尾必然浪费、卷簧起停必然有废料 | 这批线材质量差，多废了 80 支 |
| 用途 | 报价、成本估算、物料需求 | 成本差异分析、质量追踪、工人绩效 |

**核心区别：一个是"应该损失多少"，一个是"实际损失了多少"，两者的差额就是管理的抓手。** 理论损耗 5%（250 支）而实际废 400 支，超出 150 支就该查原因（料的问题？机器状态？新手操作？）。**混成一个数就永远查不出来**——这正是 R1 场景 H2"超耗说不清"的解法。

公司的 `expenses_included_in_valuation` 字段为 None（无默认值）故系统取不到、要人手填。**建议去公司的库存设置节把该字段设为 `结转库存的费用 - HDS`，以后自动带出。**

**④ 完整成本链（每个数都能往上追一层）**

```

WIP 325.5 元

成品 325.77 元 / 4750 支 = 0.0686 元/支

  ↓ 收入 1045 元（4750 × 0.22）
毛利 719.23 元
  ↓ 收款
现金净增 295 元
```
