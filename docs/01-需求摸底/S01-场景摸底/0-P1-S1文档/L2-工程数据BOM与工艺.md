## 段① 这一层要建什么

L2 的产物是**一套可复用的工程数据**：知道一支弹簧用多少料、走哪几道工序、每道工序多久、每小时多少钱，于是成本自动算出来。

顺序不能换——后面引用前面：

```
Workstation Operating Component（成本构成主数据，站点已有四条）
  ↓
Workstation（工站）
  └─ workstation_costs 子表   ← 机时费率由这里累加而来，hour_rate 只读
  ↓
Operation（工序）             ← 引用工站作默认值
  ↓
Routing（工艺路线）           ← 一串工序 + 各自工时，可复用
  ↓
BOM                          ← 引用 Routing（带入工序）+ 物料清单 → 算出成本
```

### 第一步：建工站，机时费率是本层第一个要算的数

搜「**工站**」（Workstation）——译名是「工站」不是"工作站"。新建。

三台设备各建一个 〔典型值〕：

| 工站名称 | 作业能力（`production_capacity`） |
|---|---|
| `卷簧机-01` | 1 |
| `回火炉-01` | 1 |
| `磨端机-01` | 1 |

**关键一步：填机时费率。这里与旧资料不一样。**

「净小时费率」（`hour_rate`）字段是**只读**的（`read_only=1`，R5 实测）。它由下方「运营成本构成」（`workstation_costs`）子表**累加**而来。所以要展开那张子表逐项填：

| 运营成本构成（`operating_component`） | 运营成本（`operating_cost`，元/小时） |
|---|---|
| `Wages`（工资） | 25 |
| `Electricity`（电费） | 8 |
| `Rent`（租金，含折旧分摊） | 12 |
| `Consumables`（耗材） | 5 |

〔典型值，合计 50 元/小时〕

保存后「净小时费率」自动变成 50（R3 实测三台工站均为 50.0）。这四个 `Workstation Operating Component` 记录站点里已有（R3 查证：`Wages` / `Rent` / `Consumables` / `Electricity`），直接选。

> **机时费率怎么算出来——这是场景 A1 的「落地前提①」，也是本层最需要财务配合的一件事** 〔行业通识，非本项目查证〕：
>
> ```
> 每小时费率 = 该机台的月度成本总额 ÷ 月有效工时
>
> 月度成本包含：操作工工资与社保 + 设备折旧 + 电费 + 厂房租金分摊
>                + 耗材（切削液、砂轮）+ 维修摊销
> 月有效工时 = 日班次 × 每班小时 × 月工作日 × 设备开动率
> ```
>
> **中小厂通常没算过这个数**。它是一次性基础工作，但不做则整条成本链失真——BOM 算出的工序成本会是编的，进而报价、毛利、成本分析全部不可信。
>
> **拆成四项填而非填一个总数，好处在于可追溯**：将来电费涨了只改一行，且能回答"这支簧的成本里人工占多少"。
>
> **`Rent` 这一项含折旧分摊，这是本层的一处简化**——严格做法是折旧走 L8 的固定资产模块、由会计按月计提，而这里的 12 元/小时只是把它摊进机时费率。〔两种做法的会计差异未查证，L8 展开时须核准〕

> **⚠ 子表下拉里显示英文、选中后变中文，这不是 bug。** 下拉候选显示的是**记录主键**（那四条记录的 name 本身是英文），选中后显示的才是经 `__()` 处理的标签。彻底的改法是改这四条主数据的名字而非只加翻译，已归入 `SH-P1S1004`。

**三台机的费率按实际差异填**（卷簧机功率大、电费高；回火炉更高）。本层三台都填 50 便于核算 〔典型值〕。

> **`Workstation Type` 这个对象值得知道**：当前站点 0 条（R3 实测）。它是"同型号多台设备"的抽象——建一个类型填一次费率，各台机继承（`workstation.py:118-140` 的 `_set_data_based_on_workstation_type()`，**注意它会先清空该工站的 `workstation_costs` 再从类型复制**）。
>
> **弹簧厂有 20 台同型卷簧机时该用它**，本层三台不同型故不用。**这是 C 档规模（中型多机台）会用到而 A/B 档用不上的一个对象**（DEC-005 的规模差异之一）。

### 第二步：建工序

搜「工序」（Operation）→ 新建。**它的 `autoname` 是 `Prompt`**（R5 实测），即保存时弹窗让你输名字。

三道工序 〔典型值，对应场景 B3 的工艺路线〕：

| 工序名 | 默认工站（`workstation`） |
|---|---|
| `卷簧` | `卷簧机-01` |
| `去应力回火` | `回火炉-01` |
| `磨端` | `磨端机-01` |

**工序本身没有必填字段**（R5 实测 `reqd` 全空），工站只是默认值、可在 BOM 里覆盖。

**另两个字段值得知道**（R3 实测三道工序均为默认值）：

| 字段 | 默认 | 作用 |
|---|---|---|
| `batch_size` | 1 | 一张生产任务单覆盖多少产量 |
| `create_job_card_based_on_batch_size` | 0 | 勾了则按批量拆分成多张任务单 |

**这两个解决的是"单工单内分批"，不是"跨工单合批"**（一炉混 5 个工单）。后者无原生形态，见段④。

> 站点里还有一个自带的 `Operation` 叫 `Assembly`（无工站），**不是 demo 数据**（`--clear` 只清六类主数据，Operation 不在其中），是 ERPNext 自带。无视即可。

### 第三步：建工艺路线，并定下基准量约定

搜「工艺路线」（Routing）→ 新建 → 名称 `压缩弹簧-标准`，在 `operations` 子表里按顺序加三道工序、各填工时。

**工时按 1000 支基准直接填这三个数** 〔典型值〕：

| 工序 | `time_in_mins` | 依据（按 1000 支） |
|---|---|---|
| `卷簧` | **50** | 卷簧机约 20-25 支/分钟，1000 支约 40-50 分钟 |
| `去应力回火` | **18** | 见下方 ⚠ 框——回火是批处理，这个 18 是摊出来的数 |
| `磨端` | **36** | 约 28-30 支/分钟 |

> **⚠ 为什么必须定一个基准量并全厂守住它**（DEC-021，R3 由用户发现并裁决）。
>
> **`Routing` 只有三个字段**：`routing_name` / `disabled` / `operations`（R5 实测），**没有任何数量字段**。故它的 `time_in_mins` 含义不完整——"50 分钟"是做多少支的 50 分钟？它不说，它依赖**"全厂共用同一 BOM 基准量"这条隐含约定**。
>
> ERPNext 的设计前提就是如此（此前提下不加数量字段反而避免"这条按 5000、那条按 1000"的混乱），**但它是用约定代替字段——约定靠人守，字段靠系统守**。
>
> **实际后果**：若某人按 5000 支填了 Routing、另一人按 1000 支建 BOM，成本会虚高 5 倍，而系统一句话都不说。R3 实操中操作稿 v1 正是让人在 Routing 里填 5000 支基准、再到 BOM 里除以 5，那个除法被判为"多余的出错来源"。
>
> **给 `Routing` 加基准数量字段已登记为 `SH-P1S1005` 第 ③ 层。**

> **⚠ 回火这道工序：原生有"固定工时"机制**（LG-021，R1 与操作稿 v1 都判错过的一条）。
>
> `BOM Operation` **有 `fixed_time` 字段**（Check，`default=0`，R5 实测）。机制在 `work_order.py` 的 `calculate_time()`：
>
> ```python
> for d in self.get("operations"):
>     if not d.fixed_time:
>         d.time_in_mins = flt(d.time_in_mins) * flt(self.qty)
> ```
>
> 即**勾了 `fixed_time` 的工序，工时不乘数量**——正是回火这类批处理要的语义（一炉装得下 800 kg，做 1000 支还是 2000 支都是 90 分钟）。
>
> **本层教学时仍按线性填 18**，理由是要在 L5 看到"乘以数量"这个缩放机制本身；**但你要知道这个 18 是错的**——它让系统认为做 2000 支回火要 36 分钟，而实际仍是 90 分钟。
>
> **想要正确行为就勾上 `fixed_time` 并把工时填 90（整炉实际值），零开发。**
>
> **这条的意义超出本环节**：R1 判场景 D2 为 ⚠ 的理由之一是"原生无固定工时"，该论断错了。**D2 的 ⚠ 须拆为两项**——「批处理工时不随批量变」**原生有**；「一炉混多工单合并作业」原生无（`Job Card.work_order` 必填，一炉混 5 个工单就得开 5 张分别计时）。
>
> **这是 R1 复核建议预警的"grep 未找到即推定缺口、可能使二开范围虚高"的第一个应验实例**（L0 的中国科目表是第二个）。其余 6 项未读源码的 ⚠（B4/C3/D6/E7/F5/H7）应同样复查——本层顺手做掉了 B1，见段④。

> **`fixed_time` 只是 MRP II 标准工时模型的简化版** 〔行业通识，非本项目查证〕：
>
> 标准模型把工时拆两段——**准备时间**（Setup Time，换模调机装炉，不随批量变）+ **加工时间**（Run Time，按件线性），总工时 = 准备 + 单件 × 数量。SAP 的工艺路线有基准数量（Losgröße）加准备/机器/人工三种时间类型，Oracle 与 Dynamics 同为 setup + run 结构。
>
> 而 `fixed_time` **只有"固定"与"线性"两档、不能相加**，故卷簧的"20 分钟换型 + 每支 0.05 分钟"表达不了，只能二选一。
>
> **这对弹簧厂是实质缺口**——换型时间是这个行业最大的效率杠杆（场景 C3「换型合并」判 ⚠ 正是因此）。给 `BOM Operation` 加 `setup_time` 已登记为 `SH-P1S1005` 第 ② 层。

**建 Routing 而非在 BOM 里逐道填的理由**：弹簧厂的工艺路线是**复用**的（同一套工序服务几百个规格），这正是 Routing 的用途，也是场景 B3 判 ✅ 的依据。

### 第四步：建 BOM

搜「`BOM`」→ 新建。这是本层信息量最大的一步。

**头部字段**：

| 字段 | 填什么 | 说明 |
|---|---|---|
| `item` | `SPR-C-2.0-16-50-8-65MN`（L1 生成的变体） | 必填 |
| `company` | `华东弹簧` | 必填 |
| `quantity` | **1000** | **这就是基准量**。与 Routing 的填法约定一致 |
| `uom` | `支` | |
| `currency` | `CNY` | 必填 |
| `is_active` | 保持勾选（`default=1`） | |
| `is_default` | 保持勾选（`default=1`） | 见下方说明 |
| `with_operations` | **勾上**（`default=0`，R5 实测） | **不勾则工序成本完全不进 BOM** |
| `routing` | `压缩弹簧-标准` | 选它即把三道工序带进 `operations` 子表 |
| `rm_cost_as_per` | 见下方 ⚠ 框 | `default='Valuation Rate'` |

> **⚠ `with_operations` 默认不勾，而不勾的代价很大。** R3 实测：关掉它会让成品成本虚低 **57%**——只算材料不算工费。**弹簧厂必须勾**，因为工序成本（卷簧+回火+磨端）占总成本近一半。

> **⚠ `rm_cost_as_per` 的三个取值与一个陷阱**（LG-020，操作稿 v1 在此写错过）：
>
> | 取值 | 从哪取价 |
> |---|---|
> | `Valuation Rate`（默认） | 该物料当前的库存估值单价 |
> | `Last Purchase Rate` | 最近一次采购单价 |
> | `Price List` | 指定价目表里的价格（要另填 `buying_price_list`） |
>
> **陷阱**：新站点线材还没入库，`Valuation Rate` 取到 **0**，而 BOM 里三个成本字段（`rate` / `amount` / `base_amount`）都是 `read_only=1`（R5 实测），**手填不了**。
>
> **办法**：首次建 BOM 时选 `Price List` + `Standard Buying`（L1 第八步已建好 7.5 元/kg 的价格记录）。等 L3 线材入库后可切回 `Valuation Rate` 点「更新成本」对照看。

**物料清单（`items` 子表）**：加一行线材。

| 字段 | 填什么 |
|---|---|
| `item_code` | `WIRE-65MN-2.0` |
| `qty` | **8.68** |
| `uom` | `Kg` |

**这个 8.68 就是 L1 算出的换算系数乘以基准量**：1000 支 × 0.00868 kg/支 = 8.68 kg。

**工艺损耗（`process_loss_percentage`）**：填 `5` 〔典型值：冷卷圆簧的调机废品与切头切尾约 3-8%〕。

> **⚠ 这里会撞上 L0 第九步勾的那个「必须为整数」。**
>
> `bom.py:1351-1358` 的 `set_process_loss_qty()`：`process_loss_qty = quantity × process_loss_percentage / 100`。本例 1000 × 5% = 50，是整数，过得去。
>
> **但若基准量填 1234、损耗填 5%，算出 61.7**，则 `bom.py:1365-1375` 的 `validate_uom()` 会拦：
>
> ```python
> if process_loss_qty and must_be_whole_number and process_loss_qty % 1 != 0:
>     frappe.throw("Item: {} with Stock UOM: {} can't have fractional process loss qty...")
> ```
>
> **办法**：基准量取整百整千（本层取 1000 正是为此），或损耗率取能除尽的数。**这是"UOM 勾整数"与"损耗按百分比算"两个设计的交互后果，不是 bug**——但它是个隐性约束，定基准量时要一并考虑。

**保存 → 提交。**

> **⚠ 保存后「提交」按钮不出现，须刷新页面**（R3 实测，已验证服务端 `is_submittable=1`、校验通过、有 submit 权限、无 Workflow 拦截）。这是 `SH-P1S1006` 那六例前端不刷新问题之一。

**提交后看三个成本数**（R3 实测值，本层可用作核对基准）：

| 字段 | 值 | 怎么来的 |
|---|---|---|
| `raw_material_cost` | 65.1 | 8.68 kg × 7.5 元/kg |
| `operating_cost` | 86.67 | (50+18+36) 分钟 ÷ 60 × 50 元/小时 |
| `total_cost` | **151.767** | 65.1 + 86.67（差 0.003 是精度） |

**单支成本 = 151.767 ÷ 1000 = 0.1518 元** 〔典型值〕。

> **`is_default` 与 `is_active` 这两个勾要分清**（`bom.py:729-751` 的 `manage_default_bom()`，R5 实测）：
>
> - **`is_default`**：同一物料的多张 BOM 里**只能有一张是 default**。设为 default 时其余自动取消（`set_default`），并把 `Item.default_bom` 指向它。
> - **`is_active`**：可有多张同时 active。非 active 的 BOM 不能被工单引用。
> - **取消提交（cancel）时 `is_default` 被强制置 0**（`:443`），且若 `Item.default_bom` 指向它则清空。
>
> **这套机制就是 BOM 版本管理的原生形态**——见段④的 B1。

### 第五步：图纸与图号（B1，本层新增，闭环完全没涉及）

场景 B1「图号与图纸版本管理」R1 判 ⚠（需二开），且它在 R1 的 11 层表里**没挂进任何一层**。R5 裁决归入本层并复查源码。

**原生能做的**（R5 实测）：

| 能力 | 机制 | 在哪 |
|---|---|---|
| 给 BOM / Item 挂图纸文件 | 通用附件（`File` DocType），任意 DocType 都能挂 | 表单右侧「附件」区 |
| 附件内容去重 | `File.content_hash`，同内容同私有性只存一份（`file.py:481-510`） | 自动 |
| 附件的增删留痕 | 生成 `Comment` 记录，`comment_type` 为 `Attachment` / `Attachment Removed`（`file.py:253`、`:909`） | 表单的活动流 |
| BOM 字段级改动留痕 | `BOM.track_changes=1`（R5 实测），每次修改生成 `Version` 记录 | `Version` DocType |
| BOM 有版本序号 | `autoname` 生成 `BOM-{item_code}-001` / `-002` 递增（`bom.py:183-215`） | 自动 |
| 同物料多 BOM 且只一张生效 | `is_default` 单选 + `is_active`（`bom.py:729-751`） | 自动 |
| 修订式改版 | `amended_from`（取消后修订，新文档带 `-1` 后缀并记录来源） | 提交后可 amend |
| amend 时附件自动带过来 | `copy_attachments_from_amended_from()`（`frappe/model/document.py:627-633`） | 自动 |

**操作路径**：在 BOM 表单右侧「附件」区上传图纸 PDF。改版时**不覆盖原附件**，而是走 amend（取消 → 修订）产生新版 BOM 并挂新图纸，旧版 BOM 留在系统里 `docstatus=2`。

**原生做不到的**（B1 的 ⚠ 判定依据，R5 复查后确认成立但范围比 R1 隐含的窄）：

| 缺什么 | 后果 |
|---|---|
| **图纸文件本身无版本号字段** | `File` 只有 `file_name`，改版靠"文件名里写 Rev.B"这种人守的约定。系统不知道哪份是最新 |
| **`Version` 不记录附件变动** | `FIELDTYPES_TO_IGNORE`（`version.py:12`）排除了 `no_value_fields`，附件不是字段故不进 diff。附件变动只在 `Comment` 里有一行，**不与 BOM 版本关联** |
| **无变更通知机制** | 改版后车间不会收到任何提示。**这正是 B1 乱象原文"改版没通知"的直接对应** |
| **无"车间只能看最新版"的强制** | 旧版 BOM 虽 `docstatus=2` 但附件仍可打开；纸质图纸更管不住 |
| **图号不是一等公民** | 客户图号在 `Item.customer_items.ref_code`（L1 第七步），厂内图号只能塞 `item_code` 或 Custom Field，两者无关联 |

**判定：⚠ 维持，但拆为两项**（本层的 B1 复查结论）：

1. **BOM 的版本管理——原生够用（改判 ✅）**。`autoname` 递增序号 + `is_default` 单选 + `is_active` + `amended_from` + `track_changes`，这套机制完整。R1 判 ⚠ 时把"BOM 版本"与"图纸版本"混为一件事了。
2. **图纸文件的版本与变更通知——原生缺口（⚠ 维持）**。要二开的是：给 `File` 或一个自建 DocType 加版本号与生效状态、改版时给相关角色发通知（Frappe 的 `Notification` 机制可用）、车间查看界面只列当前版。

**这条复查的价值**：R1 的 B1 ⚠ 隐含"BOM 版本管理也要做"，而实际不必——**二开范围缩小了一半**。这是 LG-021 那条教训的第三个应验实例。

**已并入 `SH-P1S1005` 的全量排查范围**，唤醒条件与 B4（模具工装）一并考虑——两者同属工程数据的周边管理。

### 本层的 B/C 类产品族差异节（DEC-004）

#### B 类：异形线成型

| 维度 | 与 A 类的差异 |
|---|---|
| **工艺路线** | 工序少（成型 → 去应力 → 表处），但**成型工序的核心是程序而非工艺参数**。数控成型机的凸轮程序 / CNC 代码是一份文件，原生只能作附件挂着（同 B1 的图纸问题） |
| **BOM 物料** | 线材用量按图纸逐段量出（L1 已说），BOM 里就是一个数，与 A 类无差别 |
| **工时** | 成型工序的换型时间占比比 A 类更高（要换凸轮组或改程序），**`setup_time` 缺失的痛感更强** |
| **模具工装** | 凸轮组是工装，属场景 B4（⚠） |

**结论**：B 类在本层的差异**集中在"成型程序是一份要管版本的文件"**，与 B1 的图纸版本问题同源、同一个二开解决。

#### C 类：板簧 / 碟簧（冲压）

| 维度 | 与 A 类的差异 |
|---|---|
| **BOM 有联产品** | 冲压的边角料有回收价值，要用 **`BOM.secondary_items` 子表**（R1 已查证该字段存在，带 `valuation_type` / `cost_allocation_per` / `process_loss_per`）。**这是 A 类基本不用而 C 类必用的一个对象** |
| **材料利用率是核心指标** | 板材冲压的利用率 60-85% 〔典型值〕，直接决定成本。A 类线材几乎无此问题（切头切尾占比小） |
| **工艺路线** | 冲压 → 热处理（淬火+回火，外协居多）→ 喷丸 → 表处。**热处理外协使 L7 的权重远高于 A 类** |
| **模具是成本大头且有寿命** | 冲压模具几万到几十万、有冲次寿命。摊销进机时费率还是单独核算是个会计决定。属 B4（⚠） |

**结论**：C 类在本层要多用一个对象（`secondary_items`）、并把材料利用率作为独立指标管起来。**`secondary_items` 原生完备，无缺口**；材料利用率报表要自建（报表层，不动数据模型）。

> **这一节对 DEC-004 的"其余八层几乎一致"给出了一处修正**：C 类的热处理外协使 **L7 的权重显著高于 A 类**，而 R1 判"差异只落在 L1/L2 两层"。R1 复核建议的中风险项第二行（"未验证冲压/成型工艺在计划、外协、质量层是否也有结构差异"）**在 L7 这一点上已可确认有差异**——不是结构差异（机制相同）而是**权重差异**（A 类外协只有电镀，C 类连热处理都外协）。L7 产出时须设专节。

## 段② 背后的数据模型

### BOM 的三条成本计算链

`bom.py:992-1010` 的 `calculate_cost()` 是枢纽，它串起三条链：

```python
def calculate_cost(self, save_updates=False, update_hour_rate=False):
    self.calculate_op_cost(update_hour_rate)          # ① 工序成本
    self.calculate_rm_cost(save=save_updates)         # ② 材料成本
    self.calculate_secondary_items_costs(...)         # ③ 联产品/废料（冲压用）
    self.set_fg_cost_allocation()
    ...
    self.total_cost = self.operating_cost + self.raw_material_cost - self.secondary_items_cost
```

**注意 `total_cost` 的公式：工序成本 + 材料成本 − 联产品成本。** 废料是**减项**——它有回收价值，故从成品成本里扣掉。这对 C 类（冲压，边角料量大）影响显著，对 A 类影响小。

#### 链① 工序成本（`calculate_op_cost`，`:1012-1048`）

```python
if self.get("with_operations"):
    for d in self.get("operations"):
        if d.workstation or d.workstation_type:
            self.update_rate_and_time(d, update_hour_rate)
        ...
        self.operating_cost += flt(operating_cost)
elif self.get("fg_based_operating_cost"):
    total_operating_cost = flt(self.quantity) * flt(self.operating_cost_per_bom_quantity)
```

**两条互斥的路**：勾了 `with_operations` 走逐工序累加；否则若填了 `fg_based_operating_cost` 则按"每基准量一个总工费"算。**两个都不给则工序成本为 0**——这就是 `with_operations` 不勾导致成本虚低 57% 的机制。

每道工序的成本在 `update_rate_and_time()`（`:1036-1060`）算：

```python
if not row.hour_rate or update_hour_rate:
    hour_rate = flt(frappe.get_cached_value("Workstation", row.workstation, "hour_rate"))
    ...
if row.hour_rate:
    row.operating_cost = flt(row.hour_rate) * flt(row.time_in_mins) / 60.0
    row.cost_per_unit = row.operating_cost / (row.batch_size or 1.0)
```

**三点要注意**：
1. **`hour_rate` 只在为空时才去取工站的值**（`if not row.hour_rate`）——已有值就不动。这是"BOM 是快照"的实现细节。
2. 费率从**工站**取，而工站的 `hour_rate` 是子表累加出来的（第一步讲过）。故**成本链的源头是那四个成本构成数字**。
3. `set_cost_based_on_bom_qty` 勾上时改用 `cost_per_unit × quantity` 算，是另一种口径。

#### 链② 材料成本（`calculate_rm_cost`，`:1064` 起）

逐行取 `get_rm_rate()`（`:638`），取价方式由 `rm_cost_as_per` 决定（第四步讲过三个取值）。**只对 `is_stock_item` 或 `is_phantom_item` 的行取价**——非库存物料（服务类）不自动取价。

`get_bom_item_rate()`（`:1385` 起）是实际取价处：

```python
if bom_doc.rm_cost_as_per == "Valuation Rate":
    rate = get_valuation_rate(args) * (args.get("conversion_factor") or 1)
elif bom_doc.rm_cost_as_per == "Last Purchase Rate":
    ...
```

**注意 `conversion_factor` 在这里参与乘法**——若 BOM 行的 uom 与物料的 stock_uom 不同，取价后要按换算系数折算。**这是 L1 的换算系数进入成本链的第二个入口**（第一个是 `qty` 本身）。

#### 链③ 联产品（`calculate_secondary_items_costs`）

C 类冲压用。`BOM Secondary Item` 带 `valuation_type`（按估值/按售价）、`cost_allocation_per`（分摊比例）、`process_loss_per`。本层不展开，L8 成本核算会讲联产品成本分摊。

### 「BOM 是快照」这件事的三处证据

这是本层最该带走的一个认识，因为它解释了一类"改了却没生效"的困惑。

**证据一：改工站费率只回写 Routing，不回写 BOM**（`workstation.py:190-202`，R3 的 FD-44 更正）：

```sql
select DISTINCT parent from `tabBOM Operation`
where workstation = %s and parenttype = 'routing'
```

**只取 `parenttype='routing'` 的父文档**，随后 UPDATE 也带同一限定。故**只改工艺路线里的工序行，不碰 `parenttype='BOM'` 的行**。

表名叫 `tabBOM Operation` 容易误以为它改 BOM——实际不是（**Routing 与 BOM 的工序子表共用这一张表，靠 `parenttype` 区分**）。

**证据二：改 Routing 工时不回改已有 BOM**。Routing 被 BOM 选中时是**复制** `operations` 过去，复制后两者脱钩。R3 实测：改 Routing 工时后，已提交 BOM 的三个成本数分毫未动。

**证据三：`update_rate_and_time()` 里的 `if not row.hour_rate`**（上面链①第 1 点）——已有费率就不重取。

**故正确表述是**：

> **BOM 一经提交，其工时与费率都是"当时快照"；Routing 侧才是"当前值"。**

**这对"钢价传导"（场景 A4）有实际影响**：改 `Item Price` 或改机时费率**不会**自动刷新已有 BOM 的成本。要刷得走两条路：

| 路 | 做法 | 适用 |
|---|---|---|
| 逐张手动 | 打开 BOM 点「更新成本」（`update_cost()`，`bom.py:677`） | BOM 少、或只关心几个主力品 |
| 批量自动 | 开 `Manufacturing Settings.update_bom_costs_automatically`，或跑 **BOM Update Tool**（`manufacturing/doctype/bom_update_tool/`，R5 实测该 DocType 存在，配套有 `BOM Update Log` + `BOM Update Batch` 做分批与日志） | BOM 多、钢价定期变动 |

**弹簧厂该开自动更新**——钢价一动全部 BOM 成本跟动，这正是场景 A1「钢价传导从'月底才发现'变'改一个价全部 BOM 跟动'」那条效率收益的实现处。**但要知道它跑起来是批量后台任务**（`BOM Update Log` 的存在即证明），**吃"调度器在跑"这个前提**（与 LG-011/051、L1 的变体批量生成同源，本项目第四处）。

### BOM 的命名与版本机制（`bom.py:183-215`）

```python
search_key = f"{self.doctype}-{self.item}%"
existing_boms = frappe.get_all("BOM",
    filters={"name": search_key, "amended_from": ["is", "not set"]}, pluck="name")
index = self.get_index_for_bom(existing_boms)
bom_name = f"BOM-{self.item}-{'%.3i' % index}"
```

**要点**：
- 主键形如 `BOM-SPR-C-2.0-16-50-8-65MN-001`，序号按同物料已有 BOM 数递增。
- **算序号时排除 amended 文档**（`amended_from is not set`）——修订产生的 BOM 不占新序号，它走 `-1` 后缀。
- **料号太长时截断**（`len(bom_name) > 140` 时截 `item` 部分并按空格回退）。**L1 的变体料号若属性多会很长**，这条兜底使它不至于建不出来，但**主键会变得不可读**。〔R5 未实测 140 字符的实际触发点，变体料号约 30 字符、远未触及〕

### 各对象的必填与主键一览

| DocType | 主键来源 | 必填字段 |
|---|---|---|
| `Workstation` | `field:workstation_name` | `workstation_name`、`production_capacity`（`default=1`） |
| `Operation` | **`Prompt`**（保存时弹窗） | 无 |

## 段③ 弹簧厂在这一层的场景

R1 给 L2 挂了六个场景：**A1**（按图询价报价）、**B2**（BOM 线材kg→成品支）、**B3**（工艺路线）、**B5**（新品试制打样）、**H2**（材料成本与线材利用率）、**H3**（工序成本与机时费率）。R5 另把 **B1**（图纸版本）归入本层。

### A1 客户按图询价 → 成本估算报价 🔧

**乱象原文**：老师傅拍脑袋，同一件不同人报不同价；同一个件三个月后再报价可能差 15%；钢价涨了没人系统性调价，月底核算才发现某几个单在亏本做。

**原生怎么接**（本层已建完前半，报价单本身属 L4）：
1. 线材建 Item + `Item Price` 挂当期采购价（L1 第八步）。
2. 工序建 Operation 绑 Workstation、填四项成本构成得 `hour_rate`（本层第一步）。
3. 建 BOM——材料用量按展开长度算出的 `conversion_factor` 乘基准量，工序填 `time_in_mins`，**BOM 自动算出 `raw_material_cost` + `operating_cost` = `total_cost`**（本层第四步）。
4. 报价时引用该 Item，系统给出成本，报价 = 成本 × (1 + 毛利率)。
5. 钢价变动改 `Item Price` + 开 `update_bom_costs_automatically` 或跑 BOM Update Tool，**所有 BOM 成本一次刷新**。

**效率收益**：报价从"凭经验 15 分钟且可能报错"变"查 BOM 30 秒且成本有据"；同规格再报价价格一致；钢价传导从"月底才发现"变"改一个价全部跟动"。

**三个落地前提（🔧 的原因）**：

| # | 前提 | 本层的落点 |
|---|---|---|
| ① | **必须先算出机时费率** | 本层第一步。中小厂通常没算过，要财务配合做一次基础工作 |
| ② | **必须把单支耗料落成公式** | L1 第六步（展开长度公式 → `conversion_factor`） |
| ③ | **询价阶段即要建料号** | L1 第一步（独立物料组「询价件」） |

**原生缺口**：无结构性缺口。Quotation 不展开成本构成（料/工/费拆分），要给老板看拆分需自定义报表——**报表层，不动数据模型**。

**判定维持 🔧**。**三个前提里两个落在 L1、一个落在本层，全部是"要人做一次基础工作"而非"要写代码"**——这正是 🔧 这个判定码的含义。

### B2 BOM：线材 kg → 成品支 ✅

**乱象原文**：单支耗料靠经验，超耗查不出。

**原生怎么接**：`Item.uoms` 存换算系数（L1），BOM 的 `items` 行按 kg 填用量、`conversion_factor` 参与取价与折算（段②链②）。实际领料与 BOM 的差额由 L8 的 BOM 差异报表（`bom_variance_report`）呈现。

**效率收益**：超耗从"查不出"变"每张工单都能对比 BOM 用量与实际领料"。

**原生缺口**：无。**但要指出一处 R1 没说的**：超耗能查出的前提是**领料按工单领**（而非"车间自己去仓库拿"），这是流程纪律问题，属 L5。

**判定维持 ✅**。

### B3 工艺路线 ✅

**乱象原文**：工艺在老师傅脑子里。

**原生怎么接**：`Routing` 存一串工序 + 各自工时，BOM 选它即带入。**同一套工艺路线服务几百个规格**——这正是 Routing 存在的理由。

**效率收益**：工艺从"在人脑子里"变"在系统里且可复用"；新规格建 BOM 时选一下 Routing 就完事。

**原生缺口**：**`Routing` 无基准数量字段**（段①第三步的 ⚠ 框）。它依赖"全厂共用同一 BOM 基准量"这条隐含约定，约定靠人守。**这一条使 B3 的 ✅ 打了个折**——机制够用，但有一处该由字段保证的东西交给了人。已登记 `SH-P1S1005` 第 ③ 层。

**判定维持 ✅**，附注上述约定风险。

### B5 新品试制 / 打样 🔧

**乱象原文**：打样料从生产料里拿，成本混在一起。

**原生怎么接**（本层的落点是 BOM，单据侧属 L5）：给打样件单独建 Item（L1 的「询价件」组或另建「样品」组）+ 单独 BOM + 工单。成本自然分开。

**落地前提（🔧 的原因）**：**要让车间接受"打样也要开工单"**。中小厂打样常是老师傅直接上机、料从生产料箱里抓——这是流程改造点，技术上无障碍。

**判定维持 🔧**。

### H2 材料成本与线材利用率 ✅ / H3 工序成本与机时费率 🔧

这两个的主体在 L8（成本核算），本层只提供数据源：

| 场景 | 本层提供什么 | R1 判定 |
|---|---|---|
| **H2** 材料成本与线材利用率 | BOM 的 `raw_material_cost` 与 `process_loss_percentage`。**C 类冲压还有 `secondary_items`（边角料回收）** | ✅ |
| **H3** 工序成本与机时费率 | `Workstation.hour_rate`（四项成本构成累加）+ `BOM Operation.operating_cost` | 🔧（乱象原文"没有机时费率概念"，故要先算出来——即 A1 的落地前提①） |

**H3 判 🔧 的实质就是本层第一步那个 ⚠ 框**：机制完备，缺的是有人把每台机的月度成本与有效工时算一次。

### B1 图号与图纸版本管理 ⚠ → **R5 复查后拆为两项**

见段①第五步。**BOM 版本管理改判 ✅**（原生机制完整），**图纸文件版本与变更通知维持 ⚠**。二开范围比 R1 隐含的缩小约一半。

## 段④ 这一层的痛点与原生缺口

R1 给 L2 标的痛点是两句：「**机时费率要先算出来**」「**展开长度公式**」。前者是 H3 的落地前提（段③已展开），后者实际落在 L1。R5 复查后另补出四条。

### 缺口一：机时费率要先算出来 → **判定维持 🔧，非缺口**

机制完备（`workstation_costs` 子表 + 累加），缺的是一次性基础工作。**拆成四项填反而比填一个总数好**（可追溯、可单项调整）。见段①第一步。

### 缺口二：展开长度公式 → **归 L1，本层只承接结果**

L1 段④缺口二已判 ⚠（无字段存放规格参数、每料号手算）。本层承接的是那个 `conversion_factor` 如何进入成本链（段②链②）。

### 缺口三（R5 新增，实为 R1 判断的更正）：`Routing` 无基准数量字段

**现象**：`Routing` 只有 `routing_name` / `disabled` / `operations` 三个字段，**没有数量字段**，故 `time_in_mins` 的含义依赖隐含约定。

**后果**：两人按不同基准填，成本差数倍而系统不报警。R3 实操中操作稿 v1 的"Routing 填 5000 基准、BOM 里除以 5"正是这条约定缺失逼出来的变通，那个除法被判为多余的出错来源（DEC-021）。

**判定**：⚠ **需二开**（加一个 `base_qty` 字段 + 在 BOM 引用 Routing 时按比例折算）。**成本低**（一个字段 + 一处折算逻辑），**价值在于把约定变成字段**。已登记 `SH-P1S1005` 第 ③ 层。

### 缺口四（R5 新增）：`fixed_time` 只有两档，表达不了"准备 + 单件"

**现象**：`BOM Operation.fixed_time` 是 Check——勾了完全不随数量变、不勾完全线性。**没有中间形态**。

**后果**：卷簧的真实工时是"20 分钟换型（不随批量）+ 每支 0.05 分钟（线性）"，两档二选一表达不了。**换型时间是弹簧行业最大的效率杠杆**，它进不了模型即意味着：

- 排产看不见换型成本，故"合并同线径订单"这个最有效的优化系统完全不知道（场景 C3 判 ⚠ 正是因此）。
- 小批量订单的成本被系统低估（真实成本里换型占比很高）。

**原生缺口成立**（R5 确认 `grep setup_time` 在 manufacturing 模块零命中，与 R1 的查证一致）。

**判定**：⚠ **需二开**。做法是给 `BOM Operation` 加 `setup_time` Custom Field 并改 `calculate_time()` 为「准备 + 单件 × 数量」，即 MRP II 标准模型。已登记 `SH-P1S1005` 第 ② 层。

**这一条与缺口三是同一批工作**，且**它是 C3（换型合并，⚠）与 C4（插单与优先级，⚠）的共同前置**——没有换型时间数据，排产优化无从做起。**L10 排优先级时应把「工时模型标准化」作为 C3/C4 二开的前置任务单列。**

### 缺口五（R5 新增）：批处理工序"一炉混多工单"无原生形态

**这是 D2 的 ⚠ 拆分后的后半项**（前半项「批处理工时不随批量变」原生有 `fixed_time`）。

**现象**：`Job Card.work_order` 必填，故一炉混 5 个工单就得开 5 张任务单分别计时。而实际是一次装炉、一次出炉。

**后果**：报工负担比纸单还重（这正是 D2 乱象"报工靠纸单，隔天录或干脆不录"的成因之一）；且工时分摊不准。

**判定**：⚠ **需二开**，属 L5（生产执行）的主要工作面。本层只指出它与 `fixed_time` 是两件事——**别因为 `fixed_time` 存在就以为 D2 的 ⚠ 可以取消**。

### 缺口六（R5 新增）：图纸文件版本与变更通知

见段①第五步与段③的 B1。**判定 ⚠ 维持，但范围缩小**——BOM 版本管理部分改判 ✅。

## 段⑤ 判定

**本层总判定：机制完备度高，但**⚠ **最密集——本层有 4 个 ⚠，且其中两个（工时模型、图纸版本）是下游多个 ⚠ 的共同前置。**

逐项：

| 对象 | 判定 | 依据 |
|---|---|---|
| `Workstation` 与机时费率机制 | ✅ | 四项成本构成累加，可追溯、可单项调。**缺的是有人算一次**（那是 H3 的 🔧） |
| `Workstation Type` | ✅ | 同型多机台的抽象，C 档规模会用到 |
| `Operation` | ✅ | 无必填、工站作默认值可覆盖 |
| **`Routing` 复用机制** | ✅ | 正是"工艺在老师傅脑子里"的解（B3） |
| **`Routing` 无基准数量字段** | ⚠ | **R5 新增**。用约定代替字段，成本差数倍而不报警。二开成本低（`SH-P1S1005` ③） |
| BOM 的三条成本计算链 | ✅ | 料/工/联产品三链清晰，`total_cost = 工 + 料 − 联产品` |
| **「BOM 是快照」+ 批量更新工具** | ✅ | 三处证据已查明（段②）。BOM Update Tool + `update_bom_costs_automatically` 覆盖钢价传导。**吃"调度器在跑"这个前提** |
| **`fixed_time` 两档不足，无 `setup_time`** | ⚠ | 换型时间进不了模型。**是 C3/C4 二开的共同前置**（`SH-P1S1005` ②） |
| **批处理"一炉混多工单"** | ⚠ | `Job Card.work_order` 必填。属 L5 主工作面。**D2 的 ⚠ 后半项** |
| **BOM 版本管理** | ✅ | **R5 改判**（R1 隐含它需二开）。序号递增 + `is_default` 单选 + `amended_from` + `track_changes`，机制完整 |
| **图纸文件版本与变更通知** | ⚠ | **R5 确认缺口**。`File` 无版本号、`Version` 不记附件变动、无通知机制、无"只看最新版"强制 |
| `secondary_items`（C 类联产品） | ✅ | 字段完备，含 `valuation_type` / `cost_allocation_per` / `process_loss_per` |
| `process_loss_percentage` | ✅ | 机制在。**与 UOM 整数校验有交互**，定基准量时要一并考虑 |

### 交给下一批（L3-L4）的四件事

1. **`Warehouse.account` 分挂后领料分录会变成什么样**（L0 缺口三留的账）。

### 留给 L10 汇总的

本层产出 **4 个 ⚠**：`Routing` 基准量、`setup_time` 缺失、一炉混多工单、图纸版本与通知。

**其中两个是"前置型"缺口**，L10 排优先级时不能与并列项同等看待：

- **工时模型标准化**（`Routing` 基准量 + `setup_time`）是 **C3 换型合并**与 **C4 插单优先级**两个最高优先级 ⚠ 的共同前置。没有换型时间数据，排产优化算法无输入。
- **图纸/程序版本管理**同时覆盖 **B1**（A 类图纸）与 **B 类的成型程序**，且与 **B4 模具工装**同属工程数据周边管理，宜合并考虑。
