## 怎么用本稿

**两层写法**（DEC-010）：每个环节分「操作」与「数据模型」两段。操作段是照着点的路径；数据模型段讲这一步在数据库里实际发生了什么——DocType 叫什么、关键字段在哪个文件、校验逻辑在哪一行。第二段是你判断"日后二开从哪切入"的抓手，**别跳过**。

**三个 ★ 节点**（环节 13 / 20 / 23）是最该停下来看的地方。ERPNext 的核心机制（库存动作如何变成会计分录、WIP 会计、成本如何从 BOM 流到利润表）全在那里。按 DEC-010，本稿**不含会计原理层**——只讲"这笔分录是什么、由哪段代码生成的"，不讲"借贷为什么这么记"。若你在 ★ 处看不懂分录本身，那是 LG-010 记着的缺口，回头另补一份会计原理材料，别在这里硬扛。

**关于本稿里的数值**（Stage 概况的恒定约束）：凡工时、损耗率、线材规格、批量这类数字，一律只具「公开资料典型值」效力，**不具本客户实际值效力**。它们的作用是让你有个能跑通的具体例子，不是业务基准。实地考察时逐项校准。本稿对此类数值一律标注 `〔典型值〕`。

**产品主线**（DEC-004）：冷卷圆簧（压缩弹簧）。B 类异形线成型与 C 类板簧冲压的差异不在本稿，在 L1/L2 教材的差异节。

**规模档位**（DEC-005）：B 档小型厂（50-150 人，多机台多班）〔典型值〕。

**环境**：`erx.localhost`，浏览器开 http://localhost:8000 或 http://erx.localhost:8000，登录 `Administrator` / `admin`。界面语言已是中文，故本稿的菜单名给中文，**并在括号里附英文原名**——报错信息和源码里只有英文，中英对照能省掉大量翻译猜测。

## 环节 0　清场：把站点变成干净的弹簧厂环境

**为什么有这一节**：DEC-011 定了"不用 ERX Demo 演示数据"，DEC-013 定了形态为"现站点内新建公司"。而 Item / Customer / Supplier 三类**没有 `company` 字段**（已查证），跨公司共享——不清掉 demo 数据，你在选料号时会看到 10 个 `SKU001`-`SKU010`、选客户时看到 3 个 demo 客户混在列表里。这正是 NV-007 否决"在演示数据上学"的理由。

### 操作

**第一步：清演示数据。** 在宿主机（Git Bash）跑：

```bash
docker/seed-demo.sh --clear
```

**先确认 `docker/start.sh` 正在另一个终端里跑着。** 这条清除走的是 Transaction Deletion Record，它把删除排进**后台队列**（`erpnext/setup/demo.py:202-211` 的 `start_deletion_tasks()`），队列 worker 不在跑就只是排了个队、什么也没删——表现为"脚本说成功但数据还在"（LG-011）。

**第二步：确认真的清干净了。** 不看脚本输出，查数据库：

```bash
export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'
docker compose -f docker/compose.yaml exec -T -w /workspace/frappe-bench/sites frappe \
  ../env/bin/python -c "
import frappe
frappe.init(site='erx.localhost'); frappe.connect()
for dt in ('Company','Item','Customer','Supplier','Sales Order','Purchase Order'):
    print(dt, frappe.db.count(dt))
"
```

> **Windows 上 `MSYS_NO_PATHCONV=1` 不可省**：Git Bash（MSYS）会把 `-w /workspace/...` 改写成 Windows 路径，报 `Cwd must be an absolute path`。这条坑在 `docker/README.md`「Windows 上的几处适配」里也记着。

期望结果：`Item` / `Customer` / `Supplier` / `Sales Order` / `Purchase Order` 全为 0，`Company` 剩 1（`ERX Demo`）。若计数没动，说明队列没跑——去看 `docker/start.sh` 那个终端有没有报错，起来后重跑第一步。

**第三步：删掉 `ERX Demo` 主公司。** 界面上搜「公司」（Company）列表 → 打开 `ERX Demo` → 右上 `...` → 删除（Delete）。

删公司会连带删它的整棵科目表与仓库树，所以可能报 `LinkExistsError`（有单据还挂在它名下）。**删不掉就不要硬删**——改成：把它的名字改为 `ZZ-废弃-ERX Demo`、勾上「禁用」类字段（若有），让它排在列表末尾不干扰，然后继续往下走（LG-012 记着这条）。公司是可以共存的，多一家废弃公司不影响本稿任何环节。

### 数据模型

- **清除逻辑**在 `erpnext/setup/demo.py`：`clear_demo_data()`（第 59-77 行）依次做三件事——建 Transaction Deletion Record 删单据、`clear_masters()` 删主数据、`delete_company()` 删 `(Demo)` 副本公司。
- **删哪些主数据由 hooks 声明**：`erpnext/hooks.py:92-99` 的 `demo_master_doctypes`，六类：`item_group` / `item` / `customer_group` / `supplier_group` / `customer` / `supplier`。`clear_masters()` 按该列表**倒序**删（第 213-219 行）——倒序是因为 item 依赖 item_group，必须先删依赖方。
- **不会被清掉的**：UOM（239 条）、Price List（`Standard Selling` / `Standard Buying`）、Warehouse Type（`Transit`）、全局币种 CNY。这四样正是 v16 全新安装的初始化缺口（见 `docker/README.md`「v16 全新安装需要的额外初始化」），由 `seed-demo.sh` 补上、`--clear` 不动。**这是选 DEC-013 而非新建站点的主要收益**：新站点得把这五处坑重踩一遍。
- **`Transaction Deletion Record`** 是 ERPNext 的通用"清空某公司所有交易"工具，不只服务 demo。它按 DocType 分批删并记录进度，故是异步的。日后你想把弹簧厂数据清空重来，用的也是它（或直接 `docker/restore.sh` 回滚到备份）。

### 做完这一节，先备份

```bash
docker/backup.sh
```

这份备份是"干净空站点"的存档。后面任何环节搞坏了，`docker/restore.sh` 回到这里重来，比手工删数据快得多。DEC-011 说的"随时重置重来"就靠它。

## 环节 1　建公司与科目表

### 操作

搜「公司」（Company）→ 新建。填：

| 字段 | 填什么 | 说明 |
|---|---|---|
| 公司名称（Company Name） | `华东弹簧` | 这个值同时成为文档主键（`autoname` 为 `field:company_name`） |
| 缩写（Abbr） | `HDS` | **会作为后缀拼进所有科目与仓库名**（如 `Stock In Hand - HDS`），定了就别改 |
| 默认货币（Default Currency） | `CNY` | |
| 国家（Country） | `China` | 决定装哪套地区化逻辑；v16 的 `erpnext/regional/` **无 china**，故此处只影响时区与地址格式，没有中国财税逻辑（这是 LG-001，第 ② 阶段的主要工作面） |
| 科目表（Chart of Accounts） | `Standard` | |
| 启用永续盘存（Enable Perpetual Inventory） | **勾上** | 这一勾决定"库存动作是否自动产生会计分录"。不勾则 ★ 节点看不到任何东西 |

保存。保存要等几秒——它在后台生成整棵科目表、仓库树和一批默认账户。

保存后回到该公司页面，确认这几个字段被自动填上了（后面的 ★ 节点全靠它们）：

| 字段 | 期望值 |
|---|---|
| 默认库存账户（Default Inventory Account） | `Stock In Hand - HDS` |
| 已收货未开票（Stock Received But Not Billed） | `Stock Received But Not Billed - HDS` |
| 库存调整账户（Stock Adjustment Account） | `Stock Adjustment - HDS` |
| 默认应付账户（Default Payable Account） | `Creditors - HDS` |
| 默认应收账户（Default Receivable Account） | `Debtors - HDS` |
| 默认成本中心（Cost Center） | `Main - HDS` |

**设为默认公司**：搜「全局默认值」（Global Defaults）→ 默认公司选 `华东弹簧` → 保存。这一步别漏——默认公司与单据公司不一致时，ERPNext 的跨公司隔离会把"取不到记录"报成**「没有权限」**，极难排查（`docker/README.md` 里专门记了这条）。

**会计年度**：搜「会计年度」（Fiscal Year），确认 `2026` 存在（`seed-demo.sh` 已建）。不存在则新建，起止 `2026-01-01` / `2026-12-31`。

### 数据模型

- **`Company`** 是几乎所有业务 DocType 的必填字段——`Purchase Order` / `Sales Order` / `Work Order` / `Stock Entry` / `BOM` 的 `reqd` 清单里全有 `company`（已逐个查证）。它是 ERPNext 多组织隔离的轴。
- **科目表不是配置项，是数据**。勾 `Standard` 后 ERPNext 从模板文件生成几百条 `Account` 记录，每条带 `parent_account` 形成树（`is_group` 标识是否为分组节点）。这意味着**科目表可以随意改**（加科目、改层级），它不是硬编码。中国厂要用的一级科目结构与 `Standard` 模板差别不小，这是第 ② 阶段要改的东西之一。
- **缩写 `abbr` 的作用**：ERPNext 用 `名称 - 缩写` 作为 Account / Warehouse / Cost Center 的主键，以此实现多公司下同名科目共存。所以 `abbr` 参与主键构成，**改它等于重命名几百条记录**，故上面说定了别改。
- **`enable_perpetual_inventory`** 是永续盘存开关。开着时每笔库存移动都由 `erpnext/controllers/stock_controller.py` 生成对应的 GL Entry；关掉则库存只有数量账、金额靠期末盘点调整。ERPNext 默认开，本稿也必须开——★ 节点要看的就是它生成的分录。
- **Item / Customer / Supplier 没有 `company` 字段**（已查证：三个 json 里 `"fieldname": "company"` 计数均为 0）。这三类是**跨公司共享**的主数据，而 `Warehouse` 有 `company`、按公司隔离。这个不对称是理解 ERPNext 数据模型的一个关键点：**"东西是什么"全公司共享，"东西在哪、值多少钱"按公司分。**

## 环节 2　建仓库

### 操作

环节 1 建公司时已自动生成一棵仓库树。搜「仓库」（Warehouse）看，应有 5 个：

```
All Warehouses - HDS        （is_group=1，树根）
├── Stores - HDS            （原料仓）
├── Work In Progress - HDS  （在制品仓）
├── Finished Goods - HDS    （成品仓）
└── Goods In Transit - HDS  （在途仓，warehouse_type=Transit）
```

自动生成的这四个正好够本稿用，**对应关系**：

| 弹簧厂的叫法 | 用哪个 |
|---|---|
| 线材仓 | `Stores - HDS` |
| 车间在制品 | `Work In Progress - HDS` |
| 成品仓 | `Finished Goods - HDS` |

再**手工加一个废料仓**（弹簧厂的切头切尾、试机废料要有地方放，对应 R1 场景 D7）：新建 → 仓库名称 `Scrap`、公司 `华东弹簧`、上级仓库 `All Warehouses - HDS`、不勾「是组」。存出来是 `Scrap - HDS`。

### 数据模型

- **`Warehouse` 是树形 DocType**（nested set）：靠 `parent_warehouse` + `lft` / `rgt` 两个整数字段维护树结构。`lft`/`rgt` 是 nested set 的左右值，查"某节点全部子孙"一条范围查询就够，不用递归。你不用手填它们，框架维护。
- **`is_group`** 区分分组节点与叶子节点。**只有叶子节点能存货**——往 `is_group=1` 的仓库做库存动作会被拒。
- **仓库可以挂会计账户**：`Warehouse` 有 `account` 字段。留空则用公司的 `default_inventory_account`（即 `Stock In Hand - HDS`），此时**所有仓库的库存金额记在同一个科目里**。想让"线材仓"和"成品仓"在资产负债表上分开显示，就给各仓库分别指定账户。本稿留空——先看懂单一科目的分录，再谈拆分。
- **`Warehouse Type`** 当前只有 `Transit` 一条。它是个分类标签，被 Putaway Rule、在途调拨等功能引用。R1 的 F5（寄售/VMI）判 ⚠ 时提到"或许能用 Warehouse Type + 客户仓变通"——那条待验，见 Stage 概况风险表。

## 环节 3　建计量单位与换算

这是本稿第一个真正属于弹簧厂的建模决定：**线材按 kg 买，弹簧按支卖，两者要能换算。**

### 操作

**第一步：确认已有的 UOM。** 搜「计量单位」（UOM）。站点已有 239 条，其中 `Kg` 和 `Nos` 都在。

**第二步：建「支」。** 新建 UOM → 名称 `支` → **勾上「必须为整数」**（Must be Whole Number）。

> 勾这个的理由：弹簧按支计，0.5 支无意义。但**这一勾会在环节 6 咬你一口**——BOM 的工艺损耗算出小数时会直接报错。到那里再说，此处先记住勾了。

**第三步：不建 UOM 换算表记录。** 你可能会想去「计量单位换算系数」（UOM Conversion Factor）里加一条 `Kg → 支`。**不要**——那张表是给"同类量纲之间的固定换算"用的（kg↔g、m↔cm），它有 `category` 必填字段（量纲类别）。而 kg→支 的换算系数**每个料号都不一样**（φ2.0 的簧一支 8.7 g，φ3.0 的一支 20 g 出头），不是量纲换算。

正确的落点是**每个 Item 自己的 `uoms` 子表**，在环节 4 填。

### 数据模型

- **两张换算表，别搞混**：

  | DocType | 管什么 | 字段 |
  |---|---|---|
  | `UOM Conversion Factor` | 全局的量纲换算（kg↔g） | `category`（必填）、`from_uom`、`to_uom`、`value` |
  | `UOM Conversion Detail` | **某个 Item 的**多单位换算，是 `Item.uoms` 子表 | `uom`、`conversion_factor` |

  前者是全局常量，后者是料号属性。弹簧的 kg↔支 属后者。

- **`stock_uom` 是锚**。每个 Item 有一个 `stock_uom`（库存计量单位，`reqd=1`），**所有库存数量与估值都以它为准**；其余单位都是它的换算视图。`Item.uoms` 子表里 `stock_uom` 那一行的 `conversion_factor` 恒为 1——框架自动加这一行（`erpnext/stock/doctype/item/item.py:401-412` 的 `add_default_uom_in_conversion_factor_table`），且校验它必须为 1（同文件 `:445-457`）。
- **`must_be_whole_number`** 在 `UOM` 上。现有的 `Nos` 是 1、`Kg` 是 0（已查证）。它会在多处触发整数校验，包括 BOM 的工艺损耗（`erpnext/manufacturing/doctype/bom/bom.py:1365-1371` 的 `validate_uom`：`process_loss_qty % 1 != 0` 且 UOM 要求整数 → 抛错）。
- **这一层的原生缺口**：R1 的 L0 层痛点写的"kg↔支 换算要设计"就是这件事。原生机制够用（`Item.uoms` 正是为此而设），**但换算系数得你自己算出来填**——ERPNext 不知道展开长度公式。环节 4 会算一次；把它落成公式并录进系统，是 R1 样板一（A1 询价）说的"落地前提②"。

## 环节 4　建物料：线材与弹簧成品

### 操作

**第一步：建物料组。** 站点已有 `Raw Material` / `Products` 等标准组（demo 那个 `Demo Item Group` 已在环节 0 被清掉）。直接用：线材归 `Raw Material`，弹簧归 `Products`。

**第二步：建线材。** 搜「物料」（Item）→ 新建：

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `WIRE-65MN-2.0` |
| 物料名称（Item Name） | `65Mn弹簧钢丝 φ2.0` |
| 物料组（Item Group） | `Raw Material` |
| 默认计量单位（Default Unit of Measure） | `Kg` |
| 维护库存（Maintain Stock） | 勾上（默认已勾） |

保存。

**第三步：算弹簧的单支重量。** 这是本环节的核心，也是 R1 样板一说的"要把老师傅心里的数落成公式"。

展开长度（一支弹簧要多长的线）：

```
展开长度 L = π × 中径 D_m × 总圈数 n
中径 D_m = 外径 − 线径 = 16 − 2.0 = 14.0 mm
L = 3.1416 × 14.0 × 8 = 351.9 mm ≈ 0.352 m
```

线材单位重量（钢密度 7.85 g/cm³）：

```
截面积 A = π × (2.0/2)² = 3.1416 mm²
每米重量 = 3.1416 mm² × 1000 mm × 7.85 g/cm³ = 24.7 g/m
```

单支重量：

```
0.352 m × 24.7 g/m = 8.68 g/支 ≈ 0.00868 kg/支
```

反过来：**1 kg 线材 ≈ 115 支** 〔典型值〕。

> **这个数只是算术结果，不是车间实际值。** 真实耗料还要加钩环/端部余量、切头切尾、试机废料——R1 样板一明确提到"钩环/端部余量"。压缩簧无钩环，但磨端要磨掉料、卷簧起停有废料。实际耗料通常比理论值高 3-8% 〔典型值〕。本稿的处理：理论值填 BOM，损耗走 BOM 的 `process_loss_percentage`（环节 6），两者分开——**这样"超耗多少"才查得出来**，混在一起就永远说不清（R1 场景 H2 的痛点正是"超耗说不清"）。

**第四步：建弹簧成品。**

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `SPR-C-2.0-16-50` |
| 物料名称（Item Name） | `压缩弹簧 2.0×16×50 65Mn` |
| 物料组（Item Group） | `Products` |
| 默认计量单位（Default Unit of Measure） | `支` |
| 维护库存 | 勾上 |

**保存后**，展开「计量单位」（Units of Measure）一节，在 `uoms` 子表里加一行：

| uom | conversion_factor |
|---|---|
| `Kg` | `0.00868` |

含义是"1 支 = 0.00868 Kg"。保存。这样你在任何单据上都能用 Kg 计这个弹簧（比如按重量报废、按重量对账），系统自动换算。

> 子表里应已有一行 `支 / 1`——那是框架自动加的 `stock_uom` 行，别删也别改。

**第五步：给线材挂采购价。** 搜「物料价格」（Item Price）→ 新建：物料 `WIRE-65MN-2.0`、价目表 `Standard Buying`、价格 `7.5`（元/kg 〔典型值〕）。

这一步不是必须（采购单可以手填单价），但填了之后 BOM 才能自动算出成本——环节 6 要用。

### 数据模型

- **`Item` 的必填字段只有三个**（已查证 `reqd` 清单）：`item_code`、`item_group`、`stock_uom`。其余上百个字段全可选。这解释了为什么 v16 全新安装会报 `MandatoryError: stock_uom`——它必填而 demo 数据不带，靠 `frappe.defaults` 的全局默认值补（见 `docker/README.md`）。
- **`Item` 有 8 张子表**（已查证）：`item_defaults`（各公司的默认仓库/账户）、`uoms`（多单位换算）、`taxes`、`barcodes`、`reorder_levels`（再订货点）、`attributes`（变体属性）、`supplier_items`、`customer_items`（客户图号 ↔ 内部料号！）。
  - **`customer_items` 正是 R1 场景 A2 的原生解**（客户图号与内部料号的对应）：`Item Customer Detail` 子表存"哪个客户管这个件叫什么图号"。A2 判 🔧 而非 ⚠ 就是因为这张表在。
  - **`item_defaults` 是按公司分的**：Item 本身无 `company`，但它的默认仓库、默认成本中心这些**确实因公司而异**的东西，放在这张子表里、每公司一行。这是 ERPNext 处理"主数据共享但默认值分公司"的通用手法，值得记住。
- **`attributes` 子表 + `Item Attribute`** 是变体机制。`Item Attribute` 支持 `numeric_values` + `from_range` / `to_range` / `increment`（R1 能力核实表已验证），即"线径 1.0 到 6.0，步长 0.1"这种数值型属性。这是 R1 场景 B6（规格变体爆炸）判 ✅ 的依据——几千个规格不必手建几千个 Item，用模板 + 变体生成。本稿不用变体（单件跑通更清楚），但 L1 教材要写透。
- **`Item Price` 不是 Item 的字段，是独立 DocType**。一个 Item 可以有任意多条 Item Price（不同价目表、不同客户、不同生效期、不同数量档）。这个设计是 R1 场景 A4（客户专属价与钢价联动）判 ✅ 的基础：改钢价只是加/改一条 `Standard Buying` 的 Item Price，不动 Item 本身。
- **换算方向的坑**：`conversion_factor` 的语义是"**1 个该 uom 等于多少个 stock_uom**"。这里 stock_uom 是「支」，所以 `Kg` 那行的 0.00868 读作"1 支 = 0.00868 Kg"——**不是** "1 Kg = 0.00868 支"。填反了差 13000 倍，且系统不会报错（两个方向都是合法数字），只会在成本上体现出来。这是本环节最容易错的一处。

| `磨端` | 180 | 约 28-30 支/分钟 |

### 数据模型

- **`Workstation` 的必填只有两个**：`workstation_name`、`production_capacity`（已查证）。
- **`hour_rate` 在 v16 是计算字段**：`erpnext/manufacturing/doctype/workstation/workstation.py:110-114`

  ```python
  def set_hour_rate(self):
      self.hour_rate = 0.0
      for row in self.workstation_costs:
          if row.operating_cost:
              self.hour_rate += flt(row.operating_cost)
  ```

  在 `before_save`（第 85-92 行）里调用。子表 `Workstation Cost` 只有两个字段，都必填：`operating_component`（Link 到 `Workstation Operating Component`）、`operating_cost`（Currency）。

  > **R1 样板一（A1 询价）里写的"Workstation 填 `hour_rate`"在 v16 不准确** —— `hour_rate` 填不了，得填子表。这不影响 A1 的判定（🔧 的理由是"机时费率要先算出来"，那个理由完全成立、且拆成四项后更需要财务配合），但操作路径变了。本稿按 v16 实际写，此事已记入本轮回执。

- **`hour_rate` 变更会回写 BOM**：同文件 `:195-201` 有一段 SQL，工位费率改了就 `update BOM Operation set hour_rate = %s, operating_cost = %s * time_in_mins / 60`。即**改机时费率会自动刷新用到该工位的 BOM 成本**。这是 R1 样板一说的"钢价传导"的工时侧对应物。
- **`Workstation Type`** 当前 0 条（已查证）。它是"同型号多台设备"的抽象——建一个类型填一次费率，各台机继承（`_set_data_based_on_workstation_type`，同文件 `:118-128`）。弹簧厂有 20 台同型卷簧机时该用它，本稿三台不同型故不用。
- **`Operation` 的 `autoname` 是 `Prompt`**（已查证），故保存时弹窗输名。它还有 `batch_size` + `create_job_card_based_on_batch_size` 两个字段——这是"一张工序卡覆盖多少产量"的控制，与 R1 场景 D2（工序报工）的批处理问题相关。D2 判 ⚠ 的三个理由里，"批处理工序与单工单 Job Card 不匹配"讲的是**跨工单**合批（一炉混 5 个工单），而 `batch_size` 解决的是**单工单内**分批——两者不是一回事，前者仍无原生形态。
- **`Routing` 也没有必填字段**（已查证）。它就是一张 `BOM Operation` 子表的模板，BOM 选中它时把 `operations` 复制过去。复制后 BOM 里的副本与 Routing 脱钩——**改 Routing 不会回改已有 BOM**。这与 `hour_rate` 会回写形成对比：费率是"当前值"语义，工艺是"当时快照"语义。

## 环节 6　建 BOM：线材 → 弹簧，含工序

这是本稿信息密度最高的一个环节。BOM 是 ERPNext 制造模块的枢纽——它同时承载"用什么料"、"走什么工序"、"成本是多少"三件事。

### 操作

搜「物料清单」（BOM）→ 新建。

**头部：**

| 字段 | 填什么 |
|---|---|
| 物料（Item） | `SPR-C-2.0-16-50` |
| 数量（Quantity / Output Qty） | `1000` |
| 公司（Company） | `华东弹簧` |
| 货币（Currency） | `CNY` |
| 是否启用（Is Active） | 勾（默认已勾） |
| 是否默认（Is Default） | 勾（默认已勾） |

> **数量填 1000 而不是 1**：BOM 的数量是"产出多少个成品时的用料与工时"。工序工时是整批的（卷簧 250 分钟是 5000 支的量），按单支填会得到 0.05 分钟这种不直观的数。取 1000 支为基准单位，工时除以 5 即可。**按 1000 建 BOM 是制造业常规做法**，不是本稿的特殊安排。

**物料明细（Items 子表）：** 加一行：

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `WIRE-65MN-2.0` |
| 数量（Qty） | `8.68` |
| 计量单位（UOM） | `Kg` |
| 单价（Rate） | 自动带出 7.5（来自环节 4 的 Item Price） |

`8.68` = 0.00868 kg/支 × 1000 支。这是**理论用量**，损耗单独走下面的字段。

**基于什么取料价（Rate Of Materials Based On）** 选 `Valuation Rate`（默认值）。此时因为线材还没入库过、没有估值，单价可能取不到——先手填 7.5。环节 11 采购入库后回来重算即可（见下方「成本重算」）。

**工序（Operations）：**

1. 勾上「含工序」（With Operations）—— **不勾这个整张 `operations` 子表不会出现**。
2. 「工艺路线」（Routing）选 `压缩弹簧-标准`，工序自动带进来。
3. 把工时按 1000 支基准改一遍 〔典型值〕：

| 工序 | 工作站 | 工时（分钟/1000支） | 换算依据 |
|---|---|---|---|
| `卷簧` | `卷簧机-01` | `50` | 250 ÷ 5 |
| `去应力回火` | `回火炉-01` | `18` | 90 ÷ 5。**注意这是摊出来的数，回火其实与批量无关**——见下方数据模型段 |
| `磨端` | `磨端机-01` | `36` | 180 ÷ 5 |

**工艺损耗：** 在「% 工艺损耗」（% Process Loss）填 `5`〔典型值〕。

保存。这时**可能报错**：

```
Process Loss Qty cannot be a fraction for UOM 支
```

原因：`process_loss_qty = quantity × process_loss_percentage / 100 = 1000 × 5 / 100 = 50`，正好整数，不报。但若你把数量填成 1 或把损耗填成 3.5，算出小数就会被拒——因为环节 3 给「支」勾了「必须为整数」。

> **这就是环节 3 说的"会咬你一口"。** 遇到时两条路：把损耗百分比调成能整除的值，或回去取消「支」的整数勾选。**推荐前者**——整数约束对弹簧是对的，为迁就一个计算结果放弃它不值。

保存成功后，看头部自动算出的三个成本字段：

| 字段 | 期望值（约） | 怎么来的 |
|---|---|---|
| 原材料成本（Raw Material Cost） | 65.10 | 8.68 kg × 7.5 元 |
| 运营成本（Operating Cost） | 86.67 | (50+18+36) 分钟 ÷ 60 × 50 元/小时 |
| 总成本（Total Cost） | 151.77 | 两者之和 |

**单支成本 ≈ 0.152 元** 〔典型值〕。这个数就是 R1 样板一（A1 询价）里说的"报价时加毛利率"的底数——**报价从"凭经验"变成"查 BOM"，靠的就是这一步。**

**提交**（Submit）这张 BOM。

### 数据模型

- **`BOM` 的必填**（已查证）：`company`、`item`、`quantity`、`items`、`currency`、`conversion_rate`。注意 `items` 在必填里——**BOM 不能没有料**。
- **`BOM Item` 的必填**：`item_code`、`qty`、`uom`、`rate`。**`rate` 必填**是个值得注意的点：BOM 不只是配方，它自带成本快照。
- **`BOM Operation` 的必填**：`operation`、`time_in_mins`。只有两个——工位可空（继承 Operation 的默认值）。
- **`with_operations` 默认为 0**（已查证）。不勾则 BOM 只算料本、`operating_cost` 为 0，且**日后按它下工单不会生成 Job Card**。R1 样板二（D2 工序报工）提到的"若不二开的退路——关掉 Job Card"，技术上就是不勾这个框。
- **成本的三层结构**：

  ```
  raw_material_cost   ← Σ (BOM Item.qty × rate)
  operating_cost      ← Σ (BOM Operation.time_in_mins / 60 × workstation.hour_rate)
  secondary_items_cost← 联产品/废料的抵减（本稿未用）
  total_cost          ← 三者组合
  ```

  这个结构是理解 ERPNext 成本核算的起点：**料与工分开算、各自可追溯**。R1 场景 H2（材料成本与线材利用率）、H3（工序成本与机时费率）判 ✅/🔧 的依据都在这里。

- **`process_loss_percentage` 与 `secondary_items` 是两回事**：

  | 字段 | 语义 | 弹簧厂对应 |
  |---|---|---|
  | `process_loss_percentage` | 投了料但**没产出成品**，料就是损失掉了 | 切头切尾、试机废料、卷废 |
  | `secondary_items` | 投料产出了**副产品**，它有价值、要分摊成本 | 冲压废料（C 类板簧可卖废钢） |

  计算在 `erpnext/manufacturing/doctype/bom/bom.py:1351-1358`（`set_process_loss_qty`）。R1 能力核实表说的"v16 字段名为 `secondary_items`"就是后者。**A 类冷卷圆簧主要用前者**，C 类板簧冲压用后者——这是 DEC-004 说的"L2 工程数据层差异"的一个具体点。

- **回火工时那个 18 分钟是个建模妥协，值得看清楚**。回火是**批处理**：一炉 800 kg 混几个工单，装炉一次、出炉一次，耗时与炉内装了多少几乎无关。而 `BOM Operation.time_in_mins` 的语义是"每 BOM 数量所需的工时"，是**线性**的——填 18 就意味着系统认为做 2000 支要 36 分钟，而实际仍是 90 分钟（同一炉装得下）。

  **这正是 R1 样板二（D2）判 ⚠ 的第二个理由在 BOM 层的体现**："批处理工序与单工单 Job Card 不匹配"。原生模型里没有"固定工时"或"一次作业覆盖多工单"的表达。本稿照线性填是为了跑通，**你要知道这个数是错的**——它在排产和成本上都会偏（批量小时低估工时、批量大时高估）。

- **成本重算**：BOM 保存时取的是当时的料价与费率快照。日后料价变了有两条路——
  - 逐张 BOM 点「更新成本」（Update Cost）按钮；
  - 开「制造设置」（Manufacturing Settings）的 `update_bom_costs_automatically`（当前为 0，已查证），由定时任务批量刷。

  R1 样板一说的"改 Item Price + 开 `update_bom_costs_automatically` 或跑 BOM Update Tool 批量重算"就是这两条。本稿环节 11 入库后建议手工点一次，看着成本变化发生比读文档清楚。

- **BOM 是可提交文档**（有 docstatus）。提交后不可改，要改得取消 + 修订（Amend）或新建一版。这是 R1 场景 B1（图纸版本管理）判 ⚠ 的部分背景——BOM 自己有版本控制，但**图纸文件**没有与 BOM 版本绑定的机制。该项待验（见 Stage 概况风险表：B1 应查 `frappe/core/doctype/{file,version}`）。

### 数据模型

- **`Purchase Order` 的必填**（已查证）：`naming_series`、`supplier`、`transaction_date`、`company`、`currency`、`conversion_rate`、`items`、`status`。
- **`conversion_rate` 必填**是 v16 全新安装的一个坑源：它是"单据货币 → 公司本币"的汇率。同币种时应为 1，但**全局币种若与公司币种不一致就校验失败**——这正是 `docker/README.md` 记的第四处初始化缺口（"全局 `currency` 仍是镜像默认的 INR"）。本站点已修正为 CNY，故无感。
- **`status` 必填但你不填**——它由工作流自动维护（`Draft` → `To Receive and Bill` → `Completed`）。ERPNext 大量单据如此：`status` 是字段而非计算属性，由 `update_status` 之类的方法写。**这个设计意味着状态可能与实际不一致**（漏跑更新逻辑时），所以排查"单据状态不对"要去看写它的那段代码，不是看数据本身。
- **PO 不产生任何会计分录与库存变动**。它是承诺，不是事实。ERPNext 的单据链普遍如此分层：订单（承诺）→ 收货/发货（库存事实）→ 发票（财务事实）→ 付款（资金事实）。四者可以各自独立发生、也可以合并（发票勾 `update_stock` 就同时动库存）。**理解这个四层分离是理解整个 ERPNext 单据体系的钥匙。**
- **`Purchase Order Item` 有 `warehouse` 字段**：采购时就指定料入哪个仓。它会带到 Purchase Receipt。

## 环节 9　采购收货（Purchase Receipt）：线材入库

### 操作

**不要新建空白单据**。打开刚提交的 PO → 右上「创建」（Create）→「采购收货」（Purchase Receipt）。物料、数量、仓库、单价全部带过来。

确认这两处：

| 字段 | 值 |
|---|---|
| 接收数量（Received Qty） | 100 |
| 仓库（Warehouse） | `Stores - HDS` |

**提交**（Submit）。

> **为什么从 PO 创建而不是新建**：从上游单据创建时 ERPNext 会写入 `purchase_order` 反向引用，PO 的 `status` 与 `received_qty` 才会更新。手工新建的收货单与 PO 无关联，PO 会永远停在「待接收」状态。**这条对整个单据链都适用**——永远从上游单据的「创建」按钮往下走。

### 数据模型

- **这是本稿第一笔真正改变库存的动作**。提交后同时产生两类记录：

  | 记录 | DocType | 作用 |
  |---|---|---|
  | 库存分类账 | `Stock Ledger Entry` | 数量与估值的流水账 |
  | 会计分类账 | `GL Entry` | 借贷分录 |

  两者由同一次提交生成、金额必须相等——这个"库存账与会计账双写"是 ERPNext 永续盘存的核心机制，也是环节 13 要细看的东西。

- **`Purchase Receipt` 的必填**（已查证）多了几个：`posting_date`、`posting_time`、`base_net_total`。有 posting 时间是因为**库存是时序的**——估值按时间顺序累计，插一笔历史单据会触发其后所有单据的重算（`repost_item_valuation`）。
- **`Stock Ledger Entry` 是不可改的流水**。它记 `actual_qty`（本次变动量）、`qty_after_transaction`（变动后余额）、`valuation_rate`、`stock_value_difference`。**库存报表全部从它算出来**，没有"当前库存"这张表——余额是流水的累计结果。这个设计使任何时点的历史库存都可回溯。
- **估值方法**在 Item 上（`valuation_method`，默认取 Stock Settings 的值，通常是 `FIFO`）。FIFO 下 `Stock Ledger Entry` 带一个 `stock_queue` 字段，存着"当前库存由哪几批、各多少、各什么价"构成的队列。R1 场景 F1（线材仓按炉号先进先出）判 ✅ 就是因为这套机制原生完整。

## 环节 10　采购发票（Purchase Invoice）

### 操作

打开刚提交的采购收货单 → 「创建」→「采购发票」（Purchase Invoice）。

确认「更新库存」（Update Stock）**没有勾**——库存已由收货单动过，这里再动就重复了。

**提交**。

### 数据模型

- **`Purchase Invoice` 的必填**（已查证）：`naming_series`、`supplier`、`posting_date`、`items`、`credit_to`。
- **`credit_to` 就是应付账款科目**（`Creditors - HDS`，来自公司的 `default_payable_account`）。它必填，因为发票的本质是"确认一笔欠款"。
- **这一步的分录**（环节 13 会完整看）把"已收货未开票"这个暂记科目转成正式应付：

  ```
  借  Stock Received But Not Billed - HDS   750
  贷  Creditors - HDS                       750
  ```

  `Stock Received But Not Billed` 这个科目的存在就是为了处理"货到了票没到"这个时间差。R1 场景 G2（外协发出收回的料账）、H6（存货核算与月结）都建立在这类暂记科目机制上。

## ★ 环节 13　看懂库存动作如何变成会计分录

**这是本稿第一个 ★ 节点，也是最该慢下来的地方。** 前面 12 个环节你只是在照着点；这一节要你看懂 ERPNext 的底层机制——**为什么它是 ERP 而不是进销存软件**。

### 操作

**第一步：看单张单据的分录。** 打开环节 9 的采购收货单 → 右上「菜单」（Menu）→「会计分类账」（Accounting Ledger）。

你会看到两行：

```
借  Stock In Hand - HDS                      750
贷  Stock Received But Not Billed - HDS      750
```

**第二步：看完整的科目流转。** 搜「总账」（General Ledger）报表 → 公司 `华东弹簧`、日期范围覆盖今天 → 不筛科目。按凭证分组看，应该是三组：

| 来源单据 | 借 | 贷 | 金额 |
|---|---|---|---|
| 采购收货 | `Stock In Hand` | `Stock Received But Not Billed` | 750 |
| 采购发票 | `Stock Received But Not Billed` | `Creditors` | 750 |
| 付款 | `Creditors` | `Cash` | 750 |

**第三步：把链条读出来。** 三笔分录首尾相接：

```
Stock In Hand  ←  Stock Received But Not Billed  ←  Creditors  ←  Cash
   (资产)              (暂记负债)                    (负债)      (资产)
```

钱从现金出去，经应付、经暂记科目，最终变成库存资产。**每一步都有一张业务单据对应，每张单据只管自己那一段。**

### 数据模型

- **谁生成这些分录**：`erpnext/controllers/stock_controller.py` 的 `make_gl_entries`。它在单据 `on_submit` 时被调用，读 `Stock Ledger Entry` 的 `stock_value_difference`，按"库存科目 vs 对方科目"生成成对的 `GL Entry`。

  关键点：**分录金额不是从单据金额算的，是从库存估值差额算的**。这保证了库存账与会计账天然一致——它们读的是同一个数。

- **`stock_entry.py:2375-2376` 的写法值得看一眼**：

  ```python
  def get_gl_entries(self, inventory_account_map):
      gl_entries = super().get_gl_entries(inventory_account_map)
  ```

  `Stock Entry` 继承 `StockController` 的通用实现再扩展。这个继承结构意味着**所有动库存的单据共用同一套分录生成逻辑**（采购收货、发货单、库存调拨、生产入库都是 `StockController` 的子类）。日后要改"库存分录怎么记"，改点在这一处，不是每个单据各改。

- **`inventory_account_map` 是仓库到科目的映射**。它先取 `Warehouse.account`，空则退到公司的 `default_inventory_account`。这就是环节 2 说的"给各仓库分别指定账户可让报表分开显示"的实现位置。

- **暂记科目的必要性**。若没有 `Stock Received But Not Billed`，收货时就得直接记应付——但那时金额未必确定（发票可能有运费、税、折扣）。暂记科目把"实物到了"与"金额定了"解耦。**这个模式在 ERPNext 里反复出现**，理解一次就能认出其余：`Stock Received But Not Billed`（采购侧）、`Unbilled Revenue`（销售侧）、`Work In Progress`（生产侧，环节 20 会见到）都是同一个思路。

### 这一节该带走什么

三件事，后面全靠它们：

1. **库存动作自动产生会计分录，两账同源**。这是永续盘存（`enable_perpetual_inventory`）的含义。手工进销存软件没有这一层，所以月底要靠人工做"存货结转"。
2. **单据链四层分离**（订单 → 实物 → 财务 → 资金），每层可独立发生，也可合并。
3. **分录由控制器统一生成**，改法在 `StockController` 而非各单据。

**若这一节的分录你看不懂"为什么这么记"**——那是会计原理层，DEC-010 明确不含在本稿内（LG-010 记着这个缺口）。判断标准：你**能读出**"这笔单据产生了哪两行分录、金额从哪来"就算过关；**为什么借这个贷那个**可以先放着。真卡住就回头提，另补材料，别硬扛。

## 环节 16　生产计划（Production Plan）

### 操作

搜「生产计划」（Production Plan）→ 新建。

| 字段 | 填什么 |
|---|---|
| 公司 | `华东弹簧` |
| 过账日期（Posting Date） | 今天 |
| 获取物料自（Get Items From） | `Sales Order` |

### 数据模型

- **`Production Plan` 的必填**（已查证）：`naming_series`、`company`、`posting_date`、`po_items`。
- **它是个批量调度器，不是排产引擎**。它做三件事：汇总需求（从 SO 或手工）、按 BOM 展开物料需求、批量生成工单与采购申请。**它不做工序级排程**——那是 Work Order 的事（环节 17）。
- **物料需求计划（MRP）在这里**：`Production Plan` 有 `mr_items` 子表，能按 BOM 展开算出"要做 5000 支需要 43.40 kg 线材，现有 100 kg，不用买"。这是 R1 场景 C2（工单下达与齐套检查）判 ✅ 的依据——"下单才发现线材没到"在系统里会被提前拦住。
- **R1 提到的 `Master Production Schedule` / `Sales Forecast` 也在 v16**（能力核实表已验证存在）。它们是 Production Plan 之上的更长周期计划层，本稿不用——最小闭环从 SO 直接到 Production Plan 就够。L5 教材会展开这一层。
- **这一层的原生缺口**：R1 场景 C1（需求汇总与主生产计划）判 ✅、C3（机台排产与换型合并）判 ⚠。差别在于 Production Plan 能汇总需求、但**不能按"同线径合并换型"重排**——它按单生成工单，不做跨单优化。这是 C3/C4 二开的起点。

## 环节 17　工单（Work Order）

### 操作

打开环节 16 生成的工单。检查这几个字段：

| 字段 | 应该是 | 说明 |
|---|---|---|
| 生产物料（Production Item） | `SPR-C-2.0-16-50` | |
| 数量（Qty） | 5000 | |
| BOM 号（BOM No） | 环节 6 那张 | |
| 计划开始日期（Planned Start Date） | 今天或明天 | 必填 |
| 在制品仓库（Work-in-Progress Warehouse） | `Work In Progress - HDS` | 空则手填 |
| 目标仓库（Target Warehouse） | `Finished Goods - HDS` | 空则手填 |

**「制造设置」里三个默认仓库当前都是空的**（已查证 `default_wip_warehouse` / `default_fg_warehouse` / `default_scrap_warehouse` 均为 None），所以工单上这两个仓库字段可能没自动填。**建议顺手去设一下**：搜「制造设置」（Manufacturing Settings）→ 填三个默认仓库（WIP / 成品 / 废料）→ 保存。之后所有工单自动带。

`required_items` 子表应已按 BOM 展开：`WIRE-65MN-2.0` 需要 43.40 kg（8.68 × 5）。

`operations` 子表应有三道工序，各带工时与工位。

**提交**。

提交后看 `operations` 子表——每道工序被填上了预计开始与结束时间。这是 ERPNext 排产的全部内容，环节 18 会细看。

### 数据模型

- **`Work Order` 的必填**（已查证）：`company`、`naming_series`、`production_item`、`bom_no`、`qty`、`planned_start_date`、`status`。
- **几个关键开关**（已查证默认值）：

  | 字段 | 默认 | 含义 |
  |---|---|---|
  | `use_multi_level_bom` | 1 | 多层 BOM 是否逐层展开。弹簧 BOM 单层，无影响 |
  | `skip_transfer` | 0 | 是否跳过"领料到 WIP 仓"这一步。勾上则直接从原料仓扣料 |
  | `from_wip_warehouse` | 0 | 勾 `skip_transfer` 时才出现：是否从 WIP 仓反冲 |
  | `transfer_material_against` | — | 领料是按整张工单还是按工序分次领 |

  **`skip_transfer` 值得注意**：勾上能少一张单据，但**就看不到 WIP 库存了**。R1 场景 D3（在制品盘点，判 🔧）的痛点"WIP 是黑洞"——若厂里为省事勾了 `skip_transfer`，那个黑洞就是自己造的。本稿不勾，为的是环节 20 能看到 WIP 会计。

- **排产算法在 `work_order.py:1262-1287`**（`set_operation_start_end_time`，R1 能力核实表已验证）。它做的事：从 `planned_start_date` 起，按 `operations` 顺序累加各工序工时，前后工序之间加 `mins_between_operations`（制造设置里的全局值，**当前为 0**，已查证）。

  **这就是全部**。没有优化、没有资源冲突消解、没有换型时间。R1 样板三（C4 插单）说的"朴素顺排"就是这 26 行代码。

- **`capacity_planning_for_days` 默认 30**（已查证）。计划开始日期超出这个窗口会抛 `CapacityError`，要求你改设置而非给出可行方案（`work_order.py:1236-1258`）。弹簧厂接年度框架订单（R1 场景 A5）时会撞上这个。
- **没有 `priority` 字段**（R1 已查证：manufacturing / selling / stock 三模块内仅 Putaway Rule 有）。这是 C4 判 ⚠ 的硬事实，也是 R1 定的"整个项目优先级最高的二开项"的起点——二开内容①就是给 Work Order / Job Card 加 `priority`（走 Custom Field + fixtures，不改源码，符合开发守则）。

## 环节 18　领料到 WIP（Stock Entry）

### 操作

打开工单 → 「创建」→「领料」（Material Transfer for Manufacture）。

系统生成一张 Stock Entry，类型 `Material Transfer for Manufacture`，把 43.40 kg 线材从 `Stores - HDS` 移到 `Work In Progress - HDS`。

**提交**。

回到工单，看「已为生产转移的物料」（Material Transferred for Manufacturing）变成 5000。

### 数据模型

- **`Stock Entry` 的必填**（已查证）：`company`、`naming_series`、`stock_entry_type`、`items`。
- **`Stock Entry Type` 是一张独立 DocType**，站点有 13 条（已查证），每条带一个 `purpose`。本稿用到三个：

  | 类型 | purpose | 用在哪 |
  |---|---|---|
  | `Material Transfer for Manufacture` | 同名 | 环节 18 领料 |
  | `Manufacture` | 同名 | 环节 19 完工入库 |
  | `Material Issue` | 同名 | 本稿未用（无工单的直接出库） |

  **`purpose` 决定行为，`stock_entry_type` 只是给它起的名字**。这个两层设计允许你建自定义类型（如"试制领料"）复用既有 purpose 的逻辑，同时在报表里分得开。R1 场景 B5（新品试制打样，判 🔧）的"打样料从生产料里拿、成本混在一起"就靠这个解——建一个专用 Stock Entry Type。

- **这一步的分录**：仓库间调拨，两个仓库若都用公司默认库存科目，则**借贷同科目、金额相等**，净效果为零：

  ```
  借  Stock In Hand - HDS   325.5  （WIP 仓）
  贷  Stock In Hand - HDS   325.5  （原料仓）
  ```

  325.5 = 43.40 kg × 7.5 元。

  **看起来白记一笔，但它不是白记的**：`Stock Ledger Entry` 层面两个仓库的余额确实变了。这就是环节 2 说的"给各仓库分别指定账户"的价值——分了账户，这笔调拨在财务报表上才看得见（原料存货减、在制存货增）。**弹簧厂要不要分，取决于财务是否关心 WIP 金额。** R1 场景 D3 判 🔧（需流程改造）而非 ✅，部分原因就在这里：机制有，但要配置对。

**逐张处理**（按工艺顺序：卷簧 → 回火 → 磨端）：

### 数据模型

- **`Job Card` 的必填**（已查证）：`work_order`、`company`、`naming_series`、`operation`、`workstation`。注意 `work_order` 必填——**Job Card 不能脱离工单存在**。这是 R1 样板二（D2）判 ⚠ 第二个理由的根源：一炉混 5 个工单要开 5 张 Job Card，因为每张只能挂一个工单。

- **重叠校验在 `job_card.py:364-435`**（`get_overlap_for` / `has_overlap`，R1 已查证）。它校验的是**工位**时间不重叠，受 `Workstation.production_capacity` 控制（默认 1，即一台机同时只能跑一张工序卡）。

  **R1 样板二说的"一人多机无原生形态"在这里可以确认**：`production_capacity` 放宽的是"这台机同时跑几个工单"，而"这个人同时看几台机"——`Job Card` 有 `employee` 字段，但**没有任何机制校验或支持一人跨多机并发**。一人 4 台机就是 4 张 Job Card 各自计时。
- **排程在 `job_card.py:517-557`**（`schedule_time_logs`）：找工位空档往后塞。**是"避免撞车"不是"优化排程"**——这是 R1 对 C4 判定的核心事实之一。
- **`Job Card` 有 96 个字段**（R1 样板二的说法）。你现在打开它就能直观确认这一点——R1 说的"50 岁卷簧工找不到完成数量按钮"不是夸张。这是 D2 二开内容①（车间报工页）的动因。
- **`process_loss_qty` 字段在 Job Card 上**，所以工序级废品是原生可记的。R1 场景 D5（废品与返工）判 🔧 而非 ⚠ 就是因为字段齐全，缺的是"工人愿不愿意填"——流程与培训问题。

## ★ 环节 20　完工入库：看懂 WIP 会计与成本回算

**第二个 ★ 节点。** 这一节要看的是：**投进去的料钱和工钱，怎么变成成品的库存价值。**

### 操作

**第一步：完工入库。** 打开工单 → 「创建」→「完工入库」（Manufacture）。

系统生成一张 Stock Entry，类型 `Manufacture`。检查：

| 项 | 值 |
|---|---|
| 源仓（items 里线材行的 Source Warehouse） | `Work In Progress - HDS` |
| 目标仓（成品行的 Target Warehouse） | `Finished Goods - HDS` |
| 成品数量 | 4850（按环节 19 的实际完工数改，不是 5000） |

**提交**。

**第二步：看成品的单位成本。** 提交后在这张 Stock Entry 的成品行看「基本费率」（Basic Rate）。它应该约等于：

```
(线材成本 + 工序成本) ÷ 完工数量
= (43.40 kg × 7.5 + 104 分钟 × 5 批 ÷ 60 × 50) ÷ 4850
= (325.5 + 433.3) ÷ 4850
≈ 0.156 元/支
```

〔典型值。与环节 6 BOM 算的 0.152 略有差异——因为实际完工 4850 支而非 5000，同样的投入摊在更少的成品上。**这个差异就是废品的成本影响，它自动体现了。**〕

**第三步：看分录。** 该 Stock Entry → 「菜单」→「会计分类账」：

```
借  Stock In Hand - HDS（成品仓）    758.8    ← 4850 × 0.156
贷  Stock In Hand - HDS（WIP 仓）    325.5    ← 线材投入
贷  Cost of Goods Sold / 制造费用     433.3    ← 工序成本（转入库存价值）
```

> 具体科目名取决于公司的 `default_expense_account` 与工序成本的处理方式。**要看的重点是第三行**：工序成本（人工、电费、折旧）从费用科目**转进了库存资产**。

**第四步：回到工单看回算。** 工单上「已生产数量」现在是 4850。工单页面下方有成本汇总，显示实际料本与实际工本。

**第五步：跑 BOM 差异报表。** 搜「BOM 差异报表」（BOM Variance Report）→ 选该工单。它对比"BOM 说该用多少"与"实际用了多少"。

### 数据模型

- **`Manufacture` 类型的 Stock Entry 做三件事**：扣 WIP 仓的原料、加成品仓的成品、把工序成本计入成品估值。第三件是它与普通调拨的本质区别。
- **成品单价怎么算的**：`stock_entry.py` 里 `Manufacture` purpose 会调 `get_bom_scrap_material` 与 `set_basic_rate_for_finished_goods`——成品的 `basic_rate` = (原料总成本 + `additional_costs`) ÷ 成品数量。工序成本作为 `additional_costs` 注入。
- **`backflush_raw_materials_based_on` 默认是 `BOM`**（已查证）。含义：完工入库时按 BOM 理论用量反冲原料，**不是按实际领了多少**。

  **这是一个很重要的行为**。它意味着：若你领了 43.40 kg 但实际只用了 42 kg，系统仍按 BOM 扣 43.40 kg 的比例 —— 差额留在 WIP 仓，成为"WIP 有余料"。另一个选项是 `Material Transferred for Manufacture`（按实际领用量反冲）。

  R1 场景 H2（材料成本与线材利用率，判 ✅）的"超耗说不清"——原生解法就是切到 `Material Transferred for Manufacture`、让实际领用与理论用量的差异显式暴露。**这是一个配置决定，不是二开**，但选错了整条成本链的意义就变了。值得在 L8 教材写透。

- **WIP 会计的完整语义**：ERPNext 的 WIP 不是一个独立的会计科目体系，而是**"在某个仓库里的库存"**。所以：
  - WIP 金额 = WIP 仓的库存估值；
  - 想在资产负债表上单独看 WIP，就给 WIP 仓指定一个专门的库存科目（环节 2 提到的 `Warehouse.account`）；
  - 不指定则 WIP 与原料、成品混在 `Stock In Hand` 一个科目里。

  **这解释了 R1 场景 D3（在制品盘点）为什么判 🔧**：机制完整（WIP 仓 + 库存流水 + 估值），但要得到"财务能看的 WIP 金额"需要配置仓库科目 + 车间真的走领料/完工单据。两件事都不是技术缺口，是流程与配置。

- **`add_corrective_operation_cost_in_finished_good_valuation` 默认 0**（已查证）：返工工序的成本默认**不**计入成品估值。弹簧厂返工（R1 场景 D5）频繁时这个开关影响成本准确性。
- **工序成本能进库存估值的前提是 BOM 勾了 `with_operations`**。环节 6 勾了，所以这里能看到 433.3 这一行。若当初没勾（即 R1 样板二说的"关掉 Job Card"那条退路），成品估值里**只有料本没有工本**——单支成本会显示 0.067 元而非 0.156，虚低 57%。

  **这是"关掉 Job Card"这条退路的真实代价，比 R1 说的"丢掉工序级数据"更严重**：它同时让成本失真。R1 说"把效率提升砍掉一半"，从成本角度看砍掉的更多。此事已记入本轮回执，建议 L5/L8 教材明确写出。

### 这一节该带走什么

1. **WIP 是"仓库里的库存"，不是独立会计体系**。想让它在报表上可见，配置仓库科目。
2. **工序成本经 `Manufacture` 类型的 Stock Entry 转入库存价值**，前提是 BOM 勾了 `with_operations`。
3. **`backflush_raw_materials_based_on` 决定超耗查得出还是查不出**。默认值（按 BOM）会把超耗藏起来。

## ★ 环节 23　看懂成本如何从 BOM 流到利润表

**第三个 ★ 节点，也是整条闭环的收口。** 这一节把前面 22 个环节串成一条线。

### 操作

**第一步：跑利润表。** 搜「利润表」（Profit and Loss Statement）→ 公司 `华东弹簧`、本会计年度。

应该看到：

| 项 | 金额（约） |
|---|---|
| 收入（Income）→ `Sales` | 1067 |
| 费用（Expenses）→ `Cost of Goods Sold` | 758.8 |
| **毛利** | **307.8** |

毛利率 ≈ 28.8%。

> **这个 28.8% 比报价时想的"45% 毛利"低很多，差距由两件事构成，要分开看。**
>
> **第一件是算术口径**。报价时做的是"成本 0.152 **加成** 45% 得 0.22"，而利润表给的是**毛利率**。两者分母不同：
>
> | 口径 | 算法 | 值 |
> |---|---|---|
> | 加成率（报价用） | (售价 − 成本) ÷ **成本** = (0.22 − 0.152) ÷ 0.152 | 45% |
> | 毛利率（报表用） | (售价 − 成本) ÷ **售价** = (0.22 − 0.152) ÷ 0.22 | 31% |
>
> 所以"加成 45%"本来就只对应 31% 毛利率，**这 14 个点不是亏掉的，是口径差**。
>
> **第二件才是真的成本上升**：实际单支成本 0.156 而非 BOM 的 0.152，因为 5000 支的投入只做出 4850 支（3% 废品）。按实际成本算毛利率 = (0.22 − 0.156) ÷ 0.22 = **28.8%**，即废品吃掉 2.2 个点。
>
> **这个算术本身就是一课**：报价用加成、看报表看毛利，中小厂"报价以为赚 45%、月底发现 28%"的困惑，绝大部分来自这个口径混淆，只有小部分是真实的成本恶化。**系统的价值在于把这两部分分开**——口径差是算法问题（学一次就会），废品与超耗才是要管的（R1 场景 H1「标准成本 vs 实际成本差异」判 ✅ 的实质）。

**第二步：跑库存余额，确认账实相符。** 搜「库存余额」（Stock Balance）：

| 物料 | 仓库 | 余额 |
|---|---|---|
| `WIRE-65MN-2.0` | `Stores - HDS` | 56.60 Kg（100 − 43.40） |
| `WIRE-65MN-2.0` | `Work In Progress - HDS` | 0 |
| `SPR-C-2.0-16-50` | `Finished Goods - HDS` | 0（4850 全发走了） |

**第三步：跑「库存与账务价值对比」**（Stock and Account Value Comparison）。差额应为 0——库存账与会计账仍然一致，走完整条链后也没有裂开。

**第四步：把成本链从头读一遍。** 这是本环节真正的功课：

```
线材采购价 7.5 元/kg              ← 环节 4 的 Item Price
   ↓ 入库估值
Stock In Hand 750 元              ← 环节 9，FIFO 队列里 100 kg @ 7.5
   ↓ 领料 43.40 kg
WIP 325.5 元                      ← 环节 18
   ↓ 加工序成本 433.3 元（104 分钟/1000支 × 5 × 50 元/小时）
成品估值 758.8 元 / 4850 支        ← 环节 20，0.156 元/支
   ↓ 发货
Cost of Goods Sold 758.8 元       ← 环节 21
   ↓ 对应收入 1067 元（4850 × 0.22）
毛利 307.8 元                      ← 环节 23
```

**每一个数都可以往上追一层，一直追到"钢价 7.5 元"和"机时费率 50 元"这两个源头输入。** 这就是 ERP 与"记账软件"的根本差别——不是账做得更漂亮，而是**每个数字都有来处**。

### 数据模型

- **成本流转的三个转折点**，各由不同机制实现：

  | 转折 | 谁做的 | 代码位置 |
  |---|---|---|
  | 采购价 → 库存估值 | `StockController.make_gl_entries` + FIFO 队列 | `erpnext/controllers/stock_controller.py` |
  | 料+工 → 成品估值 | `Manufacture` 类型 Stock Entry 的 `additional_costs` | `erpnext/stock/doctype/stock_entry/stock_entry.py` |
  | 成品估值 → 销货成本 | Delivery Note 的 GL Entry | 同 `StockController` |

  **三处都在 `StockController` 这条继承链上**，这是环节 13 说的"改法在一处"的又一次体现。

- **利润表是从 `GL Entry` 算出来的，不是从单据算的**。`erpnext/accounts/report/profit_and_loss_statement/` 按科目类型（Income / Expense）汇总 GL Entry。这意味着**任何绕过 GL Entry 的操作都不会出现在利润表上**——手工改库存数量、直接改数据库都属于此类。这是排查"报表数字不对"的第一原则：先看 GL Entry 有没有。
- **`gross_profit` 报表是另一条路**：`erpnext/accounts/report/gross_profit/` 按**单据**算毛利（每张发票的售价 − 该批货的估值成本），能下钻到单个商品、单个客户。利润表给总额，gross_profit 给结构。R1 场景 H1 的"不知道哪个品亏"用的是后者。
- **月结在哪**：本稿没做月结。ERPNext 的月结是 `Period Closing Voucher`（结转损益到未分配利润）+ 会计期间锁定。R1 场景 H6（存货核算与月结）判 🔧——机制在，痛点是"月结要两周"这个流程问题，靠单据及时录入解决，不是二开。

### 这一节该带走什么

1. **每个数字都有来处，可以逐层追到源头输入**。这是 ERP 的核心价值，也是你日后判断"某个数不对"该往哪查的方法。
2. **利润表从 GL Entry 算，不从单据算**。绕过 GL Entry 的操作在报表上不存在。
3. **加成率 ≠ 毛利率**，报价与报表用的是两套算法。这个混淆是中小厂"以为赚了其实没赚"的一半原因。
