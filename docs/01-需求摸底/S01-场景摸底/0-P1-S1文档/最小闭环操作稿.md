## 怎么用本稿

**两层写法**（DEC-010）：每个环节分「操作」与「数据模型」两段。操作段是照着点的路径；数据模型段讲这一步在数据库里实际发生了什么——DocType 叫什么、关键字段在哪个文件、校验逻辑在哪一行。第二段是你判断"日后二开从哪切入"的抓手，**别跳过**。

**三个 ★ 节点**（环节 13 / 20 / 23）是最该停下来看的地方。ERPNext 的核心机制（库存动作如何变成会计分录、WIP 会计、成本如何从 BOM 流到损益表）全在那里。按 DEC-010，本稿**不含会计原理层**——只讲"这笔分录是什么、由哪段代码生成的"，不讲"借贷为什么这么记"。若你在 ★ 处看不懂分录本身，那是 LG-010 记着的缺口，回头另补一份会计原理材料，别在这里硬扛。

**关于本稿里的数值**（Stage 概况的恒定约束）：凡工时、损耗率、线材规格、批量这类数字，一律只具「公开资料典型值」效力，**不具本客户实际值效力**。它们的作用是让你有个能跑通的具体例子，不是业务基准。实地考察时逐项校准。本稿对此类数值一律标注 `〔典型值〕`。

**产品主线**（DEC-004）：冷卷圆簧（压缩弹簧）。B 类异形线成型与 C 类板簧冲压的差异不在本稿，在 L1/L2 教材的差异节。

**本稿标记的三类框**（v2 起）：

| 标记 | 含义 |
|---|---|
| `⚠ 上游缺陷` | R3 实操撞上的 ERPNext 自身问题。**照稿子走会遇到，已给绕过办法**，并注明登记为哪条延迟需求。不是你操作错了 |
| `〔典型值〕` | 行业公开资料的典型值，**不具本客户实际值效力**（Stage 概况恒定约束） |
| `R3 实测` | 该数字/现象在 R3 闭环实操中被实际验证过，非推断 |

**规模档位**（DEC-005）：B 档小型厂（50-150 人，多机台多班）〔典型值〕。

**环境**：`erx.localhost`，浏览器开 http://localhost:8000 或 http://erx.localhost:8000，登录 `Administrator` / `admin`。界面语言已是中文，故本稿的菜单名给中文，**并在括号里附英文原名**——报错信息和源码里只有英文，中英对照能省掉大量翻译猜测。

> **本稿的中文名一律是 v16 实测译名**（v2 整批校准）。v1 的译名有约一半与实际不符（13 个科目仓库名 + 15 处菜单名），因为 ERPNext 按界面语言生成中文科目表、而 v16 的 zh 翻译与英文原名对应关系不直观（`Fiscal Year`→「财年」、`Workstation`→「工站」、`Item` 甚至未翻译）。这批不符已在 R3 实操中逐条查出并在此改正；**译名本身的改造是另一件事**，见延迟需求 `SH-P1S1004`。

**搜不到某个菜单时怎么办**（R3 闭合 LG-013，机制已查证）：

搜索框对**英文原名**一律命中——`search_utils.js:595-602` 的 `fuzzy_search` 先按译名匹配，**得分为 0 且界面非英文时自动回退用英文原名再匹配一次**。故"搜不到就搜英文"是普遍可行的办法。

**但有一个坑**：`awesome_bar.js:176-179`——输入**含空格**时，空格后的词被当作**类型过滤词**（只认 `List` / `Tree` / `Report` / `New`）。故搜 `Fiscal Year` 返回空不是因为搜不到该 DocType，而是 `Year` 不匹配任何类型。**办法：搜不带空格的片段**（搜 `Fiscal` 即出），或直接敲地址 `/app/fiscal-year`。R3 实操中用户正是被这一条卡住过。

## 环节 0　清场：把站点变成干净的弹簧厂环境

**为什么有这一节**：DEC-011 定了"不用 ERX Demo 演示数据"，DEC-013 定了形态为"现站点内新建公司"。而 Item / Customer / Supplier 三类**没有 `company` 字段**（已查证），跨公司共享——不清掉 demo 数据，你在选料号时会看到 10 个 `SKU001`-`SKU010`、选客户时看到 3 个 demo 客户混在列表里。这正是 NV-007 否决"在演示数据上学"的理由。

### 操作

**第一步：清演示数据。** 在宿主机（Git Bash）跑：

```bash
docker/seed-demo.sh --clear
```

**先确认 `docker/start.sh` 正在另一个终端里跑着。** 这条清除走的是 Transaction Deletion Record，它把删除排进**后台队列**（`erpnext/setup/demo.py:202-211` 的 `start_deletion_tasks()`），队列 worker 不在跑就只是排了个队、什么也没删——表现为"脚本说成功但数据还在"（LG-011）。

**第二步：确认真的清干净了。** 不看脚本输出，查数据库：

```bash
export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'
docker compose -f docker/compose.yaml exec -T -w /workspace/frappe-bench/sites frappe \
  ../env/bin/python -c "
import frappe
frappe.init(site='erx.localhost'); frappe.connect()
for dt in ('Company','Item','Customer','Supplier','Sales Order','Purchase Order'):
    print(dt, frappe.db.count(dt))
"
```

> **Windows 上 `MSYS_NO_PATHCONV=1` 不可省**：Git Bash（MSYS）会把 `-w /workspace/...` 改写成 Windows 路径，报 `Cwd must be an absolute path`。这条坑在 `docker/README.md`「Windows 上的几处适配」里也记着。

期望结果：`Item` / `Customer` / `Supplier` / `Sales Order` / `Purchase Order` 全为 0，`Company` 剩 1（`ERX Demo`）。若计数没动，说明队列没跑——去看 `docker/start.sh` 那个终端有没有报错，起来后重跑第一步。

> **R3 实测确认**：`start.sh` 在跑时一次清到位，且 `Transaction Deletion Record` 查询返回 **0 条**（删除任务已执行完并自行清理）。故上面那条判据成立——**查这张表有没有残留即可判断队列跑完没有**。实测清场后的保留项：UOM 239、Price List 2、Item Group 6、Fiscal Year 1、Warehouse Type 1、Currency 149（CNY 已启用）、`Workstation Operating Component` 四条。

**第三步：删掉 `ERX Demo` 主公司。** 界面上搜「公司」（Company）列表 → 打开 `ERX Demo` → 右上 `...` → 删除（Delete）。

> **R3 实测：能直接删，不必走退路。** 未加 `force`、无 `LinkExistsError`，级联清掉 95 科目 + 5 仓库 + 2 成本中心。前提是**它名下没有任何单据**（清场第一步已把单据清完）。
>
> 删前可先查它挂着什么：`Account` 95、`Warehouse` 5、`Cost Center` 2、`Mode of Payment Account` 1、单据 0。
>
> 万一真报 `LinkExistsError`（说明有单据没清掉），**不要硬删**——把名字改为 `ZZ-废弃-ERX Demo` 让它排到列表末尾，继续往下走。公司可以共存，多一家废弃公司不影响本稿任何环节。但 R3 实操中**这条退路没用上**。

### 数据模型

- **清除逻辑**在 `erpnext/setup/demo.py`：`clear_demo_data()`（第 59-77 行）依次做三件事——建 Transaction Deletion Record 删单据、`clear_masters()` 删主数据、`delete_company()` 删 `(Demo)` 副本公司。
- **删哪些主数据由 hooks 声明**：`erpnext/hooks.py:92-99` 的 `demo_master_doctypes`，六类：`item_group` / `item` / `customer_group` / `supplier_group` / `customer` / `supplier`。`clear_masters()` 按该列表**倒序**删（第 213-219 行）——倒序是因为 item 依赖 item_group，必须先删依赖方。
- **不会被清掉的**：UOM（239 条）、Price List（`Standard Selling` / `Standard Buying`）、Warehouse Type（`Transit`）、全局币种 CNY。这四样正是 v16 全新安装的初始化缺口（见 `docker/README.md`「v16 全新安装需要的额外初始化」），由 `seed-demo.sh` 补上、`--clear` 不动。**这是选 DEC-013 而非新建站点的主要收益**：新站点得把这五处坑重踩一遍。
- **`Transaction Deletion Record`** 是 ERPNext 的通用"清空某公司所有交易"工具，不只服务 demo。它按 DocType 分批删并记录进度，故是异步的。日后你想把弹簧厂数据清空重来，用的也是它（或直接 `docker/restore.sh` 回滚到备份）。

### 做完这一节，先备份

```bash
docker/backup.sh
```

这份备份是"干净空站点"的存档。后面任何环节搞坏了，`docker/restore.sh` 回到这里重来，比手工删数据快得多。DEC-011 说的"随时重置重来"就靠它。

## 环节 1　建公司与科目表

### 操作

搜「公司」（Company）→ 新建。

**⚠ 填写有先后顺序，别按一张表一次填完**（R3 实操第一个卡点）。永续盘存那个勾**保存前找不到**，见下方第三步的说明。

**第一步：主表单顶部四项。**

| 字段 | 填什么 | 说明 |
|---|---|---|
| 公司名称（Company Name） | `华东弹簧` | 这个值同时成为文档主键（`autoname` 为 `field:company_name`） |
| 缩写（Abbr） | `HDS` | **会作为后缀拼进所有科目与仓库名**（如 `存货 - HDS`），定了就别改 |
| 默认货币（Default Currency） | `CNY` | |
| 国家（Country） | `China` | 决定装哪套地区化逻辑；v16 的 `erpnext/regional/` **无 china**，故此处只影响时区与地址格式，没有中国财税逻辑（这是 LG-001，第 ② 阶段的主要工作面） |

**第二步：切「会计」（Accounts）选项卡 → 「科目表」节，填两个字段而非一个。**

| 字段 | 填什么 |
|---|---|
| 基于什么建科目表（Create Chart Of Accounts Based On） | `Standard Template` |
| 科目表（Chart of Accounts） | `Standard` |

**第三步：先保存。** 保存要等几秒——它在后台生成整棵科目表（95 条）、仓库树（5 个）和一批默认账户。

**第四步：保存后切「库存与生产」（Stock and Manufacturing）选项卡 → 「库存设置」节，确认永续盘存。**

| 字段 | 期望值 |
|---|---|
| 启用永续盘存（物料移动实时生成会计凭证）（Enable Perpetual Inventory） | **已勾**（`default='1'`，无需手动勾） |

> **⚠ 为什么这一项必须放在保存之后**（R3 查证）：`enable_perpetual_inventory` 所在的「库存设置」（Stock Settings）**Section Break 自身**带 `depends_on: eval:!doc.__islocal`——`__islocal` 是"文档尚未保存"标记，故**整节连同其下五个字段在新建界面整块不显示**。v1 把它列进"保存前要填的字段表"不成立。
>
> 这是 ERPNext 有意设计：这节里的字段填的是科目，而科目表要到保存公司那一刻才生成。
>
> **该字段 `default='1'`，故保存时已生效、不用手动勾。** 但要进来确认——这一勾决定"库存动作是否自动产生会计分录"，不勾则三个 ★ 节点全看不到东西。

### 数据模型

- **`Company`** 是几乎所有业务 DocType 的必填字段——`Purchase Order` / `Sales Order` / `Work Order` / `Stock Entry` / `BOM` 的 `reqd` 清单里全有 `company`（已逐个查证）。它是 ERPNext 多组织隔离的轴。
- **科目表不是配置项，是数据**。勾 `Standard` 后 ERPNext 从模板文件生成几百条 `Account` 记录（本例 95 条），每条带 `parent_account` 形成树（`is_group` 标识是否为分组节点）。这意味着**科目表可以随意改**（加科目、改层级），它不是硬编码。

  **科目表按界面语言生成**——本站点界面语言为 `zh`（System Settings 与 Administrator 用户均为 `zh`），故生成的是**中文科目树**。这是 v1 全篇英文科目名对不上的根本原因，不是笔误。

  **中国厂要用的一级科目结构与 `Standard` 模板差别不小**：`Standard` 是国际通用结构，只给「存货」一个笼统科目、下无细分；而中国准则的存货类是 1403 原材料 / 1405 库存商品 / 1411 周转材料 / 生产成本等分开的。第 ② 阶段"做中国大陆通用版"的一件核心事就是把科目表换成符合中国准则的结构（一级科目按 1001/1002/1403/2202 编号体系重建、存货与应收应付与税金几类的子科目补齐、各仓库与税种映射到对应科目）。**这不是二开而是配置**——科目表是数据不是代码，ERPNext 支持自定义科目表模板；**难点不在技术在会计知识**，要一个懂中国准则的会计把它设计出来。已并入 `SH-P1S1001`。
- **缩写 `abbr` 的作用**：ERPNext 用 `名称 - 缩写` 作为 Account / Warehouse / Cost Center 的主键，以此实现多公司下同名科目共存。所以 `abbr` 参与主键构成，**改它等于重命名几百条记录**，故上面说定了别改。
- **`enable_perpetual_inventory`** 是永续盘存开关。开着时每笔库存移动都由 `erpnext/controllers/stock_controller.py` 生成对应的 GL Entry；关掉则库存只有数量账、金额靠期末盘点调整。ERPNext 默认开，本稿也必须开——★ 节点要看的就是它生成的分录。
- **Item / Customer / Supplier 没有 `company` 字段**（已查证：三个 json 里 `"fieldname": "company"` 计数均为 0）。这三类是**跨公司共享**的主数据，而 `Warehouse` 有 `company`、按公司隔离。这个不对称是理解 ERPNext 数据模型的一个关键点：**"东西是什么"全公司共享，"东西在哪、值多少钱"按公司分。**

> **树视图的新建弹窗只有两个字段，这是设计使然、不是缺字段**（R3 实操的第二个困惑）。`warehouse_tree.js` 明确定义弹窗字段为 `warehouse_name`（必填）+ `is_group`（Check，标签「Is Group」），并 `ignore_fields: ["parent_warehouse"]`——**父节点由你点击的树节点位置决定**，不用填。公司等其余字段在保存后的编辑页里填（单公司站点下自动带出）。
>

>
> 建完后**回环节 1 第六步把「默认废料仓库」设为 `废料 - HDS`**。

### 数据模型

- **`Warehouse` 是树形 DocType**（nested set）：靠 `parent_warehouse` + `lft` / `rgt` 两个整数字段维护树结构。`lft`/`rgt` 是 nested set 的左右值，查"某节点全部子孙"一条范围查询就够，不用递归。你不用手填它们，框架维护。
- **`is_group`** 区分分组节点与叶子节点。**只有叶子节点能存货**——往 `is_group=1` 的仓库做库存动作会被拒。
- **`lft`/`rgt` 有空洞不等于树坏了**。建删节点后 nested set 不一定重建，会留下空洞（R3 事后复核时根节点 `rgt=16`、12-15 是空洞），**树仍完全可用**。别把"连续无断裂"当成健康判据。
- **仓库可以挂会计账户**：`Warehouse` 有 `account` 字段。留空则用公司的 `default_inventory_account`（即 `存货 - HDS`），此时**所有仓库的库存金额记在同一个科目里**。想让"线材仓"和"成品仓"在资产负债表上分开显示，就给各仓库分别指定账户。本稿留空——先看懂单一科目的分录，再谈拆分。

  **这个"留空"的代价在环节 18 会具体撞上**：领料（原料仓 → WIP 仓）两仓同科目，借贷完全抵消，**ERPNext 干脆一行分录都不写**，总账上完全看不出料进了车间。**要让财务看见 WIP，必须给仓库分别指定科目。**

  正确的结构（R3 第 24 步用户提出，判断成立）是**子科目 + 父科目汇总**——`Account` 是树形 DocType、**报表按树汇总**，故：

  ```
  存货（is_group=1，不能直接记账）
  ├── 原材料 - HDS      ← 仓库 - HDS 的科目
  ├── 在产品 - HDS      ← 进行中 - HDS 的科目
  ├── 库存商品 - HDS    ← 成品 - HDS 的科目
  └── 废料 - HDS        ← 废料 - HDS 的科目
  ```

  各仓库的 `account` 字段分别指向对应叶子科目。收益：资产负债表「存货」一行显示总数（自动汇总）、点开看得到各类明细、每个数都能追到具体仓库的库存流水。**而这恰好对上中国会计准则的存货类科目结构**，故它同时是第 ② 阶段中国本地化的一个具体入手点（已并入 `SH-P1S1001`）。
- **另有 `enable_item_wise_inventory_account`**（公司的库存设置节）：开了可**按物料**而非按仓库分科目，对应 `get_item_wise_inventory_account_map()`（`stock_controller.py:256`）。弹簧厂用不上，但知道它存在。
- **`Warehouse Type`** 当前只有 `Transit` 一条。它是个分类标签，被 Putaway Rule、在途调拨等功能引用。R1 的 F5（寄售/VMI）判 ⚠ 时提到"或许能用 Warehouse Type + 客户仓变通"——那条待验，见 Stage 概况风险表。

## 环节 3　建计量单位与换算

这是本稿第一个真正属于弹簧厂的建模决定：**线材按 kg 买，弹簧按支卖，两者要能换算。**

### 操作

**第一步：确认已有的 UOM。** 搜「**单位**」（UOM）——译名是「单位」不是"计量单位"。站点已有 239 条，其中 `Kg` 和 `Nos` 都在。

**第二步：建「支」。** 新建 UOM → 名称 `支` → **勾上「必须为整数」**（Must be Whole Number）。建完总数应为 **240**（R3 实测）。

> 勾这个的理由：弹簧按支计，0.5 支无意义。但**这一勾会在环节 6 咬你一口**——BOM 的工艺损耗算出小数时会直接报错。到那里再说，此处先记住勾了。

**第三步：不建 UOM 换算表记录。** 你可能会想去「计量单位换算系数」（UOM Conversion Factor）里加一条 `Kg → 支`。**不要**——那张表是给"同类量纲之间的固定换算"用的（kg↔g、m↔cm），它有 `category` 必填字段（量纲类别）。而 kg→支 的换算系数**每个料号都不一样**（φ2.0 的簧一支 8.7 g，φ3.0 的一支 20 g 出头），不是量纲换算。

正确的落点是**每个 Item 自己的 `uoms` 子表**，在环节 4 填。

> **R3 从数据侧印证了这一点**：`UOM Conversion Factor` 表实测 **235 条，全部带 `category`**（`Mass` 等），无一条 `category` 为空——它确实只装物理量纲换算，不是给"每个料号不同的换算"设计的。**量纲换算是物理常数，料号换算是产品属性。**

### 数据模型

- **两张换算表，别搞混**：

  | DocType | 管什么 | 字段 |
  |---|---|---|
  | `UOM Conversion Factor` | 全局的量纲换算（kg↔g） | `category`（必填）、`from_uom`、`to_uom`、`value` |
  | `UOM Conversion Detail` | **某个 Item 的**多单位换算，是 `Item.uoms` 子表 | `uom`、`conversion_factor` |

  前者是全局常量，后者是料号属性。弹簧的 kg↔支 属后者。

- **`stock_uom` 是锚**。每个 Item 有一个 `stock_uom`（库存计量单位，`reqd=1`），**所有库存数量与估值都以它为准**；其余单位都是它的换算视图。`Item.uoms` 子表里 `stock_uom` 那一行的 `conversion_factor` 恒为 1——框架自动加这一行（`erpnext/stock/doctype/item/item.py:401-412` 的 `add_default_uom_in_conversion_factor_table`），且校验它必须为 1（同文件 `:456-460` 的 `validate_conversion_factor`）。

- **动那一行的三种后果**（R3 读 `item.py` 查证，值得知道以免误操作）：

  | 动作 | 后果 | 代码位置 |
  |---|---|---|
  | 改 stock_uom 行的 `conversion_factor` | **拦得住**，报 `Conversion factor for default Unit of Measure must be 1 in row {0}` | `item.py:456-460` |
  | 删掉那一行 | **自动补回**：保存时检查 stock_uom 不在 uoms 列表则 append 一行系数 1 | `item.py:401-412` |
  | **改 `stock_uom` 本身** | **整张 uoms 子表被清空**（`self.uoms = []`），只提示"请重新定义换算系数"。**已有库存记录时后果更重**——历史数量的含义变了 | 同上方法开头 |

  **计算不是"按第一行"，是按 `stock_uom` 字段。** 子表里 stock_uom 那行恰好排 idx 1 是 append 时机所致，"第一行"无特殊含义。
- **`must_be_whole_number`** 在 `UOM` 上。现有的 `Nos` 是 1、`Kg` 是 0（已查证）。它会在多处触发整数校验，包括 BOM 的工艺损耗（`erpnext/manufacturing/doctype/bom/bom.py:1365-1371` 的 `validate_uom`：`process_loss_qty % 1 != 0` 且 UOM 要求整数 → 抛错）。
- **这一层的原生缺口**：R1 的 L0 层痛点写的"kg↔支 换算要设计"就是这件事。原生机制够用（`Item.uoms` 正是为此而设），**但换算系数得你自己算出来填**——ERPNext 不知道展开长度公式。环节 4 会算一次；把它落成公式并录进系统，是 R1 样板一（A1 询价）说的"落地前提②"。

## 环节 4　建物料：线材与弹簧成品

### 操作

**第一步：建物料组。** 站点已有 `Raw Material` / `Products` 等标准组（demo 那个 `Demo Item Group` 已在环节 0 被清掉）。直接用：线材归 `Raw Material`，弹簧归 `Products`。

**第二步：建线材。** 搜 **`Item`**（该 DocType 在 v16 的 zh 里**未翻译**，界面上仍显英文 `Item`——搜"物料"搜不到）→ 新建：

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `WIRE-65MN-2.0` |
| 物料名称（Item Name） | `65Mn弹簧钢丝 φ2.0` |
| 物料组（Item Group） | `Raw Material` |
| 默认计量单位（Default Unit of Measure） | `Kg` |
| 维护库存（Maintain Stock） | 勾上（默认已勾） |

保存。

**第三步：算弹簧的单支重量。** 这是本环节的核心，也是 R1 样板一说的"要把老师傅心里的数落成公式"。

展开长度（一支弹簧要多长的线）：

```
展开长度 L = π × 中径 D_m × 总圈数 n
中径 D_m = 外径 − 线径 = 16 − 2.0 = 14.0 mm
L = 3.1416 × 14.0 × 8 = 351.9 mm ≈ 0.352 m
```

线材单位重量（钢密度 7.85 g/cm³）：

```
截面积 A = π × (2.0/2)² = 3.1416 mm²
每米重量 = 3.1416 mm² × 1000 mm × 7.85 g/cm³ = 24.7 g/m
```

单支重量：

```
0.352 m × 24.7 g/m = 8.68 g/支 ≈ 0.00868 kg/支
```

反过来：**1 kg 线材 ≈ 115 支** 〔典型值〕。

> **这个数只是算术结果，不是车间实际值。** 真实耗料还要加钩环/端部余量、切头切尾、试机废料——R1 样板一明确提到"钩环/端部余量"。压缩簧无钩环，但磨端要磨掉料、卷簧起停有废料。实际耗料通常比理论值高 3-8% 〔典型值〕。本稿的处理：理论值填 BOM，损耗走 BOM 的 `process_loss_percentage`（环节 6），两者分开——**这样"超耗多少"才查得出来**，混在一起就永远说不清（R1 场景 H2 的痛点正是"超耗说不清"）。

**第四步：建弹簧成品。**

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `SPR-C-2.0-16-50` |
| 物料名称（Item Name） | `压缩弹簧 2.0×16×50 65Mn` |
| 物料组（Item Group） | `Products` |
| 默认计量单位（Default Unit of Measure） | `支` |
| 维护库存 | 勾上 |

**保存后**，展开「计量单位」（Units of Measure）一节，在 `uoms` 子表里加一行：

| uom | conversion_factor |
|---|---|
| `Kg` | `0.00868` |

含义是"1 支 = 0.00868 Kg"。保存。这样你在任何单据上都能用 Kg 计这个弹簧（比如按重量报废、按重量对账），系统自动换算。

> 子表里应已有一行 `支 / 1`——那是框架自动加的 `stock_uom` 行，别删也别改。

**第五步：给线材挂采购价。** 搜「物料价格」（Item Price）→ 新建：物料 `WIRE-65MN-2.0`、价目表 `Standard Buying`、价格 `7.5`（元/kg 〔典型值〕）。

选了 `Standard Buying` 后 `buying=1` 会自动置上（该价目表自带采购标记）。

> **这一步不是可选的，环节 6 必须用到它。** v1 写"不是必须（采购单可以手填单价）"——采购单确实可以手填，但 **BOM 取不到料价就算不出成本**，而 R3 实测 BOM 那里的 `Valuation Rate` 路径**手填不了**（见环节 6 的 ⚠ 框）。故这一步实际是必做。
>
> **在哪找「物料价格」**：采购工作区**主页**有「物料与价格」卡片（`Items & Pricing`），其下第二项即物料价格；销售工作区主页对应卡片叫「物料和定价」（`Items and Pricing`，英文原名一个用 `&` 一个拼出 `and`，故译名也成了两个词）。
>
> **⚠ 上游缺陷（LG-018，已登记 `SH-P1S1006`）**：采购工作区的**左侧栏**不显示「物料与价格」卡片（主页正常）。R3 已排除数据层（47 条 Workspace Link 结构对称、`hidden=0`、页面 content JSON 含该 card）、服务端缓存（`clear-cache` + `clear-website-cache` 后照旧）、浏览器本地缓存（无痕窗口同样异常），**结论收窄至侧栏渲染逻辑**。绕过办法：走主页卡片，或直接搜索。不阻塞任何环节。

### 数据模型

- **`Item` 的必填字段只有三个**（已查证 `reqd` 清单）：`item_code`、`item_group`、`stock_uom`。其余上百个字段全可选。这解释了为什么 v16 全新安装会报 `MandatoryError: stock_uom`——它必填而 demo 数据不带，靠 `frappe.defaults` 的全局默认值补（见 `docker/README.md`）。
- **`Item` 有 8 张子表**（已查证）：`item_defaults`（各公司的默认仓库/账户）、`uoms`（多单位换算）、`taxes`、`barcodes`、`reorder_levels`（再订货点）、`attributes`（变体属性）、`supplier_items`、`customer_items`（客户图号 ↔ 内部料号！）。
  - **`customer_items` 正是 R1 场景 A2 的原生解**（客户图号与内部料号的对应）：`Item Customer Detail` 子表存"哪个客户管这个件叫什么图号"。A2 判 🔧 而非 ⚠ 就是因为这张表在。
  - **`item_defaults` 是按公司分的**：Item 本身无 `company`，但它的默认仓库、默认成本中心这些**确实因公司而异**的东西，放在这张子表里、每公司一行。这是 ERPNext 处理"主数据共享但默认值分公司"的通用手法，值得记住。
- **`attributes` 子表 + `Item Attribute`** 是变体机制。`Item Attribute` 支持 `numeric_values` + `from_range` / `to_range` / `increment`（R1 能力核实表已验证），即"线径 1.0 到 6.0，步长 0.1"这种数值型属性。这是 R1 场景 B6（规格变体爆炸）判 ✅ 的依据——几千个规格不必手建几千个 Item，用模板 + 变体生成。本稿不用变体（单件跑通更清楚），但 L1 教材要写透。
- **`Item Price` 不是 Item 的字段，是独立 DocType**。一个 Item 可以有任意多条 Item Price（不同价目表、不同客户、不同生效期、不同数量档）。这个设计是 R1 场景 A4（客户专属价与钢价联动）判 ✅ 的基础：改钢价只是加/改一条 `Standard Buying` 的 Item Price，不动 Item 本身。
- **换算方向的坑**：`conversion_factor` 的语义是"**1 个该 uom 等于多少个 stock_uom**"。这里 stock_uom 是「支」，所以 `Kg` 那行的 0.00868 读作"1 支 = 0.00868 Kg"——**不是** "1 Kg = 0.00868 支"。填反了差 13000 倍，且系统不会报错（两个方向都是合法数字），只会在成本上体现出来。这是本环节最容易错的一处。

**工时按 1000 支基准直接填这三个数** 〔典型值〕：

| 工序 | 工时（time_in_mins） | 依据（按 1000 支） |
|---|---|---|
| `卷簧` | **50** | 卷簧机约 20-25 支/分钟，1000 支约 40-50 分钟 |
| `去应力回火` | **18** | 见下方 ⚠ 框——回火是批处理，这个 18 是摊出来的数 |
| `磨端` | **36** | 约 28-30 支/分钟 |

> **⚠ 为什么是 1000 支基准，而 v1 写的是 5000**（DEC-021，R3 由用户发现并裁决）。
>
> v1 让你在 Routing 里填 250/90/180（5000 支基准），再到环节 6 的 BOM 里**除以 5** 改成 50/18/36。**那个除法是多余的出错来源**——忘改则 BOM 认为 1000 支要 520 分钟、成本虚高 5 倍。
>
> **正确做法是定一个基准量（1000 支），Routing 与 BOM 都按它填，中间不做换算。**
>
> **根子上的问题**：`Routing` 只有三个字段——`routing_name` / `disabled` / `operations`（R3 已查证），**没有任何数量字段**。故它的 `time_in_mins` 含义不完整，依赖"全厂共用同一 BOM 基准量"这条**隐含约定**。ERPNext 的设计前提就是如此（此前提下不加数量字段反而避免"这条按 5000、那条按 1000"的混乱），**但它是用约定代替字段——约定靠人守，字段靠系统守**。给 Routing 加基准数量字段已登记为 `SH-P1S1005` 第 ③ 层。

> **⚠ 回火这道工序：原生有"固定工时"机制，v1 说没有是错的**（LG-021，R3 最重要的一条判定更正）。
>
> `BOM Operation` **有 `fixed_time` 字段**，勾上后工时不随数量缩放。机制在 `work_order.py:1548-1552` 的 `calculate_time()`：
>
> ```python
> for d in self.get("operations"):
>     if not d.fixed_time:
>         d.time_in_mins = flt(d.time_in_mins) * flt(self.qty)
> ```
>
> 即**勾了 `fixed_time` 的工序，工时不乘数量**——正是回火这类批处理要的语义。同表另有 `set_cost_based_on_bom_qty`、`finished_good_qty`（标签 Qty to Produce）、`batch_size`。
>
> **本稿仍不勾它**（照线性填 18），理由是要在环节 17/28 看到"乘以 5"这个缩放机制本身；但**你要知道这个 18 是错的**——它意味着系统认为做 2000 支回火要 36 分钟，而实际仍是 90 分钟（同一炉装得下）。**想要正确行为就勾上 `fixed_time` 并把工时填 90（整炉实际值），零开发。**
>
> **这条的意义超出本环节**：R1 判 D2 为 ⚠ 的理由之一是"原生无固定工时"，该论断错了。**D2 的 ⚠ 须拆为两项**——「批处理工时不随批量变」**原生有**（`fixed_time`）；「一炉混多工单合并作业」原生无（`Job Card.work_order` 必填，一炉混 5 个工单就得开 5 张分别计时）。这是 R1 复核建议预警的"grep 未找到即推定缺口、可能使二开范围虚高"的**第一个应验实例**，其余 7 项未读源码的 ⚠（B1/B4/C3/D6/E7/F5/H5/H7）应同样复查源码。
>
> **ERPNext 的 `fixed_time` 只是 MRP II 标准工时模型的简化版**：标准模型把工时拆两段——准备时间（Setup Time，换模调机装炉，**不随批量变**）+ 加工时间（Run Time，按件线性），总工时 = 准备 + 单件 × 数量。SAP 的工艺路线有基准数量（Losgröße）加准备/机器/人工三种时间类型，Oracle 与 Dynamics 同为 setup + run 结构。而 `fixed_time` **只有"固定"与"线性"两档、不能相加**，故卷簧的"20 分换型 + 每支 0.05 分"表达不了，只能二选一。给 `BOM Operation` 加 `setup_time` 已登记为 `SH-P1S1005` 第 ② 层。〔这一段是行业通识，非本项目查证〕

### 数据模型

- **`Workstation` 的必填只有两个**：`workstation_name`、`production_capacity`（已查证）。
- **`hour_rate` 在 v16 是计算字段**：`erpnext/manufacturing/doctype/workstation/workstation.py:110-114`

  ```python
  def set_hour_rate(self):
      self.hour_rate = 0.0
      for row in self.workstation_costs:
          if row.operating_cost:
              self.hour_rate += flt(row.operating_cost)
  ```

  在 `before_save`（第 85-92 行）里调用。子表 `Workstation Cost` 只有两个字段，都必填：`operating_component`（Link 到 `Workstation Operating Component`）、`operating_cost`（Currency）。

  > **R1 样板一（A1 询价）里写的"Workstation 填 `hour_rate`"在 v16 不准确** —— `hour_rate` 填不了，得填子表。这不影响 A1 的判定（🔧 的理由是"机时费率要先算出来"，那个理由完全成立、且拆成四项后更需要财务配合），但操作路径变了。本稿按 v16 实际写，此事已记入本轮回执。

- **`hour_rate` 变更只回写「工艺路线」，不回写 BOM**（R3 一处判断更正，FD-44）。同文件 `update_bom_operation()`（189 行起，UPDATE 在 197-202）确实有一段 SQL，但它取 `bom_list` 的语句是：

  ```sql
  select DISTINCT parent from `tabBOM Operation`
  where workstation = %s and parenttype = 'routing'
  ```

  **只取 `parenttype='routing'` 的父文档**，随后 UPDATE 也带同一限定——故**只改工艺路线里的工序行，不碰 `parenttype='BOM'` 的行**。表名叫 `tabBOM Operation` 容易让人以为它改 BOM，实际不是（Routing 与 BOM 的工序子表共用这一张表）。

  **故正确表述是：BOM 一经提交，其工时与费率都是"当时快照"；Routing 侧才是"当前值"。** R3 实测印证：改 Routing 工时后，已提交 BOM 的三个成本数分毫未动。

  **这对"钢价传导"有实际影响**——改机时费率**不会**自动刷新已有 BOM 的成本，要刷得走下方「成本重算」那两条路（逐张点「更新成本」或开 `update_bom_costs_automatically`）。
- **`Workstation Type`** 当前 0 条（已查证）。它是"同型号多台设备"的抽象——建一个类型填一次费率，各台机继承（`_set_data_based_on_workstation_type`，同文件 `:118-128`）。弹簧厂有 20 台同型卷簧机时该用它，本稿三台不同型故不用。
- **`Operation` 的 `autoname` 是 `Prompt`**（已查证），故保存时弹窗输名。它还有 `batch_size` + `create_job_card_based_on_batch_size` 两个字段（R3 实测三道工序均为 `batch_size=1`、`create_job_card_based_on_batch_size=0`，即每工单每工序开一张 Job Card、不按批量拆分，环节 19 会用到）——这是"一张工序卡覆盖多少产量"的控制。**注意它解决的是单工单内分批，不是跨工单合批**（一炉混 5 个工单），后者仍无原生形态（见上方 `fixed_time` 那个 ⚠ 框的拆分说明）。
- **`Routing` 也没有必填字段**（已查证）。它就是一张 `BOM Operation` 子表的模板，BOM 选中它时把 `operations` 复制过去。复制后 BOM 里的副本与 Routing 脱钩——**改 Routing 不会回改已有 BOM**（R3 实测印证）。**BOM 侧是"当时快照"、Routing 侧是"当前值"**，费率也一样（见上一条）。

## 环节 6　建 BOM：线材 → 弹簧，含工序

这是本稿信息密度最高的一个环节。BOM 是 ERPNext 制造模块的枢纽——它同时承载"用什么料"、"走什么工序"、"成本是多少"三件事。

### 操作

搜「物料清单」（BOM）→ 新建。

**⚠ 先读这个字段位置表再动手**（R3 实操中用户在这里连续找不到四个字段）。BOM 表单的字段分散在三个选项卡：

| 选项卡 | 节 | 字段 | 界面中文标签 |
|---|---|---|---|
| **成品** | （无节名） | `quantity` | Quantity (Output Qty) |
| 成品 | Cost Allocation / Process Loss | `process_loss_percentage` | **制程损耗%** |
| 成品 | 工序 | `with_operations` | **有工艺路线** |
| 成品 | 工序 | `routing` | 工艺路线 |
| 成品 | （无节名） | `operations` / `items` | 工序 / **Components** |
| **成本核算** | — | `raw_material_cost` / `operating_cost` / `total_cost` | 原材料成本 / 工费成本 / 总成本（**全部只读**） |
| **更多信息** | **成本配置** | **`rm_cost_as_per`** | **物料单价基于** |
| 更多信息 | 成本配置 | `buying_price_list` | 价格表 |

两处译名容易混：`with_operations` 译作「**有工艺路线**」（是个**开关**）而 `routing` 译作「工艺路线」（**选哪条**）；`process_loss_percentage` 译作「**制程损耗%**」——它就是"工艺损耗"，同一字段。

**头部：**

| 字段 | 填什么 |
|---|---|
| 物料（Item） | `SPR-C-2.0-16-50` |
| 数量（Quantity / Output Qty） | `1000` |
| 公司（Company） | 自动填上 `华东弹簧`（单公司站点取全局默认公司，无需操作） |
| 货币（Currency） | `CNY` |
| 是否启用（Is Active） | 勾（默认已勾） |
| 是否默认（Is Default） | 勾（默认已勾） |

> **数量必须填 1000，不能填 1。** BOM 的数量是"产出多少个成品时的用料与工时"。按单支填会得到 0.05 分钟这种不直观的数，**且会直接报错**——见下方工艺损耗那一步。取 1000 支为基准、Routing 也按 1000 填（环节 5 已如此），**中间不做任何换算**。按 1000 建 BOM 是制造业常规做法。

**物料明细（Components 子表，在「成品」选项卡下）：** 加一行：

| 字段 | 填什么 |
|---|---|
| 物料编码（Item Code） | `WIRE-65MN-2.0` |
| 数量（Qty） | `8.68` |
| 计量单位（UOM） | `Kg` |
| 单价（Rate） | 见下方 ⚠ 框——**要先改 `rm_cost_as_per` 才会带出 7.5** |

`8.68` = 0.00868 kg/支 × 1000 支。这是**理论用量**，损耗单独走下面的字段。

> **⚠ 料价这一步 v1 写错了，照它做走不通**（LG-020，R3 暴露的三条实质性错误之一）。
>
> v1 写"「基于什么取料价」选 `Valuation Rate`（默认值）…单价可能取不到，**先手填 7.5**"。**手填不了。**
>
> - `rm_cost_as_per='Valuation Rate'` 时，rate 由 `get_bom_item_rate()` **从库存估值算出**（`bom.py:1383`），而线材此刻从未入库（`Stock Ledger Entry` 为 0），故取 **0**。
> - `raw_material_cost` / `operating_cost` / `total_cost` 三个字段 `read_only=1`，**本就不该由人改**。
>
> **正确做法**：去「更多信息」选项卡 → 「成本配置」节：
>
> | 字段 | 填什么 |
> |---|---|
> | 物料单价基于（`rm_cost_as_per`） | **`Price List`** |
> | 价格表（`buying_price_list`） | **`Standard Buying`** |
>
> rate 随即取到 **7.5**（来自环节 4 第五步建的 Item Price）。**选了 `Price List` 却不指定价格表会抛 `Please select Price List`**（`bom.py:1390-1392`）。
>
> 三个取值的取价来源（`bom.py:1383-1400`）：
>
> | 值 | 取价来源 | 此刻可用否 |
> |---|---|---|
> | `Valuation Rate`（默认） | 库存估值 × 换算系数 | ✗ 无库存记录，取 0 |
> | `Last Purchase Rate` | `Item.last_purchase_rate` × 换算系数 | ✗ 无采购历史 |
> | **`Price List`** | 按 `buying_price_list` 查 Item Price | ✅ **取到 7.5** |
>
> **环节 9 采购入库之后**，可以切回 `Valuation Rate` 再点「更新成本」（Update Cost），看它从估值取价——那时两条路都通，对照着看更清楚。

**工序（Operations）：**

1. 勾上「**有工艺路线**」（With Operations）—— **不勾这个整张 `operations` 子表不会出现**。
2. 「工艺路线」（Routing）选 `压缩弹簧-标准`，三道工序自动带进来，工时即 **50 / 18 / 36**。
3. **不用改工时。** 〔v1 在这里让你"把工时按 1000 支基准改一遍"（250÷5 等），v2 已把 Routing 改为直接按 1000 支填，**这个除法步骤取消了**——它是多余的出错来源，见环节 5 的 DEC-021 说明〕

| 工序 | 工作站 | 工时（分钟/1000支） |
|---|---|---|
| `卷簧` | `卷簧机-01` | `50` |
| `去应力回火` | `回火炉-01` | `18`（**摊出来的数，回火实际与批量无关**——见环节 5 的 `fixed_time` 框与下方数据模型段） |
| `磨端` | `磨端机-01` | `36` |

**工艺损耗：** 在「**制程损耗%**」（% Process Loss，在「成品」选项卡的 Cost Allocation / Process Loss 节）填 `5`〔典型值〕。

保存。**若数量填的不是 1000，这时会报错**（R3 实操实际撞上）：

```
Item: SPR-C-2.0-16-50 with Stock UOM: 支 can't have fractional process loss qty as UOM 支 is a whole Number.
```

原因：`process_loss_qty = quantity × process_loss_percentage / 100`。数量 1000 时得 `1000 × 5 / 100 = 50`，正好整数，不报。**数量填 1 则得 0.05**，小数被拒——因为环节 3 给「支」勾了「必须为整数」。

> **这就是环节 3 说的"会咬你一口"。** 遇到时两条路：把数量或损耗百分比调成能整除的组合，或回去取消「支」的整数勾选。**推荐前者**——整数约束对弹簧是对的，为迁就一个计算结果放弃它不值。
>
> **R3 实操中用户在这里走了一次弯路**：以为是工序时间的问题，把 50/18/36 改回了 0。**那三个数原本是对的，真因是数量填了 1 而非 1000。** 报错信息里提到 `process loss qty`，与工时无关。

保存成功后，切「成本核算」选项卡看自动算出的三个成本字段（**R3 实测值，与预期完全吻合**）：

| 字段 | R3 实测 | 怎么来的 |
|---|---|---|
| 原材料成本（Raw Material Cost） | **65.1** | 8.68 kg × 7.5 元 |
| 工费成本（Operating Cost） | **86.667** | (50+18+36) 分钟 ÷ 60 × 50 元/小时 |
| 总成本（Total Cost） | **151.767** | 两者之和 |

**单支成本 = 151.767 ÷ 1000 ≈ 0.152 元** 〔典型值〕。这个数就是 R1 样板一（A1 询价）里说的"报价时加毛利率"的底数——**报价从"凭经验"变成"查 BOM"，靠的就是这一步。**

**提交**（Submit）这张 BOM。

> **⚠ 上游缺陷（LG-015 之一，已登记 `SH-P1S1006`）：保存后「提交」按钮可能不出现，须手动刷新页面。**
>
> R3 实操撞上这一例，服务端四项全查通：`is_submittable=1`、`validate` 跑通无阻塞校验、Administrator 有 submit 权限、BOM 上无 Workflow，且数据库显示保存**已生效**（三个成本数已写入）。**问题在前端表单的 dirty 状态管理**——Frappe 只在文档 clean 时把主按钮换成「提交」，此处保存后 dirty 标记未清（BOM 有大量成本重算逻辑在前端跑，疑为某字段在保存响应回来后又被客户端脚本改了一次）。
>
> **绕过办法：刷新页面（F5），「提交」按钮即出现。** 这是本闭环的第三例"不刷新就看不到"（前两例：环节 2 仓库列表空白、环节 4 侧栏卡片缺失），四例可能同源，已判为集中查一次，**唤醒条件是"第 ③ 阶段客户演示前必须闭环"**——不能让客户手动刷新。

### 数据模型

- **`BOM` 的必填**（已查证）：`company`、`item`、`quantity`、`items`、`currency`、`conversion_rate`。注意 `items` 在必填里——**BOM 不能没有料**。
- **`BOM Item` 的必填**：`item_code`、`qty`、`uom`、`rate`。**`rate` 必填**是个值得注意的点：BOM 不只是配方，它自带成本快照。
- **`BOM Operation` 的必填**：`operation`、`time_in_mins`。只有两个——工位可空（继承 Operation 的默认值）。
- **`with_operations` 默认为 0**（已查证）。不勾则 BOM 只算料本、`operating_cost` 为 0，且**日后按它下工单不会生成 Job Card**。R1 样板二（D2 工序报工）提到的"若不二开的退路——关掉 Job Card"，技术上就是不勾这个框。
- **成本的三层结构**：

  ```
  raw_material_cost   ← Σ (BOM Item.qty × rate)
  operating_cost      ← Σ (BOM Operation.time_in_mins / 60 × workstation.hour_rate)
  secondary_items_cost← 联产品/废料的抵减（本稿未用）
  total_cost          ← 三者组合
  ```

  这个结构是理解 ERPNext 成本核算的起点：**料与工分开算、各自可追溯**。R1 场景 H2（材料成本与线材利用率）、H3（工序成本与机时费率）判 ✅/🔧 的依据都在这里。

- **`process_loss_percentage` 与 `secondary_items` 是两回事**：

  | 字段 | 语义 | 弹簧厂对应 |
  |---|---|---|
  | `process_loss_percentage` | 投了料但**没产出成品**，料就是损失掉了 | 切头切尾、试机废料、卷废 |
  | `secondary_items` | 投料产出了**副产品**，它有价值、要分摊成本 | 冲压废料（C 类板簧可卖废钢） |

  计算在 `erpnext/manufacturing/doctype/bom/bom.py:1351-1358`（`set_process_loss_qty`）。R1 能力核实表说的"v16 字段名为 `secondary_items`"就是后者。**A 类冷卷圆簧主要用前者**，C 类板簧冲压用后者——这是 DEC-004 说的"L2 工程数据层差异"的一个具体点。

- **回火工时那个 18 分钟是个建模妥协，值得看清楚**。回火是**批处理**：一炉 800 kg 混几个工单，装炉一次、出炉一次，耗时与炉内装了多少几乎无关。而 `BOM Operation.time_in_mins` 默认是**线性**的——填 18 就意味着系统认为做 2000 支要 36 分钟，而实际仍是 90 分钟（同一炉装得下）。

  **原生给了解法，只是本稿没用**：勾 `fixed_time` 即工时不随数量缩放（见环节 5 那个 ⚠ 框的源码）。本稿照线性填是为了在环节 17 看到"乘以 5"这个缩放机制，**你要知道这个数是错的**——它在排产和成本上都会偏（批量小时低估工时、批量大时高估）。

  **原生真正缺的是另一半**："一炉混多工单合并作业"——`Job Card.work_order` 必填，故一炉回火混 5 个工单的料就得开 5 张任务单分别计时。**D2 的 ⚠ 应拆成这两项分别判定**，前者原生有、后者原生无。

- **成本重算**：BOM 保存时取的是当时的料价与费率快照。日后料价变了有两条路——
  - 逐张 BOM 点「更新成本」（Update Cost）按钮；
  - 开「制造设置」（Manufacturing Settings）的 `update_bom_costs_automatically`（当前为 0，已查证），由定时任务批量刷。

  R1 样板一说的"改 Item Price + 开 `update_bom_costs_automatically` 或跑 BOM Update Tool 批量重算"就是这两条。本稿环节 11 入库后建议手工点一次，看着成本变化发生比读文档清楚。

- **BOM 是可提交文档**（有 docstatus）。提交后不可改，要改得取消 + 修订（Amend）或新建一版。这是 R1 场景 B1（图纸版本管理）判 ⚠ 的部分背景——BOM 自己有版本控制，但**图纸文件**没有与 BOM 版本绑定的机制。该项待验（见 Stage 概况风险表：B1 应查 `frappe/core/doctype/{file,version}`）。

>

### 数据模型

- **`Purchase Order` 的必填**（已查证）：`naming_series`、`supplier`、`transaction_date`、`company`、`currency`、`conversion_rate`、`items`、`status`。
- **`conversion_rate` 必填**是 v16 全新安装的一个坑源：它是"单据货币 → 公司本币"的汇率。同币种时应为 1，但**全局币种若与公司币种不一致就校验失败**——这正是 `docker/README.md` 记的第四处初始化缺口（"全局 `currency` 仍是镜像默认的 INR"）。本站点已修正为 CNY，故无感。
- **`status` 必填但你不填**——它由工作流自动维护（`Draft` → `To Receive and Bill` → `Completed`）。ERPNext 大量单据如此：`status` 是字段而非计算属性，由 `update_status` 之类的方法写。**这个设计意味着状态可能与实际不一致**（漏跑更新逻辑时），所以排查"单据状态不对"要去看写它的那段代码，不是看数据本身。
- **PO 不产生任何会计分录与库存变动**。它是承诺，不是事实。ERPNext 的单据链普遍如此分层：订单（承诺）→ 收货/发货（库存事实）→ 发票（财务事实）→ 付款（资金事实）。四者可以各自独立发生、也可以合并（发票勾 `update_stock` 就同时动库存）。**理解这个四层分离是理解整个 ERPNext 单据体系的钥匙。**
- **`Purchase Order Item` 有 `warehouse` 字段**：采购时就指定料入哪个仓。它会带到 Purchase Receipt。

## 环节 9　采购收货（Purchase Receipt）：线材入库

### 操作

**不要新建空白单据**。打开刚提交的 PO → 右上「创建」（Create）→「**采购入库**」（Purchase Receipt，译名不是"采购收货"）。物料、数量、仓库、单价全部带过来。

确认这两处：

| 字段 | 值 |
|---|---|
| 接收数量（Received Qty） | 100 |
| 仓库（Warehouse） | **`仓库 - HDS`** |

**提交**（Submit）。

> **为什么必须从 PO 创建，而不是"最好从 PO 创建"**（LG-023，R3 更正）：`Purchase Receipt Item.purchase_order` 的 **`read_only=1`**（已查证），故**手工新建收货单时这个字段根本填不了**，接不上采购链。
>
> v1 说"手工新建的收货单与 PO 无关联"结论对，但理由说成了"如果你不填"——**实则不能填**。手工新建的收货单只适合"没有 PO 的临时收货"（供应商赠品、补录历史数据）。
>
> 同子表另有 `purchase_order_item`（`hidden=1`、`read_only=1`），存 PO 明细行的具体 ID。
>
> **⚠ 上游缺陷（已并入 `SH-P1S1005` 全量排查）**：该只读可用 Property Setter 零代码去掉，**但改前须测**——只读可能是上游有意防护（手填不会写 `purchase_order_item` 这个 hidden 字段，可能致 PO 数量核销不准）。
>
> **这条对整个单据链都适用**——永远从上游单据的「创建」按钮往下走。

> **分批入库怎么办，以及 PO 状态机的一处不一致**（R3 查证 `status_updater.py:68-91`）。
>
> **分批入库原生支持**：PO 的「创建」按钮可点多次、每次带出剩余数量。收 60 则 `per_received=60`、再收 40 转 `To Bill`。
>
> **但 PO 的状态值里没有 `Partially Received`**：
>
> | 状态 | 条件 |
> |---|---|
> | `To Receive and Bill` | `per_received < 100 and per_billed < 100` |
> | `To Bill` | `per_received >= 100 and per_billed < 100` |
> | `To Receive` | `per_received < 100 and per_billed == 100` |
> | `Completed` | `per_received >= 100 and per_billed == 100` |
>
> 故**收了 60% 与一点没收显示同一个状态**，得看 `per_received` 数字才知进度。对比 `Delivery Note` 的状态机——它**有** `Partially Billed`。**功能不缺（百分比字段在），但列表页按状态筛选时看不出哪些是部分收货。** 已并入 `SH-P1S1005`。

### 数据模型

- **这是本稿第一笔真正改变库存的动作**。提交后同时产生两类记录：

  | 记录 | DocType | v16 中文 | 作用 |
  |---|---|---|---|
  | 库存分类账 | `Stock Ledger Entry` | **物料凭证** | 数量与估值的流水账 |
  | 会计分类账 | `GL Entry` | **总账分录** | 借贷分录 |

  两者由同一次提交生成、金额必须相等——这个"库存账与会计账双写"是 ERPNext 永续盘存的核心机制，也是环节 13 要细看的东西。

- **R3 实测这一步的两条记录**（照着核对即可确认机制生效）：

  ```
  Stock Ledger Entry（1 条）
    actual_qty = +100           本次变动量
    qty_after_transaction = 100 变动后余额
    valuation_rate = 7.5
    stock_value = 750
    stock_value_difference = 750
    stock_queue = [[100.0, 7.5]]   ← FIFO 队列
    voucher_no = MAT-PRE-2026-00001

  GL Entry（2 行）
    借  存货 - HDS                      750
    贷  暂估库存(已收货，未开票) - HDS    750
  ```

  **注意科目名**：v1 写 `Stock In Hand` / `Stock Received But Not Billed`，实际是 `存货` / `暂估库存(已收货，未开票)`。**「暂估库存」这个中文译名比英文原名更点题**——它就是"货到了票没到"的暂记科目。

- **上游单据状态自动更新**（"从上游创建"的收益，R3 实测）：PO 的 `per_received` 由 0 变 **100**，`status` 由 `To Receive and Bill` 转 **`To Bill`**。

- **`Purchase Receipt` 的必填**（已查证）多了几个：`posting_date`、`posting_time`、`base_net_total`。有 posting 时间是因为**库存是时序的**——估值按时间顺序累计，插一笔历史单据会触发其后所有单据的重算（`repost_item_valuation`）。
- **`Stock Ledger Entry` 是不可改的流水**。它记 `actual_qty`（本次变动量）、`qty_after_transaction`（变动后余额）、`valuation_rate`、`stock_value_difference`。**库存报表全部从它算出来**，没有"当前库存"这张表——余额是流水的累计结果。这个设计使任何时点的历史库存都可回溯。
- **估值方法**在 Item 上（`valuation_method`，默认取 Stock Settings 的值，通常是 `FIFO`）。FIFO 下 `Stock Ledger Entry` 带一个 `stock_queue` 字段，存着"当前库存由哪几批、各多少、各什么价"构成的队列。R1 场景 F1（线材仓按炉号先进先出）判 ✅ 就是因为这套机制原生完整。

## 环节 10　采购发票（Purchase Invoice）

### 操作

打开刚提交的采购入库单 → 「创建」→「采购发票」（Purchase Invoice）。

**你在这张单上找不到「更新库存」（Update Stock）这个勾选框——这是对的，不用找。**

**提交**。

> **⚠ v1 这里写错了**（LG-026）。v1 说"确认「更新库存」没有勾"，**暗示它可见**；实际从入库单创建时它**整个不显示**。
>
> 该字段的 `depends_on` 是 `eval:doc.items.every((item) => !item.pr_detail)`（R3 已查证），即**每行明细都没有关联采购入库单时才显示**。你的发票从入库单创建、每行都带 `purchase_receipt`，故整个勾选框隐藏。
>
> **这不是"靠用户自觉不要勾"，是系统已经判断出"库存动过了，不该再动"并把入口拿掉了。** 这个区别重要——R3 实操中用户担心"靠用户自觉勾选是否太不安全"，答案是上游已防。
>
> 该字段的用途是**"票货同到"场景**（无单独入库单，发票直接充当入库单），那时明细行无 `pr_detail`、框子才出现。demo 数据里的发票就是勾着的（`demo.py:181`）。

> **⚠ 关于"发票价与收货价不一致怎么办"——R4 实测，结论与 R3 记录的推断不同。**
>
> R3 记录曾写"发票提交时自动把差额记入价差科目：借暂估库存 750 / 借价差 30 / 贷应付 780"（LG-050）。**该分录形态当时未经查证，R4 实测证伪。**
>
> **第一层事实：默认设置下这情形根本发生不了。** 有两道独立拦截：
>
> | 拦截 | 设置项 | 默认值 | 报什么 |
> |---|---|---|---|
> | 单价必须一致 | `Buying Settings.maintain_same_rate` | **1（开）** | `Row #1: Rate must be same as Purchase Order: xxx (7.8 / 7.5)`，且同时对 PO 与 PR 各报一条 |
> | 超额开票不许 | `Accounts Settings.over_billing_allowance` | **0** | `This document is over limit by Amount 3.0 for item xxx` |
>
> `maintain_same_rate_action` 默认为 `Stop`（不是 Warn），`role_to_override_stop_action` 为空，故**没有任何角色能绕过**。校验在 `accounts_controller.py:953-980` 的 `validate_line_items`，容差是 0.01。
>
> **第二层事实：把两道拦截都关掉之后，实际分录里没有价差科目。**
>
> R4 实测（PO 10 kg @ 7.5 = 75 元，发票改 7.8 = 78 元）：
>
> ```
> 借  暂估库存(已收货，未开票) - HDS   78.0     ← 按发票全额
> 贷  应付账款 1 - HDS                78.0
> Stock Ledger Entry：0 条（库存估值不动，仍 7.5）
> ```
>
> **差额 3 元残留在暂估库存科目里，净额 +3，没有任何科目去冲它。** 库存估值仍按收货价 7.5，`库存调整 - HDS` 也没动。即：**ERPNext 不自动处理采购价差，它靠"不许不一致"来回避这个问题。**
>
> **真实业务里价差怎么处理**（本项目未实测，属推断，标明以免误用）：走「到岸成本凭证」（Landed Cost Voucher）把差额计入库存成本，或关掉 `maintain_same_rate` 后自行做调整分录。**哪条是中国厂的正确做法，须到第 ② 阶段实测后再写进教材。**
>
> **这条对操作的实际含义**：本闭环不会撞上它（发票从入库单创建、单价一致）。但**弹簧厂真实场景会撞**——钢价波动时供应商按开票日价格开票很常见，而系统会直接拦住。到那时要先决定"是改设置还是走 Landed Cost"，这是个业务决定不是技术决定。

> **另外两种"暂估库存与实际应付不一致"的情形**（R3 讨论，机制清楚）：
>
> | 情形 | 处理 |
> |---|---|
> | **数量不同**（收 100 发票开 105） | **不能靠发票调**，须先修库存：补一张入库单或让供应商重开票。**原则：实物的事用库存单据解决，金额的事用发票解决**，混着改会让两账裂开 |
> | **货到票一直不到**（月末挂账） | 这不是"不一致"而是正常状态。暂估库存科目的余额即"已收货未开票"金额，代表**隐含负债**。查法：会计总账筛该科目，或用 Received Items To Be Billed 报表。本闭环余额为 0 因收货后立即开票，**真实工厂该科目常年有余额** |

### 数据模型

- **`Purchase Invoice` 的必填**（已查证）：`naming_series`、`supplier`、`posting_date`、`items`、`credit_to`。
- **`credit_to` 就是应付账款科目**（**`应付账款 1 - HDS`**，来自公司的 `default_payable_account`）。它必填，因为发票的本质是"确认一笔欠款"。
- **这一步的分录**（环节 13 会完整看）把"已收货未开票"这个暂记科目转成正式应付：

  ```
  借  暂估库存(已收货，未开票) - HDS   750
  贷  应付账款 1 - HDS                750
  ```

  **暂估库存科目至此被冲平**（收货时贷 750、开票时借 750，净额 0）——货到时挂上去、票到时冲掉。R1 场景 G2（外协发出收回的料账）、H6（存货核算与月结）都建立在这类暂记科目机制上。

- **R3 实测该发票的两级反向引用都写上了**：明细行同时带 `purchase_receipt=MAT-PRE-2026-00001` 与 `purchase_order=PUR-ORD-2026-00011`。提交后 PO 转 `Completed`（`per_received=100`、`per_billed=100`）、PR 转 `Completed`（`per_billed=100`）。

- **`update_stock` 勾选的语义**：勾上则本发票同时充当收货单（产生 Stock Ledger Entry）。用于"票货同到"的场景，可以少建一张单。demo 数据里的发票就是勾着的（`erpnext/setup/demo.py:181` 的 `invoice.update_stock = 1`）。**理解这个开关很重要**——它意味着 ERPNext 的单据链不是强制四段，而是可按业务实际合并。

### 操作

> **⚠ 这张单上的中文标签有一批是"付款"口径，收款时看着别扭，但数据是对的**（R3 第 35 步发现，LG-015 之一）。
>
> | 英文 | v16 中文 | 收款场景下应为 |
> |---|---|---|
> | `Payment Type` | 付款类型 | 收付款类型 |
> | `Paid Amount` | 付款金额 | 收款金额 |
> | `Mode of Payment` | 付款方式 | 收付款方式 |
> | `Pay` / `Receive` | 付款 / **收款** | ✅ 这两个译对了 |
> | `Paid From` / `Paid To` | **完全未翻译** | — |

### 数据模型

- **`Payment Entry` 的必填最多**（已查证 14 个）：`payment_type`、`paid_from` / `paid_to` 及各自的币种字段、`paid_amount`、`received_amount`、两个汇率、两个本币金额。这么多是因为它要同时支持跨币种收付——单币种时那些字段自动等值填充。
- **核销机制**：Payment Entry 有 `references` 子表（`Payment Entry Reference`），记"这笔钱核销哪几张发票各多少"。一笔付款可核销多张发票、一张发票可被多笔付款分期核销。R3 实测本单 `allocated_amount=750`、发票 `outstanding_amount=0`、状态由 `Unpaid` 转 **`Paid`**。R1 场景 F4（发货与月度对账）、H5（应收应付）判定的基础就是这张子表。
- **分录**：

  ```
  借  应付账款 1 - HDS   750
  贷  现金 - HDS         750
  ```

- **采购侧四层闭环至此走完，四个科目的净额可以核对了**（R3 实测）：

  | 科目 | 净额 | 含义 |
  |---|---|---|
  | **存货 - HDS** | **+750.00** | 资产增加——料在仓库里 |
  | 应付账款 1 - HDS | **0.00** | 已付清 |
  | 暂估库存(已收货，未开票) - HDS | **0.00** | 已冲平 |
  | **现金 - HDS** | **−750.00** | 钱付出去了 |

  链条读法：`现金 → 应付账款 → 暂估库存 → 存货`（资产减 → 负债冲平 → 暂记冲平 → 资产增）。**钱从现金出去，经应付、经暂记科目，最终变成库存资产；每一步都有一张业务单据对应，每张单据只管自己那一段。** 这正是环节 13 第三步要读的东西，此刻已可验证。

  | 场景 | 暂记科目 |
  |---|---|
  | 采购：货到票没到 | **暂估库存(已收货，未开票)** |
  | 销售：货发了票没开 | 未开票收入 |
  | **生产：料投了成品没出** | **在制品（WIP）** ← 环节 20 |

### 补讲：凭证、科目、复式记账

〔DEC-010 定本稿不含会计原理层，但 R3 实操中用户在此处卡住并要求讲解，故就地补最低限度的三个概念。这正是 LG-010 记着的缺口，完整材料另补。〕

- **科目（Account）= 给钱分类的抽屉。** 本公司 95 个，建公司时按 `Standard` 模板生成，分五大类：资产（我有什么：`存货`/`现金`/`应收账款`）、负债（我欠什么：`应付账款`/`暂估库存`）、权益（老板投了多少、赚了多少）、收入（`销售`）、费用（`销货成本`/工资/电费）。科目是树状的，故能既看总数又看明细。

- **分录（Entry）= 一笔钱的两面。** 核心规则：每笔业务至少动两个科目，借方金额 = 贷方金额。**"借"与"贷"不是借钱/贷款的意思，纯粹是记账的左右两栏**，可理解成"左"和"右"。

  本例读法：仓库里多了 750 元货（资产增加），同时欠供应商 750 元（负债增加）。**两边必须相等是因为钱不凭空出现**——多了 750 存货，这 750 必来自某处（此处是"欠着"，若现金买则是"现金减少 750"）。这就是**复式记账**，五百年前威尼斯商人发明，至今通用，好处是**自带校验**（两边不等即记错）。

- **凭证（Voucher）= 产生这些分录的那张业务单据。** 分录里的 `voucher_type=Purchase Receipt`、`voucher_no=MAT-PRE-2026-00001` 即"这两行由该采购入库单产生"。**故"凭证"不是另一个东西，就是那张单据**——手工会计时代做完分录要附发票收据作凭据，ERP 里单据本身即凭据、分录自动生成。

- **库存那个"凭证"与会计这个"凭证"是同一张单据，两套账各记一次**：

  | 账 | 记什么 | 表 |
  |---|---|---|
  | 库存账 | 数量与估值：+100 kg、单价 7.5、余额 100 | `Stock Ledger Entry`（物料凭证） |
  | 会计账 | 借贷分录：存货 +750、暂估库存 +750 | `GL Entry`（总账分录） |

  两条记录的 `voucher_no` 相同。**为什么要两套**：仓库管理员关心"还有多少公斤"（数量），财务关心"存货值多少钱"（金额）；而两套必须对得上（100 × 7.5 = 750 = 存货科目余额），**这就是永续盘存的含义**。手工进销存软件无此层，故月底须人工做"存货结转"。

### 这一节该带走什么

三件事，后面全靠它们：

1. **库存动作自动产生会计分录，两账同源**。这是永续盘存（`enable_perpetual_inventory`）的含义。手工进销存软件没有这一层，所以月底要靠人工做"存货结转"。
2. **单据链四层分离**（订单 → 实物 → 财务 → 资金），每层可独立发生，也可合并。
3. **分录由控制器统一生成**，改法在 `StockController` 而非各单据。

**若这一节的分录你看不懂"为什么这么记"**——那是会计原理层，DEC-010 明确不含在本稿内（LG-010 记着这个缺口）。判断标准：你**能读出**"这笔单据产生了哪两行分录、金额从哪来"就算过关；**为什么借这个贷那个**可以先放着。真卡住就回头提，另补材料，别硬扛。

>
> 另：该字段的 label 是 `Source Warehouse`，v16 中文译作「**发料仓**」（无"库"字）。

### 数据模型

- **`Sales Order` 的必填**与 Quotation 几乎相同，多 `customer`（报价单可对 Lead 故是 `quotation_to` + `party_name`）。
- **SO 是生产的触发源**。它的 `items` 子表每行带 `delivery_date`，生产计划（环节 16）就是按这些日期与数量倒推排产的。
- **SO 也不动库存**。但它会产生**预留**概念——**这个预留记在 `Bin` 表上，不在 SO Item 上**（LG-034，v1 写错了）。

  v1 写"`Sales Order Item` 有 `reserved_qty`"，**该字段不存在**（R3 实测查询报 `Unknown column 'reserved_qty'`）。SO Item 上只有 `stock_reserved_qty`（值 0）。

  **真正记预留的是 `Bin`**——它按"物料 + 仓库"汇总四个数量：

  | 字段 | 含义 | R3 实测（提交 SO 后） |
  |---|---|---|
  | `actual_qty` | 实际在库 | 0（还没生产） |
  | **`reserved_qty`** | **已被销售订单预留** | **5000** |
  | `ordered_qty` | 在途采购量 | 0 |

  R1 场景 A3（接单与交期承诺）判 ✅ 的机制是对的，只是 v1 把字段位置记错了。**"业务口头承诺、车间不知道"的问题在系统里天然不存在**，只要单据录进去。

### 操作

`po_items` 子表自动填入：物料 `SPR-C-2.0-16-50`、数量 5000、BOM 号自动带出、目标仓 `成品 - HDS`（从 SO 带来）。

**`mr_items` 子表应该是空的——这是正确结果，不是没跑出来。** 做 5000 支需 43.40 kg，`Bin` 里有 100 kg，够，故系统判断不需要采购。**这正是 R1 场景 C2（工单下达与齐套检查）判 ✅ 的机制在起作用**——若线材只有 30 kg，该子表会列出"还缺 13.4 kg，要申购"，把"下单才发现料没到"提前拦住。

**提交** → 右上「创建」→「生产工单」（Work Order）。系统按 `po_items` 每行建一张工单。

> **⚠ 上游缺陷（LG-039，已登记 `SH-P1S1005`，优先级不低）：生产计划不按工艺损耗反算投料量，故每张按 SO 生成的工单必然短交。**
>
> **本闭环就会撞上，而且是在环节 20 才显形**——现在先知道它：
>
> ```
> SO 要 5000 支
>   → 生产计划按 SO 数量建工单（qty = 5000）
>   → 完工入库按 BOM 损耗扣减：5000 × (1 − 5%) = 4750
>   → 成品仓只有 4750 支，SO 要 5000，缺 250 支
> ```
>
> **正确算法是反算**：`需生产 = 5000 ÷ (1 − 5%) = 5263.16 → 5264 支`，`5264 × 95% ≈ 5000` ✅。
>
> **R3 已查证这个能力完全不存在**：`grep -rn "process_loss" production_plan.py` **零命中**；另查了 `scrap` / `yield` / `wastage` / `loss` 四个同义名，`scrap` 仅 2 处且都是 `scrap_warehouse` 仓库字段，其余全零。故**不属于"原生有机制只是命名不同"那类误判**——`planned_qty` 直接取 SO 的 `pending_qty`（`production_plan.py:545`），`process_loss_percentage` 只用于"产出时扣减"，不参与"投入量反算"。
>
> 这是 MRP 的基础功能（scrap factor / yield factor），SAP 与 Oracle 均有〔行业通识〕。
>
> **真实代价不是"少 250 支"，是流程成本翻倍**——每张订单都要补做一次：多一张工单、一次领料、一次报工、一次入库、一次发货。
>
> **本闭环怎么处理**：照 5000 建工单、走完流程，到环节 21 用"关闭订单"处置那 250 支（**这是为了跑通，不是真实业务的答案**）。**若你想让这一单足量交付**，就在这里手工把工单数量改成 **5264**——那才是真实业务里该做的，且此刻改成本最低。

### 数据模型

- **`Production Plan` 的必填**（已查证）：`naming_series`、`company`、`posting_date`、`po_items`。
- **它是个批量调度器，不是排产引擎**。它做三件事：汇总需求（从 SO 或手工）、按 BOM 展开物料需求、批量生成工单与采购申请。**它不做工序级排程**——那是 Work Order 的事（环节 17）。
- **物料需求计划（MRP）在这里**：`Production Plan` 有 `mr_items` 子表，能按 BOM 展开算出"要做 5000 支需要 43.40 kg 线材，现有 100 kg，不用买"。这是 R1 场景 C2（工单下达与齐套检查）判 ✅ 的依据——"下单才发现线材没到"在系统里会被提前拦住。
- **R1 提到的 `Master Production Schedule` / `Sales Forecast` 也在 v16**（能力核实表已验证存在）。它们是 Production Plan 之上的更长周期计划层，本稿不用——最小闭环从 SO 直接到 Production Plan 就够。L5 教材会展开这一层。
- **这一层的原生缺口**：R1 场景 C1（需求汇总与主生产计划）判 ✅、C3（机台排产与换型合并）判 ⚠。差别在于 Production Plan 能汇总需求、但**不能按"同线径合并换型"重排**——它按单生成工单，不做跨单优化。这是 C3/C4 二开的起点。

### 操作

打开环节 16 生成的工单（搜「**生产工单**」，译名不是"工单"）。检查这几个字段：

| 字段 | 应该是 | 说明 |
|---|---|---|
| 生产物料（Production Item） | `SPR-C-2.0-16-50` | |
| 数量（Qty） | 5000 | |
| BOM 号（BOM No） | 环节 6 那张 | |
| 计划开始日期（Planned Start Date） | 今天或明天 | 必填 |
| 在制品仓库（Work-in-Progress Warehouse） | **`进行中 - HDS`** | 环节 1 第六步已设默认值则自动带 |
| 目标仓库（Target Warehouse） | **`成品 - HDS`** | 从 SO 带来 |
| **发料仓（Source Warehouse）** | **`仓库 - HDS`** | **在明细行上**，见下方 ⚠ 框 |

> **⚠ 那三个默认仓库不在「生产设置」里**（LG-036，v1 与 R2 回执都写错了）。
>
> v1 让你"搜「制造设置」（Manufacturing Settings）填三个默认仓库"。**R3 实测 `Manufacturing Settings` 里没有任何 warehouse 字段**，那条路走不通。
>
> 它们在 **`Company` 的「库存与生产」选项卡 → 「生产」节**（`default_wip_warehouse` / `default_fg_warehouse` / `default_scrap_warehouse`）。**本稿已把这一步提前到环节 1 第六步**，若你按新版走过那一步，此处已自动带出。
>
> 顺带：「制造设置」的译名是「**生产设置**」（`Manufacturing Settings`）。

> **⚠ 发料仓在明细行上，且清空头部不会清明细**（LG-035 第二处 + R3 第 28 步）。
>
> 工单头部有个 `source_warehouse`，它是**批量设置字段**（一次性给所有明细行填仓库），**真正生效的是明细行上的 `source_warehouse`**。
>
> R3 实操中用户的操作序列是：填头部 → 推送到明细行 → 清空头部 → 明细行的值留下 → 保存通过。**"第一次报错没填发料仓、设了又取消后再保存就不报错了"——不是 bug，是这个不对称造成的困惑。**
>
> **⚠ 上游缺陷（LG-044，已登记 `SH-P1S1005`）**：**改头部值会跟着改明细行**（`transaction.js` 的 `set_warehouse` handler 遍历 items 逐行赋值），**只有清空不跟着清**。这个不对称本身就是困惑来源。已裁决按**双向同步**改（清空头部时同步清空明细行）——行为一致性本身即防错，且明细行为空时提交会被校验拦住，故不会造成脏数据。
>
> ERPNext 里这类批量字段有好几个（`set_warehouse`、`set_from_warehouse`）。

`required_items` 子表应已按 BOM 展开：`WIRE-65MN-2.0` 需要 **43.4** kg。

**43.4 = 8.68 × 5** —— BOM 是 1000 支基准、工单 5000 支，**系统按比例缩放**。你只提供工艺知识（一支多少料、一分钟几支），系统负责缩放、累加成本、跨单据传递。

`operations` 子表应有三道工序，各带工时与工位。

**提交**。

提交后看 `operations` 子表——**工时被乘了 5 倍**，且每道工序被填上了预计开始与结束时间（R3 实测）：

| 工序 | BOM 里 | 工单里 | 计划开始 | 计划结束 |
|---|---|---|---|---|
| 卷簧 | 50 | **250** | 19:09 | 23:19 |
| 去应力回火 | 18 | **90** | 23:**29** | 00:59 |
| 磨端 | 36 | **180** | 01:**09** | 04:09 |

机制在 `work_order.py:1550`：`if not d.fixed_time: d.time_in_mins = flt(d.time_in_mins) * flt(self.qty)`——**即环节 5 那个 `fixed_time` 框说的缩放**。

**这个 250 恰好等于当初"卷簧机 20-25 支/分钟、5000 支约 250 分钟"那个推算**，绕一圈回到原点，说明整套换算自洽。**而回火那 90 分钟现在是"18 × 5"线性算出来的**——若工单改 2000 支它会变 36 分钟而实际仍是 90。**勾上 `fixed_time` 后这里会恒定显示 90。**

> **⚠ 工序间隔实测 10 分钟，且这个字段填 0 也取消不了**（LG-037，R3 闭合）。
>
> 上表中 23:19→23:29、00:59→01:09 各有 10 分钟间隔，即 `mins_between_operations`。而「生产设置」里这个值**实测就是 0**。
>
> **真因是兜底代码**（`manufacturing_settings.py:49-52`）：
>
> ```python
> minutes = cint(frappe.db.get_single_value("Manufacturing Settings", "mins_between_operations")) or 10
> ```
>
> **`or 10` 把 0 吃掉了**（字段 json 无 default）。故"设置值 0"与"实际间隔 10 分钟"同时为真、并不冲突。
>
> **换来一条有用的事实：该字段填 0 无法取消工序间隔，想真正无间隔须二开。** 这对排产演示有影响——你算计划总时长时要把每道工序之间的 10 分钟算进去。

### 数据模型

- **`Work Order` 的必填**（已查证）：`company`、`naming_series`、`production_item`、`bom_no`、`qty`、`planned_start_date`、`status`。
- **几个关键开关**（已查证默认值）：

  | 字段 | 默认 | 含义 |
  |---|---|---|
  | `use_multi_level_bom` | 1 | 多层 BOM 是否逐层展开。弹簧 BOM 单层，无影响 |
  | `skip_transfer` | 0 | 是否跳过"领料到 WIP 仓"这一步。勾上则直接从原料仓扣料 |
  | `from_wip_warehouse` | 0 | 勾 `skip_transfer` 时才出现：是否从 WIP 仓反冲 |
  | `transfer_material_against` | — | 领料是按整张工单还是按工序分次领 |

  **`skip_transfer` 值得注意**：勾上能少一张单据，但**就看不到 WIP 库存了**。R1 场景 D3（在制品盘点，判 🔧）的痛点"WIP 是黑洞"——若厂里为省事勾了 `skip_transfer`，那个黑洞就是自己造的。本稿不勾，为的是环节 20 能看到 WIP 会计。

- **排产算法在 `work_order.py:1262-1287`**（`set_operation_start_end_time`）。它做的事：从 `planned_start_date` 起，按 `operations` 顺序累加各工序工时，前后工序之间加 `mins_between_operations`（**设置值为 0 但实际生效 10 分钟**，见上方 ⚠ 框）。

  **这就是全部**。没有优化、没有资源冲突消解、没有换型时间。R1 样板三（C4 插单）说的"朴素顺排"就是这 26 行代码。**R3 实测的三段计划时间（19:09→23:19→00:59→04:09，共 9 小时）正是这个算法的输出。**

- **`capacity_planning_for_days` 默认 30**（已查证）。计划开始日期超出这个窗口会抛 `CapacityError`，要求你改设置而非给出可行方案（`work_order.py:1236-1258`）。弹簧厂接年度框架订单（R1 场景 A5）时会撞上这个。
- **没有 `priority` 字段**（R1 已查证：manufacturing / selling / stock 三模块内仅 Putaway Rule 有）。这是 C4 判 ⚠ 的硬事实，也是 R1 定的"整个项目优先级最高的二开项"的起点——二开内容①就是给 Work Order / Job Card 加 `priority`（走 Custom Field + fixtures，不改源码，符合开发守则）。

### 数据模型

  | `仓库 - HDS` | **−43.4** | 56.6 | −325.5 |

  **R1 判 D3（在制品盘点）为 🔧 的理由在此得到最直接的验证**：机制有（库存流水清楚记着 43.4 kg 在 `进行中 - HDS`），但**财务看不见**。这不是技术缺口，是配置与流程问题。

## 环节 19　工序报工（生产任务单 / Job Card）

### 操作

工单提交后，系统已自动为三道工序各建一张 Job Card。搜「**生产任务单**」（Job Card，译名不是"工序卡"）看，应有三张，`for_quantity` 均为 5000、状态 `Open`、`docstatus=0`（草稿是正常的——工序还没干）。

**逐张处理**（按工艺顺序：卷簧 → 回火 → 磨端）：

1. 打开「卷簧」那张；
2. 点「**开始**」（Start Job）→ 选员工 `张师傅` → 开始计时；
3. **让它真实走一段时间**（见下方 ⚠ 框，这一步最容易毁掉整条成本链）；
4. 点「**完成**」（Complete Job）—— 弹窗让你填完工数量。填 `4850`，废品（`process_loss_qty`）`150`〔典型值，3% 废品率〕；

> **这里填的 150 废品与环节 20 那个"4750"是两套机制，别指望它们相加**。环节 20 的成品数量由 **BOM 的工艺损耗**算出（`5000 × 95% = 4750`），与你在这里填的**工序废品**是两个独立的数——区别见本环节末尾那张对照表。**填了工序废品，环节 20 的 4750 不会因此再减 150。**
>
> 之所以仍要你填：① 它是 R1 场景 D5（废品与返工）的原生字段，得看一眼它在哪；② **两个数的差额才是管理抓手**（理论该废 250、实际废了多少）。

三张都走完。

> **⚠ 这一步的计时时长直接决定成本对不对，R3 实操在这里毁掉了整条成本链的数值。**
>
> **工序成本按 Job Card 的实际报工工时算，不按 BOM 的计划工时。** R3 实操中三张任务单各只计时几秒（0.167 / 0.117 / 0.05 分钟），于是：
>
> | | 认真报工时应为 | **R3 实测（只计时几秒）** |
> |---|---|---|
> | 三道工序总工时 | 520 分钟（250+90+180） | **0.33 分钟** |
> | 工序成本 | **433.3 元**（104 分/1000支 × 5 批 × 50 元/时） | **0.27 元** |
> | 成品单价 | 0.1598 元/支 | **0.0686 元/支** |
> | 毛利率 | 27.4% | **68.8%** |
>
> **差 41.4 个百分点。老板看着报表以为赚 68%，实际赚 27%。**
>
> **这个偏差比本稿设计的演示更有价值**——它证明 **ERPNext 的成本准确性完全建立在车间真实报工之上**。这正是 R1 判 D2（工序报工）为 ⚠、D3（在制品盘点）为 🔧 的实质；也说明 R1 样板二"车间报工页"二开的价值**不是省事，是让成本数字可信**。
>
> **你怎么做**：想看到正确的成本数值，就按 BOM 计划工时认真计时（或至少按比例缩放，如每道工序计时 1/10）。想快速跑通闭环，就随意计时，**但要知道环节 20、23 看到的成本与毛利是错的**，照上表换算回去。

> **⚠ 上游缺陷（LG-029，已登记 `SH-P1S1006`）：`time_logs` 每次操作都残留一个空行，会让计时器状态错乱。**
>
> R3 实测三张任务单各残留一个空行，且 **idx 重复**、`new-job-card-time-log-*` 这种**前端临时 ID 入了库**（两处违反数据完整性）。
>
> **后果是计时器状态判断错**（`job_card.js:614-621`）：
>
> ```js
> const last_log_complete = time_logs?.length && time_logs[time_logs.length - 1].to_time;
> const is_actively_running = !!(time_logs?.length && !last_log_complete && !is_on_hold && !doc.is_paused);
> ```
>
> **它只看最后一行有没有 `to_time`，不检查该行是否为有效行。** 故把工时记录删空再保存后，系统 append 一个空行 → `length=1`（不是"还没有 time_log"）→ 最后一行 `to_time` 为 None → **显示"停止计时"而非"开始计时"**，系统认为正在计时而那一行完全是空的。
>
> **绕过办法：不要手动编辑 `time_logs` 子表，只用按钮操作。** R3 实操中用户是"计时前手动动了工时记录"才触发这一串混乱的。
>
> 零侵入的根治：`Job Card.validate` 的 `doc_events` hook 里删掉 `from_time`/`to_time` 皆空的行并重排 idx。

> **⚠ 按钮是四个不是两个，"反复计时"的入口是「暂停」而非「停止」**（R3 更正）。
>
> `job_card.js:670-673` 有 `Start Job` / `Resume Job` / `Pause Job` / `Complete Job` **四个**。
>
> **"今天做一半明天做一半"的正确操作是「暂停」**：暂停 → `is_paused=1` → 下次显示「继续」→ append 新的 time_log 行。**故多段计时原生支持**，只是入口不明显。
>
> **「开始」只在三种情况显示**（`job_card.js:610-613`）：还没有任何 time_log、上一轮完成了还有剩余数量、子工序循环完成。**其余时候一律只显示 暂停/完成**——这解释了为什么会觉得"只能记一次时"。

> **⚠ 上游缺陷（LG-041，已登记 `SH-P1S1006`）：在 `time_logs` 子表里手填完工数量会让「完成」按钮消失，于是填废品的弹窗没机会出现。**
>
> 「完成」按钮的显示条件（`job_card.js:632-643`）要求处于"正在计时"分支：
>
> ```js
> if (should_show_start) { show_start = true; }
> else if (doc.is_paused) { show_resume = true; }
> else if (qty_yet_to_manufacture > 0) { show_pause = true; show_complete = true; }
> ```
>
> 直接在子表填 `completed_qty` 并保存后，`total_completed_qty=5000`、`qty_yet_to_manufacture=0`，**故「完成」按钮不显示、那个能填废品的弹窗永远出不来**。
>
> **这是又一处"两条路径并存且其中一条绕过关键字段"**（子表手填 vs 弹窗），与环节 9 的 LG-023、环节 18 的 LG-032 同类。
>
> **务必走「完成」按钮那条路**——弹窗里有四个字段：`for_quantity`（本轮要做多少）、`completed_qty`（完工数）、**`process_loss_qty`（废品数）**、`pending_qty`，且描述文字明确写着三者之和必须等于 `for_quantity`。**R3 实操正是因为走了子表那条路，废品数没记上（三张单都是 5000 完工 / 0 废品）。**

> **⚠ 上游缺陷（LG-040，已登记 `SH-P1S1005`）：工序之间不传递数量。**
>
> 三张任务单的 `for_quantity` 都是 5000，**从工单 `qty` 直接来，不从上一道工序的净产出算**。理想应为：卷簧投 5000 出 4900 → 回火投 4900 出 4850 → 磨端投 4850 出 4800。
>
> **填了卷簧废 100，回火的 `for_quantity` 仍是 5000**——系统不知道只有 4900 支能进回火。
>
> MRP II 的标准做法是每道工序有 Input / Output / Scrap 三栏，前一道的 Output 即后一道的 Input〔行业通识〕。**这是 R1 判 D5（废品与返工）为 🔧 的具体表现——字段有（`process_loss_qty`）但工序间数量链不通。**

**回到工单**，看「已生产数量」（Manufactured Qty）—— **它仍是 0**。

> **这不是 bug。** 生产任务单只记录"工序做完了多少"，不产生库存。成品入库要单独一张物料移动单（环节 20）。这个分离是有意的：工序完成 ≠ 成品可入库（还要终检、包装）。

### 顺手分清：工艺损耗 vs 工序废品

这两个数容易混，但**分开记正是管理的抓手**（R3 实操中用户问过）：

| | 工艺损耗（BOM 的 `process_loss_percentage`） | 工序废品（Job Card 的 `process_loss_qty`） |
|---|---|---|
| 在哪定 | BOM，**事前** | Job Card，**事后** |
| 性质 | 计划值、标准损耗 | 实际值、这一批真实发生的 |
| 业务含义 | "这个产品按工艺**注定**损失 5%" | "这一批**实际**废了多少支" |
| 弹簧厂例子 | 每卷线材切头切尾必然浪费、卷簧起停必然有废料 | 这批线材质量差，多废了 80 支 |
| 用途 | 报价、成本估算、物料需求 | 成本差异分析、质量追踪、工人绩效 |

**核心区别：一个是"应该损失多少"，一个是"实际损失了多少"，两者的差额就是管理的抓手。** 理论损耗 5%（250 支）而实际废 400 支，超出的 150 支就该查原因（料的问题？机器状态？新手操作？）。**混成一个数就永远查不出来**——这正是 R1 场景 H2"超耗说不清"的解法。

### 数据模型

- **`Job Card` 的必填**（已查证）：`work_order`、`company`、`naming_series`、`operation`、`workstation`。注意 `work_order` 必填——**Job Card 不能脱离工单存在**。这是「一炉混多工单」无原生形态的根源：一炉回火混 5 个工单要开 5 张任务单分别计时。（**这一半才是 D2 该判 ⚠ 的部分**；另一半"批处理工时不随批量变"原生有 `fixed_time`，见环节 5。）
- **`time_logs` 子表**记每段工作时间（`from_time` / `to_time` / `completed_qty`），`time_in_mins` 由 `to_time - from_time` 自动算（`job_card.py:340`）、累加成 `total_time_in_mins`——**这是"实际工时"，用于与 BOM 的"计划工时"对比**。一张 Job Card 可以多段计时（用「暂停/继续」，见上方 ⚠ 框）。
- **`employee` 字段是 `Table MultiSelect` 而非 Link**（`options = Job Card Time Log`）。这类字段按设计**不建数据库列**，故 `select employee from tabJob Card` 会报 `Unknown column`——**那是正常的，不是 v16 改了字段名**。真正持有员工的是子表 `Job Card Time Log.employee`。
- **重叠校验在 `job_card.py:364-435`**（`get_overlap_for` / `has_overlap`，R1 已查证）。它校验的是**工位**时间不重叠，受 `Workstation.production_capacity` 控制（默认 1，即一台机同时只能跑一张任务单）。

  **R1 样板二说的"一人多机无原生形态"在这里可以确认**：`production_capacity` 放宽的是"这台机同时跑几个工单"，而"这个人同时看几台机"——`Job Card` 有 `employee` 字段，但**没有任何机制校验或支持一人跨多机并发**。一人 4 台机就是 4 张 Job Card 各自计时。
- **排程在 `job_card.py:517-557`**（`schedule_time_logs`）：找工位空档往后塞。**是"避免撞车"不是"优化排程"**——这是 R1 对 C4 判定的核心事实之一。
- **`Job Card` 有 96 个字段**（R1 样板二的说法）。你现在打开它就能直观确认这一点——R1 说的"50 岁卷簧工找不到完成数量按钮"不是夸张。这是 D2 二开内容①（车间报工页）的动因。
- **`process_loss_qty` 字段在 Job Card 上**，所以工序级废品是原生可记的。R1 场景 D5（废品与返工）判 🔧 而非 ⚠ 就是因为字段齐全，缺的是"工人愿不愿意填"——流程与培训问题。

## ★ 环节 20　完工入库：看懂 WIP 会计与成本回算

**第二个 ★ 节点。** 这一节要看的是：**投进去的料钱和工钱，怎么变成成品的库存价值。**

### 操作

**第一步：完工入库。** 打开生产工单 → 「创建」→「完工入库」（Manufacture）。

系统生成一张**物料移动**，类型 `Manufacture`。检查：

| 项 | 值 |
|---|---|
| 源仓（items 里线材行的 Source Warehouse） | `进行中 - HDS` |
| 目标仓（成品行的 Target Warehouse） | `成品 - HDS` |
| **成品数量** | **系统自动算出，别手改**——见下方说明 |

> **成品数量从哪来**：`fg_completed_qty × (1 − process_loss_percentage)`。R3 实测工单 5000 支 → 成品行 **4750**（`5000 × 95%`），`process_loss_qty=250`。**BOM 的工艺损耗在这一步自动扣减**：投料按 5000 支的量、产出按 4750 支。

> 若你在环节 19 通过「完成」弹窗记了废品（本稿设计的 4850 完工 + 150 废品），这个数会相应不同。**R3 实操没记上废品**（走了子表手填那条路，见环节 19 的 LG-041），故实际是 4750。

**⚠ 保存时会被拦住，报「额外费用」的费用科目必填。** 这是本环节最大的坑：

```
Please fill the following mandatory fields before saving:
In 额外费用, 费用科目 is required in every row.
```

**科目填 `结转库存的费用 - HDS`**（`account_type = Expenses Included In Valuation`，正是为"转入库存估值的费用"设计的科目）。

> **⚠ 上游缺陷（LG-043，已登记 `SH-P1S1005`）：这些行要逐行手填，本例 11 行。**
>
> 系统自动在「额外费用」（`Landed Cost Taxes and Charges` 子表）里按「工序 × 成本构成」生成了工序成本行——R3 实测 11 行（3 道工序 × 4 项成本构成，磨端少一行）：

> 工序卷簧的Rent运营成本          0.03

> 工序卷簧的Consumables运营成本   0.01

> **字段名注意**：R3 记录曾误记为 `expenses_included_in_valuation`——那是 v13/v14 旧名，**在 v16 的 erpnext 源码里零命中**，照它去公司表单上找不到该字段。v16 的名字是 **`expenses_added_to_stock_account`**（在 `stock_controller.py:929/953/965/2717-2732` 真实参与分录生成）。混淆源是 `Expenses Included In Valuation` 作为 **account_type 值**在 v16 仍在用。

> **⚠ 上游缺陷（LG-042，已登记 `SH-P1S1006`）**：若用「批量修改」（Bulk Edit）弹窗一次填这 11 行，**Link 字段在那个弹窗里退化为纯文本输入**、无搜索下拉，须手打完整科目名 `结转库存的费用 - HDS`，极易打错。绕过办法：逐行在子表里填（有下拉）。

**提交**。

**第二步：看成品的单位成本。** 提交后在这张物料移动的成品行看「基本费率」（Basic Rate）：

| | 认真报工时应为 | **R3 实测（工序只计时几秒）** |
|---|---|---|
| 线材成本 | 325.5（43.4 kg × 7.5） | **325.5** ✅ 相同 |
| 工序成本（`total_additional_costs`） | **433.3** | **0.27** |
| 成品总估值 | 758.83 | **325.77** |
| 完工数量 | 4750 | 4750 |
| **成品单价（Basic Rate）** | **0.1598 元/支** | **0.068526 元/支** |

> **这两列的差别全部来自环节 19 的计时时长**，见那里的 ⚠ 框。**工序成本按实际报工工时算，不按 BOM 计划工时。**
>
> 〔"认真报工时应为"一列的 433.3 是本项目实算值（104 分/1000支 × 5 批 × 50 元/时 = 433.33）；由它推出的 0.1598 也是按 4750 完工反算的。**v1 写的 0.156 是按 4850 完工的旧场景算的，与当前数据不同源，别混用。**〕
>
> 对比环节 6 BOM 算的单支成本 0.152：**差异来自"同样的投入摊在更少的成品上"（5000 支的料做出 4750 支）——这就是工艺损耗的成本影响，它自动体现了。**

**第三步：看分录。** 该物料移动 → 「菜单」→「会计凭证」。

**R3 实测只有两行**：

```
借  存货 - HDS                0.27
贷  结转库存的费用 - HDS       0.27
```

〔认真报工时这两行应为 433.3。〕

**线材从 WIP 仓转成品仓那部分没有分录**——两仓同科目、借贷抵消，与环节 18 领料同理（LG-033）。

> **v1 在这里写了三行分录（借成品仓存货 758.8 / 贷 WIP 仓存货 325.5 / 贷制造费用 433.3），那是推断出来的形态，实际不是这样。** 真实情况是：**只有工序成本这一笔产生分录**，料的部分因同科目而不记。
>
> **但要看的重点不变，反而更清楚**：这一行 `贷 结转库存的费用` / `借 存货` 就是**整条成本链里唯一一处"费用变资产"的转折**——人工、电费、折旧从费用科目转进了库存资产。这是第二个 ★ 的核心。
>
> 科目是 **`结转库存的费用 - HDS`**，**不是** v1 猜的 `销货成本`。R2 回执曾把"这个科目名待回填"列为高风险项，R3 已闭合。

**第四步：回到工单看回算。** R3 实测工单 `status='Completed'`、**`produced_qty=4750`**、`process_loss_qty=250`。仓库终态：`成品 - HDS` 有 4750 支、`进行中 - HDS` **清零**（料全部转化为成品）、`仓库 - HDS` 剩 56.6 kg。

**第五步：跑 BOM 差异报表。** 搜「BOM 差异报表」（BOM Variance Report）→ 选该工单。它对比"BOM 说该用多少"与"实际用了多少"。

> **⚠ 这里还会撞上一个短交问题，别慌**：SO 要 5000 支而成品仓只有 4750，缺 250。**这不是你操作错了，是环节 16 那个 ⚠ 框说的 LG-039**（生产计划不反算投料量）。处置见环节 21。

### 数据模型

- **`Manufacture` 类型的 Stock Entry 做三件事**：扣 WIP 仓的原料、加成品仓的成品、把工序成本计入成品估值。第三件是它与普通调拨的本质区别。
- **成品单价怎么算的**：`stock_entry.py` 里 `Manufacture` purpose 会调 `get_bom_scrap_material` 与 `set_basic_rate_for_finished_goods`——成品的 `basic_rate` = (原料总成本 + `additional_costs`) ÷ 成品数量。工序成本作为 `additional_costs` 注入，即上面那 11 行。
- **那 11 行的可追溯性值得看一眼**：它们正是**环节 5 填的那四项成本构成**（工资/电费/租金/耗材）**乘以实际工时**算出来的，且按工序拆开。**故"某道工序的电费花了多少"是查得出来的**——这是 R1 场景 H3（工序成本与机时费率）判 🔧 的机制基础。全部 11 行 `has_operating_cost=1`。
- **`backflush_raw_materials_based_on` 默认是 `BOM`**（已查证）。含义：完工入库时按 BOM 理论用量反冲原料，**不是按实际领了多少**。

  **这是一个很重要的行为**。它意味着：若你领了 43.40 kg 但实际只用了 42 kg，系统仍按 BOM 扣 43.40 kg 的比例 —— 差额留在 WIP 仓，成为"WIP 有余料"。另一个选项是 `Material Transferred for Manufacture`（按实际领用量反冲）。

  R1 场景 H2（材料成本与线材利用率，判 ✅）的"超耗说不清"——原生解法就是切到 `Material Transferred for Manufacture`、让实际领用与理论用量的差异显式暴露。**这是一个配置决定，不是二开**，但选错了整条成本链的意义就变了。值得在 L8 教材写透。

- **WIP 会计的完整语义**：ERPNext 的 WIP 不是一个独立的会计科目体系，而是**"在某个仓库里的库存"**。所以：
  - WIP 金额 = WIP 仓的库存估值；
  - 想在资产负债表上单独看 WIP，就给 WIP 仓指定一个专门的库存科目（环节 2 提到的 `Warehouse.account`）；
  - 不指定则 WIP 与原料、成品混在 `存货 - HDS` 一个科目里（本稿如此，故环节 18 领料零分录）。

  **这解释了 R1 场景 D3（在制品盘点）为什么判 🔧**：机制完整（WIP 仓 + 库存流水 + 估值），但要得到"财务能看的 WIP 金额"需要配置仓库科目 + 车间真的走领料/完工单据。两件事都不是技术缺口，是流程与配置。

- **`add_corrective_operation_cost_in_finished_good_valuation` 默认 0**（已查证）：返工工序的成本默认**不**计入成品估值。弹簧厂返工（R1 场景 D5）频繁时这个开关影响成本准确性。
- **工序成本能进库存估值的前提是 BOM 勾了 `with_operations`**。环节 6 勾了，所以这里能看到那一行。若当初没勾（即 R1 样板二说的"关掉 Job Card"那条退路），成品估值里**只有料本没有工本**。

  **这是"关掉 Job Card"这条退路的真实代价**：按"认真报工"那一列算，成本会从 0.1598 掉到 0.0685（只剩料本），**虚低 57%**。R1 说那条退路的代价是"丢掉工序级数据、把效率提升砍掉一半"，**从成本角度看砍掉的更多——它同时让成本失真**。建议 L5/L8 教材明确写出。

  **注意这个"57% 虚低"与 R3 实测的"68.8% 毛利率"是两件不同的事**：前者是"不勾 `with_operations`"的后果（结构性），后者是"报工工时不实"的后果（数据性）。**两者都会让成本虚低，但成因与解法完全不同**——第一个是配置决定，第二个是车间流程。

### 这一节该带走什么

1. **WIP 是"仓库里的库存"，不是独立会计体系**。想让它在报表上可见，配置仓库科目。
2. **工序成本经 `Manufacture` 类型的物料移动转入库存价值**，前提是 BOM 勾了 `with_operations`。**这是整条链唯一一处"费用变资产"的转折。**
3. **`backflush_raw_materials_based_on` 决定超耗查得出还是查不出**。默认值（按 BOM）会把超耗藏起来。
4. **成本准确性完全建立在车间真实报工之上**——这一条是 R3 实操用一个 41.4 个百分点的偏差换来的，比前三条更值钱。

## 环节 21　发货（销售出库 / Delivery Note）

### 操作

打开环节 15 的销售订单 → 「创建」→「**销售出库**」（Delivery Note，译名不是"发货单"）。

数量改为**实际做出来的那么多**（R3 实测 `4750`）。源仓库确认为 `成品 - HDS`。

**提交**。

**然后处理短交的那 250 支。** SO 要 5000、只发了 4750，`per_delivered=95%`，状态机要求 `>= 100` 才算交付完成，故 SO 停在 `To Deliver and Bill`。**这不是错误状态，是真实业务状态**——确实欠客户 250 支。

三种处置：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A 补做 250 支** | 再建工单（考虑损耗要做 264 支）→ 完工 → 再发货 | **客户要足量，真实业务最常见** |
| **B 关闭订单** | SO 右上「...」→「关闭」 | 客户同意少收，或尾数不追。**本稿走这条** |
| ~~C 改 SO 数量~~ | 取消 SO 修订成 4750 | **走不通**——下游已有发货单，取消会连带影响已建的 DN 与工单链 |

**本稿取 B**，理由是本环节的目的是跑通闭环，而 A 要重走的工单/领料/报工/入库四步**你已经全走过一遍了**。

> **但 A 才是真实业务的答案，而它暴露了 LG-039 的真实代价**：每张工单都短交，就意味着**每张订单都要补做一次**——多一张工单、一次领料、一次报工、一次入库、一次发货。**不是"少 250 支"的问题，是流程成本翻倍。** 这比"数量不够"更能说明为什么那个反算功能（`SH-P1S1005`）必须做。
>
> **想避开它**：回环节 16 把工单数量手工改成 5264。

### 数据模型

- **`Delivery Note` 的必填**（已查证）：`naming_series`、`customer`、`posting_date`、`posting_time`、`company`、`currency`、`conversion_rate`、`selling_price_list`、`price_list_currency`、`plc_conversion_rate`、`items`、`status`。
- **这一步的分录**是本稿第一次确认收入成本（**第三个成本转折点**）：

  ```
  借  销货成本 - HDS   325.77    ← 费用确认（R3 实测；认真报工时应为 758.83）
  贷  存货 - HDS       325.77    ← 资产减少
  ```

  **注意这里只记成本、不记收入**。收入在开票时记（环节 22）。这又是四层分离的体现：实物出去了（发货）与钱该收了（发票）是两件事。

  R3 实测该单 `incoming_rate=0.07`（这批货的库存成本单价），库存流水 `成品 - HDS` **−4750**、变动后 **0**。

- **`Delivery Note Item` 带 `against_sales_order` 反向引用**，SO 的 `delivered_qty` 因此更新。R1 场景 F4（发货与月度对账）判 ✅ 靠的就是这条链——"送货单手写、月底扯皮"在系统里不会发生，因为每张发货单都挂在订单上。
- **欠交状态可查**，是 R1 场景 I1（交期达成率 OTD，判 ✅）的数据来源：`per_delivered` 字段记着交付百分比（R3 实测 95），列表与报表都能筛。

## 环节 22　销售发票与收款

### 操作

**开票。** 打开销售出库单 → 「创建」→「销售发票」（Sales Invoice）。

与环节 10 同理，「更新库存」（Update Stock）**在这张单上不显示**——库存已由出库单动过，系统已把入口拿掉。

**提交**。

> **从 SO 创建发票也可以，关联不会少一级**（R3 实测更正了一处判断）。
>
> Claude 曾说"从销售订单创建发票只有 `sales_order` 一级引用，出库单的 `per_billed` 不会更新、会永远停在 `To Bill`"。**实测全错**：发票明细行上 `delivery_note`、`sales_order`、`dn_detail`、`so_detail` **四个引用全部填上**，出库单 `per_billed=100`、状态 `Completed`。**ERPNext 会按 `sales_order` 找到对应的出库单明细行并一并写入引用。**

**提交**。

> **⚠ 这张发票的状态标签写着「未付」，应为"未收"**（R3 第 35 步发现，LG-015 之一）。同样地，「创建」菜单里的选项写「付款」而非"收款"。
>
> **数据方向是对的**（`payment_type='Receive'`、`paid_from='应收账款 1 - HDS'` → `paid_to='现金 - HDS'`），只是标签是单向命名。完整对照表见环节 11 的 ⚠ 框。
>
> **`Unpaid` / `Paid` 这批字符串的调用处没传 context**（如 `subscription_list.js:12` 的 `__("Unpaid")` 是裸调用），故翻译按源文本匹配、采购与销售显示同一个词。**但 `Translation` 的 `context` 机制在本仓库里是通的**——有传 context 的实例（`warehouse.js:52/53/82` 形如 `__("General Ledger", null, "Warehouse")`）。**故二开改法有三条**：销售侧加 Custom Field 覆盖标签、client script 改显示文本、或**给上游这些调用处补 context 参数 + 建对应的 `Translation` 记录**（第三条侵入度最低）。已记进 `SH-P1S1004`。

### 数据模型

- **`Sales Invoice` 的必填**（已查证）多了 `debit_to`、`base_net_total`、`grand_total`、`base_grand_total`。`debit_to` 就是应收科目（**`应收账款 1 - HDS`**）。
- **两笔分录**（R3 实测）：

  ```
  发票：借  应收账款 1 - HDS   1045
        贷  销售 - HDS         1045

  收款：借  现金 - HDS         1045
        贷  应收账款 1 - HDS   1045
  ```

  发票状态由 `Unpaid` 转 **`Paid`**、`outstanding_amount=0`。

- **增值税在哪**：Sales Invoice 有 `taxes` 子表，挂「销售税费模板」（Sales Taxes and Charges Template）。**税额能算、能记账**——13% 增值税建个模板就行。

  **缺的不是税额计算，是这三样**（R1 的 H5 判 ⚠ 的实质）：
  - **专用发票的开具**（票面格式、发票号管理、作废与红冲流程）；
  - **金税系统对接**（开票数据推送、发票回传）；
  - **进销项匹配与申报表**。

  v16 的 `erpnext/regional/` 无 china（R1 已查证），故这三样全无。**税率能配 ≠ 有中国财税逻辑**——这个区别对第 ② 阶段的工作量估算很关键，别把"能算 13%"当成"支持增值税"。

## ★ 环节 23　看懂成本如何从 BOM 流到损益表

**第三个 ★ 节点，也是整条闭环的收口。** 这一节把前面 22 个环节串成一条线。

### 操作

**第一步：跑损益表。** 搜「**损益表**」（Profit and Loss Statement，译名不是"利润表"）→ 公司 `华东弹簧`、本会计年度。

| 项 | 认真报工时应为 | **R3 实测（工序只计时几秒）** |
|---|---|---|
| 收入（Income）→ `销售` | 1045 | **1045** ✅ 相同 |
| 费用（Expenses）→ `销货成本` | 758.83 | **325.77** |
| **毛利** | **286.17** | **719.23** |
| **毛利率** | **27.4%** | **68.8%** |

> **⚠ 两列差 41.4 个百分点，全部来自环节 19 的报工工时。** 见那里的 ⚠ 框。
>
> **老板看着报表以为赚 68%，实际赚 27%。** 这是整个闭环最值钱的一条发现，比本稿原本设计的演示更有价值——**它证明 ERPNext 的成本准确性完全建立在车间真实报工之上**。
>
> 〔"认真报工时应为"一列按本项目实算：工序成本 433.3（104 分/1000支 × 5 批 × 50 元/时）+ 料本 325.5 = 758.83。**v1 写的 1067 / 758.8 / 28.8% 是按"4850 完工 @ 0.22"那个旧场景算的，与当前数据不同源，已全部替换。**〕

> **拿"认真报工"那一列的 27.4% 与报价时想的"45% 毛利"比，差距由两件事构成，要分开看。**
>
> **第一件是算术口径**。报价时做的是"成本 0.152 **加成** 45% 得 0.22"，而损益表给的是**毛利率**。两者分母不同：
>
> | 口径 | 算法 | 值 |
> |---|---|---|
> | 加成率（报价用） | (售价 − 成本) ÷ **成本** = (0.22 − 0.152) ÷ 0.152 | 45% |
> | 毛利率（报表用） | (售价 − 成本) ÷ **售价** = (0.22 − 0.152) ÷ 0.22 | 31% |
>
> 所以"加成 45%"本来就只对应 31% 毛利率，**这 14 个点不是亏掉的，是口径差**。
>
> **第二件才是真的成本上升**：实际单支成本 0.1598 而非 BOM 的 0.152，因为 5000 支的投入只做出 4750 支（5% 工艺损耗）。按实际成本算毛利率 = (0.22 − 0.1598) ÷ 0.22 = **27.4%**，即损耗吃掉约 3.6 个点。
>
> **这个算术本身就是一课**：报价用加成、看报表看毛利，中小厂"报价以为赚 45%、月底发现 27%"的困惑，绝大部分来自这个口径混淆，只有小部分是真实的成本恶化。**系统的价值在于把这两部分分开**——口径差是算法问题（学一次就会），损耗与超耗才是要管的（R1 场景 H1「标准成本 vs 实际成本差异」判 ✅ 的实质）。
>
> **而 R3 实测那 68.8% 是第三件事，性质完全不同**：前两件是"钱确实这么赚的、只是算法要看懂"，第三件是**数据本身是假的**。前两件靠学，第三件靠车间把单据跑起来。

**第二步：跑库存余额，确认账实相符。** 搜「库存余额(收发存汇总表)」（Stock Balance）——**注意它是空表**，见环节 12 的 ⚠ 框，改看「物料凭证」：

| 物料 | 仓库 | 余额 |
|---|---|---|
| `WIRE-65MN-2.0` | `仓库 - HDS` | **56.6 Kg**（100 − 43.4） |
| `WIRE-65MN-2.0` | `进行中 - HDS` | 0 |
| `SPR-C-2.0-16-50` | `成品 - HDS` | 0（4750 全发走了） |

**第三步：跑「库存与账务价值对比」**（Stock and Account Value Comparison）。**差额应为 0 行**——库存账与会计账走完整条链后没有裂开。

| 侧 | 值 |
|---|---|
| 库存估值（线材 56.6 kg × 7.5） | **424.50** |
| `存货 - HDS` 科目净额 | **424.50** |
| 报表差额行数 | **0** |

> **⚠ 若你直接查 `Bin` 表，可能看到一个和 SLE 对不上的 `stock_value`——那是后台任务还没跑，不是账裂了**（LG-051，R3 发现、R4 查清成因）。
>
> **现象**：R3 实测 `Bin.stock_value` 为 424.43（与自身 `qty × rate` = 56.6 × 7.5 = 424.5 差 0.07）；R4 做完 LG-050 实测并取消三张单据后，该字段变成 499.5（差 75）。**两次 SLE 侧都是干净的**（`stock_queue=[[56.6, 7.5]]`、`stock_value=424.5`），报表也都报 0 行。
>
> **成因**（`stock_ledger.py:604-610`）：
>
> ```python
> if self.args.get("sle_id"):
>     self.process_sle_against_current_timestamp()
>     if not future_sle_exists(self.args):
>         self.update_bin()          # ← 只有"没有更晚的流水"时才即时刷新 Bin
> ```
>
> **存在更晚的库存流水时就跳过即时更新**，改为建一条 `Repost Item Valuation` 记录丢给后台重算。**这是对的设计**——插一笔历史单据会改变 FIFO 队列、其后每一笔估值都要重算，同步做会卡死页面。
>
> **所以这不是 BUG，是那条后台任务还没执行。** R4 实测站点里积压着三条 `Queued` 状态的 `Repost Item Valuation`（两条是 R3 那天留下的、一条是 R4 的）——**R3 那 0.07 与 R4 那 75 是同一个成因**，不是两个独立现象。
>
> **为什么没跑**：repost 走 `scheduler_events` 的 cron（每 15 分钟一次 `run_parallel_reposting`，`erpnext/hooks.py:436`），而调度器要 **`docker/start.sh` 在跑**才会触发（`Procfile` 里的 `schedule` 与 `worker` 两个进程）。**这与环节 0 的 LG-011（清场走后台队列）是同一个前提条件。**
>
> **怎么处理**：
> - **开发环境**：确认 `docker/start.sh` 在另一个终端跑着，等一个 cron 周期（≤15 分钟）即自愈；`Bin` 有 `recalculate_values()`（`bin.py:40-71`）直接从最后一条 SLE 重读该字段。
> - **生产环境**：残差是**暂态的**，最多滞后十几分钟。真正要监控的是"调度器本身有没有挂"——那会让所有定时任务都停，属运维范畴。
>
> **两件事要分清**：`Bin.actual_qty` **始终是对的**（56.6 ✅），滞后的只有 `stock_value`；而**报表读的是 SLE 不是 `Bin`**，故它不影响任何报表结论。**唯一会困惑的场景是绕过报表直接查 `Bin`**（自己写 SQL 或做自定义报表时）。
>
> **顺带说准一件事**：报表报 0 行的机制**是容差**——`stock_and_account_value_comparison.py:51` 只收 `abs(difference_value) > 0.1` 的行。故"两账没有裂开"这个结论成立（三路互证：算术、GL 汇总、活跃 SLE 差额合计均为 424.50），**但依据是"差额落在容差内 + 报表查的是 SLE 这一侧"，不是所有表里的数字全等。**

**第四步：把成本链从头读一遍。** 这是本环节真正的功课。

**认真报工时的链条**（每个数都能往上追一层）：

```
线材采购价 7.5 元/kg              ← 环节 4 的 Item Price
   ↓ 入库估值
存货 750 元                        ← 环节 9，FIFO 队列 [[100, 7.5]]
   ↓ 领料 43.4 kg（两仓同科目，无分录）
WIP 325.5 元                       ← 环节 18
   ↓ 加工序成本 433.3 元（结转库存的费用 → 存货）
成品估值 758.83 元 / 4750 支       ← 环节 20，0.1598 元/支
   ↓ 发货（销货成本 ← 存货）
销货成本 758.83 元                 ← 环节 21
   ↓ 对应收入 1045 元（4750 × 0.22）
毛利 286.17 元（27.4%）            ← 环节 23
```

**R3 实测的链条**（同一条链，只有工序成本那一段不同）：

```
存货 750 → WIP 325.5
   ↓ 加工序成本 0.27 元 ← 三张任务单各只计时几秒
成品估值 325.77 元 / 4750 支 = 0.0686 元/支
   ↓ 发货
销货成本 325.77 元
   ↓ 收入 1045 元
毛利 719.23 元（68.8%）+ 现金净增 295 元（付 750、收 1045）
```

**每一个数都可以往上追一层，一直追到"钢价 7.5 元/kg"和"机时费率 50 元/小时"这两个源头输入。** 这就是 ERP 与"记账软件"的根本差别——不是账做得更漂亮，而是**每个数字都有来处**。

**而两条链的对照恰好说明了另一半**：链条完整 ≠ 数字正确。**机制通了，数值还要靠车间真实报工。** 追溯性是软件给的，准确性是流程给的。

### 数据模型

- **成本流转的三个转折点**，各由不同机制实现：

  | 转折 | 谁做的 | 代码位置 | 本闭环的分录 |
  |---|---|---|---|
  | 采购价 → 库存估值 | `StockController.make_gl_entries` + FIFO 队列 | `stock_controller.py` | 借存货 / 贷暂估库存 750 |
  | 料+工 → 成品估值 | `Manufacture` 类型物料移动的 `additional_costs` | `stock_entry.py` | 借存货 / 贷结转库存的费用 |
  | 成品估值 → 销货成本 | 销售出库单的 GL Entry | 同 `StockController` | 借销货成本 / 贷存货 |

  **三处都在 `StockController` 这条继承链上**，这是环节 13 说的"改法在一处"的又一次体现。

- **全部 14 笔 GL Entry**（R3 实测，照着核对即可确认整条链无断点）：

  | 凭证 | 借 | 贷 | 金额 |
  |---|---|---|---|
  | 采购入库 | 存货 | 暂估库存 | 750 |
  | 采购发票 | 暂估库存 | 应付账款 1 | 750 |
  | 收付款（付） | 应付账款 1 | 现金 | 750 |
  | **完工入库** | **存货** | **结转库存的费用** | **0.27**〔认真报工时 433.3〕 |
  | **销售出库** | **销货成本** | **存货** | **325.77**〔认真报工时 758.83〕 |
  | 销售发票 | 应收账款 1 | 销售 | 1045 |
  | 收付款（收） | 现金 | 应收账款 1 | 1045 |

  **三个过渡科目（应收账款 1 / 应付账款 1 / 暂估库存）净额全部为 0.00**——它们的职能就是"挂上去再冲掉"。

- **损益表是从 `GL Entry` 算出来的，不是从单据算的**。`erpnext/accounts/report/profit_and_loss_statement/` 按科目类型（Income / Expense）汇总 GL Entry。这意味着**任何绕过 GL Entry 的操作都不会出现在损益表上**——手工改库存数量、直接改数据库都属于此类。这是排查"报表数字不对"的第一原则：先看 GL Entry 有没有。
- **`gross_profit` 报表是另一条路**：`erpnext/accounts/report/gross_profit/` 按**单据**算毛利（每张发票的售价 − 该批货的估值成本），能下钻到单个商品、单个客户。损益表给总额，gross_profit 给结构。R1 场景 H1 的"不知道哪个品亏"用的是后者。
- **月结在哪**：本稿没做月结。ERPNext 的月结是 `Period Closing Voucher`（结转损益到未分配利润）+ 会计期间锁定。R1 场景 H6（存货核算与月结）判 🔧——机制在，痛点是"月结要两周"这个流程问题，靠单据及时录入解决，不是二开。

### 这一节该带走什么

1. **每个数字都有来处，可以逐层追到源头输入**。这是 ERP 的核心价值，也是你日后判断"某个数不对"该往哪查的方法。
2. **损益表从 GL Entry 算，不从单据算**。绕过 GL Entry 的操作在报表上不存在。
3. **加成率 ≠ 毛利率**，报价与报表用的是两套算法。这个混淆是中小厂"以为赚了其实没赚"的一半原因。
