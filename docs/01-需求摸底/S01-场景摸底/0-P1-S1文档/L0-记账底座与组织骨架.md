## 怎么读本层

**五段结构**（DEC-008）：① 该层要建什么 → ② 背后的数据模型 → ③ 弹簧厂在这层的场景 → ④ 痛点与原生缺口 → ⑤ 判定。

**两层深度**（DEC-010）：操作路径 + 背后数据模型。**不含会计原理层**——本层会告诉你"科目树长什么样、`root_type` 是什么、哪段代码校验它"，不会告诉你"为什么资产=负债+权益"。那是 LG-010 记着的缺口。

**与最小闭环操作稿的关系**：本层操作路径**完整可独立执行**，不必跳回操作稿。若你已跑过闭环，环节 0-3 覆盖了本层的一部分——本层在那之上**补足闭环没用到的内容**（税率模板、价目表分层、成本中心树、各仓库分科目）并把数据模型讲透。

**数值口径**（Stage 概况恒定约束）：凡本层出现的行业数值一律标 `〔典型值〕`，只具公开资料效力，不具本客户实际值效力。

**环境**：`erx.localhost`，http://localhost:8000，`Administrator` / `admin`。界面中文，菜单名给中文并附英文原名。

**导航方式：点击路径，不用搜索**（R6 用户裁决）。每步给"哪个工作区 → 哪张卡片 → 哪个标签"，照着点即可。理由：搜索框直达目标，却绕过了界面结构——学的人不知道某个功能挂在哪个工作区的哪张卡片下，也就建立不起"ERPNext 怎么组织功能"的心智模型，而理解骨架正是本层的目的之一。**搜索仍然可用**（作为熟练后的快捷方式），它自己的两个坑见本层末尾「附注：搜索框的两个坑」。

**标记**：

| 标记 | 含义 |
|---|---|
| `⚠ 上游缺陷` | ERPNext 自身问题，已给绕过办法，注明登记为哪条延迟需求 |
| `〔典型值〕` | 行业公开资料典型值 |
| `R3 实测` / `R5 实测` | 该数字或现象经实际验证，非推断 |
| `〔未查证〕` | 行业通识或推断，本项目未取证 |

## 段① 这一层要建什么

L0 的产物是一具**空骨架**：没有任何物料、没有任何单据，但每一笔将来的业务都知道自己该记到哪个科目、哪个成本中心、哪个仓库、按什么货币、按什么税率。

建的顺序不能随意换——后面的对象要引用前面的：

```
Company（公司）
  └─ 保存时生成 → Account 树（科目表，95 条）
                   Warehouse 树（仓库，5 个）
                   Cost Center 树（成本中心，2 个）
  ├─ Fiscal Year（财年）      ← 独立于公司，但单据要用
  ├─ UOM（计量单位）          ← 全局，不属任何公司
  ├─ Price List（价目表）      ← 全局，买卖各一
  └─ Tax Template（税率模板）   ← 挂公司，引用科目
```

### 第零步：先看清界面是怎么组织的

**登录后你看到的不是空白页，也不是一排工作区列表。** 先把 v16 的导航结构说清——**否则后面每一步都会找不到地方**，而这件事本身就是"理解骨架"的一部分。

**首页是一个图标网格，没有左侧栏。** 左侧栏不是全站共用的，它属于你点进去的那个具体页面（机制见段②）。

**首页上有两类图标**，靠 `link_to` 字段区分（`Desktop Icon` 表，R6 实测）：

- **填了 `link_to` 的**：点击直接进页面（如 `采购`、`销售`、`库存`、`生产`、`组织`、`委外`、`ERPNext设置`）。
- **`link_to` 为空的是分组**：点开只展开一组子图标，不跳页面。**`会计` 就是这种**——本层要用的 `Accounts Setup` 藏在它下面。

> **⚠ 本教材不给"首页共有几个图标"这种数量断言**，因为那个数**不等于表里的记录数**：`Desktop Icon` 共 36 条，`parent_icon` 为空的 9 条，而首页实际显示的比 9 个多。原因是 `icon_type` 为 `App` 的图标（如 `ERPNext`）**自身 `hidden=1`，其子图标却照样显示**——`desktop_icon.py:170-210` 的过滤只检查父图标是否有权限，不检查父图标的 `hidden`。故 `库存`/`资产`/`采购`/`质量`/`销售`/`项目`/`生产` 这 7 个虽然挂在隐藏的 `ERPNext` 组下，**它们就在首页上**。
>
> **要点**：`hidden` 是否向下传递**取决于 `icon_type`**（`Folder` 与 `App` 行为不同），这一点字段描述里没写。排查"某个图标为什么不见了/为什么还在"时须连 `icon_type` 一起看。

**点进任何一个非分组图标后，才出现左侧栏。** 左侧栏的结构是「分节标题 + 其下若干可点条目」。

**故完整的三层导航是**：

```
首页图标网格（Desktop Icon）
  └─ 分组图标 → 展开一组子图标
       └─ 子图标 → 进入页面，此时才有左侧栏（Workspace Sidebar）
            └─ 左侧栏的分节（Section）
                 └─ 条目（Link）→ 点它进到某个 DocType 的列表页
```

**这一层要建的东西，大部分在「会计」组的 `Accounts Setup` 里**（公司、科目表、财年、销项税模板），仓库与计量单位在别处（第七、九步各自给路径）。

> **⚠⚠ 「首页图标」与「表单选项卡」是两个不同层级，名字却相似，极易混淆**（R6 用户指出）：
>
> | 层级 | 承载物 | 本层会遇到的例子 |
> |---|---|---|
> | **首页图标** | `Desktop Icon` 记录 | `采购` / `销售` / `库存` / `生产` 是**四个独立图标** |
> | **表单内部的选项卡** | DocType 里的 `Tab Break` 字段 | `Company` 表单里是 `采购与销售` / `库存与生产` **两个合并的选项卡** |
>
> **同样一组词，在首页是四个、在公司表单里是两个。** 本教材此后严格区分用词：**首页那层一律叫「图标」，表单内部那层才叫「选项卡」**。看到"选项卡"三个字，指的一定是打开某条记录后表单顶部的那排标签。

> **首页没有"第一步做什么"的引导条**（R6 实测）。`Home` 那个 Workspace 的 `content` 里确实有一个 `type: "onboarding"` 的块，但 `Module Onboarding` 表里**没有** `Home` 这条记录，故它渲染不出来。别找引导，按本层顺序走。

### 第一步：建公司

**点击路径**：首页 → **`会计`**（Accounting，分组图标）→ **`Accounts Setup`**（**显示为英文**）→ 左侧栏 **`设置`**（Setup）分节 → **`公司`**（Company）。

这条路径有**三个坑**，逐个说清：

> **坑一：`Accounts Setup` 在组里排第四，不是第一。**
>
> 点开「会计」后，9 个子图标的顺序是：`开票管理` / `付款` / `财务报表` / **`Accounts Setup`** / `税` / `银行` / `预算` / `股份管理` / `订阅`（R6 实测 idx 0-8）。
>
> "建公司"直觉上是第一件事，但第一眼看到的是「开票管理」。**要找的是第四个，且它显示为英文**——`Accounts Setup` 未翻译（`frappe._()` 原样返回）。

> **坑二（最要紧）：左侧栏里有两个分节都叫「设置」。**
>
> `Setup` 与 `Settings` **的中文译名都是「设置」**（R6 实测，两者 `frappe._()` 均返回「设置」）。侧栏里两个分节因此同名：
>
> ```
> 设置（Setup）            ← 公司、科目表、成本中心表、财年、Sales Taxes 在这里
> POS机交接班（Opening & Closing）
> 设置（Settings）         ← 只有 Accounts Settings 等三项
> ```
>
> **要点的是上面那个（`Setup`）**——它在侧栏最上方，条目多（14 项）。下面那个 `Settings` 只有三项。**本层第一、六、十一步都在上面那个分节里。**

> **坑三：中间那个分节的译名是错的。**
>
> `Opening & Closing` 译作 **「POS机交接班」**（R6 实测）。原意是"期初与期末"（建账与关账），译文来自零售 POS 语境，与该分节的实际内容（科目表导入、期初发票工具、会计期间、汇率重估、期末结转凭证）**毫无关系**。看到它别困惑，本层不用它，L8 月结时会用到其中的「期末结转凭证」。

`设置`（Setup）分节下共 14 项，顺序为：`科目表` / `成本中心表` / `Account Category` / `Accounting Dimension` / `Currency` / `Currency Exchange` / `Finance Book` / `Mode of Payment` / `Payment Term` / `Journal Entry Template` / `Terms and Conditions` / **`公司`**（第 12 项）/ `财年`（第 13 项）/ `Sales Taxes`（第 14 项）。

> **⚠ 别先点第一项「科目表」。** 它此刻是空的（0 条），而**科目表不是手工建的**——你保存公司的那一刻它自动生成 95 条。先建公司。
>
> **⚠⚠ 而且从侧栏点「科目表」会看到一片空白，即使科目已经建好了**（R6 实测，用户在此卡住过）。原因：侧栏那条链接生成的是 DocType 的**列表**路由（`/desk/account`），而 `Account` 是**树形** DocType（`is_tree=1`、`default_view='Tree'`），**`account_list.js` 是个空文件**（实测存在但零内容），有实现的是 `account_tree.js`。
>
> **办法：地址栏直接敲 `http://localhost:8000/desk/account/view/tree`**（实测 200，能看到 95 条），或进去后在页面上把视图切成树。**`Warehouse` 与 `Cost Center` 同理**（三者都是 `is_tree=1`）。
>
> 这与 R3 撞到的"仓库列表页空白"是**同一现象**，已登记 `SH-P1S1006`（本轮在科目表上重现，是该条的第五例）。

点「公司」进到列表页，它是空的。空列表页上显示的是一句说明加一个大按钮：

| 元素 | 实际显示 |
|---|---|
| 说明文字 | 「属于本机构的，带独立科目表的法人/附属机构。」 |
| 按钮 | **`创建您的第一个公司`** |

**点那个大按钮即可**，不必去右上角找「+ 新建」。

> **为什么这里显示的是一句业务说明、而不是"您尚未创建公司"**（R6 读源码 + 实测）：`list_view.js:533-544` 的 `get_no_result_message()` 三分支——设了筛选器则报"无匹配记录"；**未设筛选器且该 DocType 的 `description` 字段非空，则显示 description**；两者都不成立才显示 `You haven't created a {0} yet`（译作「您尚未创建公司」）。
>
> `Company` 的 `description` 非空且有中文译文，故走第二分支。**别的 DocType 若 `description` 为空，空列表页显示的就是「您尚未创建 XX」**——两种文案都会遇到，是同一段代码的两个分支，不是哪里出错了。

**⚠ 填写有先后顺序，不能按一张表一次填完。** 永续盘存那个勾在保存前根本不显示（原因见第二步）。

**主表单顶部四项：**

| 字段 | 填什么 | 说明 |
|---|---|---|
| 公司名称（Company Name） | `华东弹簧` 〔典型值〕 | 这个值同时成为文档主键（`autoname` 为 `field:company_name`） |
| 缩写（Abbr） | `HDS` | **会作为后缀拼进所有科目、仓库、成本中心名**（如 `存货 - HDS`）。它参与主键构成，**定了别改**——改它等于重命名几百条记录 |
| 默认货币（Default Currency） | `CNY` | |
| 国家（Country） | `China` | **这个字段的实际作用比你想的小**，见下方 ⚠ 框 |

> **⚠ 选 `China` 不会给你中国财税逻辑**（R5 源码复查，比 R1 的表述更精确）。
>
> 国家字段影响三件事：时区与地址格式、默认节假日表、**以及科目表下拉里出现哪些候选**。第三件是本层该知道的机制：
>
> `chart_of_accounts.py:135-166` 的 `get_charts_for_country()` 按**国别码前缀**扫模板目录——`country_code` 取 `Country.code`（中国是 `cn`），然后找文件名以 `cn` 或 `China` 开头的 `.json`。命中几个就在下拉里列几个；**命中数不等于 1 时额外加上 `Standard` 与 `Standard with Numbers` 两项**（第 164-165 行）。
>
> 而它**只扫 `verified/` 目录**（第 147-149 行，除非 `frappe.local.flags.allow_unverified_charts` 为真）。`verified/` 下 78 个模板文件（R5 实测），**无一个以 `cn` 开头**。故中国用户的下拉里只有 `Standard` 与 `Standard with Numbers` 两项。

**科目表那两个字段：** 切「会计」（Accounts）选项卡 → 「科目表」节。

| 字段 | 填什么 |
|---|---|
| 基于什么建科目表（`create_chart_of_accounts_based_on`） | `Standard Template` |
| 科目表（`chart_of_accounts`） | `Standard` |

这是**两个字段而不是一个**——后者的 `depends_on` 指向前者。前者另有一个值 `Existing Company`（从已有公司复制科目树，多公司站点用），选它时出现的是 `existing_company` 字段而非 `chart_of_accounts`。

> **⚠⚠ 这里有一份中国科目表，但你选不到**（R5 的核心发现，修正了项目概况里"ERPNext 无中国科目表"的表述）。
>
> **事实**：`accounts/doctype/account/chart_of_accounts/unverified/cn_l10n_chart_china.json` **存在**，名为 `China - 中国会计科目表（财会[2006]3号《企业会计准则》）`，含 **82 个一级节点**（R5 实测），涵盖原材料 / 生产成本 / 库存商品 / 委托加工物资 / 应交税费（下挂 11 个税种子科目，含应交增值税）/ 主营业务收入 / 主营业务成本 等中国准则科目。
>
> **为什么选不到**：它在 `unverified/` 而非 `verified/`，而 `get_charts_for_country()` 默认只扫 `verified/`。
>
> **为什么它没被 verify**（R5 读文件结构判断）：**82 个节点全部平铺在 `tree` 顶层，且每个节点的 `root_type` 均为空**。而 `create_charts()`（`chart_of_accounts.py:20-66`）对顶层节点做 `root_account=True` 处理——`root_type = child.get("root_type")` 取到 `None`，`parent_account` 也是 `None`。于是导进来的是 **82 棵各自为根、且无 `root_type` 的孤树**，而不是一棵挂在资产/负债/权益/收入/费用五个根下的树。
>
> 对比 `verified/standard_chart_of_accounts.py`：它只有 **5 个顶层节点**，各带 `root_type`（`Asset` / `Liability` / `Equity` / `Income` / `Expense`，R5 实测），94 个节点挂在其下。
>
> **后果**：`root_type` 为空会让报表归类失效——`report_type` 由它推出（同文件第 39-43 行：在 `Asset`/`Liability`/`Equity` 里则为 `Balance Sheet`，否则 `Profit and Loss`），空值会全部落到「损益表」。而 `Account.validate_root_details()`（`account.py:242-250`）要求"无父科目者必须是 group"，这 82 个叶子节点作为根会被拦——导入时靠 `account.flags.ignore_mandatory = True`（第 58 行，`root_account or allow_unverified_charts` 时置位）绕过校验，于是数据能进库但语义是坏的。
>
> **这对第 ② 阶段（做中国大陆通用版）是一件好消息加一件实事**：好消息是**不必从零设计中国科目表**，有一份按 2006 准则整理好的科目名清单可直接用作素材；实事是它**不能直接导**，要做的是给这 82 个节点补 `root_type`、按五大类重新组织成树、给各节点填 `account_type`（`Receivable` / `Payable` / `Stock` / `Tax` 等，当前只有「应交税费」下几个子科目带值）、再移进 `verified/`。**这是配置与数据整理工作，不是写代码**——难点在会计知识不在技术。已并入 `SH-P1S1001`。
>
> **要现在看看它导进来什么样**，可在 `bench console` 里置 `frappe.local.flags.allow_unverified_charts = True` 后新建一家测试公司，下拉里就会出现它。**别在 `华东弹簧` 上试**——科目表一经生成不可换。

**保存。** 要等几秒——后台在生成整棵科目表（95 条）、仓库树（5 个）、成本中心（2 个）和一批默认账户。

> **⚠ 税率能配 ≠ 有中国财税逻辑**（`SH-P1S1001`，本层最重要的缺口判定）。
>
> 能配的：税率数字、记到哪个科目、按什么基数算、按客户/供应商自动带出模板。
>
> **配不出来的**：增值税专用发票的开具与作废流程、金税盘/税控设备对接、进项税认证与抵扣链、销项税与开票流水的勾稽、增值税申报表格式、价税分离的凭证形态（中国发票上"金额+税额"分列且以票管税，而 ERPNext 的税是单据上的一个计算行）。
>
> **这一条是四阶段战略第 ② 阶段的主要工作面**，L4 与 L8 会各自展开一次。本层只需把"税率模板是什么"和"它不是什么"分清。

## 段② 背后的数据模型

### 导航结构本身也是数据（v16 的三张表）

把这一节放在最前面，因为**它决定你能不能找到后面所有东西**，而且它和"科目表是数据"是同一个道理——菜单不是写死在代码里的，是几十条记录。

| DocType | 本站点记录数 | 职能 |
|---|---|---|
| **`Desktop Icon`** | **36** | 首页的图标网格。`parent_icon` 指向父图标（为空＝顶层）；**`link_to` 为空＝分组图标**（点开只展开子图标，不跳页面）；`hidden=1` 则不显示；`idx` 定顺序 |
| **`Workspace Sidebar`** | **32** | **一个页面的左侧栏**。故左侧栏不是全站共用的——你点哪个图标进来，看到的就是那个 Sidebar |
| `Workspace Sidebar Item` | — | `Workspace Sidebar` 的子表。`type=Section Break` 是分节标题、`type=Link` 是可点条目，`link_to` 指向 DocType |

标准记录以 json 文件形态存在源码里：`erpnext/workspace_sidebar/*.json`（22 个，如 `accounts_setup.json`）。

> **⚠ `Workspace` 这张表（19 条）不直接渲染导航，但它是导航记录的生成源。** 它容易被误认为就是导航结构——名字最像，数量看着也合理。实情是：它的 19 条 `parent_page` **全部为空**、不构成层级，它装的是**页面内容**（快捷方式、卡片、图表）；而 `desktop_icon.py` 的 `create_desktop_icons_from_workspace()` **会遍历 `Workspace`（`public=1`、排除 `Welcome Workspace`）为每条生成一个 `Desktop Icon`**。
>
> **故两套表是"源与产物"的关系，不是"废弃与现行"**——这也是它容易误导人的根源：查 `Workspace` 能查到相关的东西，只是查不到最终呈现。
>
> **判据**：要确认某条导航路径的**实际呈现**，查 `Desktop Icon` 与 `Workspace Sidebar`；`Workspace` 只能告诉你某个工作区**可能**存在。
>
> **这个混淆有代价**：R6 第一次给出的点击路径就是照 `Workspace` + `Workspace Link` 推的，整条路径全错（推出"左侧栏有 19 个工作区平铺"，而实际首页连左侧栏都没有）。

> **⚠⚠ 查导航必须两层都查：数据层 + 渲染层。** R6 连续三次判错导航（工作区平铺、首页顶层 7 个、图标与选项卡混淆），**三次的共同错法都是"查到一张表就直接推界面"**。数据层的条数与界面显示数经过滤后普遍不等——本例 `Desktop Icon` 36 条、顶层 9 条、实际显示更多，三个数字没有一个相同。
>
> | 层 | 查什么 |
> |---|---|
> | 数据层 | `Desktop Icon` / `Workspace Sidebar` 的记录、DocType meta 的 `Tab Break` |
> | **渲染层** | `boot.py` 的 `get_sidebar_items()`、`desktop_icon.py:170-210` 的 `get_desktop_icons()` 过滤、`list_view.js` 的视图选择 |

**改导航的三条路**（弹簧厂将来做客户演示时会用到——把用不到的模块藏掉、把常用的提到首页）：

| 改法 | 做什么 | 代价 |
|---|---|---|
| **A 改记录** | `Desktop Icon` 与 `Workspace Sidebar` 都有界面可直接编辑：调 `idx` 改顺序、设 `hidden` 藏掉、改 `parent_icon` 换分组 | 零代码。**但 `standard=1` 的记录改动是否会在 `bench migrate` 时被 json 同步回覆盖，未实测**——这是本层留给后续轮次的待查项 |
| **B 自有 app 出 fixtures** | 在自有 app 里放 `workspace_sidebar/*.json`，后装覆盖先装 | 与翻译改造的 B 路径同构（`SH-P1S1004`）。可进版本管理、换机器不丢 |
| **C 只补译名** | 上面那三个坑（`Accounts Setup` 未译、`Setup`/`Settings` 撞名、`Opening & Closing` 误译）本质是翻译问题 | **最低成本、收益最直接**，已在 `SH-P1S1004` 的 A+B 路径内 |

**判定**：导航结构**原生可配、不需二开**（A/B 都不改源码）。缺的只是译名，走 C。

### `Company`：多组织隔离的轴，也是默认值的仓库

- **`company` 是几乎所有业务 DocType 的必填字段**——`Purchase Order` / `Sales Order` / `Work Order` / `Stock Entry` / `BOM` 的 `reqd` 清单里全有（R3 逐个查证）。
- **`Company` 上有 30 多个 `Link` 到 `Account` 的字段**（R5 实测，含 `default_receivable_account` / `default_payable_account` / `round_off_account` / `write_off_account` / `exchange_gain_loss_account` / `stock_received_but_not_billed` / `expenses_added_to_stock_account` / `accumulated_depreciation_account` 等）。**理解这一点就理解了 ERPNext 的记账模型**：单据本身不知道该记哪个科目，它去问三个地方——

  ```
  单据行上手填的科目            ← 最具体，覆盖下面两级
      ↑ 取不到则问
  Item.item_defaults 子表      ← 按公司分的物料级默认（L1 段②展开）
      ↑ 取不到则问
  Company 上的默认科目字段      ← 兜底
  ```

  **三级取值链，越靠前越具体。** 排查"这笔为什么记到了这个科目"时按这个顺序倒查。
- **`is_group` + `parent_company`**：Company 自己也是树，多公司集团用它做合并报表。本项目按 DEC-016 走**一客户一 Site、每 Site 一家公司**，故这两个字段用不上。
- **`enable_item_wise_inventory_account`**：开了可按**物料**而非按仓库分库存科目，实现在 `stock_controller.py:256` 的 `get_item_wise_inventory_account_map()`。弹簧厂用不上，但它说明"库存科目从哪来"在 ERPNext 里是可切换策略。

### `Account`：科目表是数据，不是配置

- **树形 DocType**（`is_tree=1`、`default_view='Tree'`、`nsm_parent_field='parent_account'`，R5 实测），靠 `parent_account` + `lft`/`rgt` 维护 nested set。
- **`autoname` 不是简单的 `field:`**，而是 `account.py:102-105` 调 `get_autoname_with_number(account_number, account_name, company)`——主键形如 `[编号 - ]名称 - 缩写`。**故科目编号是主键的一部分**。这对中国厂很要紧：中国准则用 1001/1002/1403/2202 这套编号体系，而 `Standard` 模板生成的科目**没有编号**（`account_number` 为空）。要上编号体系得逐条补 `account_number`，补完主键会变（触发 rename）。
- **五个 `root_type`**（R5 读模板 + R6 运行态实测）：`Asset` / `Liability` / `Equity` / `Income` / `Expense`。`report_type`（`Balance Sheet` / `Profit and Loss`）由它推出，规则在 `chart_of_accounts.py:39-43`。**改错 `root_type` 会让科目出现在错的报表上**，这是 L8 排查报表问题的第一个检查点。

  **界面上这五个根的中文名是**（R6 实测，**别照英文找**）：

  | 中文名 | root_type | report_type |
  |---|---|---|
  | **`资金(资产)使用 - HDS`** | `Asset` | Balance Sheet |
  | **`资金来源（负债） - HDS`** | `Liability` | Balance Sheet |
  | `权益 - HDS` | `Equity` | Balance Sheet |
  | `收入 - HDS` | `Income` | Profit and Loss |
  | `费用 - HDS` | `Expense` | Profit and Loss |

  **⚠ 前两个的译名很反直觉**：英文原名是 `Application of Funds (Assets)` 与 `Source of Funds (Liabilities)`，用的是"资金运用 / 资金来源"这套旧式平衡表术语，**不是通行的"资产 / 负债"**。所以**在科目树上找不到叫"资产"的根**——它叫「资金(资产)使用」。另注两者**一个用半角括号、一个用全角括号**，搜索时尤其容易落空。并入 `SH-P1S1004`。
- **`account_type` 是 34 个取值的 Select**（R5 实测全列表），它不是分类标签而是**功能开关**：

  | account_type | 谁按类型找它 |
  |---|---|
  | `Receivable` / `Payable` | 应收应付单据（客户/供应商的往来科目只认这两类） |
  | `Stock` | 库存模块的估值科目 |
  | `Stock Adjustment` | 盘盈盘亏、估值重算的差额落点 |
  | `Stock Received But Not Billed` | 已收货未开票的暂估科目 |
  | `Expenses Included In Valuation` | 计入库存估值的费用（L5 完工入库那 11 行填的就是这类） |
  | `Tax` | 税率模板的 `account_head` 只列这类 |
  | `Round Off` | 单据尾差 |
  | `Cost of Goods Sold` | 销货成本 |

  **填错 `account_type` 的典型症状是"下拉里找不到这个科目"**——不是权限问题，是类型不匹配被筛掉了。
- **五条关键校验**（`account.py`，R5 实测行号）：

  | 校验 | 位置 | 报什么 |
  |---|---|---|
  | 父科目必须是 group、必须同公司、不能是自己 | `:139-160` | `Parent account {0} can not be a ledger` 等 |
  | 根科目不可编辑；无父科目者必须是 group | `:242-250` | `Root cannot be edited.` / `The root account {0} must be a group` |
  | 有交易的科目不能转成明细科目；有子节点的不能转成明细 | `:298-310` | `Account with existing transaction cannot be converted to ledger` |
  | group 不能带 `account_type` | `:305-307` | `Cannot covert to Group because Account Type is selected.` |
  | 已被设为公司默认值的科目不能停用 | `:311-320` | `Account {0} cannot be disabled as it is already set as {1} for {2}.` |

  **`validate_parent_child_account_type()`（`:125-137`）有一条容易撞的**：`Direct Income` / `Indirect Income` / `Current Asset` / `Current Liability` / `Direct Expense` / `Indirect Expense` 这六个类型，**父子不能同类型**，报 `Only Parent can be of type {0}`。建中国科目表时按"流动资产 → 存货 → 原材料"嵌套就可能撞上。
- **科目表可以随意改**——它是几百条 `Account` 记录而非硬编码。这是"科目表是数据"这句话的实际含义，也是中国本地化改造**属配置而非二开**的依据。

### `Warehouse`：数量与金额的落点

- 树形 DocType，`parent_warehouse` + `lft`/`rgt`。**只有叶子节点能存货**——往 `is_group=1` 的仓库做库存动作会被拒。
- **`lft`/`rgt` 有空洞不等于树坏了**。建删节点后 nested set 不一定重建（R3 事后复核时根节点 `rgt=16`、12-15 是空洞），树仍完全可用。别把"编号连续"当健康判据。
- **`Warehouse` 有 `company` 字段，而 `Item` / `Customer` / `Supplier` 没有**（R3 查证：三个 json 里 `"fieldname": "company"` 计数均为 0）。这个不对称是理解 ERPNext 数据模型的关键点：

  > **"东西是什么"全公司共享，"东西在哪、值多少钱"按公司分。**

  **DEC-016 正由此而来**——用 Company 隔离不同客户会导致 Item / Customer / Supplier 跨客户可见，构成数据泄露。故多客户部署走一客户一 Site。
- **`Warehouse.account`** 决定该仓库的库存金额记到哪个科目。留空则用公司的 `default_inventory_account`。段④缺口三讲留空的代价。
- **`Warehouse Type`** 当前只有 `Transit` 一条。它是被 Putaway Rule、在途调拨引用的分类标签。场景 F5（寄售/VMI）判 ⚠ 时提到"或许能用 Warehouse Type + 客户仓变通"——那条待验，属 L3/L4。

### `Fiscal Year` / `Cost Center` / `UOM` / `Price List`

- **`Fiscal Year`**：`autoname` 为 `field:year`（R5 实测），无 `company` 字段但有 `companies` 子表限定适用范围；`is_short_year` 支持短会计年度；`auto_created` 标记系统自动建的那些。
- **`Cost Center`**：树形，`autoname` 同 `Account` 走编号+名称+缩写，`cost_center_number` 是编号位。它与科目**正交**——科目答"这是什么费用"，成本中心答"这笔费用归谁"。
- **`UOM`**：全局主数据，不挂公司。`must_be_whole_number` 会在多处触发整数校验（`Nos` 是 1、`Kg` 是 0，R3 实测）。
- **两张换算表别搞混**：

  | DocType | 管什么 | 关键字段 |
  |---|---|---|
  | `UOM Conversion Factor` | 全局量纲换算（kg↔g） | `category`（必填）、`from_uom`、`to_uom`、`value` |
  | `UOM Conversion Detail` | **某个 Item 的**多单位换算，是 `Item.uoms` 子表 | `uom`、`conversion_factor`（就这两个字段，R5 实测） |

  前者是物理常数，后者是产品属性。弹簧的 kg↔支 属后者。

## 段③ 弹簧厂在这一层的场景

**R1 的 11 层表给 L0 的「挂哪些场景」是空的**——52 场景里没有一个直接落在 L0。这不是遗漏：L0 建的是骨架，它**不解决任何业务问题，但每个业务场景都踩在它上面**。

具体的踩踏关系（本层新增，R1 表里没有）：

| L0 建的东西 | 哪些场景靠它 | 不建好的症状 |
|---|---|---|
| 科目表结构 | H1 标准成本vs实际、H5 增值税专票、H6 存货核算与月结、H7 银行对账 | 科目太粗则"不知道哪个品亏"（H1 的乱象原文）；无税种子科目则专票无处记 |
| 各仓库分挂科目 | D3 在制品盘点、F2 半成品仓、H6 存货核算 | WIP 在总账上零痕迹（见段④缺口三） |
| 成本中心树 | H3 工序成本与机时费率、I2 设备利用率 | 费用摊不到车间，机时费率算不出分母 |
| UOM 与换算 | B2 BOM 线材kg→成品支、F3 成品仓多层单位（支/盒/箱） | 单支耗料无从落地 |
| 价目表分层 | A4 客户专属价与钢价联动、A5 框架订单、B5 打样 | 改价靠 Excel、改漏（A4 的乱象原文） |
| 财年 | H6 月结与期间关账 | 期间无边界，关不了账 |
| 税率模板 | H5 增值税专票/金税 | 见段④缺口四 |

**弹簧厂在这一层唯一真正需要动脑的建模决定是 kg↔支 换算**，它是 R1 给 L0 标的两个痛点之一。具体算法在 L1（它是 Item 的属性），本层只需知道：**ERPNext 提供了正确的机制（`Item.uoms`），但换算系数得你自己算出来填**——ERPNext 不知道弹簧的展开长度公式。

**规模档位的影响**（DEC-005 主线 B 档 50-150 人）：L0 的内容对 A/B/C 三档**几乎没有差别**。科目表、仓库树、UOM 这些不随厂大小变。唯一会变的是成本中心树的细度——A 档（小微 <50 人）可能只要一个「生产」，C 档（中型多厂区）要按车间甚至按机台分组。这也是本层不急着建成本中心的理由。

**产品族差异**（DEC-004 主线冷卷圆簧）：L0 对 A/B/C 三类产品族**无差别**。B 类（异形线成型）与 C 类（板簧碟簧冲压）的差异落在 L1 物料规格与 L2 工程数据，本层的骨架三类共用。

## 段④ 这一层的痛点与原生缺口

R1 给 L0 标了两个痛点：「**无中国科目表**」与「**kg↔支 换算要设计**」。R5 复查后各有修正，另补出两条 R1 没标的。

### 缺口一：无中国科目表 → **修正为"有一份但不可用"**

**R1 的表述**（据 `ls erpnext/regional/` 无 china 推出）：ERPNext 无中国本地化，故无中国科目表。

**R5 实测修正**：`regional/` 确实无 china（这一半成立），**但科目表模板不住在 `regional/`**——它们在 `accounts/doctype/account/chart_of_accounts/{verified,unverified}/`。而 `unverified/cn_l10n_chart_china.json` **存在**，82 个一级节点、按 2006 年《企业会计准则》整理、含 11 个税种子科目。

**为什么仍算缺口**：它选不到（`get_charts_for_country()` 只扫 `verified/`）、且直接导会坏（全部节点 `root_type` 为空、无五大类根，导入靠 `ignore_mandatory` 绕过校验，进库后语义是坏的）。

**缺口的真实形状变了**：不是"从零设计一套中国科目表"（要会计从头做），而是"**把一份现成的科目名清单补全成可导的树**"——补 `root_type`、按五大类重组、填 `account_type`、补 `account_number`（中国的 1001/1403 编号体系）、移进 `verified/`。**工作量显著小于 R1 的隐含估计，但仍需懂中国准则的会计参与。**

**这是 LG-021 那条教训的第二个应验实例**——R1 的 ⚠ 判定系"grep/ls 未找到即推定缺口"，而实际查下去往往"原生有、只是不在你找的地方"。R1 复核建议预警的风险再次成立。

**处置**：并入 `SH-P1S1001`，并**把这条实测结论回填项目概况**——概况现在写的是"ERPNext v16 无中国本地化"，该补上"科目表模板有一份 unverified 的中国版"，否则第 ② 阶段开工时会重复做一遍从零设计。

### 缺口二：kg↔支 换算要设计 → **判定维持，归 L1 落地**

原生机制完备（`Item.uoms` 子表正是为此设计），缺的是**换算系数的来源**——展开长度公式要人算。这属 Item 属性，L1 段①展开。

**本层要点明的是它的反面**：新手会想去 `UOM Conversion Factor` 加 `Kg → 支`，那张表的 `category` 必填会把你挡住。R3 实测 235 条全带 `category`，证明它的设计意图确是量纲换算。**这是一处"原生用对了机制但命名容易误导"的例子，不是缺陷。**

### 缺口三（R5 新增）：各仓库不分挂科目，WIP 在总账上零痕迹

**现象**（R3 实测）：领料（原料仓 → WIP 仓）时，两仓都用公司的 `default_inventory_account`（`存货 - HDS`），借贷完全抵消，**ERPNext 干脆一行分录都不写**。总账上完全看不出料进了车间。

**这不是 bug**——借贷同科目同金额，不记是对的。**问题在配置**：`Warehouse.account` 全部留空。

**正确结构**（R3 第 24 步用户提出，判断成立）：`Account` 是树形且**报表按树汇总**，故用子科目 + 父科目：

```
存货（is_group=1，不能直接记账）
├── 原材料 - HDS      ← 仓库 - HDS 的 account
├── 在产品 - HDS      ← 进行中 - HDS 的 account
├── 库存商品 - HDS    ← 成品 - HDS 的 account
└── 废料 - HDS        ← 废料 - HDS 的 account
```

**收益**：资产负债表「存货」一行显示总数（自动汇总）、点开见各类明细、每个数都能追到具体仓库的库存流水。

**而这恰好对上中国准则的存货类科目结构**（1403 原材料 / 生产成本 / 1405 库存商品），故它同时是中国本地化的一个具体入手点。

**操作顺序有个坑**：把现有的「存货」科目转成 group 时，若它已带 `account_type='Stock'`，`account.py:305-307` 会报 `Cannot covert to Group because Account Type is selected.`——**要先清掉 `account_type` 再转 group**。且它已被设为公司的 `default_inventory_account`，`:311-320` 那条校验还会拦停用操作。〔这两条是 R5 读校验代码推出的操作顺序，**未实测**〕

**判定**：🔧 **需培训与流程改造，不需二开**。原生机制齐备（`Warehouse.account` 字段在、报表按树汇总在），缺的是有人把这四个子科目建出来并挂上去。**与中国科目表改造同批做**，已并入 `SH-P1S1001`。

### 缺口四（R5 新增）：税率能配，中国财税链缺失

见段①第十一步的 ⚠ 框。能配的是税率数字与记账科目，配不出的是专票流程、金税对接、进项抵扣链、申报格式、价税分离凭证形态。

**判定**：⚠ **需二开**，对应场景 H5（R1 已判 ⚠）。这是四阶段战略第 ② 阶段的主要工作面，L4 与 L8 各展开一次。本层只承接"税率模板是什么"这一小段。

## 附注：搜索框的两个坑

本层的操作路径一律走点击（见「怎么读本层」），**不依赖搜索**。但熟练之后搜索框仍是最快的入口，而它有两个坑会让你以为"这个功能不存在"。两条都并入 `SH-P1S1004`。

**坑一：搜含空格的英文原名会返回空。** 搜 `Fiscal Year` 得到空结果——**不是搜不到，是那一路根本没去查**。`awesome_bar.js:176-179`：输入含空格时，**空格后的词被当作类型过滤词**，而它只认 `List` / `Tree` / `Report` / `New` 四个。`Year` 不匹配任何类型，故该路返回空。

**办法：搜不带空格的片段。** 搜 `Fiscal` 即出。

**坑二（其实是个救命机制，别误判为坑）：中文界面下搜英文原名是可行的。** `search_utils.js:595-602` 的 `fuzzy_search` 先按译名匹配，**得分为 0 且界面非英文时，自动回退用英文原名再匹配一次**（R4 已在容器内构建产物 `desk.bundle.*.js` 里验证该逻辑已编译进前端）。故译名想不起来时打英文是有效的——**只要不带空格**。

两坑叠起来的实际后果：`Fiscal Year` 这种"译名不直观（财年）+ 英文原名带空格"的对象最难搜。这正是本层改走点击路径的一个附带收益。
