### LG-050 实测过程与结论

**实测方法**（依 FD-41 给的验证办法）：建 PO 10 kg @ 7.5（75 元）→ 采购入库 → 开票时改单价为 7.8（78 元）→ 查 `GL Entry`。

**第一层发现：默认设置下这情形根本发生不了，有两道独立拦截。**

| 拦截 | 设置项 | 默认值 | 报什么 |
|---|---|---|---|
| 单价必须一致 | `Buying Settings.maintain_same_rate` | **1（开）** | `Row #1: Rate must be same as Purchase Order: xxx (7.8 / 7.5)`，且对 PO 与 PR 各报一条 |
| 超额开票不许 | `Accounts Settings.over_billing_allowance` | **0** | `This document is over limit by Amount 3.0 for item xxx`（`OverAllowanceError`） |

`maintain_same_rate_action` 默认为 **`Stop`**（不是 Warn）、`role_to_override_stop_action` 为空，故**没有任何角色能绕过**。校验在 `accounts_controller.py:953-980` 的 `validate_line_items`，容差 0.01。

**第二层发现：把两道拦截都关掉之后，实际分录里没有价差科目。**

```
借  暂估库存(已收货，未开票) - HDS   78.0     ← 按发票全额，不是 75
贷  应付账款 1 - HDS                78.0
Stock Ledger Entry：0 条（库存估值不动，仍 7.5）
```

**差额 3 元残留在暂估库存科目里，净额 +3，没有任何科目去冲它**（实测该科目净额从 0 变为 3.0；`库存调整 - HDS` 未动）。

**故结论是：ERPNext 不自动处理采购价差，它靠"不许不一致"来回避这个问题。** R3 记录里那三行分录（含"借价差 30"）**是虚构的形态，站点里不会出现**。

**已写进操作稿环节 10**，并明确标出两件未实测的事：Landed Cost Voucher 那条路怎么走、中国厂的正确做法是哪条——**留给第 ② 阶段实测，不在教材里写成确定结论。**

**清理与还原**：三张单据全部取消，两个设置恢复原值，科目净额已核回 R3 终态（存货 424.5 / 暂估库存 0 / 应付 0 / 应收 0 / 销货成本 325.77 / 销售 −1045 / 现金 295），「库存与账务价值对比」报表 0 行。

### LG-051 查清成因并闭合（本轮追加，非原定范围）

**原状态**：R3 忠实度报告 FD-43 记为「待观察」——`Bin.stock_value` 为 424.43，与自身 `qty × rate`（56.6 × 7.5 = 424.5）差 0.07，归因写的是"已取消的 `MAT-STE-2026-00002` 未在 Bin 回滚"。

**R4 又撞上一次且幅度更大**：做 LG-050 实测并取消三张单据后，该字段变成 **499.5**（差 75）。据此我原以为"取消不回滚、误差会累积"，准备升级定性。**查下去发现归因错了。**

**真实成因**（`stock_ledger.py:604-610`）：

```python
if self.args.get("sle_id"):
    self.process_sle_against_current_timestamp()
    if not future_sle_exists(self.args):
        self.update_bin()          # ← 只有"没有更晚的流水"时才即时刷新 Bin
```

**存在更晚的库存流水时即跳过即时更新**，改为建 `Repost Item Valuation` 记录交后台重算。**这是正确设计**——插一笔历史单据会改变 FIFO 队列、其后每笔估值都要重算，同步做会卡死页面。

**实测证据**：站点里积压 **三条 `Queued` 状态的 `Repost Item Valuation`**——两条是 **R3 那天（09-21 00:18）** 留下的、一条是 R4 的。**故 R3 那 0.07 与 R4 那 75 是同一个成因，不是两个独立现象，也与"取消"无关**（取消只是恰好生成了更晚的流水）。

**为什么任务没跑**：repost 走 `scheduler_events` 的 cron（每 15 分钟一次 `run_parallel_reposting`，`erpnext/hooks.py:436`），而调度器要 `docker/start.sh` 在跑才触发（`Procfile` 的 `schedule` 与 `worker` 两个进程，已核对）。**这与 LG-011（清场走后台队列）是同一个前提条件。**

**影响评估**（用户问"生产环境有无影响"）：

| 维度 | 结论 |
|---|---|
| 报表 | **无影响**——「库存与账务价值对比」等报表读 SLE 不读 `Bin` |
| 数量 | **无影响**——`Bin.actual_qty` 始终正确（56.6 ✅），滞后的只有 `stock_value` |
| 自愈 | **会自愈**——`bin.py:40-71` 的 `recalculate_values()` 直接从最后一条 SLE 重读该字段，任务跑完即修正 |
| 生产环境 | **残差是暂态的**，调度器正常时滞后 ≤15 分钟。真正要监控的是"调度器有没有挂"，那属运维范畴（挂了则所有定时任务都停），不是本条的问题 |
| 唯一困惑场景 | **绕过报表直接查 `Bin` 表**（自己写 SQL 或做自定义报表） |

**处置：直接闭合，不改代码、不入延迟需求登记册。** 理由——上游逻辑正确（条件判断、repost 机制、自愈方法俱在），要做的是环境层面的提示，与 LG-011 同类（LG-011 的处置也是"写进操作稿判据 + 记进排查手册"，未入登记册）。

**落两处**：① 操作稿环节 23 那段改写（贴源码、说清成因与影响边界、区分开发/生产环境的处理）；② 环节 12 新增贯穿性前提框，列出本稿三处依赖后台任务的地方（环节 0 清场、环节 12/23 的 `Bin` 重算、环节 12 的 `prepared_report`）。

## 复核建议

### 1. 最该先看的：LG-050 那段实测结论（本轮唯一改变判断方向的改动）

**风险最大的地方在于它推翻了一条已被写成确定结论的内容**，而我做的是"关掉两个默认校验后观察"——**这个实验条件本身不是默认状态**。

**具体怎么核**：
- 打开 [最小闭环操作稿.md](../0-P1-S1文档/最小闭环操作稿.md) 环节 10 那个"关于发票价与收货价不一致"的 ⚠ 框；
- 核第一层（两道拦截）：`Buying Settings.maintain_same_rate` 与 `Accounts Settings.over_billing_allowance` 现在应已恢复为 **1** 与 **0**，可直接在界面上看；校验代码在 `accounts_controller.py:953-980`；
- 核第二层（分录形态）：这一段是**关掉校验后**的观察，**站点上已无该实验的痕迹**（三张单据都取消了）。若要复现，照框里给的方法重跑一遍。

**我拿不准的**：`maintain_same_rate=0` 是不是真实工厂会用的配置。若中国厂普遍要关它（钢价波动时供应商按开票日价格开票很常见），那么"差额残留在暂估库存、无人冲"就是个**每月都会发生的实际问题**，而不是一个理论边界——**这个判断我没有依据下**，已在环节 10 写明"哪条是中国厂的正确做法，须到第 ② 阶段实测后再写进教材"。

### 2. 第二该看的：环节 1 第六步那个"提前"

我把两件事从原位置提到了环节 1：三个默认仓库（原在环节 17）、`expenses_added_to_stock_account`（原本稿子里没有，R3 只在第 32 步提到"建议去设"）。

**理由是照原位置走已经太晚**——工单建出来时仓库字段就是空的、完工入库单一保存就被 11 行必填拦住。

**但这改了稿子的教学顺序**：环节 1 现在有八步，比 v1 长一倍，而其中两步（默认仓库、库存费用科目）的意义在环节 17/20 才显现。**读到环节 1 的人不知道自己为什么要填这些。** 我在每一项后面写了"不填的后果"并指向对应环节，但这是个折中。

**怎么核**：从头读环节 1 一遍，判断"八步 + 两处前向引用"是否比"到环节 17/20 现场补"更好。**若判断该退回原位置，只需把第六步那张表移回环节 17 与环节 20，其余不动。**

### 3. 第三该看的：双列数值有没有互相污染

三处双列（环节 19/20/23）的"认真报工时应为"一列是**算出来的、不是实测的**：433.3（工序成本）、0.1598（单价）、758.83（成本）、27.4%（毛利率）、286.17（毛利）。

**算法**：104 分钟/1000支 × 5 批 ÷ 60 × 50 元/小时 = 433.33；325.5 + 433.33 = 758.83；758.83 ÷ 4750 = 0.1598；(1045 − 758.83) ÷ 1045 = 27.4%。

**怎么核**：对着这四步算一遍。**尤其核 4750 这个分母**——它来自 BOM 工艺损耗（5000 × 95%），与环节 19 手填的 150 废品**无关**（两套机制，我在环节 19 那一步专门加了提示）。若这两个数该相加，那么整列都要重算。

### 4. 拿不准处

- **8 条上游缺陷的 ⚠ 框会不会太长。** 裁决是"写进对应环节，就地提示"，我照做了，但环节 18、19 各有四到五个 ⚠ 框，**读起来像"这软件到处是坑"而不像操作稿**。环节 19 尤其重（六个框）。我保留了全部，因为每条都有"照稿子走会遇到"的实际价值，**但这一节的可读性我判不准，可能该把纯背景性的两三条（LG-040 工序间数量、LG-029 空行成因）移到「留给 L0-L10 的账」**。
