## 二、初始目的

**需求怎么来的**。本项目的四阶段战略第 ② 阶段是「做中国大陆通用版」，而 ERPNext v16 **没有中国本地化**：`erpnext/regional/` 只有六国、没有 china；唯一一份中国科目表在 `unverified/` 里选不到、82 个节点 `root_type` 全空、内容停在 2006 年准则；增值税月末处理、中国格式三张报表全都没有。P1 被重定向为「在客户面前跑通整个流程」后，S2 的需求图谱把财税定为四条核心需求：**CR-014** 并入 zelin 财税模块、**CR-005** 中国科目表、**CR-006** 增值税逻辑、**CR-007** 三表＋月末结转＋银行对账。路线文档把这四条放进同一个 Stage（S4），目标是「中国会计准则的账与表一次做完，zelin 源码只并入一次」。

**用户的原始表述与三次方向性要求**（S4 的 A 步里定下，决定了本文件的形态）：

1. **整段替换可以接受**（R1 第 3 步议题 ④）：「原生的规则如果不适用于中国的话，实际上没有太大用处，我的客户基本上都是中国客户」——必要时可借 hook 或其它非侵入机制把 ERPNext 的某个阶段整段换成中国规则；非侵入做不到的，也要给出侵入方案供其评估。
2. **不照抄 zelin，按官方规范构建**（R1 第 6 步议题 ⑤）：zelin 的代码「只作为一种思路参考」，结合财政部等官方规范「按照标准的方式去构建报表逻辑」。调查结果把 zelin 拆成三层——数据层（科目表、税模板）已实测可信；报表层可用但列形态不合规；约 600 行胶水层集中了已知的全部缺陷。
3. **列头逐字合规**（R3 第 12 步议题 ①）：报表列头以逐字合规为准。

**要解决的核心问题**：让客户的会计看到一套**账务口径可信**的中国账——科目名是熟悉的、税是按中国规则算的、三张法定报表的格式与数字经得起追问——且这套东西**不改 ERPNext 与 Frappe 的源码**、将来可被别的中国项目复用。

**本 Stage 不做的**（边界）：开票接口与金税对接（用户裁决出 P1 范围，需求图谱 §3.2）；现金流量表的间接法附表（`SH-P1S4001`）；两套准则报表并存（RL-02，客户正式部署前须回头问定）；弹簧行业明细科目（`SH-P1S4003`）；单号格式与界面调整（`SH-P1S4004`）；中文大写金额打印（`SH-P1S4005`）；企业所得税计提（LG-143）；小规模纳税人的账务处理（LG-150）。

### 4.7 月末结转（TS-011，DEC-099：账结法）

#### 4.7.1 每月三张凭证，按序生成

一次操作为指定公司、指定月份按下列顺序生成三张 Journal Entry：

**① 增值税结转**（规则依财会〔2016〕22 号，BR-004）

取「应交增值税」（`2221000` 组，含 `2221001`…`2221010` 十个专栏）截至月末、本张凭证之前的余额：

| 余额情形 | 分录 | 结果 |
|---|---|---|
| 贷方余额（当月应交未交） | 借 `2221003 转出未交增值税` 贷 `2221020 未交增值税` | `2221000` 组余额归零 |
| 借方余额，且本月 `2221002 已交税金` 有发生额 | 多交部分（取借方余额与本月已交税金二者较小者）：借 `2221020 未交增值税` 贷 `2221009 转出多交增值税` | 其余借方余额视为留抵 |
| 借方余额（留抵） | **不生成分录** | 借方余额留在应交增值税下，下月继续抵扣 |

- **进项税额转出**（`2221007`）本身由业务事件触发（非正常损失、用于免税项目等），**以手工凭证录入，本 Stage 不自动生成**；月末结转的余额计算自然包含它（⚠ 本条是按会计实务推定，见回执）。
- 预交增值税（`2221011`）等其余明细科目不在结转范围。

**② 附加税计提**（BR-005）

- **计税依据**：本月应纳增值税额 ＝ ① 的结转额（贷方情形）＋本月已交税金；本项目无消费税。留抵月份为 0，不生成凭证。
- **税费率**：城市维护建设税按公司所在地——市区 7%／县城与镇 5%／其它 1%；教育费附加 3%；地方教育附加 2%。**城建税档位须能按公司设定**（存放形态留 C 步）；演示公司暂按市区 7%，**待客户确认**（LG-144）。
- **分录**：借 `5403 税金及附加` 贷 `2221040 应交城市维护建设税`／`2221110 应交教育费附加`／`2221150 应交地方教育费附加`。
- 小规模纳税人与「六税两费」减征**不处理**（LG-150）。

**③ 损益结转**

- 把全部 `root_type` 为 Income 与 Expense 的明细科目本月发生额净额结转到 `3103 本年利润`，使这些科目月末余额为 0。成本类科目（`4001`／`4101` 等，`root_type = Asset`）**不结转**。
- 须排在 ②之后（② 产生的税金及附加要被一并结转）。

#### 4.7.2 年末

12 月的三张凭证之后，再生成一张：把 `3103 本年利润` 的余额转入 `3104090 利润分配—未分配利润`，使本年利润余额为 0。**不使用原生期末结账单**（`Period Closing Voucher` 只能按整个会计年度结、且会产生本 Stage 不需要的结转分录；R3 V-27 已证其对报表期初无帮助）——故 LG-138（非 legacy 结账路径未经实测）不在本 Stage 的执行路径上。利润分配各明细（提取盈余公积、应付利润等）的结转**不自动化**，由手工凭证处理。

#### 4.7.3 生成的约束

1. **不重复**：同一公司同一月份已有已提交的结转凭证时，拒绝再次生成并提示先取消。
2. **可重做**：取消某月结转须按 ③→②→① 的逆序整体取消；之后可重新生成。
3. **单据未完先提醒**：生成前若该月仍有未提交（草稿）的记账类单据，给出提示（是否阻止留 C 步定）。
4. **结转后又有新单据进该月**：该月结转已不完整，须在出表时明确提示（形态留 C 步定），不得静默输出。

#### 4.7.4 结转凭证可被机械识别

四类结转凭证（增值税结转、附加税计提、损益结转、年末本年利润结转）**须能被机械识别**（标记方式留 C 步定），因为：

- **利润表取数必须排除损益结转凭证与年末本年利润结转凭证**（及任何原生 `Period Closing Voucher` 的分录）。不排除，则从结转那一刻起利润表本月损益类发生额被冲成 0（RS-007）。
- 增值税结转与附加税计提是真实的经济业务，**不排除**。

### 4.11 三张报表的共同要求

1. **列头逐字合规**（DEC-087／DEC-096）：屏幕、XLSX 导出、PDF 打印三处的列头与法定格式逐字一致。**报表层保证的是字串**；人眼所见另依赖两件环境事项：容器装中文字体（TS-002）、译名词典不把中文列头当键替换（LG-134，S6 的 CR-002 须遵守）。
2. **在 `zh` 会话下验收**：探针与测试进程的 `frappe.local.lang` 默认是 `en`，不显式设会得到偏乐观的结论（R3 V-31）。
3. **不启用 Prepared Report**：该模式下屏幕列头也经 `_()`（`query_report.py:376`），且 `report.py:186-198` 会在报表跑满 15 秒时自动把它打开（LG-136）。
4. **不静默出 0**：某一行的取数规则命中零个科目时报错（区别于「命中了科目、余额恰为 0」）。原生引擎在这种情况下静默返回 0（R1 己案、R3 V-30），自写须避免。
5. **漏科目检查**：列出有余额或有发生额、却不被任何报表行覆盖的明细科目（zelin `bs_and_pl_missing_account` 的思路，按本 Stage 的映射重写）。在演示公司上结果须为空。
6. **逐行验收清单**：TS-003 核准的填列说明同时是 E 步逐行核对的清单。
7. **不用 zelin 的两对 Settings DocType**（资产负债表 Settings、利润表 Settings）：它们服务于不抄的那两张报表。「行 ← 科目」映射放在代码常量、数据文件还是自有 DocType，留 C 步定（⚠ 本条由不抄报表推出，见回执）。

  3. **列序对齐**——`Bank Transaction Mapping` 子表**从不被读取**（写入端以表头为键、读取端 `importer.py:879` 以列序号取值），能导进去靠的是文件列序与目标字段顺序一致；
  4. **每次导入后复位银行的映射表**——`update_mapping_db()` 每次导入都先删光再重建，并把陈旧键带回（`:315-324`）；
  5. **余额列不映射**——`Bank Transaction` 无余额字段，映到 Link 字段会静默失败。
- **业务约束**：**收付款凭证的 `reference_no` 必须与银行流水的流水号完全一致**，自动核销才可能命中——自动模式下它是硬条件（`bank_reconciliation_tool.py:1381-1382`），金额、日期、往来单位全对也不行（LG-129）。S7 造的演示凭证须带流水号；演示流程须讲清这一条。
- **样本**：本项目没有任何真实网银导出文件。前置处理至少要能处理一份**仿常见网银版式**的样本（带表头抬头块、合计行），真实版式到现场再调（LG-147）。

## 七、预期使用流程

**实施者（首次建站，一次性）**

1. 核两份备份完好 → 经用户确认后清站（§4.13）。
2. 跑建站脚本，还原站点级设置（国家、语言、时区、币种、日期格式等）。
3. 装 `frappe_china`：自动补中文计量单位、关闭凑整合计。
4. 建公司 `华东弹簧有限公司`（缩写 `HDTH`），国家选中国，科目表下拉选 `小企业会计准则(2024)`。
5. 跑建账结果自检，确认全部通过。

**会计（每月）**

1. **日常**：销售与采购单据按票种选税类别（如销售 13% 专票选 `P13专票含税`，运费发票选 `P9专票含税`）；物料税率走 `Item Tax Template`。收付款凭证填银行流水号。
2. **银行对账**：导出网银流水 → 经前置处理导入 → 在对账工具里跑自动对账 → 未自动核销的手工核对。
3. **特殊业务**：需转出的进项税额（非正常损失等）手工做凭证。
4. **月末结转**：选公司与月份，一次生成增值税结转、附加税计提、损益结转三张凭证。发现有误时按逆序取消后重做。
5. **现金流**：新建当月「现金流量」单据 → 取明细 → 检查并修正现金流项目代码 → 提交（下月要用它的本年累计）。
6. **出表**：资产负债表、利润表、现金流量表选公司与月份查看；导出 Excel 或打印 PDF。
7. **年末**：12 月结转之后，生成本年利润结转凭证，把全年利润转入未分配利润。

**演示者**：按演示脚本（S7）打开三张报表、展示月末结转一键生成与银行流水自动对账。

## 九、术语定义

| 术语 | 定义 |
|---|---|
| 账结法／表结法 | 损益类科目的月末处理方式。**账结法**每月把损益类科目余额结转到「本年利润」，月末损益科目余额为 0；**表结法**月内不结转，只在年末结转，月度利润由报表计算。本项目取账结法 |
| 转出未交增值税 | 「应交增值税」下的专栏，月末把当月应交未交的增值税由此转入「未交增值税」明细科目 |
| 留抵 | 当月进项大于销项，「应交增值税」呈借方余额，留待以后月份抵扣 |
| 附加税 | 城市维护建设税、教育费附加、地方教育附加的合称，以实际缴纳的增值税（与消费税）为计税依据 |
| 价税分离 | 把含税金额拆成不含税金额与税额 |
| 含税模板／未税模板 | 税模板的两种：单价已含税（系统倒算税额）与单价不含税（系统加算税额）。命名如 `P13专票含税` |
| 填列说明、分析填列 | 准则附录里对报表每一行「由哪些科目怎么算」的说明；「分析填列」指须结合科目内容判断，而非直接加总 |
| 行次 | 法定报表每行的序号，含合计行 |
| 覆盖位 `[-1]` | Frappe 多个覆盖机制取**最后安装的 app** 注册的那一项；占住该位置即锁死其它 app |
| 让位 | 借上游既有开关让原生某段逻辑整段不执行，由自有代码接替（如 `ignore_chart_of_accounts`） |
| 并入式 | 把 zelin 的源码抄进自有 app，而不是把 zelin 作为 app 安装 |
| FRT | ERPNext v16 的 `Financial Report Template`，按行配置的报表模板引擎；本 Stage 不用 |
| 静默归零 | 取数失败或取数规则命中零个科目时输出 0 而不报错，与「合法的 0」在结果上无法区分 |
| 建账结果自检 | 检查一家公司的科目表是否按预期建成的函数，由本 Stage 提供、S8G-S1 调用 |
| 清站 | 把站点清回无业务数据的状态，再建演示公司 |
