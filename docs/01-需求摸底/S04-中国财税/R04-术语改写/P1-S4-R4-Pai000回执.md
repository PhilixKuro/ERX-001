## 复核建议

### 1. 最该先看：CR-015 的判据强度有没有在改写中被悄悄放宽（风险最大）

**为什么要看**：这批词是**承载物**而非装饰——CR-015 是用户在 S2-R4 第 19 步①亲自裁决单立的核心级需求，它的判据、S5 两条完成标志、ADR-0008 的被依赖行全靠这些句子表达。改写这类句子时最容易发生的偏移不是丢信息，而是**把"必须"写软、把"两个"写成"一个"**。

**怎么查**：
```
git diff P1-S4-R4-start -- "docs/01-需求摸底/0-P1文档/需求图谱.md" "docs/01-需求摸底/0-P1文档/路线文档.md"
```
逐处对读左右两栏，只盯三件事：**① 9100 与 8000 是不是都还在**（不能只剩 8000）；**② "必须"「均」「不只是」这类强度词有没有被换掉**；③ CR-015 的**核心级分级**与"此项不成立则 CR-008／CR-009 在真实演示环境下均不成立"这句因果有没有变弱。

### 2. 第二该看：四份跨轮演进产物的版本行说的和实际改的是不是一回事

**为什么要看**：版本变更记录是此后各轮唯一的追溯入口（规范 §11.1）。**版本行写得比实际改动小**（漏记一处）会让将来查不到；**写得比实际大**（声称零结构变更但其实动了结构）更糟，因为它会让人跳过复核。

**怎么查**：`git diff --stat P1-S4-R4-start` 的逐文件行数（需求图谱 17／路线文档 21／架构文档 7／ADR-0008 2／P1-概况 6／P1-S2-概况 8）与各版本行自述的改动处数对照。**特别看架构文档 v1.1 那行**——它替 ADR-0008 兜着留痕，若那句指针不清楚，ADR-0008 的改动就成了无版本表可查的孤儿。
