3. **zelin 没做对账**（全仓零 `Journal Entry`、零对账），故这一项**与 CR-014 并入无关**——它是纯原生能力，并入与否都在。

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **甲：直接缩范围** | 银行对账改为「配一次列映射 ＋ 准备一份中文流水样本 ＋ 实测一次」，不自研匹配逻辑。估 **0.5–1 人日**（原 3–5） | 省 2.5–4.5 人日；用原生即享上游维护，不背自研债 | 若实测发现中文格式导入有坑，要在 S4 内临时补，而此刻没有预留量 |

| **丙：先派探针实测，再定范围**（推荐） | 唤起 SA 步（`附属=新Session做`、`可并行至阻塞项`），命题是「拿一份中文银行流水（xlsx/csv）经 `Bank Statement Import` ＋ `Bank Transaction Mapping` 导入并 `auto_reconcile_vouchers` 跑通」。判定回来再定甲还是乙 | 判据最硬——本项目已五次因「读码即判断」而判错（LG-021），这一条又正是靠读码得出的；**且它不阻塞**，探针跑的同时本讨论继续推进其它议题 | 多一次往返；但按 SA 的并行性不占额外 Round，成本接近零 |

**推荐丙，且预期落到甲。** 理由：这一项的结论完全建立在读码上，而本项目的记录里「读码即判断」已五次被实测推翻；代价只是并行派一次探针，而收益是 2.5–4.5 人日的范围变更有实测背书、不是又一次推定。

**用户回答：** 取**甲：直接缩范围**（未采纳推荐的丙）。

**结论：** **DEC-082 定甲案。** 银行对账不自研，改为「配一次列映射 ＋ 准备一份中文流水样本 ＋ 实测一次」：

**背景：** 三条遗留问题的触发条件全部落在本 Stage 开工，须当轮定去向（play-shape 纪律 8：事实型转探针、判断型留讨论）。

|---|---|---|---|

| **LG-080** | **中国科目表的同名父子结构会致选错科目**（小企业(2024) 2 处）。症状是「只差科目号前缀」——`11220` 是 group、`11221` 才能记账；**改译名解决不了** | 「CR-005 定科目表方案时单独处理（如给 group 层加「（汇总）」后缀）」 | **判断型** → 留讨论 |

**本步对这三条各有一点须先交代：**

1. **LG-084 的消费方已经变了，图谱那句「最要紧」按现状偏高。** 图谱写它时，CR-005～007 的覆盖判断被认为全建在 `regional_overrides` 上。但 ADR-0007 的 NV-038 已把 `regional_overrides` 路线否决——上游 18 个 `@allow_regional` 挂点**全部是交易时点**，**没有一个在建账路径上**；A 案走的是 4 个 whitelisted 覆盖 ＋ Company 三钩子。**故 `get_region()` 的返回值对 CR-005 建账不再是前置**，它仍牵动两处：CR-006 若要用 `regional_overrides` 挂计税覆盖、以及 IM-007 那条 `get_hooks("regional_overrides")["China"]` 的自检断言（S8G-S1）。**仍值得一测**（一行命令），但「阻塞否」应为**否**。
2. **LG-098 的动机已被议题 ② 砍掉一半。** 它的理由是「zelin 缺月末结转与银行对账，saoxia 可能有」——而 ② 已查明**银行对账原生就完整、谁都不用抄**。故只剩**月末结转**那一半值得翻。
3. **LG-080 是判断型，本轮不派探针**，但它有一个前置事实可顺手确认：那 2 处同名父子具体是哪两对。这一条与 ② 的探针可同批，成本接近零。

**选项**（三条的处置打包成一个取向选择）：

**② ⚠ V-22 推翻了 DEC-082 的一条判据——`Bank Transaction Mapping` 这个机制是坏的**

**④ 用户明确可接受「把 ERPNext 某个阶段整段换成中国财税规则」，非侵入优先、侵入方案也要看**

**提出者：** 用户

**背景：** 用户原话意图：**必要情况下可以接受借助 Hook 或其它非侵入机制，把 ERPNext 的某个阶段整段替换成中国财税规则**——理由是「原生的规则如果不适用于中国的话，实际上没有太大用处，我的客户基本上都是中国客户」。若**非侵入机制做不到，也要给出需要侵入的方案供其评估**。

**② ⚠ 丙的性质由我上一步的措辞造成误解，本步澄清并更正**

**提出者：** 用户（原话「财报模板本质是**图标**吧，**图标**不是也可以在 ERPNext 里自己配置的吗，为什么会涉及到架构取舍」，随后另发一条更正「我打错字了，我的意思是财报模板是**图表**」）／Claude（澄清）

**背景：** 用户先写作「图标」、随即另发一条消息自行更正为「图表」。**两个读法都不对，而根源在我**——我在第 5 步把 `Financial Report Template` 与 G1c 报的两个 svg 图标放在相邻位置陈述，导致误读。

**实物核实**（A 步自读）：`Financial Report Template` 是一张**报表定义表**，字段 `template_name`／`report_type`／`rows`（子表）／`disabled`。其 `rows` 每行的真实字段是：

```
data_source: "Account Data"                                    ← 这行数据从哪来
calculation_formula: ["account_category", "=", "Share Capital"] ← 取哪些科目
display_name: "Share Capital"                                   ← 显示成什么
indentation_level: 1                                            ← 缩进几级
reverse_sign: 1                                                 ← 要不要反号
reference_code: "L_SHARE_CAPITAL"                               ← 给这行起代号
```

下一行可写 `calculation_formula: "L_SHARE_CAPITAL + L_RESERVES + L_RETAINED_EARNINGS"`、`data_source: "Calculated Amount"` ⇒ **用代号做加减算合计行**。

**故它既不是图表也不是图标，是「报表怎么排版、每行取哪些科目」的配置表。**

**⭐ 而它是好消息，三条实测事实**：

1. **v16 自带 6 份模板**（`erpnext/accounts/financial_report_template/`），其中 **`horizontal_balance_sheet_(columnar)`** 是**横式分栏资产负债表**——64 行定义、含 `Column Break` 与右栏 `Equity & Liabilities`。**左右双栏正是中国资产负债表格式** ⇒ v16 已把「中国式报表排版」这个能力做进来了，只是模板内容是国际科目名
2. **取数字段不限于 `account_category`**（A 步核实，这是决定工作量的一条）：`financial_report_validation.py:403` 是 `set(self.account_meta._valid_columns)` ⇒ **Account 的任何列都能当筛选条件**（科目号／科目名／`account_type` 都行）。`financial_report_engine.py:440` 与 `:816` 的示例正是 `["account_type", "=", "Cash"]`
3. `sync_financial_report_templates()`（`financial_report_template.py:131-153`）**遍历所有已安装 app 自动导入模板** ⇒ 自有 app 可带自己的模板

**故丙的准确性质是**：**不是架构取舍，而是「我们把一个本可以用的现成机制关掉了」**——`ignore_chart_of_accounts=True` 让位得太彻底，把 v16 新增的这套一并让掉（`company.py:346-350` 把它与 `create_default_accounts` 同置一个 flag 分支）。**落点 L1–L2，不碰上游。**

**结论：** 我上一步把丙描述成「架构取舍」是把问题说重了，此处更正。**处置形态待议题 ⑤（己案调查）回来后定**——因为它与「抄 zelin 报表代码 vs 用 v16 引擎配模板」是同一个选择。

**⑥ 1-1 的答复：不为 React 另建 Debug App，但 FrappeDebug 内部分三层**

**提出者：** Claude（答用户 1-1）

**判据：工具链不同 ≠ app 要分开，因为真正贵的两层与界面无关。**

| 分层 | 内容 | desk 与 React 共用吗 |
|---|---|---|
| **数据层** | 造数据（100 条全链数据集、样本 A/B）、建单辅助函数、清理复位 | **完全共用**——都是服务端调 whitelisted 方法建单，**与界面无关** |
| **编排层** | 23 个节点的业务语义（如「第 7 步：提交采购收货」） | **完全共用**——节点定义是业务流程，不是界面操作 |
| **驱动层** | 怎么点那个按钮、怎么填那个输入框 | **不共用**——desk 走 Cypress、SPA 走 Playwright |

**⇒ 造数据与节点定义是工作量的大头，而它们跟界面无关。** 拆成两个 Debug App 则这两层要么复制一遍、要么变成「React Debug App 依赖 desk Debug App」——**那仍是两个 app 的成本，却拿不到隔离的收益**。

**建议形态**（A 步只给取向，具体目录留 C 步）：

```
FrappeDebug/
├── data/          ← 造数据 + 建单辅助（服务端，两边共用）
├── nodes/         ← 23 个节点的业务定义（两边共用）
└── drivers/
    ├── desk/      ← Cypress
    └── spa/       ← Playwright（将来给 React）
```

**该拆的条件（写明以备将来判断）**：**若 React 界面的测试不再依赖 ERPNext 的数据层**（如另配独立 mock 数据源），则两层共用的基础消失，届时拆开才划算。**现在拆是为一个还不存在的界面付双倍维护成本。**

**另一条现实理由**：React 重写按用户规划是**远期**，而 FrappeDebug **S7 就要用**。先建一个、将来真需要时再拆，优于现在建两个（其中一个空着）。

## 复核建议

按规范 §2.2 与 A 步 Spec 的四类写。**本轮的特殊性：主产物之外另有 5 份探针留档与 5 份调查留档，复核时应连带看。**

### 一、收敛得最勉强的议题

**⭐ 最勉强的是「BS＋PL 自写」这条（第 7 步议题 ⑤）。** 查法：读第 7 步议题 ⑤ 的选项段，会发现**它没有给过 2–3 个方案的对比表**——它是在用户下了两条合规要求（列头合规＋利润表两列合规）之后**由 Claude 单方判定**的，判据是「两处缺口都在列上、而模板引擎只管行」。

**风险**：该判据建立在两条**未实测**的引擎缺口上（己案自陈）——① 双栏＋两个会计年度时列头的**实际**长相；② `accumulated_values` 是否真的无法做到一列累计一列单月。**若其中任一条实测后不成立，自写这个决定就该重判**（改回「配模板 ＋ Custom API」更省）。

**建议**：B 步写需求文档前，**先派一次探针实测这两条**（成本低：新建空测试站点跑一次，不碰演示站点）。这是本轮**最值得抽查的一处**。

### 二、验收标准最虚的那条

**完成标志② 「13% 销项模板实建得出」。** 它建在一条**已被推翻的因果链**上——原表述的因果是「科目号笔误 ⇒ 模板静默建不出来」，而实测是 `or_filters` 取 OR、按 `account_name=销项税额` 即命中、**模板照常建出且指向正确科目**（缺口 #10 已记改写要求）。

**故这条标志现在的形态是「验一件不会发生的事」**。B 步须把它改写成可判真假且**真有风险**的表述，建议方向：断言 `Sales Taxes and Charges Template` 里 13% 那条的 `account_head` **确实指向 `2221005`**（而非被兜底逻辑创建出的野科目）。

**另一条虚的是标志① 「演示公司建成且自检断言通过」**——自检函数**签名未定**（路线文档 §七自陈这是接口双向对账里「最勉强的一处」），故「断言通过」目前无法判真假。已记 LG-124。

### 三、业务规则的疑似冲突

**本轮无「待领域专家确认」项**，但有**两条须会计参与才能定的**，且都已登记而非硬判：

1. **列头合规到什么程度**（己案点名这条决定方案成立与否）——「年初余额／期末余额」逐字合规是否硬要求，取决于给谁看（内部管理 vs 报送税务 vs 会计师审阅）。**用户已裁「需要合规」，故本轮按最严处理**，但若将来发现内部管理用不必如此严，自写那个决定可以放松
2. **间接法附表要不要做**——依据是**单一来源、可信度中低**（己案自陈），用户已裁「先不管，实地考察后按企业财务要求定」

**另有一条会计实务问题本轮刻意未判**：zelin 把「共同类」归为 `Asset` 而无注释说明理由，戊案未找到讨论此事的中文资料 ⇒ **建议实地考察时问客户会计或代账**（虽本项目那份表无共同类科目，不影响 S4）。

### 四、拿不准处（用户表述有两种读法而按其中一种推进的）

1. **⚠「财报模板」那处误会的责任在我，但更正后的处置我按一种读法推进了**：用户先读作「图标」、自行更正为「图表」，而实物是**报表定义表**（既非图标亦非图表）。我据此把丙的性质从「架构取舍」改判为「我们把一个现成机制关掉了」。**但用户没有对这个改判本身表态**——他随后的注意力转到了列头合规上。**若用户认为丙仍是架构取舍，第 7 步的结论要重看。**

2. **「App 等 D 步再建」与裁决 3 的关系我按「时机推后、实质不变」读**（第 9 步已记）。另一种读法是「裁决 3 整条作废」——即不再要求 S5 后重装 FrappeChina 并实测。**我按前者推进**（缺口 #21 保留该约束），因为那条约束防的是一个已知会静默失效的坑，与建 app 的时机无关。

3. **「顺序到时再定」（React app）我未追问**，故 React app 在装载顺序里的位置**本轮未定**，只记了 FrappeChina 与 FrappeDebug 的相对序。若 React app 将来要覆盖上游行为（如覆盖 desk 路由），它与 FrappeChina 争 `[-1]` 的问题届时要重判。
