## 复核建议

**1. 验收条件最不确定是否覆盖到位的两个切片**

- **SL-007（三问）**：需求 §4.6.5 要「3 次都答对且说得出依据」。方案把「对」定为名次或对象一致、数值在误差内、列出依据三条同时满足（Part3 TS-012 第 4 步）。**查法**：对照需求 §4.6.5 的表逐问读 TS-012 第 1 步的数据表，看各问的干扰项是否真能让错误解法答错——这是我设计数据时最用心、也最可能算错的地方（标准答案都写在表里，可手算复核）。
- **SL-008（局域网连通）**：检查工具的回执走页面通路，所以「实时不通则必然失败」成立；但「通过」只证明了 Administrator 这一个用户在那一台终端上通。**查法**：读 Part4 接口契约 §1 的 `run()`／`ack()`，判断它是否足以代表 S7 演示时的情形（演示用户可能不是 Administrator）。

**2. 切片划分**：按「装进来 → 每个 App 各一块 → 网络 → 收尾」切。**第二种合理切法**是把 SL-003（测试站）与 SL-004（演示站）合成一个「接入」切片，以「两站都装好」为验收——没这样切，是因为 RS-002 要求测试站全过之后才动演示站，两个切片之间正好是那道闸。

**3. 技术假设是否有遗漏**：判为「成熟做法、故未列」的有：`bench execute` 结束时自动 commit（已读 `commands/utils.py`）；nginx 官方镜像以 envsubst 渲染 `templates/` 下的模板；`frappe.show_alert` 与 `frappe.realtime.on` 在桌面端 `startup` 之后可用。**`docs/开发守则.md` 没有 Spec 所说的 §12「高风险技术点清单」**，故无从对照，只按开发守则「判据必须能区分」一节自查了每个检查的判别力。

**4. 拿不准处**：

| 位置 | 推断内容 | 依据 |
|---|---|---|
| 总纲 A11 | 测试站装序取 `crm → hrms → raven → insights` | 需求 §4.3 第 1 条自相矛盾，按 RW-02 取「Insights 最后」 |
| Part3 TS-009 | bot `debug_mode=1`，演示前由 S7 关 | 便于实测看报错原因；需求未提 |
| Part3 TS-012 | 数据不含税、问 2 各张数量相同 | 让「含税与否」「平均法」不成为答错原因；代价是 S7 的真数据下须重测（RS-007 已含） |
| Part4 接口契约 §2 | 监视端口改为只绑本机 | 需求 §4.8 表「6787 不对外」；原写在外网暴露约束里，局域网下同样适用 |
| Part1 TS-002 | `reorder_installed_apps` 由 `frappe_china` 提供 | 总纲 A4 的理由；也可写在 `setup.sh` 里用 `bench execute` 直调框架入口 |
