## 演化过程

#### 第 1 步：续做 TS-003／004 时发现空值与零无法区分

**提出者：** Codex（执行中发现）。
**背景：** 用户要求继续开发项目，按流程从 S8 R6 D 回执的 TS-003 接续。TS-003 原有 3 条用例在补齐工位与整数单位夹具后通过；继续 TS-004 的真实单据验收时发现：新建 BOM 工序损耗率未填写，手填整体 5% 后在内存中可保存，但读取已落库 BOM 时工序字段均为 0。`overall_loss_percentage` 以 None／空字符串判“未填写”，误将全零作为显式工序设置；反算量返回 5000，非验收要求的 5264。重新加载再保存 BOM 还会把手填整体 5% 改为 0。

**⚠ 执行中发现：** 方案 SL-003 的“工序全部为空时整体可手填”依赖的存储判据不成立，影响 TS-003、TS-004 的公共算法与后续生成器。不能靠修改期望值为 5000 或跳过重新加载来通过验收。

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐） | 全部工序为 0 时视为未启用，沿用可手填的整体损耗率；任一非 0 才自动计算 | 不增加字段；现存全零 BOM 与手填整体值兼容 | 不再区分“未填”与“全部显式填 0 覆盖整体值” |
| B | 新增“按工序计算损耗”开关，启用状态与各道百分数分开保存 | 可明确表达全零覆盖整体值 | 需调整字段、界面与方案；增加维护项 |

**用户回答：** 用户在下一轮明确选择 A：全部工序为 0 时视为未启用，保留可手填的整体损耗率；任一工序非 0 才自动计算，不新增字段（裁决见第 2 步）。
**结论：** 保留 TS-004 的实现草稿与红绿证据；TS-003 不能按原有 3/3 结果认定“重新读库后仍可手填”。等待口径裁决后先补回归、修实现，再完成切片验收。

**可复现路径：**
- 原生写入：`frappe-bench/apps/frappe/frappe/model/base_document.py` 的 `get_valid_dict`，float_like_fields 对非 float 的 None 调 `flt(value)`；写库值为 0。
- 原生字段定义：`frappe-bench/apps/frappe/frappe/database/schema.py` 的 Float／Currency／Percent 默认值同样经 `flt`。
- 自有读取：`frappe-bench/apps/frappe_china/frappe_china/production/process_loss.py` 的 `overall_loss_percentage`、`required_input_qty`。
- 运行：`bench --site test.localhost run-tests --module frappe_china.tests.test_process_loss`。`frappe-bench/logs/s8-ts004-green-plan.log` 实测 6 条中 3 条失败，均为应反算 5264 而得到 5000；旧 TS-003 3 条通过。
- 超产：`frappe-bench/logs/s8-ts004-green-overproduction.log` 实测 5 条中 1 失败、1 错误；哈希守卫、5265 超限、5000+265 超限通过，正常 5264 路径受同一原因阻塞。

#### 第 2 步：确定全零工序损耗沿用整体手填值

**提出者：** Codex（上轮提供选项），用户裁决。
**背景：** Frappe 将未填写的 Percent 存为 0，原有空值判据无法在重新读库后保持手填整体损耗率。
**用户回答：** 选择 A。全部工序损耗为 0 时视为未启用工序损耗；沿用可编辑的整体损耗率。任一工序非 0 才自动计算整体值，无需新增字段。
**结论：** 前后端统一以“任一数值非 0”判断是否启用工序模式。先补全零／混合零／重新加载保存回归，再修实现；订单 5000、整体 5% 的推荐量仍须为 5264。该口径作为 R5 SL-003／TS-003 空值语义的经用户批准补充，不改反算验收值。

**落地与实测：** `overall_loss_percentage` 与 `bom.js` 同步改为非零判据。先红：Python 8 条中 5 失败、前端 2/2 失败；修正后损耗／计划 8/8、超产 5/5、补货规则 6/6、Node 全量 92/92 通过。回滚探针 `process_loss_probe.py` 实测读回工序 `[0, 0, 0]` 时自动整体值为 None、手填整体 5% 保留、订单 5000 反算 5264、再次保存仍为 5%。测试站浏览器截图 `Spike/P1S8R6-D/SL003-manual-recommendation.png` 显示手改 5300 与「推荐 5264」；专用夹具已清理 10 项。SL-003 全量 Python 尚在运行，未以定向测试代替全量门。

**提出者：** Codex（执行中发现）。
**背景：** 用户已批准全零损耗沿用整体手填，本轮完成该补充的完整回归（431＋5＋4 全过、Node 92/92），并推进 TS-006 工时实现及定向验收（新验收 10/10、拆卡 9/9、容量报表 2/2、工序流转 16/16）。在 TS-006 切片全量运行期间反查 TS-007，发现冻结方案内部存在矛盾。

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐） | `kept` 且推荐仍与当前 BOM 不同，每次保存重询；`confirmed/manual` 不重询 | 保留原验收能力，用户下次保存可改变选择 | 再保存仍弹框，须补充实现判据 |
| B | 首次选择后不再询问，继续只处理来源为空的行 | 不重复打扰，保留实现段判据 | 要调整原验收，下一次保存不能直接改选推荐 |

**用户回答：** 用户在下一轮选择 A，保留后再次保存重新询问（见第 4 步）。
**结论：** 提问时推荐 A 并等待裁决，TS-007 仅在 Spike 暂存测试草稿；第 4 步已解除此口径阻塞。TS-006 完整回归继续，不阻塞已授权工作。
**可复现路径：** R5 Part1「切片划分与验收」SL-006①与「任务 TS-007」第 1、3 项；`Spike/P1S8R6-D/before_save_probe.cjs` 在 test.localhost 新建 BOM 页实点保存，拦截实际服务端保存：Promise 未 resolve 时调用数 0，resolve 后 1，reject／validated=false 后仍为 1。证据 `frappe-bench/logs/s8-before-save-probe.json`，未落库。
