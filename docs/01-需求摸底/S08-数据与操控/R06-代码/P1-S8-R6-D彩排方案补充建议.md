# P1-S8-R6 D 彩排方案补充（A 已批准）

**日期**：2026-10-23｜**状态**：用户选择 A，作为 R5 Part3 TS-023 的实施补充；不另起 Round。

## 触发原因

按 R5 Part3 TS-023 开工前反查，现有接口不能直接执行其伪代码：

1. TS-023 第1步要求克隆清洁基库到 `{base}_work` 并切入。总纲§5.3也把工作库列为 `switch_to_db` 用途，但没有给出工作库登记、创建和删除接口。现有 `registry.validate_registry` 只接受 `base_db` 与每幕 o/m/b；`switch._registered_target` 只允许基库和已登记 ready/used 的 m/b，工作库会被拒。
2. TS-023 失败续跑要求从该幕原始快照换库重来；总纲 A4 明令站点不得指向 `_o`。而 `take_snapshot` 又要求当前库与登记的基库一致、同幕不可重复，不能直接在其他快照库重建后续幕。
3. TS-023 的 SL-015 整场验收要求完整九幕业务步骤，但这些步骤和命名函数安排在 TS-024。当前 `demo.yaml` 只有九幕入口骨架，跑通骨架不足以证明业务彩排通过。

## A 的完整补充范围

- 登记表新增 `work_db` 与工作库状态；`base_db` 始终表示清洁基准，幕快照命名仍从 `base_db` 派生。只允许固定派生的 `{base}_work`，不开放任意库切换。
- 新增 Administrator 专用的工作库准备接口：首次只从当前清洁基库创建；有旧工作库、在途生成或克隆时明确拒绝，先按受控清理顺序处理。创建前登记，失败保留可诊断状态，不覆盖未知库。
- 新增续跑准备接口：先返回基库，确认没有生成/克隆在途，再从第 N 幕 `_o` 克隆到工作库；始终不把站点指向 `_o`。保留第1至 N−1幕和第 N 幕原始快照；第 N 幕 m/b 恢复为干净副本，失效的第 N+1幕及之后快照按登记删除后重建。
- `take_snapshot` 允许在已登记工作库创建幕快照；续跑时复用第 N 幕原始快照，避免重复创建；后续幕从恢复后的工作库创建，进度和 refs 取该幕原始快照。
- `switch_to_db` 仅增加已登记且就绪的工作库白名单；现场 m/b 的消费仍经 `switch_to_act`。所有准备、恢复、切换和删除的复合操作使用同一站点操作锁，拒绝冲突操作。
- “回到演示前”返回清洁基库；“清理快照库”在基库执行，等待生成和克隆结束后删除全部登记的幕库及临时工作库，最后清空登记；基库永不删除。
- TS-023 先验证编排、状态持久化、故障停止和恢复分支；TS-024 补齐真实业务九幕后联合跑 SL-015①②③和 SL-016①～③。不以入口骨架代替整场业务验收，不减少既定验收条件。
