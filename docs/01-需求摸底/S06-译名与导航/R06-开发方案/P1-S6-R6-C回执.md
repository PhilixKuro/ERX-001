## 复核建议

**1. 验收条件最不确定是否覆盖到位的切片**

- **SL-012（批量重译）**：抽检 100 条只能证明可用率，证明不了 5500 条里没有成片的同类错误。我能想到的兜底是四道守卫进测试，但守卫抓的是形态（繁体、逐词、占位、混排），**抓不了「通顺但意思错」**。查法：D 回执出来后，在 `Spike/P1S6R6-sample.out.csv` 之外，按 app 各随手翻 10 行 csv 看意思。
- **SL-014（逐屏核）**：屏数按 DEC-032／034 约翻倍（状态两态＋15 个 DocType 两种确认框），我没有逐行算出总屏数，D 开工写 `screens.json` 时才定。查法：看 D 回执的「§4.9 行 → 屏 id」映射表有没有空行。

**2. 切片划分**：按「守卫 → 清场 → 演示线 → 批量 → 逐屏核」切，守卫在先，后面每次写 csv 都受它约束。第二种合理切法是把清场（TS-018）并入批量重译（TS-021），清一块译一块——没这样做，因为演示线定词要在干净的 csv 上做占用核查，旧批量行留着会把占用判错。

**3. 技术假设是否有遗漏**：判为「成熟做法、故未列」的有：子 Agent 按同一份术语表翻译、术语一致性靠主 Session 合并时过守卫与 `test_named_terms`；`csv.writer` 写回不改变既有行的引号形态以外的内容。`docs/开发守则.md` 无 §12「高风险技术点清单」（同 R3），未能对照。

**4. 拿不准处**：

| 位置 | 推断内容 | 依据 |
|---|---|---|
| A16 | 覆盖官方的批量行删掉回落官方，不重译 | 需求 §4.3「批量档补缺口、不覆盖官方」；这些行没有任何决策依据 |
| TS-017 第 2 步 | R4 TS-014 用户批准的整句修复（`Global Defaults` 等 11 条）算「有依据」保留 | DEC-026 批准过 TS-014 的整句修复做法，但没有逐条过目 |
| A21 | `default_data` 不使 `pass` 变假 | DEC-033「计为发现、处置交 S7」；若判为 `pass=false`，演示站上这些屏永远过不了 |
