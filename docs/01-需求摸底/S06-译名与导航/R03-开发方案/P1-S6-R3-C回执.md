## 复核建议

**1. 验收条件最不确定是否覆盖到位的两个切片**

- **SL-004（演示线译名）**：「演示线撞名组 0 残留」的判据依赖 Part1 TS-001 的 `demo_surface` 取得全不全。部分 2（`/crm`、`/raven` 屏）我只让脚本追一层 `import`，可能漏掉深层组件里的文案；漏掉的会在 SL-010 逐屏核时被抓到，但那时已是演示站阶段。**查法**：读 Part1 TS-001 第 2 步，对照需求 §4.9 表二的屏，想一想每屏的文案在不在列出的文件里。
- **SL-010（逐屏核）**：「无英文词」由脚本抽可见文本加正则判。`extract_visible_text()` 排除了用户数据与记录链接文字，排除规则写宽了会漏判。**查法**：读 Part4 接口契约的排除清单，判断有没有把界面文案也排除掉的风险；⑧ 的反证只证明「有英文 label 时能报」，证不了「排除规则没有吃掉该报的词」。

**2. 切片划分**：按「守卫 → 改名 → 小缺陷 → 演示线 → 批量 → 裸渲染点 → 导航 → 开账 → 不刷新 → 收尾」切，先守卫后改 csv。**第二种合理切法**是把 SL-004 与 SL-005 合为一个「全量译名」切片，以缺口 0 为验收——没这样切，是因为 DEC-017 要求批量档可用率不达标时停下，两切片之间正好是那道闸，且批量档必须沿用演示线档的术语。

**3. 技术假设是否有遗漏**：判为「成熟做法、故未列」的有：`bench build --app frappe_china` 后 `app_include_js` 的新文件被页面加载（S5 的 `realtime_check.js` 已证）；`frappe.rename_doc` 在补丁中以 Administrator 运行；`docker/backup.sh`／`restore.sh` 的行为（S5 已多次用）。**`docs/开发守则.md` 没有 Spec 所说的 §12「高风险技术点清单」**（同 S5-R3），故无从对照，只按开发守则「判据必须能区分」一节自查了每个反证的判别力。

**4. 拿不准处**：
