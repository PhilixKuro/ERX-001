## 复核建议

**1. 验收条件最可能没覆盖到需求意图的两个切片**

- **SL-008 工序间数量传递**：需求 §4.8 只说对齐「下一道」，本方案改成逐道级联到其后全部工序（偏离 3），并定了「预计产出」口径（A17）。这是本方案对需求改动最大的一处。**查法**：读需求 §4.8 与 AC-018，对照总纲 A17、偏离 3～6 与 Part2 TS-012 的伪代码，用「1000 支、第一道 950、第二道已开工」走一遍，看第三道该是多少。
- **SL-005 按订单规则**：需求说「复用原生算法」，本方案直接调原生函数，但待展开量取「未交−已建工单」、不扣成品库存（偏离 15）。客户若有成品库存，这条规则会多建议。**查法**：需求 §4.2.3 按订单行，对照总纲 A9、偏离 15 与 Part1 TS-008 的 `order_proposals`。

**2. 切片划分**

按「一个功能点＝一个切片」切，与需求 TS 编号基本一一对应。有第二种合理切法的一处：SL-003（安全库存＋再订货点）与 SL-005（建议单）可以合成一个「补货」切片，因为再订货点单独看不到演示效果。分开是为了让 EOQ 的触发线（再订货点）先单独验准，再进建议单。

**3. 判为「成熟做法」而没进技术假设表的**

- `scheduler_events.daily` 在演示站不跑（scheduler 关），演示靠「立即计算」按钮；不影响验收，故未列。
- `frappe.db.set_value` 不触发文档钩子（安全库存、再订货点、后道卡都靠它避开 `save()` 的副作用）。
- `Notification Log` 在 migrate 进程里直接 insert 能落库（TS-003 显式 commit）。
- `Has Role` 查 System Manager 用户。
开发守则没有 §12 高风险技术点清单（Spec 引用的那一节在本项目不存在）；按开发守则「判据必须能区分」一条自查，探针设计都有可区分的输出。

**4. 拿不准处**

| 位置 | 推断 | 依据 |
|---|---|---|
| A4 日需求白名单 | 生产领料只认 `Material Issue`、`Manufacture`、`Material Consumption for Manufacture` 三种 Stock Entry 用途，`Material Transfer for Manufacture`（发到在制仓）不算 | 发到在制仓后，`Manufacture` 再从在制仓扣料，两者都算会重复；但若客户不用在制仓、直接从原料仓 `Manufacture`，口径仍对 |
| Part1 TS-005 | 单位成本不扣副产品（`secondary_items_cost`） | 需求公式不含它；弹簧废料回收若计副产品，最低成本 BOM 可能判错 |
| Part1 TS-006 | 子装配 BOM 不参与按成本选择 | 生产计划子装配取 BOM 行上的 `bom_no`，属 BOM 结构；需求只说「为某弹簧选 BOM」 |
| 偏离 8 | 计件期间取自然月、`payroll_date`＝月末 | 需求 §4.9 与 §4.13 两处写法不一致，取能保证幂等的一种 |
| 偏离 21 | 物料在多家启用公司都有出库时跳过安全库存 | `Item.safety_stock` 是全站单值；演示站只有一家公司，不会触发 |
| Part3 TS-015 | Nelson 窗口规则只标窗口末点；Ppk 的中心用 X̿ | 需求未说标哪些点；Ppk「同式」按字面 |
