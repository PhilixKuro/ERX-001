> Stage 级概况：当前 Workflow 是哪条、进行到哪个步骤/轮次、本 Stage 延迟需求登记册。

## 当前编排

**`devBlueprint` Workflow**（非自由编排）。文件：[../../流程体系/workflows/devBlueprint/0-devBlueprint-workflow.md](../../流程体系/workflows/devBlueprint/0-devBlueprint-workflow.md)

**本次规划层级：Phase 级**（该 Workflow「规划层级」节要求起 Stage 时写明）。即：目标是 **P1 需求摸底这个 Phase 剩下要做的事**，分解出**本 Phase 内的后续 Stage**（S3、S4…），不是分解整个项目。

按该层级的四处差异：

| 项 | 本次取值 |
|---|---|
| 目标 | P1 剩余部分——**让客户演示能跑通** |
| 分解出 | 多个 Stage（S3 起，可能是原子或议题） |
| 议题形式 | `S{m}` 或 `S{m}G` |
| 非本级功能的去向 | **本 Phase 内的后续 Stage**——属规划产物，不经延迟需求 |
| 跨单位接口契约的家 | **本 Phase 概况**（[../P1-概况.md](../P1-概况.md)） |

**为何走 devBlueprint 而非直接开工**：用户的新目标（客户面前跑通整个流程）牵动三件互有依赖的事——译名、导航、外部操控机制——且远期还要用 React 全面重写 UI。**三者的次序与边界须先定清**（如"译名必须在导航与按钮文案之前，否则要改两遍"），而这正是 devBlueprint 的职能：定需求图谱 → 定架构 → 定分解路线。
