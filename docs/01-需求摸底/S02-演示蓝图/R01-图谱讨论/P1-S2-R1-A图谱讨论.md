## 演化过程

#### 第 1 步：范围分解检查与定位裁决

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**① 范围分解检查（Spec「开场必做」）**

**提出者：** Claude
**背景：** A 步 Spec 要求先判初始目标是否其实是多个彼此独立的目标，判据三条：多个不相关用户场景 / 多个彼此无关联数据模型 / 多个独立目标用户群。用户的初始目标是「在客户面前跑通整个流程」，下挂三件事（译名、导航、外部操控机制）。

三条判据逐条：

| 判据 | 判定 | 依据 |
|---|---|---|
| 多个不相关的用户场景 | 不成立 | 三件事全服务同一场景——客户面前走完接单到收款 |
| 多个彼此无关联的数据模型 | 不成立 | 全在 ERPNext 既有 DocType 上动，无新数据模型 |
| 多个独立的目标用户群 | **部分成立** ⚠ | **外部操控机制（`PH-P1003`）的目标用户是开发者，不是客户**。其三个消费方（演示脚本 / MCP / React 前端）中只有第一个与演示有关；它是长期基础设施，被演示这个用例顺带拉出 |

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| 仍作单目标 | 操控机制在本次规划里只做到「够演示用」一档，超出部分留给后续 Phase | 保留演示这个唯一已知的验收场景约束它的范围 | 它的长期资产属性在本次规划里被压缩表达 |
| 拆成两个目标 | 演示一个目标，外部操控基建另一个目标，各自规划 | 基建能按自己的完整需求规划 | 脱离唯一已知的验收场景，变成无需求约束的基建 |

**用户回答：** 选「仍作单目标」。
**结论：** **判为单目标**，按单目标继续 A 步。第三条判据虽部分成立，但操控机制在本次规划中只做到「够演示用」一档；其超出演示需要的部分留给后续 Phase。

**② 定位（议题清单第 1 节）**

**提出者：** Claude
**背景：** 定位决定后续架构与路线全建在什么上面，也决定译名做到哪一档、导航重排多少、S1 交下的三个雷堵几个——是本条 Workflow 里回退最贵的一处。触发它的关键事实：**四阶段战略把 ④定制 排在 ③演示 之后，而至今未实地考察**，客户规模与需求均未明确，S1 的 52 场景按行业通识生成、数值只具行业典型值效力。故这次演示是项目与客户真实业务的第一次接触；把它只当销售展示、还是同时当摸底工具，是两条不同的路。

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| **A 可信度优先**（"这就是你将来用的系统"） | 修好全量译名与导航的原生 desk + 数据正确的完整闭环样本 + 脚本驱动演示；三个雷在服务端逐一堵死，客户看到的每个界面都是上线后要用的那个 | 演示即预交付，无"演示能跑上线不能跑"的落差；交付物全是长期资产；成本数字正确，经得起客户会计追问 | 工作量最大（译名须全量准确、三个雷须改服务端 mapper）；演示内容受限于 S1 已跑通的 23 环节，质检/外协/月结仍是空白 |
| **B 业务契合优先**（"这系统装得下你的厂"） | 覆盖面优先：把 S1 未覆盖的质检、外协、月结也粗走一遍；译名与导航只修演示路径上的；每到一环节问"你们厂这里怎么做"，演示同时是需求访谈 | 一次动作补两个缺口（既演示又完成实地摸底，填 P1 从未实地考察这个洞）；覆盖面宽，客户更易认出自己的厂；未覆盖环节的缺口能当场问清而非回来猜 | 客户会看到未译或不准的字段，与用户「不应该出现有些翻译了有些没翻译」的要求直接冲突；粗走的环节可能现场卡住；数据正确性要求降档 |
| **C 观感优先**（演示门面） | 不修 desk，另做少量 React 页面只覆盖演示要走的八步，数据仍落 ERPNext | 绕开译名与导航两项工作；界面可按弹簧厂话术定制，观感最好；是远期 React 重写的第一块砖 | **客户看到的不是他将来用的系统**——成交后进 desk 是完全另一套，信任反噬；desk 的译名导航一件未解决、只是推后；三个雷在服务端，门面盖不住错的成本数字 |

**Claude 推荐**：A 为主 + 吸收 B 的一项。三层理由：① **C 先出局**——它的缺点不是工作量而是方向，演示的隐含承诺是"这就是交付物"，门面让这句话变成假的，且它省下的译名工作是必做项、只是推后；② **A 与用户已下裁决一致**——用户要求"不应该出现有些翻译了有些没翻译的情况"是 A 的立场，B 明确要放弃它；③ **但 B 有一件 A 拿不到且不贵的东西**——演示过程中的结构化提问：不改变 A 的交付物，只要求演示编排里为每个环节预留一个"你们厂这里怎么做"的问点并记录答案，使演示顺带补上实地摸底而不增加开发工作量（增加的只是演示脚本里的问题清单）。

**用户回答：** 选「A + 内置摸底问点」。
**结论：** **定位＝可信度优先（A），并在演示编排中内置摸底问点。**

已接受的代价：**演示覆盖面仍限于 S1 已跑通的 23 环节**；质检 / 外协 / 月结改为"现场口头询问 + 记录"而非演示。

由本定位推出的三条下游约束（后续各节据此推进）：
1. 译名须**全量准确**，不是只修演示路径——这是 A 与 B 的分野所在。
2. S1 交下的**三个雷都在服务端**（工艺损耗不反算投料量 / 报工工时致毛利率虚高 40 点 / 完工入库费用科目逐行手填），A 定位要求逐一堵死，故本次规划**必然包含服务端改动**，不止界面层。
3. 演示须有**数据正确的完整闭环样本**，故 `20260922_145623` 备份的恢复与校验进入范围。

#### 第 2 步：核心需求盘点与三处摇摆项裁决

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**① 核心需求候选清单（议题清单第 2 节）**

**提出者：** Claude
**背景：** 核心需求判据是「缺了这个目标就不成立」。目标为「在客户面前**可信地**跑通整个流程」（第 1 步定位取 A），故按"客户在演示现场会不会看到问题"筛选。候选来自 S1 移交的三件事 + 三个雷 + P1 概况登记册 9 条。

**产物快照（v1，初判）：**

| # | 候选 | 缺了会怎样 | 初判 |
|---|---|---|---|
| 1 | 译名全量准确 | 客户看到同一侧栏两个「设置」、下拉里两个「应收账款」。直接违反用户裁决 | 核心 |
| 2 | 导航按业务流重排 | 客户跟不上"接单→排产→领料"的顺序，要在 19 个工作区里找入口 | 核心 |
| 3 | 树形 DocType 点进不空白 | 点科目或仓库即白屏。**必然而非偶发**（`*_list.js` 是空文件） | 核心 |
| 4 | 工艺损耗反算投料量 | 每张工单必然短交（SO 5000 支 + 5% 损耗 → 完工 4750）。走到排产即暴露 | 核心 |
| 5 | 完工入库费用科目默认值 | 演示时手填 11 行，填错即成本进损益表 | 核心 |
| 6 | 完整闭环演示样本数据 | 站点现为空（0 Item / 0 BOM / 0 单据），无从演示 | 核心 |
| 7 | 报工工时的成本正确性 | 毛利率 68.8% vs 应为 28.8% | **摇摆** ⚠ |
| 8 | 外部操控机制 | 演示只能手工点 | **摇摆** ⚠ |
| 9 | 前端不刷新即不显示（其余四例） | 演示中可能要手动刷新 | **摇摆** ⚠ |
| 10 | 客户可读版演示材料（`PH-P1006`） | 客户看完无留存物 | 重要，非核心 |
| 11 | 拼音检索（`PH-P1007`） | 输中文找不到记录时体验差 | 增强 |
| 12 | 中国本地化（专票/金税/财报格式） | 客户会问"能开专票吗" | **另议** ⚠ |

**用户回答：** 未对清单整体提出异议，逐一裁决三个摇摆项与一个另议项（见下方②③④）。
**结论：** 1-6 项为核心；10 为重要；11 为增强。7、8、9、12 按下方各议题裁决。

**② 第 12 项 中国本地化的处置**

**提出者：** Claude
**背景：** 该项性质与其余项不同——**不是演示能不能跑的问题，是客户会不会当场否决整个方案的问题**。弹簧厂会计一定会问增值税专用发票。P1 概况对 `PH-P1004` 记载的唤醒条件是"第 ② 阶段开工时；**给客户演示前必须有方案**"——是"有方案"不是"做完"。

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| 只进演示编排，不进开发 | 准备一份「中国本地化路线图」当现场回答 | 零开发成本；符合 P1 概况"必须有方案"的记载 | 客户若追问细节，回答仍是承诺而非演示 |
| 科目表进范围，其余不进 | 整好中国科目表并用它建演示公司，让客户会计看到熟悉科目名 | 中等成本，可信度提升明显 | 专票与金税仍是承诺 |
| 本次完全不处理 | 不涉及 | 零成本 | 现场被问时无准备 |

**用户回答：** **倾向把系统做完整**（"如果可以的话我还是想先把这个系统做完整"），但**先派子 Agent 深度测工作量**——具体猜测：是否单靠新建一个 app + 用 ERPNext 的 hook 就能直接接入，若是则工作量应不会太大。

**Claude 对该猜测的回应（当轮给出）：猜测有一半成立。** hook 确实是 ERPNext 认可的扩展点，`regional/` 下各国即如此实现（**当轮 Claude 口述为"五个国家"，实为六个**——australia / italy / south_africa / turkey / united_arab_emirates / united_states，V-01 实测确认；此处照录原话并更正），故"新建 app + hook 接入"这条路走得通，工作量集中在业务逻辑而非接入机制。但完整性分三块、代价差一个数量级：

| 块 | Claude 预判 | 依据 |
|---|---|---|
| 科目表 + 财报格式 | 小 | 有 82 节点现成清单；ERPNext 财报是配置驱动 |
| 增值税逻辑（进项/销项、税率档位、价税分离） | 中 | 原生 `Tax Template` 机制支持，要建的是中国税率模板 + 价税分离取值规则 |
| 金税盘 / 专票开票 | **大且不可控** | 要对接第三方（航信、百望等）硬件或云接口。**可能不是"工作量大"而是"现阶段拿不到"**——开票接口通常需企业资质才能申请测试环境，是资质与商务问题而非代码量问题 |

**结论：** 中国本地化的分级**暂不定**，转事实验证。写入 A 待验表 `V-01` ~ `V-06`（V-01 标**阻塞**：它决定本地化是"在自有 app 里做"还是"必须改 erpnext 本体"，后者会改变架构基调并带来上游同步的持续负担，故不拿到结论无法定分级）。

**③ 第 7 项 报工工时成本正确性的定性**

**提出者：** Claude 提出为摇摆项，**用户改判其性质**
**背景：** Claude 原判该项"可能不需要开发"——工序成本按实际报工工时计是 ERPNext 设计而非缺陷，R3 记成 0.27 元是因任务单只计时几秒；若样本工时合理则成本正确，该项即从"改代码"降为"备数据"。但 Claude 未验证过"填一个合理工时后成本是否真的对"，故列为事实型未知。

**用户回答：** **报工工时是现实落地的流程控制，跟软件关系不大。** 不必列为待验的软件问题。

**结论：** **第 7 项不进本次开发范围，转演示纪律**——样本数据的工时必须合理。

**⚠ 讨论中发现**：该裁决同时**修正了 S1 对 `LG-063` 的定性**。S1 概况与 P1-S2 概况均把它列为"演示的三个已知雷"之一；按本裁决它是**操作前提而非软件缺陷**——ERPNext 按实际报工计工序成本是正确设计，车间不真报工就没有真成本，这靠培训与流程约束解决，代码改不了。故**S2 概况「演示的三个已知雷」表应改为两个雷 + 一条操作前提**，待 B 步落图谱时处理。

**④ 第 9 项 其余四例不刷新是否同源**

**提出者：** Claude
**背景：** 第 3 项（树视图空白）已单列为核心，因它是必然的。`PH-P1002` 剩余四例是偶发的（仓库列表空白 / 工作区卡片缺失 / BOM 提交按钮不出现 / `Job Card` 空行）。偶发缺陷在演示时是概率问题——可能整场不出现，也可能卡在关键处。S1 判断"五例可能同源"，若真同源则修第 3 项时顺手修掉其余四例、成本近零。故"是否同源"是决定分级的事实型未知。

**用户回答：** 「跟软件关系不大，**其它三个需要测**，但是可以等先把其它讨论完再测」（与 V-01~V-06 同批，不打断当前讨论节奏）。

**⚠ 一处口径不一致，当轮未澄清（Fid 核查补记）**：用户说的是「其它**三个**」，而第 9 项本身是**四例**（仓库列表空白 / 工作区卡片缺失 / BOM 提交按钮不出现 / `Job Card` 空行）。Claude 当轮回作"那三项"，同样含糊，**原始对话中从未澄清指哪三例**。故 V-07 实际按四例全验（结论不受影响——它判四例互不相交，比三例的任何组合都更完整），但**"用户当时心里排除的是哪一例"这点未知**。

**结论：** 写入 A 待验表 `V-07`，标**不阻塞**。按用户要求与中国本地化各条同批交 SA 步验证，**A 步继续推进不依赖它的议题**（符合 play-shape 纪律 9 与交接契约纪律 1）。

**⑤ 第 8 项 外部操控机制的档位**

**提出者：** Claude
**背景：** `PH-P1003`，用户已裁决排在译名与导航之后，2-4 周，是三件事里最贵的一件。它是否核心取决于演示要的是"系统自己动起来"还是"能顺畅走完"——23 环节手工点约需 40 分钟以上且现场手滑即中断，但替代方案不止一个。

**选项：**

| 选项 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| 降为预建数据 + 手工走查看 | 预先建好全部单据，演示只走查看与讲解 | 成本近零（已含在第 6 项样本数据里） | 客户看不到单据怎么生成、流转怎么发生 |
| **取中档：演示脚本驱动** | 只做演示脚本驱动所需的最小机制（按钮触发后端按序建单），MCP 与 React 复用留到后续 | 中等成本；客户能看到流转真的发生 | 不是完整的外部操控基建，后续仍要扩 |
| 完整建（甲方案） | 按 S2 概况待定项的甲方案做完整服务端推事件机制 | 一次到位，长期资产 | 2-4 周，三件事里最贵 |

**用户回答：** 选**取中档：演示脚本驱动**。

**结论：** 第 8 项**进核心需求，但限定在"演示脚本驱动所需的最小机制"这一档**。完整的外部操控基建（MCP 复用 / React 复用 / 服务端推事件的甲乙之争）留到后续 Phase。

**⚠ 由此推出**：S2 概况「未裁决、A 步须处理的三件事」里的第 1 项（"界面自己动"走甲还是乙）**在本档位下降级为局部选择**——最小机制不必现在定甲乙，但须在 C 步（架构讨论）确认最小机制的形态不会堵死将来走甲的路。

**产物快照（v2，本步裁决后的分级）：**

| 分级 | 条目 |
|---|---|
| **核心** | 1 译名全量准确 / 2 导航按业务流重排 / 3 树形 DocType 不空白 / 4 工艺损耗反算投料量 / 5 完工入库费用科目默认值 / 6 完整闭环演示样本数据 / **8' 演示脚本驱动的最小操控机制** |
| **重要** | 10 客户可读版演示材料（`PH-P1006`） |
| **增强** | 11 拼音检索（`PH-P1007`） |
| **转演示纪律，不进开发** | 7 报工工时（样本工时须合理） |
| **待验证后定级** | 12 中国本地化（V-01~V-06）/ 9 其余四例不刷新（V-07） |

#### 第 3 步：重要/增强需求分级，行业资料前置，兜底形态（Claude 前一轮判断被用户推翻）

**来源项目：** ERX-001
**适用面·状态：** 仅本项目·已落地

**① 重要与增强需求候选（议题清单第 3、4 节合并）**

**提出者：** Claude
**背景：** 第 2 步裁决后「重要」级只剩一条（演示材料），Claude 判此不正常——定位取 A（可信度优先）把可信度相关项全部拉高成核心。故重扫 S1 产出，补入"演示能跑但客户体验会打折"的条目。

**① V-01 判定 `go`：中国本地化可在自有 app 内实现，不改 erpnext 本体**

**提出者：** V-01~V-06 探针 Agent（填回 [P1-S2-R1-A待验表.md](P1-S2-R1-A待验表.md)，探针留档 `Spike/V01-*.py` 等）

核心机制是 `regional_overrides` hook：
- `erpnext/__init__.py:145` 读 `frappe.get_hooks("regional_overrides").get(get_region())`；
- `:152` 取 `[-1]`——**末位装的 app 胜出**；

**是实测生效而非读代码推断**（注入 hooks 缓存模拟装了 app）：
- 覆盖前 `update_itemised_tax_data()` → `None`；注入后 → `'CN-OVERRIDE-RAN'` 且**参数原样传入**；
- 两个 app 同 target → **末位胜出**（与源码一致）；

**结论：** 阻塞项解除。**中国本地化走"自有 app + hook"这条路成立**，架构基调不必改，无上游同步的持续负担。

2. **不得把配置装载包在裸 `except` 里只写 log**。zelin 的 `setup_tax_template`/`setup_tax_rule`/`set_default_accounts`/`set_item_group_account` 全是这个写法，**后果是建完公司看不出问题、做账时才发现**。
3. **现金流量表不能指望原生报表配置**——须按 zelin 的路子自建单据 + 从 GL Entry 按现金银行科目拉流水。

**② ⚠ V-06 的 `go` 对现金流量表不成立（本步据 V-09b 改判）**

V-06 判 `go` 时 Agent 已自述"**最不放心现金流量表**——判定建立在 `Cash Flow` 是原生 report_type + 资产负债表跑通上，但现金流量表按收支性质归集、性质与余额表不同，**资产负债表跑通不构成它也能跑通的证据**"。

**V-09b 提供了反面证据**：zelin **把现金流量表做成了可提交单据（DocType）而不是 Report**，从 GL Entry 拉现金/银行科目流水、四级优先级自动打编码、支持一笔拆多项并校验拆分和等于总账原值。

**故改判**：V-06 的 `go` **只覆盖资产负债表**（实建跑通）；利润表**未单独验**；**现金流量表须自建，不是报表配置能产出的**。
