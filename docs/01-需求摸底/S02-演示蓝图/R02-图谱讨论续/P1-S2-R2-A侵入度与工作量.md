## 侵入度分级（本项目专用，按升级维护成本排）

| 级 | 名 | 含义 | 升级时要跟什么 |
|---|---|---|---|
| **L0** | 零开发 | 改配置/记录，无代码 | 无（但 `standard=1` 记录可能被 `bench migrate` 覆盖，**未实测**） |
| **L1** | 数据层 | Custom Field / fixtures / `zh.csv` / `Translation` 记录 | 无 |
| **L2** | app 内新建 | 自有 DocType / Report / whitelisted 方法，不碰上游 | 无 |
| **L3** | hook 追加 | `doc_events` / `regional_overrides` / `app_include_js` —— **累加执行** | 只跟**字段名与子表结构** |
| **L4** | hook 覆盖 | `override_whitelisted_methods` / `override_doctype_class` —— **后者胜出** | **跟方法体**；且覆盖位占掉即锁死其它 app |
| **L5** | 改上游源码 | 改 `apps/erpnext` 或 `apps/frappe` | 每次升级必冲突。**本项目禁止，除非无路可走** |

**用户第 5 条问的「能否尽量用 App 覆盖或 Hook 解决」→ 基本能**：全表 **L5 = 0 项**，**L4 仅 3 项**（第 7.5 项并入 zelin、第 9 项自制科目表进建公司下拉、第 29 项工时基准量解耦），其余全部可用追加式（L0–L3）解决。

**已查清的三条边界**：① `doc_events` 累加、**具体 DocType handler 先于 `"*"`**；② compose runner **先跑类方法体、再跑 app hooks**，故追加式改写的顺序天然正确；③ `app_include_js` 累加无覆盖，**realtime 监听注入不会被别的 app 挤掉**。
