# ADR-0005: 配置与业务记录的管理形态按语义分派

- 状态：accepted
- 日期：2026-09-25 / 决策者：用户裁决（C 步第 6 步①），Claude 提选项
- 对应决策：DEC-056

## 上下文

本项目要落地的「非代码内容」横跨五类对象：`Custom Field` 之类的 schema 扩展、Company 默认科目之类的业务配置、科目表 JSON 之类的基础数据、演示数据集、译名。而 Frappe 提供四种落地手法，**它们的覆盖语义互不相同、不可互换**：

| 手法 | 覆盖语义 | 源码依据 |
|---|---|---|
| `fixtures` | **强制覆盖**，每次 migrate 抹回 | `data_import.py:362` 传 `force=True` |
| `module/custom/` | 增改不删 | — |
| 标准记录 json | 按 `modified` 时间戳判据 | — |
| `after_install` | 一次性，改了不重跑 | — |

五类对象横跨「代码」与「配置」两端，用同一种手法必有一端错。

## 决策

**按语义分派，四法混用**：schema 扩展走 `module/custom/`；业务配置走 `after_install`（一次性建立、之后属客户可改）；基础数据与演示数据集走 app 内数据文件 + whitelisted 方法（见 ADR-0010）；译名走 csv（见 ADR-0006）。每类对象的手法选择以「该对象被改动后是否应当被抹回」为判据。

## 后果

**正面**
- 每类对象的覆盖语义与它的实际归属对齐：客户能改的不被 migrate 抹回，开发期资产该抹就抹。
- 避免了 `fixtures` 的强制覆盖套在业务配置上这个错误。

**负面**
- 同一件事的落地位置可能分散在多处，读代码时要按对象类别去找，没有单一入口。**这一点在 ADR-0007（中国财税）上最明显**——「建出 13% 销项模板」这件事分散于模块／`hooks.py`／`after_install` 三处。
- `after_install` 的「改了不重跑」意味着每次改配置要自己写 patch，长期是负债。

**中性**
- 四法混用要求每个新对象落地前先判语义，这是持续的判断成本，不是一次性的。

## 备选方案

**五类配置全用 `fixtures`** —— 一种手法走遍，无须逐类判断。**没选**：**强制覆盖语义套在业务配置上是错的**——`data_import.py:362` 传 `force=True`，故客户改了 Company 默认科目，下次 migrate 被抹回；且 `Custom Field` 走 fixtures 与 `module/custom/` 的既有约定冲突。见 NV-033。

**五类配置全用 `after_install` 代码**（zelin 的做法）—— 全部逻辑集中在一处，可读性最好。**没选**：**改了不重跑**，每次改配置要自己写 patch，长期是负债；且 V-09c 已查明 zelin 四个 setup 函数全包在裸 `except` 里只 log（本轮复核实为 **5 处**），**这条路的典型失败形态正是「建完看不出问题、做账时才发现」**。见 NV-034。

## 关联

- 依赖：ADR-0001（单 app 是「一份 hooks.py 里分派」的前提）
- 被依赖：ADR-0006（译名走 csv 是本分派的一个实例）、ADR-0007（中国财税的三处分派）、ADR-0010（数据生成走 app 内数据文件）

## 失效条件

若上游改变任一手法的覆盖语义。
