# ADR-0001: 自有 app 采用单 app 形态

- 状态：accepted
- 日期：2026-09-25 / 决策者：用户裁决（C 步第 5 步①），Claude 提选项
- 对应决策：DEC-052

## 上下文

本项目当前 `frappe-bench/apps/` 下只有 frappe 与 erpnext，**自有 app 尚未建立**（V-14 探针侧证：`installed_apps` 仅这两个）。需求图谱 v1.1 的全部需求代码都要落进它（或它们）。

本决策必须排在第一位，因为 ADR-0003（装载顺序）、ADR-0006（译名落点）、ADR-0007（中国财税覆盖位归属）全部以「自有 app 有几个」为前提。

关键机制前提：**四处 `[-1]` 机制都取 `installed_apps` 的顺序**——区域覆盖（`erpnext/__init__.py:152`）、whitelisted 覆盖（`frappe/__init__.py:1577-1580`）、类覆盖（`base_document.py:110-125`）、译名 csv（`translate.py:179`）。自有 app 每多一个，要守住的位置就多一个。

## 决策

自有 app 只建 **1 个**，内部按模块分目录（财税／译名／演示／生产增强）。`installed_apps` 里只占一个位置，四处 `[-1]` 语义只需守住一个位置。

## 后果

**正面**
- IM-007 的升级后自检只需断言一个模块前缀，而非 N 个位置的相对序。
- 模块间共享代码无跨 app 依赖；只需一次 `install-app`。
- 需求图谱 §7.3 明写的两处共享得以落地：数据生成机制与 CR-008 共享「同一套机制、不是两套」；事件协议推送侧是跨 Phase 资产。

**负面**
- 演示专用代码（操控脚本、100+ 条数据生成器）与长期资产同仓发布。客户正式库要么带着、要么靠开关关掉。
- 单个 `hooks.py` 会长（可 import 拆分缓解）。

**中性**
- 「演示专用 vs 交付资产」这条业务边界在代码里不再有物理对应物，只能靠模块目录与 Settings 开关表达。本项目定位是「可信度优先、演示即预交付」，该边界本就不稳定，故此处不视为损失。

## 备选方案

**B 两 app（`erx_core` + `erx_demo`）** —— 演示代码可整体不进客户正式库，边界与「演示 vs 交付」对齐。**没选**：两个自有 app 之间也要定序，四处 `[-1]` 要守两个位置；且边界会划错两处——需求图谱 §7.3 明写数据生成机制是「同一套机制，不是两套」（CR-012 ↔ CR-008），而 CR-008 的事件协议是跨 Phase 资产（远期 React 重写要复用推送侧），住在 demo app 里名不正。见 NV-030。

**C 按域分 4 个（`erx_cn_tax` / `erx_i18n` / `erx_demo` / `erx_mfg`）** —— 每个域可独立演进、可单独开源。**没选**：四个 app 的相对顺序都要定且要守；**译名分散在多份 `zh.csv`，而后装的覆盖先装的**（`translate.py:179`）——同一个词在两个 app 里译得不同时，生效的那个取决于装载顺序，这是最难查的一类 bug；四份 `hooks.py`；单人 AI 开发拿不到多 app 的隔离收益，成本照付。见 NV-030。
