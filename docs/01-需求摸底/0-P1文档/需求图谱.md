## 一、定位

**一句话定位**：把 ERPNext 改造到"客户在演示现场看到的每个界面都是上线后真要用的那个"，并让弹簧厂全链业务在客户面前从销售漏斗一路跑到收款。

**目标用户**：**客户方决策者**（演示的观众）——首个潜在客户是弹簧厂，规模与需求均未经实地考察。执行者（本项目用户）是生产者，不是目标用户群。

**核心价值**：**可信度优先**（DEC-024，A 案）。演示即预交付，没有"演示能跑、上线不能跑"的落差；交付物全是长期资产；成本数字正确，经得起客户会计追问。

由定位推出的三条约束，是后续一切的前提：

1. **译名须全量无缺口**——这正是 A 案与 B 案（业务契合优先）的分野。用户原话：「不应该出现有些翻译了有些没翻译的情况」。
2. **服务端缺陷须逐一堵死**，不止界面层。
3. **演示须有数据正确的完整闭环样本**。

**并在演示编排中内置摸底问点**（吸收 B 案唯一不贵的那一项）：每环节预留"你们厂这里怎么做"的问点。**该清单不是一次性交付物，而是长期跟厂边调研边改进的机制起点**（第 24 步用户裁决）——这反过来要求译名做成可配置文件、而非一次性翻译动作。

**演示范围**：**S1 已定稿的 23 环节最小闭环**（DEC-025）+ **CRM 销售漏斗三环的前向延伸**（DEC-038）。质检、外协、月结不演示，改现场口头询问。

**范围分解判定：单目标**（DEC-023，R2 复核维持）。三条拆分标准逐条不成立——全部需求服务同一个场景（客户面前跑通弹簧厂全链）；CRM／生产／财务三块共用同一条单据链，且 CR-012 要求它们在同一批数据上贯通；目标用户只有一个。**唯一部分成立的是"外部操控机制的目标用户是开发者"**，处置办法是把它限定在"够演示用"一档（CR-008），超出部分留后续 Phase。

## 二、核心需求

> 判据：**缺了这个目标就不成立**。共 14 条。
> **超 5 条的降级自问已做**：14 条中 6 条属"演示现场会出错"（CR-003 / CR-004 / CR-009 / CR-010 / CR-011 / CR-012）、4 条属"演示内容本身"（CR-005 / CR-006 / CR-007 / CR-013）、4 条属前置与基础设施（CR-001 / CR-002 / CR-008 / CR-014）。降任一条，"可信地跑通全链"这句话就缺一块。逐条降级检验见回执。

| **CR-003** | **完工入库费用科目默认值** | Company 的 `expenses_added_to_stock_account` 出厂为空，故每张完工入库单要手填 N 行费用科目（N = 工序数 × 成本构成数，实测 11 行）。演示时手填不可接受，**且填错即成本进损益表而非库存资产、成本核算直接错** | 客户方决策者 | → CR-011、CR-012 |
| **CR-004** | **工艺损耗反算投料量** | `planned_qty` 直接取 SO 待交数量、不按 BOM 损耗率反算，故每张按销售订单生成的工单**必然短交**（SO 5000 支 + 5% 损耗 → 完工 4750 支）。"一路下一步"走到排产就会暴露，**UI 层补不了**。注：库存层其实是通的（`Job Card.process_loss_qty` 到 WO 的汇总链完整），**不通的只是计划层** | 客户方决策者 | → CR-011、CR-012 |
| **CR-005** | **中国会计科目表（选定 + 补弹簧科目）** | 客户会计看不到熟悉的中国科目名，账务可信度垮掉。**准则已定：小企业会计准则(2024)**（DEC-047）——实测一般企业准则不是小企业的超集（按科目名 SME 独有 47 条即已否定；编号体系还是 4–7 位对 5–8 位），且在增值税明细上严格更差（`应交增值税` 下缺进项／销项／转出未交增值税／进项税额转出／已交税金五条）。**公司一旦开始记账科目表不能换**，故它是建演示公司的硬前置 | 客户方决策者（客户会计） | CR-014 →｜→ CR-006、CR-007、CR-012 |
| **CR-006** | **增值税逻辑（进项销项分离、四档税率、价税分离）** | 客户会计一定会问增值税怎么算。原生 `Tax Template` 三件套可表达（V-04 三项实跑通过：价税分离 113→100+13、多档位 13%+6%=19、进项侧同样），zelin 提供现成 7 档。**⚠ 手填 `item.item_tax_rate` 无效**——会被 `update_item_tax_map()` 重算覆盖，必须走真的 `Item Tax Template` | 客户方决策者（客户会计） | CR-005、CR-014 → |
| **CR-007** | **中国财务三表 + 月末结转 + 银行对账** | 中国法定三大报表齐全才经得起客户会计追问。含：资产负债表（中国式左右双栏）、利润表、**现金流量表**、月末结转（进项税额转出 + 未交增值税，**原生 Tax Template 表达不了**，属期末账务）、银行对账（只导入流水做匹配，不需资质）。**⚠ 现金流量表不是原生报表配置能产出的**——须自建可提交单据 + 从 GL Entry 按现金银行科目拉流水（直接法） | 客户方决策者（客户会计） | CR-005、CR-006、CR-014 → |
| **CR-008** | **演示脚本的半自动操控机制** | 23 环节手工点约需 40 分钟以上，现场手滑即中断。形态定为**半自动**（DEC-042）：脚本推一个事件 → 界面跳到该节点、单据打开、字段填好，**停在那里等讲解**；人按一下再走下一步。**"可从任一节点起跑"由此自然满足**（每节点一个独立事件）。技术路径：后端在自有 app 的 whitelisted 方法内 `publish_realtime(event, user=演示用户, after_commit=True)`；前端 `app_include_js` 注入监听，走 `cur_frm.save()`/`savesubmit()` 等 API 而非模拟 DOM 点击。**客户看到的是"界面自己完成了操作"，不是"鼠标自己在动"**（DEC-041） | 客户方决策者；执行者（演示者） | CR-002、CR-011、CR-012 →｜↔ EX-002（共享事件协议与推送侧） |
| **CR-009** | **realtime 心跳自检** | **realtime 断连是静默的**——演示时若断了，症状是"脚本在跑、界面不动"，且当场分不清是脚本没跑还是链路断了。已确立的事实：**S1 全程实操都是在 realtime 死的环境下做的**（socketio 端口错位，已两头同挪 9100 并由用户实证）。做法：演示前推一个事件、前端收到后回显，确认链路通再开始 | 执行者（演示者） | CR-008 → |
| **CR-010** | **导航按业务流重排** | 客户跟不上"接单→排产→领料"的顺序，要在 19 个工作区里找入口。**并须折叠 CRM／HRMS／Insights／Raven 四个 App 带进来的无关入口**——HRMS 的整套 HR 模块（考勤／请假／招聘／薪资）与弹簧生产无关，演示时客户会看到一堆噪音。⚠ 走零开发（改记录）还是出 fixtures 取决于 LG-089 实测 | 客户方决策者 | CR-002 →｜→ EN-001 |
| **CR-011** | **闭环样本 A/B 两套** | 演示数据须是真实弹簧产品——客户看到不认识的产品名，"这系统装得下你的厂"这句话弱一半。产品范围**压簧 + 拉簧**两类（均取自国标参数表、可溯源；扭簧无国标尺寸参数表，**不编造数值**），命名用**国标型号标记法**。**A 套从零演示 + B 套已推进到各节点**——这是演示兜底形态（DEC-028）：A 套第 N 步卡住即切 B 套那条"已过第 N 步"的单据往下走。兜底是数据准备而非代码能力，故并入本项 | 客户方决策者；执行者（演示者） | CR-003、CR-004、CR-005、IM-001 →｜→ CR-008 |
| **CR-012** | **100 条全链数据集 + 生成器** | AI 分析需要有统计意义的数据量 + 可被发现的规律或异常，而两套闭环样本的量级只是"能走通一遍"。口径＝**全链**（从销售漏斗到生产到交付货物全流程，用户第 25 步明示）。三项数据要求：**多个 BOM**（据公开资料）、**数十个供应商与客户**、**最好带历史成交单价**。**⚠ 必须走单据、不能裸插数据**——直接写库、或 insert 时带 `docstatus:1` 会跳过 `on_submit`，则 GL Entry 与 SLE 不生成、财务与库存不一致，**AI 分析出来的结论是错的**。**本项是演示前全部工作的汇流点，必须排最后** | 客户方决策者；EX-001 的数据源 | CR-003、CR-004、CR-005、CR-013 →｜↔ CR-008（共享生成机制）｜→ EX-001 |
| **CR-013** | **CRM 接入 + 销售漏斗** | 演示线起点前移——`Lead → Deal → 报价 → 接单 → … → 收款`，**衔接点是 Quotation**（`ERPNext CRM Settings` 装了表单脚本，Deal 页面有按钮直接生成 ERPNext 报价单）。漏斗七档带概率（Qualification 10% → … → Won 100%），`probability` 字段使金额×概率的加权预测可算。**客户自己是销售、看得懂漏斗**。侵入性是六个候选 App 里最低的一档（`doc_events` 只挂三个具体 DocType，不是 `"*"`），且不与中国本地化方案抢覆盖位。⚠ 代价：自带中文未译率 38.7%（689 条），已纳入 CR-002 范围 | 客户方决策者 | → CR-012｜↔ CR-012（衔接点 Quotation） |
| **CR-014** | **并入 zelin 财税模块（MIT）** | CR-005～CR-007 的共同实现前置。zelin `erpnext_china` 做的正是"不需资质的内账部分"（全仓零 `Journal Entry`、零对外接口、零开票），四份科目表／7 档税模板／三张报表均现成可用。**取并入式（抄源码进自有 app），不走 `bench get-app` 整包安装**（DEC-046）——三条实测理由：它 `get_chart` 硬编码 `apps/erpnext_china/` 路径；它 `install.py` 会改 System Settings 并**把不在它 45 个中文单位表里的所有 UOM 禁用**；它 `doc_events` 接 Company 三钩子并置 `ignore_chart_of_accounts=True`。**⚠ 自带一个真 bug 必须修**：`tax_template.json` 小企业准则(2024) 键下 P13 销项引用 `222105`/`22210005` 两个不存在的科目号（应为 `2221005`），而装载包在 `try/except` 里只 log ⇒ **最常用的 13% 销项模板会静默建不出来** | 执行者（实现前置） | → CR-005、CR-006、CR-007 |

**⚠ 两条落地纪律（不是需求，但缺了会让上表若干条白做）**

1. **报工工时必须填合理值**——工序成本按实际报工工时计是 ERPNext 的正确设计而非缺陷（DEC-026，用户改判）。任务单计时几秒即导致工序成本记 0.27 元而非应有的 433.3 元、毛利率虚高 40 个百分点。**这靠培训与流程约束解决、代码改不了**，故不列为需求；但**样本数据（CR-011、CR-012）的工时必须合理**，否则客户看到漂亮但错误的成本数字，比不演示更糟。
2. **不要在改 CR-004（工艺损耗）这类服务端逻辑的同时装着 Raven 与 Flow**——`doc_events` 累加执行，两者都对 `"*"` 挂了五个写事件，写路径上多两层第三方 hook 会让问题定位变难。

### 7.4 App 接入的三条边（CR-013 / IM-005 / IM-006 / EX-001）

四个 App 的接入（CRM、HRMS、Insights、Raven）是用户已下的指令，**它们对其余需求的影响是同一组三条边**，故合并在此说明，不在主链里各画一次：

```
CR-013 CRM     ─┐
IM-005 HRMS    ─┤                  ┌─→ CR-002 译名覆盖档（各自的未译条数并入其范围）
IM-006 Insights─┼─（每个 App 都有）─┼─→ CR-010 导航重整（各自的无关入口须折叠）
EX-001 Raven   ─┘                  └─→ 写路径多一层 doc_events（Raven 对 "*" 挂 5 个写事件）

另有两条只属个别 App 的边：
CR-013 CRM  ─→ CR-012 数据集      （漏斗是数据链起点，硬次序④）
IM-005 HRMS ─→ IM-016 计件工资    （提供发放侧的 Additional Salary 注入口）
```

**这组边的实际含义**：**每接入一个 App，CR-002 与 CR-010 的工作量就增加一份**——这是"接入四个 App"这个决定的真实代价所在，而不是各 App 自身的安装成本。四者合计给 CR-002 带来 3037 条自译（Raven 独占 1867 条、占 61%）。

### 7.5 §3.2 那批（演示之后）的内部依赖

```
IM-007 regional_overrides 自检   ← 依赖 CR-005/006/007 已落地（它守的就是那套覆盖）
IM-009 安全库存自动计算  ─→ IM-008 再订货点回写   （σ 与 Z 算出来，推荐值算式才完整）
IM-010 CRP 产能负荷报表  ─→〔阶段 C 的 ATP/CTP〕  （没有产能计划就算不出交期承诺）
IM-013 工时基准量解耦    ─→ IM-014 优先级+换型矩阵 （同属工时模型，解耦后换型才好表达）
IM-015 工序间数量传递    ← 与 CR-004 同源（同一缺口的计划层另一面）
IM-016 计件工资          ← IM-005 HRMS（发放侧）+ IM-003 摸底确认是否行计件制
IM-011 SPC+CPK ↔ IM-010 CRP        （共享"记录层有、计算层缺"这一形态，无先后）
IM-012 UOM 批次级换算              （无依赖，可随时做；弹簧特有）
```

**本批的共同性质**：除 IM-007 外，全部是**为已存在的记录层补计算层**——读数已在 `Quality Inspection Reading`、工时已在 `Job Card Time Log`、产能参数已在 `Workstation`，缺的是算法。**故自研重心是计算层，不是重建记录层。**

**⚠ 但这条模式不可反推**：采购块有三处是真算法（`Supplier Scorecard` 真能算分且挂 daily 自动跑、`Blanket Order` 累计量控制、`Item Lead Time` 确有消费方），销售侧另有四项"以为缺、实际有完整计算层"（信用额度硬拦、价格阶梯、副产品成本分配、成本卷积）。**用它当排查视角有效，用它断定"某处必定缺算法"会错。**
