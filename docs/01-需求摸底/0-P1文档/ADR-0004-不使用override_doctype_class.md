# ADR-0004: 不使用 `override_doctype_class`，挂逻辑一律走 `doc_events`

- 状态：accepted
- 日期：2026-09-25 / 决策者：**用户第 17 步补裁**，Claude 提议
- 对应决策：DEC-055

## 上下文

本条起于 ADR-0003 议题中的一处读码发现（需求图谱与工作量表均未记）：**HRMS 覆盖了 `Payment Entry` 的 DocType 类**（`EmployeePaymentEntry`），而 `Payment Entry` 正压在演示闭环的收款环节上。

机制细节：`base_document.py:110-125` 取 `override_doctype_class` 的 `[-1]`，并校验该类须为**原始类的子类**。按 ADR-0003，`erx_core` 在 HRMS 之后 ⇒ 我们末位胜出，即**静默绕过 HRMS 的 `EmployeePaymentEntry`**。而 `installer.py:325-331` 遇到这种情形**只警告不阻止** ⇒ 失效形态是静默的。

**⚠ 本条同样有越权史。** C 步第 2 步③的原记录写成「附带硬约束同时定案」，而用户当时只答了选项字母 A（末位）；硬约束是 Claude 的提议（第 16 步③核实：`override_doctype_class` 与「硬约束」在用户发言里均零命中）。**用户第 17 步补裁采纳。**

## 决策

`erx_core` **不使用 `override_doctype_class`**。需要在文档生命周期上挂逻辑的，一律走 `doc_events`（累加执行、不互斥）。

## 后果

**正面**
- 不会静默绕过 HRMS 的 `EmployeePaymentEntry`，收款环节的 HR 相关行为得以保留。
- `doc_events` 是累加语义，多 app 挂同一事件时各自都跑，不存在「谁赢」的问题。
- 侵入度表全表只有 3 项 L4 且无一项是类覆盖，故这条约束**现在不花代价**。

**负面**
- 若某需求确实只能靠改类方法实现（如要改某个方法的返回值而非在其前后加动作），`doc_events` 表达不了，须重新评估本约束。

**中性**
- `doc_events` 累加带来另一种风险：同一事件上多个 app 的 handler 执行顺序按装载序，且彼此可见对方的改动。**ADR-0007 的 Company 三钩子正踩在这一点上**（LG-101：HRMS 也挂 `Company.on_update`）。即本约束躲开了「静默互斥」，换来的是「同钩子交互」，两者都要守，但后者可观测、前者不可观测。

## 备选方案

本条是补裁项，无独立选项表。原始提议只有「采纳／不采纳」两档，不采纳即默认允许类覆盖——其代价就是上文「上下文」节所述的静默绕过。**故没有第三条备选方案**，如实记录。

## 关联

- 被依赖：ADR-0007（中国财税的 Company 钩子因本约束必须走 `doc_events`，不得走类覆盖）
- 取代：无

若某需求确实只能靠类覆盖实现，须重新评估并登记。
