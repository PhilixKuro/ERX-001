### 明确记为不做的三条

> 自评审①要求图谱里每个功能都被分到某个议题**或明确记为不做**。图谱 37 条里 34 条已分入上表六个议题，**余下三条在此显式记为 P1 不做**——不是漏项。

| 编号 | 需求 | 分级 | 不做的理由 | 将来做的触发条件 |
|---|---|---|---|---|
| **DF-001** | 弹簧参数结构化字段 | 暂缓 | **改用国标型号标记法后零开发即可满足演示**——`YA 1.2×8×40 GB/T 2089` 本身就是行业认的写法。且三类弹簧参数集不同（拉簧多初拉力、扭簧是扭角），结构化要么分三套要么取交集。**另：属性定义层原生已有数值能力**（`Item Attribute` 的 `numeric_values`／`from_range`／`to_range`／`increment` 真做范围与步进校验），故"线径 0.5~5.0 步进 0.1"这类约束不必自建 | 客户明确要求按线径筛选／分组，或报表要按规格分类时 |
| **EN-002** | 拼音检索 + 演示环境可重置性 | 增强 | **两半都有现成替代**：可重置性的现成手段是 `20260922_145623` 备份 + `docker/restore.sh`（**已可用，只是手工**），演示后 restore 一次即可；拼音检索是 `PH-P1007` 延迟需求。**判据是增强级定义"不做不影响演示成立"** | 可重置性：多客户连续演示、手工 restore 成为负担时。**⚠ 拼音检索那半的唤醒条件名义上是「与译名改造同批」（即 S6）**——本步判为不做是因为它不影响演示成立，**若要与 S6 捆做须用户裁决**，见 RL-06 |
| **EX-002** | 演示录屏与自动记录／移动端查看 | 实验性 | 价值不明——用户可能只要演示成功、不需录；ERPNext 有移动端但项目内从未验证，且非演示必需 | **演示成功一次之后**，若要复用演示过程、或需远程展示。⚠ **它是 P-1 前瞻性设计的锚点**（架构文档 §四），故 P-1 的预留照做、但 EX-002 本身不实现——这正是 RL-04 交代的那处锚点偏弱 |

### S3 演示前置（原子，`shapeApply`）

**目标**：把三件"不定下来后面就会做错"的事定下来，**全部无编码**。

| 项 | 内容 |
|---|---|
| **类型** | 原子 |
| **Workflow** | **`shapeApply`**（A 讨论 → B 按讨论改文件 → C 落实审核）。判据：三项产出都是"讨论收敛时已知每处改哪个文件的哪一节"（术语标准表、参数复核结论、问点清单），**无需先冻成开发方案**，故不取 `plannedDev` |
| **纳入功能** | **CR-001** 目标侧术语标准／**IM-001** 弹簧行业参数复核／**IM-003** 内置摸底问点清单 |
| **前置依赖** | **无**（图谱 §7.1 起点）。IM-003 按 §7.6 与一切并行，放这里是因为它与 CR-001 共享"须用户参与"这一性质 |
| **产出后效** | CR-001 → S6 的 CR-002（译名要有目标侧标准才定得下名）；IM-001 → S7 的 CR-011（不复核则样本带错数值）；IM-003 → 现场问回来的用词回流 CR-001，且**决定 S8G 的 IM-016 要不要做** |
| **工作量** | **3–4 人日**（CR-001 1／IM-001 1–2／IM-003 1，含 LG-061 实测 0–0.5） |

**本议题执行所需的清单与边界**：

1. **CR-001 的范围已被图谱限死**：**只统一「收付款方向」与「撞名」两类最确定的**，行业术语留到实地考察后。**不要在本 Stage 试图定全部术语**——914 组撞名里绝大多数不在演示线上。
2. **撞名的两条已核实来源**：`Accounts Receivable`／`Debtors` 与 `Opening & Closing` 两条**继承自官方 `erpnext/locale/zh.po`**（`:2244`／`:15827`／`:33973`），不是 zelin 引入的。
3. **`context` 参数解决不了撞名**（图谱已查明）：`context` 是按 source + 场景**拆分**译文，解决"同一源词多义"；撞名的形态相反——**多个源词撞到同一目标词**，只能改其中一方的用词。**故 CR-001 的产出必须是"哪个源词改用哪个新词"，不是"加 context"。**
4. **IM-001 的复核对象只是"实际要用的那几行"**，不是整张国标表。已知矛盾：d=5/D=30 → 661 vs 962；d=8/D=50 → 1154 vs 2203（同源页面内部自相矛盾，该站表格系 OCR 转录）。
5. **一条填字段时会踩的**：**`12Cr18Ni9` 不对应 `SUS304`**（它对应 SUS302/AISI 302；SUS304 对应 `06Cr19Ni10`）。
6. **LG-061 实测在本 Stage 做**（改 `standard=1` 记录会不会被 `bench migrate` 覆盖）——它决定 **S6 的 CR-010 走 L0 还是 L1**，是那条需求的开工前置。放本 Stage 是因为它零依赖且极小。

**四者之间无硬依赖**——故它们的次序是排期选择而非约束，可按性价比或按人手并行。

**本议题执行所需的清单与边界**：

1. **S8G-S1 是全清单性价比最高的一段**（工作量表排期建议 1）：3.5–4.5 人日拿到“再订货点自动算 + 安全库存自动算 + 覆盖失效告警”，其中 **IM-008 算法现成、只差回写**。**本议题一开工就做它。**
2. **本批 11 条的共同性质**：除 IM-007 与 DF-002 外，**全部是为已存在的记录层补计算层**——读数已在 `Quality Inspection Reading`、工时已在 `Job Card Time Log`、产能参数已在 `Workstation`，缺的是算法。**故自研重心是计算层，不是重建记录层。**
3. **⚠ 但这条模式不可反推**：采购块有三处是真算法（`Supplier Scorecard` 真能算分且挂 daily 自动跑、`Blanket Order` 累计量控制、`Item Lead Time` 确有消费方），销售侧另有四项“以为缺、实际有完整计算层”（信用额度硬拦、价格阶梯、副产品成本分配、成本卷积）。**用它当排查视角有效，用它断定“某处必定缺算法”会错。**
4. **IM-007 实测第一步须确认 `get_region()` 对中国返回的字符串是否真是 `China`**。
5. **IM-014 开工前置是 LG-088**：须先实跑验 `scheduled_time_logs[-1]` 末行约定。
6. **IM-010 同时是阶段 C 的 ATP/CTP 前置**——没有产能计划就算不出交期承诺。**勿被 MRP 报表里那列 `Capacity` 误导**：它取自 `Item Lead Time.capacity_per_day`、是物料级的，与 Workstation/Routing 无关。
7. **⚠ 两套提前期字段并存**（`Item Lead Time.purchase_time` 与旧的 `Item.lead_time_days`，消费方不同）：**IM-008 与 IM-010 都会碰到，须统一口径**，否则“改了一个另一个没生效”。
8. **IM-016 的计算侧装不装 HRMS 都得自己写**（`COMPONENT_EVAL_GLOBALS` 只白名单 13 个数学/日期函数，薪资公式读不到 Job Card 任何东西）；**HRMS 省的是发放侧**。
9. **P-3 前瞻性设计在本议题兑现**：`modules.txt` 追加第 2 个模块（生产增强），承载 IM-010 CRP 与 IM-011 SPC 两个 Report。判据（什么该成模块）须写进 app README。
