# ADR-0010: 数据生成走 app 内 whitelisted 方法 + app 内数据文件

- 状态：accepted
- 日期：2026-09-25 / 决策者：用户裁决（C 步第 12 步①），Claude 提选项
- 对应决策：DEC-061

## 上下文

CR-012 要求演示站点有跨时间的成体系业务数据（100+ 张单据，倒填 `posting_date`）。需求图谱 §7.3 已把「与 CR-008 共享同一套机制」写成事实，不是待定项。

会计语义前提：单据一旦提交即产生 GL Entry 与 SLE，**「重跑一次」在会计语义上不是幂等操作**。

## 决策

**数据生成器住在 `erx_core` 内**：whitelisted 方法作入口，数据集作 app 内 json 文件。**不追求幂等，改为可重置**——重跑前先清掉上次生成的数据，而非试图让生成本身幂等。

## 后果

**正面**
- 与 ADR-0008 的演示操控共享同一套机制，需求图谱 §7.3 的「同一套机制、不是两套」得以落地。
- 省掉认证与 CSRF 整块（在站点内调用，不经 HTTP）。
- 出错拿到完整 traceback，不是状态码加片段。
- 100+ 张单据无 HTTP 往返，快一档。

**负面**
- 数据生成代码随 app 发布到客户正式库（ADR-0001 已接受这个后果）。
- 「可重置」意味着要另写一套清理逻辑，且清理的牵连面要自己算清（删单据牵动 GL／SLE／库存）。

**中性**
- **⚠ `demo/` 包内部「演示操控」与「数据生成」的共享深度**：本 ADR 只定「共享同一套机制」这件事本身。C 步复核建议第二节把「共享到什么程度未定——是共用建单辅助函数，还是共用一套节点定义？」点名交给 D 步。**本步裁定：共用建单辅助函数，不共用节点定义。** 理由：23 个演示节点的粒度是「演示者讲一段话的量」，而数据生成的粒度是「一张单据」，两者不同构——强行共用节点定义会把演示节点的粒度强加到生成器上，而生成器根本不需要分节点。建单辅助函数（如「建一张采购收货并提交」）两侧粒度相同，共用是实的。
- LG-100 未验：倒填 `posting_date` 时建单顺序与估值结果的关系。若生成器按「先建完全部采购再建生产」跑而 `posting_date` 交错在几个月内，估值可能与真实按时间推进不同。CR-012 开工时先验。

## 备选方案

**外部脚本 + API v2** —— 生成器与 app 解耦，可独立运行。**没选**：须自己处理认证与 CSRF；**与 CR-008 不共享机制**（演示脚本在 app 内、生成器在 app 外，两套），使需求图谱 §7.3「同一套机制」落不了地；100+ 张单据的 HTTP 往返慢一档；出错只拿到状态码与部分 traceback。见 NV-042。

**直接写库** —— 最快。**没选**：**违反需求图谱硬约束**——跳过 `on_submit`，GL Entry 与 SLE 不生成，**AI 分析出来的结论是错的**（EX-001 建在真实账务数据上）。见 NV-043。

## 关联

- 依赖：ADR-0001（单 app 是共享机制的前提）、ADR-0005（数据集走 app 内数据文件是「按语义分派」的一个实例）
- 被依赖：EX-001 的 AI 分析建在本机制生成的数据上
- 取代：无

## 失效条件

若将来要从外部系统驱动数据生成。
