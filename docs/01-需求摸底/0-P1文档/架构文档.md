## 一、架构总览

本系统是一个**两 app 扩展形态的 ERPNext v16 站点**：不 fork 上游、不改上游源码，自有代码分两个 app——**`frappe_china`** 装中国财税、译名与导航、对原生 ERPNext 与官方 app 的修复、事件协议推送侧，**客户正式库一定装**；**`frappe_debug`** 装演示操控、数据生成与自动化测试，**客户正式库不装**。二者经官方接入点（3 个 whitelisted 方法覆盖、`doc_events`、`app_include_js`、`translations/zh.csv`、`after_install`、`after_migrate`）挂接到 erpnext 上；中国会计准则的科目表与报表以**并入式**取自 zelin 的 `erpnext_china`（构建期依赖，站点上不存在该 app；科目表原样抄、胶水层重写）；演示操控经一个单一 realtime 事件 `erx_demo_step` 半自动驱动 desk 界面，数据生成与它共享同一套机制。**`frappe_china` 压在全部业务 app 之后**这一点不是操作细节而是架构基石——上游四处 `[-1]` 取值机制（区域覆盖 / whitelisted 覆盖 / 类覆盖 / 译名 csv）的胜出权全部依赖它；`frappe_debug` 虽在末位，但不在这四处注册任何条目。顺序的守护由 `after_migrate` 自检承担。

## 三、模块划分

**⚠ 先读本节的单位约定**（否则会把普通包当模块）：Frappe 的「模块」是 `modules.txt` + `Module Def`，每个 `Module Def` 可能自动生成一条侧栏进 boot（`__init__.py:899`、`installer.py:749-755`、`workspace_sidebar.py:239-252`）。**该界面成本带三条限定**（ADR-0012「上下文」）：站上有与模块同名的 `Workspace Sidebar` 则不生成（`workspace_sidebar.py:243`）；没有可见条目的侧栏整条丢弃（`boot.py:500-504`），纯代码模块本就不产侧栏；`hammer` 图标是死值。故本项目只为**真需要 `Module Def` 的东西**声明模块（DocType / Report / Page / Workspace），**覆盖实现、接口、工具放普通 python 包**——与官方 app 一致（DEC-108）。`hooks.py` 与安装入口只做接线。判据须写进各 app 的 README。见 ADR-0012。

**两个 app**（ADR-0013）

| app | 装载位置 | 客户正式库 | 内含单位 | 占 `[-1]` |
|---|---|---|---|---|
| **`frappe_china`** | 全部业务 app 之后 | **装** | §3.1 `cn_tax`（模块＋普通包）／§3.2 `i18n/`／§3.3 `patches_mfg/`／§3.4 推送助手／§3.5 `workspace_sidebar/`／§3.6 `desktop_icon/` | **四处全占** |
| **`frappe_debug`** | 末位 | **不装** | §3.4 演示操控与数据生成（`data/`／`nodes/`／`drivers/{desk,spa}`） | **一处不占**（守法约束见 ADR-0003） |

依赖单向：`frappe_debug` 在 `required_apps` 里声明 `frappe_china`、调用其推送助手；`frappe_china` 不引用 `frappe_debug` 的任何东西。

共 7 个单位（`frappe_china` 6 个、`frappe_debug` 1 个）。低于 D 步 Spec 的规模自查阈值（10 个）。

### 3.1 `cn_tax`（`frappe_china` 的模块，`modules.txt` 唯一一项；逻辑可在普通包内）

| 项 | 内容 |
|---|---|
| **职责** | 按中国会计准则出账与出表。 |
| **对外接口** | ① **3 个**被覆盖的 whitelisted 方法：`get_charts_for_country`／`get_chart`／`get_coa`（均在 erpnext 业务层）<br>② Company 的 3 个 `doc_events` handler：`before_insert`／`on_update`／`after_insert`<br>③ 4 个 DocType：现金流四件套（`Cash Flow`／`Cash Flow Item`／`Cash Flow Subtotal`／`Cash Flow Code`）<br>④ Report：资产负债表／利润表／漏科目检查（自写）；现金流量表法定格式展示（形态留 S4 的 C 步）<br>⑤ `after_install` 的入口函数（中文计量单位、关闭凑整合计）<br>⑥ 月末结转的 whitelisted 方法<br>⑦ 银行流水导入前置处理<br>⑧ **建账结果自检函数**（供 IM-007 调用；`.get()` 语义、缺键告警不抛异常；签名留 S4 的 C 步） |
| **依赖** | erpnext 的 `Account`／`Company`／`GL Entry`／税模板三件套（`Sales Taxes and Charges Template`／`Purchase Taxes and Charges Template`／`Tax Rule`）／`Bank Statement Import`／`Bank Transaction`；zelin 的**一份**科目表 JSON（`cn_smes_chart_of_accounts2024.json`）与税模板数据（并入式，MIT） |
| **所属分解单位** | P1-S4 中国财税；消费方为 P1 后续全部 Stage |
| **关联决策** | ADR-0007（并入形态）／ADR-0012（模块划分）／ADR-0004（钩子须走 `doc_events`）／ADR-0005（配置数据的分派）／ADR-0013（落点） |

**不覆盖 `get_all_nodes`**（v1.2 更正）：v1.0 把它与另三个并列为「erpnext 的 whitelisted 方法」，但它**在 frappe 框架层**（`frappe/desk/treeview.py:10`），且 `:17` 已自行调用 `override_whitelisted_method`，`get_coa` 的覆盖自动生效，zelin 那份是纯转发。省掉它也省掉了唯一一处框架层覆盖。

**科目表路径只能走 L4**：三个方法都**不带 `@allow_regional`**（只有 `@frappe.whitelist()`），`regional_overrides` 对这条路完全不可用、没有 L3 替代路。这是印证 NV-038 的第三条独立判据。

**⚠ 拆分信号**（v1.2 更正）：v1.0 登记「对外接口 16 项，命中『公开接口超过 10 个』；若报表继续增加应把报表独立成第二个模块」。**后半句是反向参照**：erpnext 的 `Accounts` 一个模块装 92 个非子表 DocType 与 52 个 Report，没有为报表另立模块，而是挂 8 份 `module` 全是 `Accounts` 的侧栏 fixture ⇒ 「报表要不要单独露出」是侧栏问题，不是模块问题。`Report.module` 确是报表**列表**的分组依据，但不是**侧栏**的分组依据。接口数随上表变化，确切数目待 S4 的 C 步；**当前不拆**，理由同 v1.0：同属一个内聚职责。

**⚠ 侵入度**：3 个覆盖位与 Company 三钩子是**全站行为**，改它们影响任何建公司动作。这是全表侵入度最高的一处，且已是 L4。

**一处 v1.0 裁定，v1.2 改读法**：v1.0 采纳 C 步的收拢办法——「`after_install` 与 `hooks.py` 里不写业务逻辑，只做接线」，并据此要求「中国财税的逻辑全在模块内」。**前半句仍成立；后半句已由普通包分层取代**（DEC-108）：逻辑可放 `frappe_china` 内的普通包，包的划分留 S4 的 C 步。

**A 案带进来的四处缺口的现行处置**（成因见 ADR-0007「负面」；v1.0 的应对被 S4 需求文档 §4.4 取代）：

| # | 缺口 | 现行处置 |
|---|---|---|
| 1 | **无编号 17% `VAT` 科目不会建出** | **不建**。中国税模板指向 `2221005`／`2221001`，不依赖它 |
| 2 | **`round_off_account` 仍为空** | 连同 zelin 填不上的另 5 个默认科目，**建公司时按 S4 需求文档 §4.4.4 设定**（DEC-097，均待客户会计确认） |

| **依赖** | erpnext 的全部 23 环节业务 DocType；`frappe.publish_realtime`（`realtime.py`）；`frappe_debug` → `frappe_china` 的推送助手 |
| **所属分解单位** | P1-S7（CR-008／CR-009／CR-011／CR-012） |
| **关联决策** | ADR-0008（事件协议与落点）／ADR-0010（数据生成机制）／ADR-0009（节点 js 的注入机制）／ADR-0013（`frappe_debug` 内部三层：`data/` 造数据与建单辅助、`nodes/` 23 节点的业务定义——两者 desk 与 SPA 共用；`drivers/desk`（Cypress）与 `drivers/spa`（Playwright）不共用。具体目录留 S7 的开发方案） |

**推送侧为何在 `frappe_china`**：客户正式库不装 `frappe_debug`；推送能力若在其中，生产环境的 React 界面将拿不到实时推送（DEC-110）。协议本体是契约不是代码，量很小。

**一处 v1.0 裁定（C 步复核建议第二节点名交给 D 步的）**：C 步问「演示操控与数据生成共享到什么程度——是共用建单辅助函数，还是共用一套节点定义？」**本步裁定：共用建单辅助函数，不共用节点定义。** 理由是两者粒度不同构——演示节点的粒度是「演示者讲一段话的量」，数据生成的粒度是「一张单据」；强行共用节点定义会把演示粒度强加到生成器上，而生成器不需要分节点。建单辅助函数（如「建一张采购收货并提交」）两侧粒度相同，共用是实的。详见 ADR-0010「后果·中性」。

## 四、前瞻性设计清单

> D 步 Spec 硬要求：**每条前瞻性设计必须锚定到需求图谱里具体存在的需求编号，不允许悬空预留**。故本清单只列锚得上的三条。

| 编号 | 当前要做的设计 | 为支持哪个未来功能 | 锚点（需求图谱 v1.1 编号） | 不做的代价 | 多做的成本 | 决策 |
|---|---|---|---|---|---|---|
| **P-1** | **事件协议与业务代码解耦**：推送侧只依赖 `(事件名, payload, user)` 三元，不依赖任何 desk API；节点名清单在服务端独立成常量 | 远期 React 重写 UI 时复用推送侧；录屏／移动端查看演示 | **EX-002** | 推送侧与 desk 细节缠在一起，React 重写要把服务端一并改 | **接近零** —— ADR-0008 定的事件协议本就是这个形状（单一事件名 + payload + 节点清单） | **采纳** |
| **P-2** | **译名做成可反复修正的配置文件**：csv 单一来源 ＋ 断言 `Translation` 表为空的自检 | 摸底问点回流的行业用词，要能一轮轮修正译名 | **IM-003** | 译名成为一次性动作，现场问回来的用词无处回流 | **零** —— ADR-0006 已定 csv 单一来源 | **采纳** |
| **P-3** | **`modules.txt` 留出第二个模块的位置**：现在只 1 个，目录结构与 app 的 README 写明「什么该成模块」的判据 | CRP 负荷报表、SPC 控制图（都是 Report，需要 `Module Def`） | **IM-010／IM-011** | 演示后加报表时要么塞进 `cn_tax`（财税与产能报表同组、职责不单一），要么临时改结构 | **零** —— `modules.txt` 可追加（**v1.2 补前提**：`bench migrate` 不调 `add_module_defs`；新模块含 DocType 时 DocType 同步很可能会补建 `Module Def`，**只含 Report 时补不上**——读码、未实测，见 ADR-0012「上下文」第 4 条） | **采纳** |

**⚠ P-1 的锚定弱点，如实交代**（C 步第 15 步要求转写，不得隐去）：P-1 锚的 **EX-002 是实验性需求**，其评估触发条件是「演示成功一次之后，若要复用演示过程、或需异地展示」——**它本身可能不做**。而 P-1 真正的支撑理由不是 EX-002，是「远期 React 全面重写」，**那条在需求图谱里没有需求编号**（它记在项目概况的技术栈远期计划里，不是一条需求）。取 P-1 的实际理由是它**成本接近零**：CR-008 无论如何要设计事件协议，把它设计成不依赖 desk 细节并不额外花钱。故本条**锚点合规但理由偏弱**，已写进 D 回执的复核建议。

**⚠ 一条被有意排除在本清单之外的设计**：**desk js 覆盖登记表**（每处覆盖记类／方法、目标行为、升级复验清单）。它是**采纳的**，但它服务的不是「未来某功能」而是「上游升级」这件持续性的事，**锚不上任何需求编号**。按 Spec「不允许悬空预留」，它不进本清单；它的正确归属是 **ADR-0009 的组成部分**，已写在那份 ADR 的「关联」节里。此处列出是为防止误判为漏记。
