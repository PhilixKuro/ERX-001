## 一、架构总览

本系统是一个**单 app 扩展形态的 ERPNext v16 站点**：不 fork 上游、不改上游源码，全部自有代码集中在末位装载的 `erx_core` 一个 app 内，经六类官方接入点（4 个 whitelisted 方法覆盖、`doc_events`、`app_include_js`、`translations/zh.csv`、`after_install`、`after_migrate`）挂接到 erpnext 上；中国会计准则的科目表与报表以**并入式**抄自 zelin 的 `erpnext_china`（构建期依赖，站点上不存在该 app）；演示操控经一个单一 realtime 事件 `erx_demo_step` 半自动驱动 desk 界面，数据生成与它共享同一套 app 内机制。`erx_core` 末位装载这一点不是操作细节而是架构基石——上游四处 `[-1]` 取值机制（区域覆盖 / whitelisted 覆盖 / 类覆盖 / 译名 csv）的胜出权全部依赖它，它的守护由 `after_migrate` 自检承担。

## 三、模块划分

**⚠ 先读本节的单位约定**（否则会把普通包当模块）：Frappe 的「模块」是 `modules.txt` + `Module Def`，而 `modules.txt` 每多一项，`auto_generate_sidebar_from_module()` 就自动生成一个 hammer 侧栏进 boot（`__init__.py:899`、`installer.py:749-755`、`workspace_sidebar.py:239-252`）⇒ **模块数是界面成本**。故本 app 只为**真需要 `Module Def` 的东西**声明模块（DocType / Report / Page / Workspace），纯代码放普通 python 包。判据须写进 app 的 README。见 ADR-0012。

本节共 6 个单位：**1 个模块 + 3 个普通包 + 2 个 app 级 json 目录**。远低于 D 步 Spec 的规模自查阈值（10 个）。

### 3.1 `cn_tax`（模块，`modules.txt` 声明）

| 项 | 内容 |
|---|---|
| **职责** | 按中国会计准则出账与出表。 |
| **对外接口** | ① 4 个被覆盖的 whitelisted 方法：`get_charts_for_country`／`get_chart`／`get_coa`／`get_all_nodes`<br>② Company 的 3 个 `doc_events` handler：`before_insert`／`on_update`／`after_insert`<br>③ 8 个 DocType：现金流量表四件套 + 资产负债表 Settings 一对 + 利润表 Settings 一对<br>④ 3 个 Report：资产负债表／利润表／漏科目检查<br>⑤ **`after_install` 的单一入口函数**（见下「一处本步裁定」） |
| **依赖** | erpnext 的 `Account`／`Company`／`GL Entry`／税模板三件套（`Sales Taxes and Charges Template`／`Purchase Taxes and Charges Template`／`Tax Rule`）；zelin 的科目表 JSON ×4 与配置数据（并入式，MIT） |
| **所属分解单位** | P1-S2 演示蓝图（演示前必需）；消费方为 P1 后续全部 Stage |
| **关联决策** | ADR-0007（并入形态）／ADR-0012（模块划分）／ADR-0004（钩子须走 `doc_events`）／ADR-0005（配置数据的分派） |

**⚠ 已登记的拆分信号**：对外接口 16 项，命中 C 步分解检查「公开接口超过 10 个」这一条。**当前不拆**，理由是这 16 项同属一个内聚职责（按中国准则出账出表）。**若将来报表继续增加**（如纳税申报表），应把「报表」独立成第二个模块。

**⚠ 侵入度**：4 个覆盖位与 Company 三钩子是**全站行为**，改它们影响任何建公司动作。这是全表侵入度最高的一处，且已是 L4。

**一处本步裁定（C 步复核建议第二节点名交给 D 步的）**：C 步指出「中国财税」这件事在代码里分散于三处——模块 `cn_tax/`、`hooks.py`、`after_install`——并给出收拢办法。**本步采纳该收拢办法**：`after_install` 与 `hooks.py` 里**不写业务逻辑，只做接线**；`after_install` 按序调用 `cn_tax` 模块内的入口函数，`hooks.py` 的 handler 路径指向 `cn_tax` 内的函数。这样中国财税的逻辑全在模块内，模块边界与代码位置一致。

**⚠ A 案带进来的四处缺口，本模块须自己补**（V-19 实测查出，C 步未掌握；逐条成因见 ADR-0007「负面」）：

| # | 缺口 | 本模块要做的事 |
|---|---|---|
| 1 | **无编号 17% `VAT` 科目不会建出** —— `company_before_insert` 置 `country_change=False`，`company.py:355` 的 `create_default_tax_template()` 整块未执行（这也是 A 案 266 条 vs 原生 267 条的唯一差异） | `after_install` 里自建该科目，或显式确认本项目不需要它（13% 税模板已另有 `2221005`／`2221001` 指向，**不依赖这条**） |
| 2 | **`round_off_account` 仍为空** —— zelin `default_accounts.csv` 35 行里 14 行在本科目表查不到对应科目，`round_off_account` 那行写的 `财务费用-圆整差异` 本表无此名 | `after_install` 里显式设定该字段（CR-006 的尾差处理要用） |
| 3 | **`ignore_chart_of_accounts` 置 `1` 后全仓无复位点** —— 一个进程内从第二家公司起，erpnext 自己的建账分支永远被跳过 | 本项目建公司的脚本／数据生成器**每次建公司前显式复位该 flag**，不依赖进程边界 |
| 4 | **zelin 源码两处缺陷**：`custom_account.py:52` 漏 `account_category`（上游 8 键 / zelin 硬编码 7 键）抛 `AttributeError`；`:97` 的 `log_error` 首位置参误用抛 `TypeError`，**出错时连日志都写不下**（同一误用 6 处） | 抄进来时**修掉这 6 处 `log_error` 误用**并补上 `account_category`；修改点登记进 app README（并入式抄源码的改动须可追溯） |

**⚠ 与本模块相关的一条正面实测**：A 案的 `set_company_default` **把六个默认科目里的五个从 erpnext 的错选修正了回来**（`1122 应收账款`／`2202 应付账款`／`1403 原材料`／`1002 银行存款`／`5001010 销售商品收入`）。故「默认科目必须自己设」这条纪律的**范围由六个缩为一个**（`round_off_account`，即上表第 2 条）。此处更正 P1-S2 概况开发纪律 6 的原判断「A 案同样会踩」——V-19 证明 A 案**不踩**，只漏 `round_off_account`。

**一处本步裁定（C 步复核建议第二节点名交给 D 步的）**：C 步问「演示操控与数据生成共享到什么程度——是共用建单辅助函数，还是共用一套节点定义？」**本步裁定：共用建单辅助函数，不共用节点定义。** 理由是两者粒度不同构——演示节点的粒度是「演示者讲一段话的量」，数据生成的粒度是「一张单据」；强行共用节点定义会把演示粒度强加到生成器上，而生成器不需要分节点。建单辅助函数（如「建一张采购收货并提交」）两侧粒度相同，共用是实的。详见 ADR-0010「后果·中性」。

## 四、前瞻性设计清单

> D 步 Spec 硬要求：**每条前瞻性设计必须锚定到需求图谱里具体存在的需求编号，不允许悬空预留**。故本清单只列锚得上的三条。

| 编号 | 当前要做的设计 | 为支持哪个未来功能 | 锚点（需求图谱 v1.1 编号） | 不做的代价 | 多做的成本 | 决策 |
|---|---|---|---|---|---|---|
| **P-1** | **事件协议与业务代码解耦**：推送侧只依赖 `(事件名, payload, user)` 三元，不依赖任何 desk API；节点名清单在服务端独立成常量 | 远期 React 重写 UI 时复用推送侧；录屏／移动端查看演示 | **EX-002** | 推送侧与 desk 细节缠在一起，React 重写要把服务端一并改 | **接近零** —— ADR-0008 定的事件协议本就是这个形状（单一事件名 + payload + 节点清单） | **采纳** |
| **P-2** | **译名做成可反复修正的配置文件**：csv 单一来源 ＋ 断言 `Translation` 表为空的自检 | 摸底问点回流的行业用词，要能一轮轮修正译名 | **IM-003** | 译名成为一次性动作，现场问回来的用词无处回流 | **零** —— ADR-0006 已定 csv 单一来源 | **采纳** |
| **P-3** | **`modules.txt` 留出第二个模块的位置**：现在只 1 个，目录结构与 app 的 README 写明「什么该成模块」的判据 | CRP 负荷报表、SPC 控制图（都是 Report，需要 `Module Def`） | **IM-010／IM-011** | 演示后加报表时要么塞进 `cn_tax`（财税与产能报表同组、职责不单一），要么临时改结构 | **零** —— `modules.txt` 可随时追加 | **采纳** |

**⚠ P-1 的锚定弱点，如实交代**（C 步第 15 步要求转写，不得隐去）：P-1 锚的 **EX-002 是实验性需求**，其评估触发条件是「演示成功一次之后，若要复用演示过程、或需远程展示」——**它本身可能不做**。而 P-1 真正的支撑理由不是 EX-002，是「远期 React 全面重写」，**那条在需求图谱里没有需求编号**（它记在项目概况的技术栈远期计划里，不是一条需求）。取 P-1 的实际理由是它**成本接近零**：CR-008 无论如何要设计事件协议，把它设计成不依赖 desk 细节并不额外花钱。故本条**锚点合规但理由偏弱**，已写进 D 回执的复核建议。

**⚠ 一条被有意排除在本清单之外的设计**：**desk js 覆盖登记表**（每处覆盖记类／方法、目标行为、升级复验清单）。它是**采纳的**，但它服务的不是「未来某功能」而是「上游升级」这件持续性的事，**锚不上任何需求编号**。按 Spec「不允许悬空预留」，它不进本清单；它的正确归属是 **ADR-0009 的组成部分**，已写在那份 ADR 的「关联」节里。此处列出是为防止误判为漏记。
