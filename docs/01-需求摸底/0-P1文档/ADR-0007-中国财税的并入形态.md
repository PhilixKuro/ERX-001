# ADR-0007: 中国财税的并入形态——A 案（原样抄 zelin，含 Company 三钩子）

- 状态：accepted
- 日期：2026-09-25 / 决策者：**用户裁决改判 B→A**（C 步第 14 步「确认改判」）；A 案本体由 **V-19 实测背书**（SA 步附属探针，判定 `go`）
- 对应决策：DEC-058

## 上下文

CR-005 要求按中国会计准则出账与出表（科目表 / 资产负债表 / 利润表 / 现金流量表），CR-006 要求增值税，CR-007 要求银行对账。这三条的素材本项目不自研，取 zelin 的 `erpnext_china`（MIT）。**并入形态是架构决策**：抄哪些、挂哪儿。

CR-005 里有一条**硬约束**：公司一旦开始记账，科目表就换不掉（ERPNext 无换表通道，`Account` 树与全部 `GL Entry` 绑死）。**建账只有一次机会**，它建对与否决定整个财务演示能否成立。

zelin 的中国科目表投递机制有两层，本项目起初以为只需要第一层：

1. **4 个 `override_whitelisted_methods`**：`get_charts_for_country`／`get_chart`／`get_coa`／`get_all_nodes`。
2. **Company 的 3 个 `doc_events`**：`before_insert`（置 `ignore_chart_of_accounts=True`，跳过 `company.py:346` 整块）／`on_update`（自己调 `erpnext_china_create_charts` 建账）／`after_insert`。

C 步原定 **B 案**——只抄那 4 个覆盖、不碰 `Company`，理由是少挂三个钩子就少一处与 HRMS 抢 `Company.on_update` 的风险（LG-101）。**V-18 把 B 案实测判为 `no-go`**：那 4 个覆盖只对 **HTTP / treeview / mapper 派发层**有效（5 个查询点，服务下拉框、科目树、预览），而**建账路径是 `company.py` 内的直接 import**，派发层的覆盖到不了它。即 B 案能让中式科目表在界面上被选中，却建不出来。

用户据此**裁决改判取 A**，并接受 LG-101 这项代价。但改判时 A 案本身**零实测**——V-18 为了不污染自己的命题，**刻意没把 `erpnext_china_create_charts` 与三个 `doc_events` 抄进测试 app**。C 步复核建议因此要求「D 步开工前补一次实测」，用户 2026-09-25 指名派出，即 V-19。

## 决策

**取 A 案：把 zelin 的四个覆盖与 Company 三钩子一并并入 `erx_core`，源码原样抄（不装 app、不进 `installed_apps`）。**

- 4 个覆盖负责**界面侧**：下拉框列出三份中式科目表、科目树与预览按中式结构呈现。
- Company 三钩子负责**建账侧**：`before_insert` 让 erpnext 原生建账整块让位，`on_update` 用 zelin 自己的 `erpnext_china_create_charts` 把 JSON 建成 `Account` 树。
- 两层**都要**，缺任一层都不成立：只有覆盖则选得中建不出（V-18 的 `no-go`），只有钩子则界面上选不到那三份表。

**A 案原样抄，但本项目须另补四处**（下节「负面」逐条列出成因，均为 V-19 新查出、C 步未掌握的事实）。这四处属 `cn_tax` 模块职责，见[架构文档](架构文档.md) §3.1。

## 后果

**正面**

- **建出来的科目表与 JSON 源逐项一致，非抽查。** V-19 实测：`Account` **266** 条 = JSON 递归节点 266；逐对 `(account_number, account_name)` **双向**集合差**两边都空**；父子边 `(子号, 父号)` **双向**亦空（各 266 边）；`is_group`／`account_type` 不一致各 **0**。
- **六个顶层 `root_type` 全对**：`1 资产类`=Asset／`2 负债类`=Liability／`3 权益类`=Equity／`4 成本类`=Asset／`500 收入类`=Income／`540 费用类`=Expense。增值税明细 `2221001`…`2221020` **20 条齐全**，父级分布与 V-18 更正过的前提吻合（前 10 条挂 `2221000 应交增值税`，后 10 条是 `2221 应交税费` 直接子级）。
- **树完整性零缺陷**：NSM 坏行（`lft>=rgt` 或空值）本公司 0、站内 0；孤儿父引用 0；重名加后缀 0；跨公司父引用 0；`report_type` 与 `root_type` 不符 0；`root_type` 为空 0。
- **A 案顺带修对了五个默认科目**，这是「必须取 A」的一条额外硬理由。erpnext 原生 `company.py:425-434` 那组查询**不带 `order_by`**、取 DB 第一条，V-18 实测挑错；A 案的 `set_company_default` 按 CSV 覆盖对了五个：`default_receivable_account` `1122 应收账款`（原生错在 `2203 预收账款`）、`default_payable_account` `2202 应付账款`（原生错在 `2211010 职工工资`）、`default_inventory_account` `1403 原材料`（原生 `1421 消耗性生物资产`）、`default_bank_account` `1002 银行存款`（原生 `1012 其他货币资金`）、`default_income_account` `5001010 销售商品收入`（原生 `None`）。这不是巧合：V-19 在同进程内照抄那组无序查询复现，erpnext **仍**挑出原生那两个错答案，即 A 案是「先被挑错、再被覆盖对」。
- **幂等**：对已建成的公司重复 `save()`（第二次 `on_update`），十二项计数 delta **全为 0**、无异常、六个默认科目逐值未变。机制已测定——`after_insert` 置的 `erpnext_china_in_insert` **不是 Company 的 docfield**，只活在内存里，重载后为 `None`；建账那段另有 `if not frappe.db.exists("Account", ...)` 守卫。
- **多公司互不串**：同站点第二家公司同样 266 条、第一家不变，跨公司父引用双向 0，公司隔离靠 `Account.name` 拼公司 abbr，`Tax Category` 复用未翻倍。
- **副作用与原生持平**：仓库 5／成本中心 2／部门 13／`Financial Report Template` 6／`Tax Category` 7／销项模板 5／进项模板 5，**七项与 V-18 原生逐项相同**；`Error Log` 跑前跑后均 1 条（且是 2026-09-21 的旧条目），`set_company_default` 那个裸 `except` 四种查法均未查到触发。

**负面**

以下四条是 A 案带进来的缺口，**本项目须自己补**（`cn_tax` 模块职责，见架构文档 §3.1）：

1. **无编号 17% `VAT` 科目不会建出来。** V-18 原生路径下有（`account_type=Tax`、`root_type=Liability`、父 `2221000 应交增值税`），A 案下**无**。成因测定：`company_before_insert` 置 `frappe.flags.country_change = False`，而 `company.py:355` 上 `create_default_tax_template()` 的判断发生在 zelin 钩子把它置回之前，**整块未执行**。这条差异正是 A 案 266 条 vs 原生 267 条、`Liability` 68 vs 69、`is_group=0` 为 225 vs 226、`lft/rgt` 跨度 1..532 vs 1..534 的**同一成因**。**顺带查明**：`install_country_fixtures()` 在两条路径下都等于没跑——`erpnext/regional/` 下 10 个地区目录里**没有 `china`**，实测 import 得 `ImportError` 被 `company.py:858` 的 `except ImportError: pass` 静默吞掉。
2. **`round_off_account` 仍为空。** A 案修对了六个默认科目里的五个，这一个没修好。成因定到数据行：zelin 的 `default_accounts.csv` 共 **35** 行映射，其中 **14 行在本科目表里查不到对应科目**，`round_off_account` 那行写的是 `财务费用-圆整差异`，本表无此名（另如 `应付账款-供应商款`／`应付职工薪酬-职工工资`／`主营业务收入`／`主营业务成本`）。
3. **`ignore_chart_of_accounts` 被置 `1` 后全仓无任何复位点。** `company_before_insert` 与 `company_on_update` 各置一次，本项目／erpnext／frappe 全仓无处置回。**后果**：一个进程内从第二家公司起，erpnext 自己的建账分支（`company.py:346`）**永远被跳过**。桌面 UI 每请求一个新上下文，单人手工建公司不受影响；`bench execute`、数据导入、`Chart of Accounts Importer`、批量脚本会受影响。**这正是下一条缺陷的触发前提。**
4. **zelin 源码两处实质缺陷，同进程连续建公司时会崩且连日志都写不下。** V-19 第三段的错误路径（`country='China'` 但 `chart_of_accounts='Standard'`）实测：在**全新进程**里成功（落原生 Standard 表 95 条、`VAT - V19C` 在、`round_off_account` 有值、**两条建账路径只跑一条**，zelin 那条被自己的守卫正确跳过）；但在**同进程内先建过中式公司之后**当场崩、公司整体回滚——
   - `custom_account.py:52` 抛 `AttributeError: 'str' object has no attribute 'get'`。成因：zelin 硬编码的元数据跳过清单只有 **7** 个键、**漏了 `account_category`**，而上游 `chart_of_accounts.py:281` 的 `get_chart_metadata_fields()` 实为 **8** 个；`Standard` 表节点带 `account_category`，该字符串值被当成子节点递归。
   - 紧接着**恢复处理自身又崩**：`custom_account.py:97` 写的是 `frappe.log_error(f"...", title="Tree Rebuild Error")`，而 `frappe.log_error` 的首个位置参**就是** `title`，抛 `TypeError: log_error() got multiple values for argument 'title'`。**`Error Log` 前后均 1 条、今日新增 0 条——出错时连日志都没留下。** 同一误用在 zelin 原文件里共 **6 处**（第 86／173／189／208／227／245 行），其中仅 1 处有实测栈，另 5 处是同一写法、读码得出。

另有一条代价不来自缺陷、来自形态本身：

5. **LG-101 未解且本次仍无法验。** A 案把三个钩子挂到 `Company` 上，正是改判时接受的那项风险的落点。本 bench **未装 hrms**（用户明确指示不为此装 app），故「`Company.on_update` 上多 app 钩子并存时，zelin 的 `not exists Account` 守卫与 hrms 自己的 Company 钩子谁先跑、会不会互相吃掉对方前提」**完全未测**。**装 HRMS 之后须重验 V-19 第三段。**

**中性**

- **`Financial Report Template` 不构成缺口，与命题预判相反。** V-19 任务书预判「`sync_financial_report_templates` 被守卫跳过，那 6 条财报模板很可能一条都没有」。实测站内**仍 6 条**：该 doctype **没有 `company` 字段**，那 6 条是 erpnext 安装时按 `module=Accounts` 装好的**站级**模板，被跳过不减少站内条数。「站级模板对中式科目表取数对不对」是另一个命题，未测。
- **税侧与原生无差异**：销项五条 `account_head` 全指 `2221005 销项税额`（税率 13/3/13/3/0），进项五条全指 `2221001 进项税额`（13/3/0/13/1），另建 `Tax Rule` 11 条。
- **`existing_company` 分支零实测**，本项目无此场景（父子公司／集团架构才走它）。V-19 如实记为未触及。
- **只验了一份科目表**（`小企业会计准则(2024)`）。另两份（`一般企业会计准则(2024)`／`民间非营利组织会计制度(2025)`）未建过，其节点带不带 `account_category`（即上条缺陷 4 会不会在它们上触发）未知。
- **`account_category` 缺陷的触发条件随上游演进**：它是「上游元数据 8 键 vs zelin 硬编码 7 键」的差值，换 erpnext 版本须重验。本次环境 frappe 16.34.0 / erpnext 16.35.0。

## 备选方案

**B 只抄 4 个 `override_whitelisted_methods`、不碰 `Company`** —— 少挂三个钩子即少一处 HRMS 抢 `Company.on_update` 的风险（LG-101）。**没选**：**V-18 实测判 `no-go`**——那 4 个覆盖只作用于 HTTP / treeview / mapper 派发层（5 个查询点），**建账路径是 `company.py` 内的直接 import，派发层覆盖到不了**。B 案能让中式表在下拉框里被选中，却建不出科目。V-18 另实测 `create_charts(不存在的公司, ...)` 不抛错、静默返回 `None`、建 0 个 `Account`，即「不崩」与「建出来」是两件事。见 NV-037。

**用 `regional_overrides` 挂区域实现** —— 名字最像为此而设的官方机制。**没选**：技术上不成立——上游 18 个 `@allow_regional` 挂点**全部是交易时点**（发票校验、税额计算一类），**没有一个在建账路径上**。见 NV-038。

**把科目表 JSON 直传 `create_charts(custom_chart=...)`** —— 不覆盖任何方法、不挂 Company 钩子，只在建公司后自己调一次，形态上最轻。**没选**，三条：① 撞 CR-005 的**硬约束**——它要求公司先建好再补建科目表，而公司一旦开始记账科目表就换不掉，这个时序把「建对」的唯一机会放在了一个额外步骤上；② `from_coa_importer=True` 会改变 `_import_accounts` 的语义（走 importer 分支，与本项目场景不符）；③ **零实测**。**保留为 LG-102 退路**：若 LG-101 的 HRMS 同钩子交互出事，A 案要退，退到这里。见 NV-050。

## 关联

- 依赖：ADR-0001（单 app 形态是并入式的前提）、ADR-0003（`erx_core` 末位装载 —— 4 个 whitelisted 覆盖的 `[-1]` 胜出权全靠它）、ADR-0004（三个钩子走 `doc_events` 而非 `override_doctype_class`）、ADR-0005（zelin 的配置数据按语义分派落点）
- 被依赖：ADR-0012（`cn_tax` 是 `modules.txt` 里唯一那个模块，其职责由本决策定义）
- 取代：无
- **一条由本决策派生、须落到 IM-007 的纪律**：`after_migrate` 自检**不能只断言 4 个覆盖位的 `[-1]` 归属**。那条断言守得住下拉框与科目树，**守不住建账路径**（建账不经派发层，这正是 V-18 的 `no-go` 根因）。建账侧须另加一条：**建公司后断言科目数与六个 `root_type`**。见架构文档 §5.2 接入点⑥。

## 失效条件

- **LG-101 出事**：装 HRMS 后重验 V-19 第三段，若 `Company.on_update` 上的钩子互相吃掉前提，A 案失效，退路见 NV-050 / LG-102。
- **换 erpnext 版本**：`account_category` 那处缺陷的触发条件（上游 `get_chart_metadata_fields()` 的键数）随上游加字段而变。
- **要建父子公司／集团架构**：会走 `existing_company` 分支，该分支零实测。
