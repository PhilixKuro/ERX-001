# ERX-001 开发守则

## 长效约定

### 扩展 ERPNext 优先用 hook，不改源码

能用 Frappe 的扩展机制实现的，一律不动 `frappe-bench/apps/erpnext/` 与 `.../frappe/` 源码。每一处源码改动都是此后每次合并上游的冲突点，而 hook 不是。

| 需求 | 用什么 | 写在哪 |
|---|---|---|
| 文档生命周期挂逻辑 | `doc_events` | 自有 app 的 `hooks.py` |
| 覆盖 DocType 类方法 | ~~`override_doctype_class`~~ **本项目不用**，改走 `doc_events`（它取最后安装的 app、会静默绕过 HRMS 对 `Payment Entry` 的类覆盖，见 [ADR-0004](01-需求摸底/0-P1文档/ADR-0004-不使用override_doctype_class.md)） | — |
| 覆盖 whitelisted 方法 | `override_whitelisted_methods` | 自有 app 的 `hooks.py` |
| 给现有 DocType 加字段 | Custom Field + `fixtures` | 自有 app 的 fixtures |
| 新业务实体 / 报表 / 页面 | 自有 DocType / Report / Page | 自有 app |

**侵入度分级**（按升级维护成本排；凡给接入点定级、评估方案时用这张表，级别写进方案与 ADR）：

| 级 | 名 | 含义 | 升级时要跟什么 |
|---|---|---|---|
| **L0** | 零开发 | 改配置/记录，无代码 | 无（`standard=1` 导航记录改后不被 `bench migrate` 覆盖已实测，直到上游换掉那个 json） |
| **L1** | 数据层 | Custom Field / fixtures / `zh.csv` | 无 |
| **L2** | app 内新建 | 自有 DocType / Report / whitelisted 方法，不碰上游 | 无 |
| **L3** | hook 追加 | `doc_events` / `regional_overrides` / `app_include_js` —— **累加执行** | 只跟**字段名与子表结构** |
| **L4** | hook 覆盖 | `override_whitelisted_methods` / `override_doctype_class` —— **最后安装的 app 胜出** | **跟方法体**；且占掉覆盖位即锁死其它 app |
| **L5** | 改上游源码 | 改 `apps/erpnext` 或 `apps/frappe` | 每次升级必冲突。**本项目禁止，除非无路可走** |

**确须改源码时**（上游无 hook 入口、或须改框架层行为）两条义务：

1. 改动落在自有 fork 的 `version-16` 分支，提交信息注明为何 hook 不可行
2. 在 `docs/项目概况.md` 的「已知限制 / 技术债」记一行，标明改了哪个文件、原因、以及能否将来上游化

### 三层仓库的分工

本项目涉及三层独立的 git 仓库，改动各自提交、互不影响：

| 改了什么 | 在哪提交 | 推到 |
|---|---|---|
| `docker/`、`docs/`、`CLAUDE.md`、`.vscode/` 等 | 项目根 | `PhilixKuro/ERX-001` |
| `frappe-bench/apps/frappe/` | 该目录内 | `PhilixKuro/frappe` |
| `frappe-bench/apps/erpnext/` | 该目录内 | `PhilixKuro/erpnext` |
| 自有 app（`frappe_china`／`frappe_debug`） | 各自目录内 | 各自单独建的仓库 |

`frappe-bench/` 整个在 `.gitignore` 内，故项目根的 `git status` 看不到各 app 的改动。VS Code 已配 `git.scanRepositories`，源代码管理面板会并列显示三者。

各 app 的 remote 分工（`setup.sh` 自动配）：

| remote | 指向 | 用途 |
|---|---|---|
| `origin` | `PhilixKuro/{frappe,erpnext}` | 推送自有改动 |
| `upstream` | `frappe/{frappe,erpnext}` | 拉取官方更新，只读不推 |

`upstream` 的 push URL 已设为无效值，**不得向其推送**。

注意 `bench init` / `get-app` 用 `git clone --origin upstream` 建仓库，会把自有 fork 命名成 `upstream` 且不设 `origin`——与惯例相反。`setup.sh` 会归位，新增 app 后若手工 clone 过须自行检查。

### 各 app 用 shallow clone

以 `--depth 1` 拉取，只保留 `version-16` 的最新快照。理由：在稳定版基础上开发不需要上游十余年历史，查上游改动源流去 GitHub 网页更快。

shallow 不影响改源码、commit、push、`fetch upstream && merge`、建分支。确需完整历史时在该 app 目录内 `git fetch --unshallow`。

### 版本锁定

`docker/apps.json` 记各 app 的 url + branch + commit。**合并上游后须跑 `docker/lock-apps.sh`** 更新它，否则换机器会拿到分支最新提交、与本机版本不一致。

该文件进主仓库 git，是本仓库唯一的版本记录（`frappe-bench/` 本身不进版本管理）。

### 合并上游更新的流程

frappe 与 erpnext 版本须配套（同为 `version-16`），**两者一起升，不单独升一个**。

```bash
cd frappe-bench/apps/frappe
git fetch upstream
git merge upstream/version-16        # 冲突只出现在自有改动过的文件
git push origin version-16
cd ../erpnext
git fetch upstream
git merge upstream/version-16
git push origin version-16
cd ../../..
docker/lock-apps.sh                  # 更新 apps.json 里的 commit
git add docker/apps.json
git commit -m "chore: 合并上游 frappe/erpnext version-16 更新"
```

合并后须在容器内跑 `bench migrate` 与 `bench build`，确认站点可用再提交。

### 自己要排除的文件写进 .git/info/exclude

各 app 带着上游的 `.gitignore`（已覆盖 `node_modules`、`public/dist`、`__pycache__` 等）。你额外要排除的临时文件写进该仓库的 `.git/info/exclude`——语法相同，只对该仓库生效，且在 `.git/` 内故不进版本管理、不与上游冲突。

**不要改上游的 `.gitignore`**，它是上游文件，改了会成为每次合并的冲突点。

代价：`.git/info/exclude` 不随 push 走，换机器会丢。

### 非文本附件必须按原始字节读写

对非 UTF-8 编码或必须保留 BOM 的附件，创建 `File` 时用 `File.content` 传原始字节；读取时从 `File.get_full_path()` 以二进制打开。不得用旧的 `frappe.utils.file_manager.save_file` 承载这类内容——`File` 插入流程可能按兜底编码解码并改写字节，导致银行流水等文件静默损坏。

### git 需显式配代理

Windows 系统代理（Clash 全局模式等）写在注册表，git 用 libcurl、不读注册表，故 git 流量会绕过代理直连 GitHub 而超时。须为每个仓库显式配置——**主仓库与各 app 的 `.git/config` 相互独立，都要配**：

```bash
git config http.https://github.com/.proxy http://127.0.0.1:7897   # 端口按实际改
```

配置在 `.git/config`，不进版本管理，**换机器须重配**。症状为 `Connection was reset` 或 `Failed to connect to github.com port 443` 时先查这一条。

**容器内的代理是另一回事**：容器里的 `127.0.0.1` 指容器自己，须用 `host.docker.internal`。见 `docker/.env` 的 `GIT_PROXY`，`setup.sh` 用 `GIT_CONFIG_*` 环境变量注入——不能写进 `/workspace/.git/config`，那是主仓库的配置文件、宿主机的 git 也在用。

### 断言任何机制可用前，写入端与读取端两侧都要查

查到一张结构对的表、一个名字贴切的字段，就推定它被正确消费，会错。**写入端**（谁往里写、按什么键写）与**读取端**（谁读它、按什么键取）必须分别找到并对上，才能说这个机制生效。

两个实例：

| 机制 | 写入端 | 读取端 | 错在哪 |
|---|---|---|---|
| 导航（界面呈现） | 数据层：相关表的记录、DocType meta 的字段与 `Tab Break` | **渲染层**：`boot.py` 的 `get_sidebar_items()`、`desktop_icon.py` 的 `get_desktop_icons()` 过滤、`list_view.js` 的视图与空状态选择 | ERPNext 里同一件事常有多张表（`Workspace` 与 `Desktop Icon`+`Workspace Sidebar` 两套并存，前者是后者的生成源），且**表里的记录数不等于界面显示数**——中间隔着过滤逻辑 |
| 银行流水导入的列映射 | `Bank Transaction Mapping` 子表，以文件的**表头文字**为键写入（`bank_statement_import.py:68-70`） | `importer.py:879` 以**列序号**取值 | 子表结构（`bank_transaction_field` ↔ `file_field`）看着完全对，但读取端根本不认它的键 ⇒ **该子表永不被命中**；能导进去只是因为文件列序碰巧与目标字段顺序一致 |

**凡给数量断言（"共 N 个"）须标明是哪一端、哪一层的 N。** 反例：`Desktop Icon` 36 条 / 顶层 9 条 / 界面实际显示更多，三个数字没一个相同。

**本条的误判方向两种都有**：多数时候是「以为没有、其实藏在别处」（范围虚高），银行映射这次是反方向——「查到结构对的表就以为它在用」（范围虚低）。两个方向都用同一个检查挡：写入端与读取端各找到一处代码。

### 判据必须能区分它要区分的两种情形

上一条是这条的一个特例。通用形式：**取证用的命令，其输出必须只对应一种解释。**

反例五则（前三则出自 P1-S1-R6，第四则出自 P1-S2-R2，第五则出自 P1-S4-R3）：

| 用了什么 | 无输出/命中的含义 | 错在哪 |
|---|---|---|
| `cat x.js 2>/dev/null` | 文件是空的 **或** 文件不存在 | 重定向吞掉了错误，遂把"不存在"读成"空文件"。**应用 `test -f`** |
| `grep pattern file` 未命中 | 功能不存在 **或** 命名/位置不同 | "grep 未找到即推定缺口"使二开范围虚高，**已五次应验为误判，且五次全是范围缩小方向** |
| 查到一张名字贴切的表 | 它就是那个机制 **或** 它只是相关 | `Workspace` 看着像导航表，实为 `Desktop Icon` 的生成源 |
| A 的节点数多于 B | A 包含 B **或** 两者各有独有 | 会计准则选型：一般企业 353 节点多于小企业 266，**实测小的那份有 47 条大的没有**（按科目号交集更只有 9 条）。包含关系只能靠"小的减大的"这一侧差集判，计数判不了——**且只有这一侧算数**，大的独有多少与包含判定无关 |

| **实跑了**，但两种情形给出同一个输出 | 假设成立 **或** 探针设计让两种情形产出一样的数 | 前四则都是「取证命令选错」，这一型是**判据设计错，全程实跑也会得出错结论**。两例：① 验「某设置按行生效还是按段生效」，却把两类行各放一段——两种情形输出相同，无从区分（另建单段模板才补上）；② 解析器与兜底值**同返 1000**，读到 1000 分不清是谁给的（改成 300 对 100 才可判）；同一探针清缓存时漏了键的库名前缀，什么也没清掉，却被读成「属性存活」。**设计探针时先问：若假设不成立，输出会变成什么？答不出一个不同的值，这个探针就没有判别力** |

**五者同一个病：拿间接证据当直接证据。** 判据是问一句"**这个输出还有别的解释吗**"——有，就换一个能排除它的命令或探针。

**断言"原生没有 X"须满足三条**（上表第二行的操作化形式）：默认假设是"可能有但藏在别处"，须 ① grep 过多个同义关键词；② 看过相关模块的**目录清单**（不只 grep）；③ 说明为什么它不可能在别的模块。三条不齐只能写"未查到"，不能写"没有"。**典型藏法三种**：算法藏在**报表**里而不是 DocType；字段藏在**成本节**且无 description，从功能视角看不见；能力藏在**一个 Check 字段的条件分支**里。

**静默失败自成一类排查对象**：`try/except` 只 log、异常被吞、写入无回执的地方，**"没报错"不等于"成功"**。凡断言某步骤已生效，须有正向证据——查得到落库记录、界面可见、或有返回值——不能以"没报错"代替。反例：GBK 编码的银行流水 csv 经原生 `Bank Statement Import` 导入，`status=Success`、`success=1`、单据也建了，**但中文全是乱码**——预览时的编码告警与实际导入用的不是同一个文件对象（`start_import()` 另建了一个不带模板选项的 `ImportFile`）。只看「导入成功」会漏掉它，须打开一条导入结果逐字看。

**引用计数时须附明细**：写"共 N 条问题"而列不出那 N 条，该数就不可核验，却会被下游当硬证据链式引用。**援引既有留档不等于核实**：留档本身会错（如 `@allow_regional` 记成 20 个，实为 18），被引用一次就多扩散一处。

### 在站点上跑探针的三条纪律

探针常在事务里跑、结束时 `frappe.db.rollback()` 复原。以下三处 rollback 管不到，或会让结论偏乐观：

1. **`tabError Log` 是 MyISAM，`rollback()` 对它无效**（全库非 InnoDB 仅三张：`tabError Log`／`tabData Import Log`／`__global_search`）。凡会触发 `frappe.log_error` 的探针，**清理必须正向限定——只删能证明是自己造的行，不得按「排除掉原有的，剩下全删」的方式删**。反例：一次探针按排除法清理，误删了两条原有日志，且无法恢复。
2. **探针进程的 `frappe.local.lang` 默认是 `en`，真实会话是 `zh`**。凡结论与语言有关（列头、译名、`_()` 的替换），探针须显式设 `zh`，否则会得到偏乐观的结论。
3. **报表跑满 15 秒，上游会自动把它改为 Prepared Report 模式并跨连接提交**（`report.py:186-198` 挂一个定时器 → `enable_prepared_report` → 另一连接上 `db.commit()`），rollback 撤不掉。在站点上跑报表类探针时须防着它（如把该函数换成空操作），事后核对报表的 `prepared_report` 标志。
### 容器内执行的脚本必须是 LF

`.gitattributes` 已强制 `*.sh` 为 `eol=lf`。若被 checkout 成 CRLF，bash 报 `bad interpreter: no such file or directory`，脚本在新机器上直接不可用。
