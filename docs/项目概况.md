## 系统现状

### 项目定位

基于 ERPNext 的二次开发项目。上游 ERPNext 与 Frappe 框架从自有 fork 取得，本项目的功能以 Frappe app 形态叠加在其上。

**目标行业**：弹簧制造（中国大陆中小型厂）。首个潜在客户为弹簧厂，规模与需求待实地考察确认；产品定位为可复用于多家同行业客户，非单客户定制。

**四阶段战略**（P1-S1-R1 讨论记录 DEC-007）：

| 阶段 | 内容 |
|---|---|
| ① 自学 + 摸底 | 先学会用 ERPNext 原生功能，在此过程中摸清原生对弹簧制造业的适用边界与痛点 |
| ② 做中国大陆通用版 | 针对摸出的原生缺口（首要是无中国财税逻辑）改造出适合中国大陆的通用版本 |
| ③ 客户演示 | 以通用版向客户演示 |
| ④ 定制 | 调研客户实际生产环境，定制专属业务逻辑与简单界面 |

后三阶段依次以前一阶段为前置，不并行。

### UI 路由结构

沿用 ERPNext 标准 Desk 路由。自有页面待确立。

**v16 的 desk 路由前缀是 `/desk/`**，`/app/*` 已降为 301 重定向（`frappe/hooks.py` 的 `website_redirects`）。旧前缀仍可用，故照旧写法不会立刻报错——写文档与脚本时一律用 `/desk/`。

**导航结构由三张表承载，不是硬编码**（P1-S1-R6 查清）：

| DocType | 职能 |
|---|---|
| `Desktop Icon` | 首页图标网格。`link_to` 为空＝分组图标（点开只展开子图标）；`hidden` **是否向下传递取决于 `icon_type`**——`Folder` 传递、`App` 不传递 |
| `Workspace Sidebar` | **一个页面的左侧栏**（故左侧栏不是全站共用，首页没有左侧栏）。标准记录在 `erpnext/workspace_sidebar/*.json` |
| `Workspace Sidebar Item` | 上者的子表：`Section Break`＝分节标题、`Link`＝可点条目 |

**`Workspace`（19 条）不承载导航层级**——它装页面内容（快捷方式/卡片/图表），`parent_page` 全空；但它是 `Desktop Icon` 的**生成源**（`create_desktop_icons_from_workspace()`），故两者是"源与产物"而非"废弃与现行"。**要确认某条导航路径的实际呈现，查 `Desktop Icon` 与 `Workspace Sidebar`，不查 `Workspace`。**

**树形 DocType（`is_tree=1`，如 `Account`/`Warehouse`/`Cost Center`）必须走树视图** `/desk/{doctype}/view/tree`——它们的 `*_list.js` 是空文件、实现在 `*_tree.js`，落到列表路由会显示空白。

**改导航不需二开**：改记录（零代码，但 `standard=1` 是否被 `bench migrate` 覆盖**未实测**）或自有 app 出 fixtures。**远期计划用 React 全面重写前端**（走 REST API v2，与 jQuery 的 desk 两套独立，无技术债传递）。

### 已知限制 / 技术债

- **`frappe-bench/` 不进版本管理**，故各 app 的源码改动只存在于自有 fork，本仓库仅靠 `docker/apps.json` 记录 commit。换机器前须确认改动已 push，否则会丢。
- **v16 全新安装需额外初始化**：官方把一批初始化搬进了界面配置向导，而 `bench new-site` 会跳过向导。`docker/scripts/seed-demo.sh` 已覆盖（fixtures、默认计量单位、标准价目表、全局币种、配置完成标记），细节见 `docker/README.md`。
- 对 `frappe-bench/apps/erpnext/` 或 `.../frappe/` 的源码改动须登记于此（见 `开发守则.md`）。
- **ERPNext v16 无中国本地化**：`erpnext/regional/` 只有 australia / italy / south_africa / turkey / united_arab_emirates / united_states 六国，**无 china**。增值税专用发票、金税盘对接、银行对账、中国财务报表格式均无原生支持。这是四阶段战略第 ② 阶段（做中国大陆通用版）的主要工作面。
  - **但已查明它可以在自有 app 内实现、不必改 erpnext 本体**（P1-S2-R1 实测，探针留档 `Spike/V01-*`）：接入点是 `regional_overrides` hook——`erpnext/__init__.py:145` 读 `frappe.get_hooks("regional_overrides").get(get_region())`、`:152` 取 `[-1]`（**末位装的 app 胜出**），全仓 **20 个 `@allow_regional` 覆盖点**涵盖 GL 分录、计税、税额拆分、地址取值、采购估值。分派已实测生效（注入 hooks 缓存后覆盖函数被调用且参数原样传入；两 app 同 target 时末位胜出；改 `get_region()` 为 Italy 则覆盖失效，按国家隔离）。**四处不是 hook 但均有 app 侧替代**：`install_country_fixtures()`（`company.py:858-861` 硬编码 `erpnext.regional.<country>.setup.setup`）、`update_regional_tax_settings()`（`taxes_setup.py:120-125`）、`country_wise_tax.json`（**China 条目仍是 17%、早已过期**）、科目表 json 目录。
  - **另有三处实测结论**：① 增值税可用原生 `Tax Template` 三件套表达（价税分离、多档位、进项销项分离均实跑通过；**但手填 `item.item_tax_rate` 无效**，会被 `update_item_tax_map()` 重算覆盖，必须走真的 `Item Tax Template`）；② 自制科目表模板可用 `override_whitelisted_methods` 进建公司下拉，**但须连 `get_chart` 一并覆盖**（它不经 `execute_cmd`）；③ **现金流量表不是原生报表配置能产出的**，须自建可提交单据 + 从 GL Entry 按现金银行科目拉流水（直接法）。
  - **但科目表模板另有一份中国版，不在 `regional/`**（P1-S1-R5 实测，修正此前"完全无中国科目表"的表述）：`accounts/doctype/account/chart_of_accounts/unverified/cn_l10n_chart_china.json` 存在，名为 `China - 中国会计科目表（财会[2006]3号《企业会计准则》）`，含 82 个一级节点（原材料 / 生产成本 / 库存商品 / 委托加工物资 / 应交税费下 11 个税种等）。**可作第 ② 阶段的素材，但不能直接用**，三个原因：① 它在 `unverified/` 而 `get_charts_for_country()` 默认只扫 `verified/`（`chart_of_accounts.py:147-149`），故建公司时下拉里选不到（`verified/` 下 78 个模板无一以 `cn` 开头，中国用户只有 `Standard` 与 `Standard with Numbers` 两项）；② **82 个节点全部平铺、`root_type` 全为空**，导进来是 82 棵无 `root_type` 的孤树而非挂在资产/负债/权益/收入/费用五根下的树，导入靠 `ignore_mandatory` 绕过校验、进库后报表归类失效；③ **内容停在 2006 准则未更新**——含营改增（2016）后已废止的「应交营业税」与「营业税金及附加」，且「应交增值税」下无进项/销项二级明细。**故第 ② 阶段的工作是"补全一份现成清单"（补 `root_type`/`account_type`/`account_number`、按五大类重组、清理废止科目）而非"从零设计"，但仍须懂中国准则的会计参与。** 详见 [L0 教材](01-需求摸底/S01-场景摸底/0-P1-S1文档/L0-记账底座与组织骨架.md) 段④缺口一。
- **⭐ ERPNext 的系统性特征：各领域都有"记录层"，多处缺"计算层"**（P1-S2-R2 六路全链路排查所得，是本项目自研策略的总纲）。**自研重心应是计算层，不是重建记录层**——记录层大多可复用。
  - **缺计算层（须自研）**：SPC 控制图与 CPK（读数已在 `Quality Inspection Reading` 的 `reading_1..reading_10`，公式是公开标准）；RCCP/CRP 产能负荷（Workstation 的 `working_hours`×`production_capacity` 可作数据源）；**安全库存**（`Item.safety_stock` 全库 30 处命中**无一处是写入或计算**，`Z×σ×√LT` 缺失）；**再订货点定量**（触发层真跑、挂 daily 自动建 Material Request，但 `Item Reorder` 只有固定值；**而推荐值算法已存在于 `itemwise_recommended_reorder_level.py:29` 却不回写——这是性价比最高的一处二开**）；不合格品处置流程（`Non Conformance` 仅 10 字段、无数量无物料无批次）；计件工资计算（数据源 `Job Card Time Log` 已有 `completed_qty`+`employee`+`operation`）。
  - **⚠ 但"缺计算层"不是普适规律，采购块有三处是真算法**（勿误判为记录表）：`Supplier Scorecard` **真能算分**（`supplier_scorecard_period.py:49-55` 校验权重合计 100、`:73-74` 用 `frappe.safe_eval` 解析公式并钳制、按权重汇总；变量是 20+ 个真 SQL 函数；`hooks.py:468` 挂 daily 自动跑，**故到货准时率与合格率的数据已含在内、不必另造**）；`Blanket Order` 累计量控制与价格锁定（`blanket_order.py:254-255` 按 `remaining_qty` 拦截）；`Item Lead Time` 确有消费方（MPS 与 MRP 报表）。
  - **另有四项"以为缺、实际有完整计算层"**：**信用额度**（`customer.py:619 check_credit_limit()` 三级限额回退 + 占用额计算 + `raise_exception=1` 硬拦，挂 SO/SI/DN/JV 四处；**但放行靠 `credit_controller` 角色、非审批流、无留痕**）；**价格阶梯**（`Pricing Rule` 的 `min_qty`/`max_qty` 在 `utils.py:405-406` 参与过滤，"买 1000 支价 X、5000 支价 Y"直接可表达，`priority` 做冲突解决，**无需二开**）；**副产品成本分配**（`cost_allocation_per` 全链路校验合计 100%、从主产品扣除、**并落到实际入库估值**，对弹簧废料回收直接可用）；**成本卷积**（`bom.py:677 update_cost()` 递归多级累加）。
- **两处两层皆无的洞（连记录层都没有）**：
  - **ATP/CTP 可承诺量**：`available_to_promise`/`capable_to_promise` 全仓**零命中**。`Sales Order Item.delivery_date` 是人填，唯一算过的是 `get_item_details.py:190-191` 的 `add_days(transaction_date, item.lead_time_days)`——单件固定提前期加法，不看库存/在制/产能/排队。**与"无 CRP"是同一个洞的两端：没有产能计划就算不出交期承诺**，故 CRP 负荷报表同时是 ATP 的前置。
  - **ECN/ECO 工程变更**：对 erpnext 与 frappe **同时** grep `engineering_change`/`change_request` **双双零命中**，且**已排除"被内置 `Workflow` 覆盖"**——`Workflow` 只做状态流转，不提供变更单实体（无变更号/原因/受影响清单/生效批次）、不带影响分析。**对弹簧厂是硬缺口**（客户改图纸是常态，改一次要知道影响哪些 BOM 与在制工单）。变更影响分析**半有**：反向有 `stock/report/item_where_used/`、正向有 `bom_explorer`，但都是静态清单、不联动在制工单。
- **标准成本法不存在，且有一段死代码**（P1-S2-R2）：`Item.valuation_method` 的 options 只有 `FIFO / Moving Average / LIFO`，**无标准成本法**，故**价差/量差/效率差三分解无从谈起**。而 `bin.py:56-62` 有 `if get_valuation_method(...) == "Standard Cost":` 分支并 import `item_standard_cost` 模块——**该模块全 bench 零文件、且 `"Standard Cost"` 不在任何取值域里**，是永不执行的死代码（上游在开发中或被删功能的残留，**未查实**）。**二开前应实机看一眼该下拉，免得重复造。**
- **间接费用只能按工时单一基准分摊**（P1-S2-R2 纠正此前表述）：`Workstation.over_heads` **是 Tab Break 标签、不是数值字段**；真正的费用来源是子表 `Workstation Cost`（`operating_component`+`operating_cost`），由 `workstation.py:110-115 set_hour_rate()` 逐行相加得小时费率。**故无法按产量/重量/材料成本分摊**，也无费用池与吸收差异。
- **弹簧行业特有：计量单位换算无批次级与公式级能力**（P1-S2-R2 发现，不在原缺口清单内）：`UOM Conversion Detail` 只有 `uom` + `conversion_factor` 两个实字段，**系数是物料级固定 float**。而弹簧 kg↔pcs 换算随线径与圈数变、同规格不同批次钢丝的线密度还有差异。**直接影响领料与成本准确性。**
- **质量能力的实际分布**（P1-S2-R2 排查，修正"质检完全未覆盖"的笼统表述）：
  - **检验执行层在 `stock` 模块且三段检验齐全**：`Quality Inspection.inspection_type` 取值 `Incoming / Outgoing / In Process`（IQC/OQC/IPQC），`reference_type` 可挂 **Job Card**（故 IPQC 能挂工序卡）。拒收有拦截（`Stock Settings.action_if_quality_inspection_is_rejected` = Stop/Warn，逻辑在 `controllers/stock_controller.py:1676-1695`）。**但拒收之后无流程**：无隔离仓、无让步接收审批、无 MRB。
  - **`quality_management/` 那 17 个 DocType 是 ISO 9001 文档留痕体系，不是检验执行系统**——判据是 `Non Conformance` 仅 10 个字段（无数量/物料/批次/仓库、无到 QI 的链接），**记不住"哪批多少件不合格"**。CAPA 有壳无骨，8D 完全无。
  - **SPC / CPK / MSA / APQP 全无**：`control_chart`/`process_capability`/`cpk`/`nelson`/`western_electric`/`standard_deviation` 六个关键词**全部零命中**。`Quality Inspection Reading` 只有 10 个读数 + min/max/acceptance_formula，**是单次判合格、无跨批次时序统计**。抽样方案几乎无（只有人工填的 `sample_size`，连 options 都没有）。**易混点**：Item 上的 `sample_quantity`/`retain_sample` 是**留样**，不是抽样方案。
  - **批次/序列追溯原生完整、不必自研**：`stock/report/serial_no_and_batch_traceability/` 带 `traceability_direction` 过滤器，取值 **Backward / Forward / Both**（`:50`/`:63-72`），反查原料走 Stock Entry、正查流向亦支持。另有 `serial_and_batch_summary`、`batch_wise_balance_history`、`serial_no_ledger`。**故弹簧断裂索赔追责那条链是通的。** 未实测：多级 BOM 的连续穿透深度。
- **预测能力：有算法但开环**（P1-S2-R2，修正"无预测算法"的表述）：`manufacturing/report/exponential_smoothing_forecasting/`（264 行）实现**一次指数平滑**（`prev_forecast + α×(prev_actual - prev_forecast)`，滤器有 `smoothing_constant`/`periodicity`/`no_of_years`），**但结果不落库**（`insert()`/`save()`/`new_doc` 零命中），要转成 `Sales Forecast` 须人工再录。**缺的是**：预测误差 MAPE/bias（**故 α 无法标定、预测层是开环的**）、趋势与季节项（无 Holt/Holt-Winters）。`Sales Forecast` 本身只有 92 行、是人工录入独立需求的容器。
- **⚠ 两套提前期字段并存**（P1-S2-R2 发现的一个坑）：`Item Lead Time.purchase_time` 与旧的 `Item.lead_time_days`，**消费方不同**（前者被 MPS 与 MRP 报表用，后者被 `get_item_details.py:190` 用于算交期）。**二开时须统一口径**，否则会出现"改了一个另一个没生效"。
- **hrms app 未安装**：当前 `frappe-bench/apps/` 只有 frappe 与 erpnext。薪资相关能力（含计件工资）无 app 支撑。
- **ERPNext v16 落在 MRP 层，够不上 MRP II**（P1-S2-R2 读码判定，判据是**产能这一维未参与任何计划层计算**）：
  - **有的**：`Master Production Schedule`（480 行，递归 BOM 累加提前期算 `order_release_date`）、1427 行的 `Material Requirements Planning Report`（BOM 逐层展开 / 净需求扣库存与在途 / 提前期倒排 / 安全库存，且 `:1303 make_order()` 能直接转出采购单与工单）、预测消耗按标准 greater-of 取大规则（`:449-450`，故预测与实单不双算）。
  - **缺的**：**RCCP/CRP 产能需求计划**（MRP 报表那列 `Capacity` 取自 `Item Lead Time.capacity_per_day`，是物料级、与 Workstation/Routing 无关，且无一处把需求与产能做比较或削峰）、**优先级字段**（`work_order.json`/`job_card.json`/`sales_order.json` 均无 `priority`）、**换型矩阵**（`setup_time`/`setup_mins` 全仓零命中，仅有全局固定的 `mins_between_operations`）、时界、净变式 MRP、重排与闭环反馈。
  - **唯一真查产能的地方**是 `job_card.py:400 has_overlap`，但那是工单下达后的**执行层防重叠**（FCFS 顺延），不是计划层 CRP，**且不反馈给计划**。
  - **Workstation 的产能模型部分可用**：`working_hours` 子表按时段切分、跨班次拆分、跳假日；`production_capacity` 是并行槽位数；冲突检查真查已有 Job Card 重叠。**缺的是产能负荷报表**（22 个报表 + 8 个 dashboard chart 无一是负荷口径）；`Workstation Type` 无任何产能字段、按 type 排产不做负载均衡。
- **⚠ `Master Production Schedule` 提交必然失败**（P1-S2-R2 **实跑复现**）：`master_production_schedule.py:445` 调 `make_mrp`，而该方法全仓无定义、`MRP Log` DocType 不存在，实测 `AttributeError`。且其 json **无 `is_submittable` 键**，故界面上本就没有提交按钮；绕过界面用 Python `.submit()` 则**前台静默成功**（docstatus 落 1、提示照常弹出），失败只发生在后台 worker。**旁证**：`master_production_schedule.js:65` 的 `View MRP` 按钮跳的是报表而非 MRP Log 单据——这条线是未完成的设计残留。
- **生产计划不按工艺损耗反算投料量**（P1-S1-R3 实测，P1-S2-R2 复验 `production_plan.py` 内 `process_loss` 仍为 **0 命中**）：`planned_qty` 直接取 SO 待交数量，故每张按销售订单生成的工单必然短交（SO 5000 支 + BOM 5% 损耗 → 完工 4750 支）。MRP 的 scrap factor / yield factor 缺失，SAP 与 Oracle 均有该能力。真实代价是每张订单都要补做一次，流程成本翻倍。
  - **但库存层其实是通的**（P1-S2-R2 复核，修正此前"字段有而链不通"的笼统表述）：`Job Card.process_loss_qty` → `job_card.py:1073` 写 `WO Operation` → `work_order.py:938-940` 汇总到 `WO`，且 `track_semi_finished_goods=1` 下半成品入库数量**确实扣了损耗**。**不通的只是计划层**——`create_job_card` 照发 `WO.qty`。故它与"工序间数量链不通"是**同一缺口的两面**，不是两条独立缺口。
  - **工序间数量不传递**（原 LG-040，P1-S2-R2 复核**仍成立**）：`work_order.py:2969` 的 `qty = row.job_card_qty or work_order.get("qty", 0)`，与前道工序的 `completed_qty`/`process_loss_qty` 无任何关联。
- **工序成本按实际报工工时计，故成本准确性完全依赖车间真实报工**（P1-S1-R3 实测）：任务单计时几秒即导致工序成本记 0.27 元而非应有的 433.3 元，毛利率虚高 40 个百分点。
- **完工入库的额外费用科目须逐行手填**（P1-S1-R3 实测）：公司的 **`expenses_added_to_stock_account`**（Company「库存费用」节）为 None，故每张完工入库单要手填 N 行费用科目（N = 工序数 × 成本构成数），填错（如填成 `销货成本`）会让成本进损益表而非库存资产、成本核算直接错。须设该字段默认值为 `结转库存的费用 - HDS`。**注**：该字段名曾误记为 `expenses_included_in_valuation`（v13/v14 旧名，在 v16 源码零命中），照旧名找不到该字段；`Expenses Included In Valuation` 在 v16 仅作 **account_type 值**存在。见 P1-S1-R3 忠实度报告 FD-07。
- **前端多处改动后不刷新即不显示**（P1-S1-R3 累积六例）：仓库列表空白、工作区侧栏卡片缺失、BOM 保存后「提交」按钮不出现、`Job Card` 的 `time_logs` 残留空行致计时器状态错乱等。**客户演示前必须闭环**，详见 P1 概况登记册 `PH-P1002`。
  - **另一类是必然而非偶发**（R6 改判）：树形 DocType 从侧栏点进恒落列表路由而显示空白（`*_list.js` 是空文件）。R3 原判"偶发、`breadcrumbs.js` 已兜底、不必二开"被推翻——那套兜底只管"无视图记录时的默认值"，管不了侧栏链接生成的显式列表路由。
- **中文译名多处缺失或不准，其中一批会导致操作出错**（P1-S1-R3 与 R6 累计）。典型四条：`Setup` 与 `Settings` **都译「设置」**致同一侧栏两个分节同名（会点错地方）；父子科目 `Accounts Receivable`/`Debtors` **都译「应收账款」**致子科目被追加 `1`，而下拉里 group 与明细只差一个数字（会选错科目，**能记账的是带 `1` 的那个**）；`Opening & Closing` 误译「POS机交接班」；`默认成品仓(收料仓)` 括注错误。另有多处未译（`Item`、`Accounts Setup`、`Sales Taxes` 等）。**已提升为客户演示前的最高优先级**，见 `PH-P1001`。改造技术路径已查清（`Translation` DocType 记录最高优先 + 自有 app 的 `zh.csv` 做批量基线，均零侵入）。
  - **⚠ `context` 参数解决不了上述前两条**（P1-S2-R1 查明，此前记载有误）：`context` 是按 source + 场景**拆分**译文，解决的是"同一源词多义"；而 `Setup`/`Settings`、`Accounts Receivable`/`Debtors` 的形态**相反**——**多个源词撞到同一目标词**，只能改其中一方的用词。
