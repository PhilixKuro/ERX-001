## 系统现状

### 项目定位

基于 ERPNext 的二次开发项目。上游 ERPNext 与 Frappe 框架从自有 fork 取得，本项目的功能以 Frappe app 形态叠加在其上。

**目标行业**：弹簧制造（中国大陆中小型厂）。首个潜在客户为弹簧厂，规模与需求待实地考察确认；产品定位为可复用于多家同行业客户，非单客户定制。

**四阶段战略**（P1-S1-R1 讨论记录 DEC-007）：

| 阶段 | 内容 |
|---|---|
| ① 自学 + 摸底 | 先学会用 ERPNext 原生功能，在此过程中摸清原生对弹簧制造业的适用边界与痛点 |
| ② 做中国大陆通用版 | 针对摸出的原生缺口（首要是无中国财税逻辑）改造出适合中国大陆的通用版本 |
| ③ 客户演示 | 以通用版向客户演示 |
| ④ 定制 | 调研客户实际生产环境，定制专属业务逻辑与简单界面 |

后三阶段依次以前一阶段为前置，不并行。

**装载顺序**：`frappe → erpnext → CRM → HRMS → Insights → Raven → frappe_china → frappe_debug`。上游四处取「最后安装的 app」的机制（区域覆盖、whitelisted 覆盖、类覆盖、译名 csv）全归 `frappe_china`；`frappe_debug` 虽在末位，但不在这四处注册任何条目。新装的 app 一定追加到末尾，会夺走 `frappe_china` 的位置——`setup.sh` 装完 app 后调 `frappe_china.install.reorder_installed_apps` 归位，`check_app_order` 验覆盖是否真生效（做法见 `开发守则.md`）。依据 [ADR-0013](01-需求摸底/0-P1文档/ADR-0013-自有app按域分为frappe_china与frappe_debug.md)／[ADR-0003](01-需求摸底/0-P1文档/ADR-0003-app装载顺序自有app末位.md)。

遵循 frappe_docker 官方模型：bench 自己 clone 各 app，`frappe-bench/` 不进主仓库版本管理，版本由 `docker/apps.json` 记录（url + branch 或 tag + commit）。frappe、erpnext 与自有 app 在其目录内独立 commit、push 到自有 fork；四个官方业务 App 不改不推。

frappe 与 erpnext 版本须配套，同为 `version-16`。扩展方式与上游同步流程见 `开发守则.md`。

### UI 路由结构

沿用 ERPNext 标准 Desk 路由，另有三个官方 App 自带的独立前端：`/crm`（CRM）、`/insights`（Insights）、`/raven`（Raven），与 desk 是两套界面、各自建连接。HRMS 走 desk。**`frappe_china` 的功能目前没有导航入口**：`CN Tax` 模块的侧栏有意留空（只为压住框架自动生成的侧栏），结转凭证、三张报表、现金流量底稿等只能经顶部搜索进入；侧栏「财务报表」里同名的三张是 ERPNext 原生报表。正式入口归 S6 导航重整。

**v16 的 desk 路由前缀是 `/desk/`**，`/app/*` 已降为 301 重定向（`frappe/hooks.py` 的 `website_redirects`）。旧前缀仍可用，故照旧写法不会立刻报错——写文档与脚本时一律用 `/desk/`。

**导航结构由三张表承载，不是硬编码**（P1-S1-R6 查清）：

| DocType | 职能 |
|---|---|
| `Desktop Icon` | 首页图标网格。`link_to` 为空＝分组图标（点开只展开子图标）；`hidden` **是否向下传递取决于 `icon_type`**——`Folder` 传递、`App` 不传递 |
| `Workspace Sidebar` | **一个页面的左侧栏**（故左侧栏不是全站共用，首页没有左侧栏）。标准记录在 `erpnext/workspace_sidebar/*.json` |
| `Workspace Sidebar Item` | 上者的子表：`Section Break`＝分节标题、`Link`＝可点条目 |

**`Workspace`（19 条）不承载导航层级**——它装页面内容（快捷方式/卡片/图表），`parent_page` 全空；但它是 `Desktop Icon` 的**生成源**（`create_desktop_icons_from_workspace()`），故两者是"源与产物"而非"废弃与现行"。**要确认某条导航路径的实际呈现，查 `Desktop Icon` 与 `Workspace Sidebar`，不查 `Workspace`。**

**树形 DocType（`is_tree=1`，如 `Account`/`Warehouse`/`Cost Center`）必须走树视图** `/desk/{doctype}/view/tree`——它们的 `*_list.js` 是空文件、实现在 `*_tree.js`，落到列表路由会显示空白。

**改导航不需二开**：改记录（零代码；**`standard=1` 记录改后不被 `bench migrate` 覆盖已实测**——三张导航表 `Workspace Sidebar`／`Workspace Sidebar Item`／`Desktop Icon` 均不被覆盖，判据是比对 `modified` 时间戳而非 hash（`frappe/modules/import_file.py:141`）；**失效边界**：改动只维持到上游升级换掉那个 json 为止）或自有 app 出 fixtures。**远期计划用 React 全面重写前端**（走 REST API v2，与 jQuery 的 desk 两套独立，无技术债传递）。

### 已知限制 / 技术债

- **`frappe-bench/` 不进版本管理**，故各 app 的源码改动只存在于自有 fork，本仓库仅靠 `docker/apps.json` 记录 commit。换机器前须确认改动已 push，否则会丢。
- **v16 全新安装需额外初始化**：官方把一批初始化搬进了界面配置向导，而 `bench new-site` 会跳过向导。`docker/scripts/seed-demo.sh` 已覆盖（fixtures、默认计量单位、标准价目表、全局币种、配置完成标记），细节见 `docker/README.md`。
- 对 `frappe-bench/apps/erpnext/` 或 `.../frappe/` 的源码改动须登记于此（见 `开发守则.md`）。
- **ERPNext v16 无中国本地化**：`erpnext/regional/` 只有 australia / italy / south_africa / turkey / united_arab_emirates / united_states 六国，**无 china**。增值税专用发票、金税盘对接、银行对账、中国财务报表格式均无原生支持。这是四阶段战略第 ② 阶段（做中国大陆通用版）的主要工作面。**其中账与表（科目表、增值税、月末结转、三张报表、银行对账）已由 `frappe_china` 补上**（见上「能力」节）；开票接口、金税盘对接仍无，已划出 P1。
  - **但已查明它可以在自有 app 内实现、不必改 erpnext 本体**（P1-S2-R1 实测，探针留档 `Spike/V01-*`）：接入点是 `regional_overrides` hook——`erpnext/__init__.py:145` 读 `frappe.get_hooks("regional_overrides").get(get_region())`、`:152` 取 `[-1]`（**注册了该项的 app 里最后安装的那个胜出**），生产代码 **18 个 `@allow_regional` 覆盖点**（grep 得 20 行，其中一个是测试样本、一个在装饰器自身的 docstring 里）涵盖 GL 分录、计税、税额拆分、地址取值、采购估值——**但没有一个在建科目表或建税模板的路径上**，科目表只能走 `override_whitelisted_methods`（见架构文档 §3.1）。分派已实测生效（注入 hooks 缓存后覆盖函数被调用且参数原样传入；两 app 同 target 时末位胜出；改 `get_region()` 为 Italy 则覆盖失效，按国家隔离）。**四处不是 hook 但均有 app 侧替代**：`install_country_fixtures()`（`company.py:858-861` 硬编码 `erpnext.regional.<country>.setup.setup`）、`update_regional_tax_settings()`（`taxes_setup.py:120-125`）、`country_wise_tax.json`（**China 条目仍是 17%、早已过期**）、科目表 json 目录。
  - **另有三处实测结论**：① 增值税可用原生 `Tax Template` 三件套表达（价税分离、多档位、进项销项分离均实跑通过；**但手填 `item.item_tax_rate` 无效**，会被 `update_item_tax_map()` 重算覆盖，必须走真的 `Item Tax Template`）；② 自制科目表模板可用 `override_whitelisted_methods` 进建公司下拉，**但须连 `get_chart` 一并覆盖**（它不经 `execute_cmd`）；③ **现金流量表不是原生报表配置能产出的**，须自建可提交单据 + 从 GL Entry 按现金银行科目拉流水（直接法）。

  - **⚠ `context` 参数解决不了上述前两条**（P1-S2-R1 查明，此前记载有误）：`context` 是按 source + 场景**拆分**译文，解决的是"同一源词多义"；而 `Setup`/`Settings`、`Accounts Receivable`/`Debtors` 的形态**相反**——**多个源词撞到同一目标词**，只能改其中一方的用词。
  - **工作量有了实测量级**：同类撞名（同一目标词 ≥2 源词）**共 747 组，其中演示线涉及 143 组**（扫两份生效的官方 `locale/zh.po` 所得）。**基线口径不取 zelin `zh.csv`**——本站点 `sites/apps.txt` 只装 `frappe`+`erpnext`，那份 csv 不生效（`translate.py:172-187`）。其中 `Accounts Receivable`/`Debtors` 与 `Opening & Closing` 两条**已核实是从官方 `erpnext/locale/zh.po` 继承**（`:2244`/`:15827`/`:33973`），**收付款 5 条亦全部出自官方 po**（`Unpaid` `:59191`／`Paid` `:35517` 等）。
  - **⚠ `Request for`／`Requesting Site` 不是「明显误归／张冠李戴」**（P1-S3-R1 实核更正此前记载）：`Request for` 是 `item_reorder.json` 上 `warehouse` 字段的官方 label，`Requesting Site` 是 `procurement_tracker.py:46` 的官方报表列，两条都继承自官方。**实际形态是「官方 label 用词差 ＋ 官方译文过度合并」**，不是误归。
  - **收付款方向那批保留官方原译**（`Unpaid` → 未付款、`Paid` → 已付款，P1-S3-R1 DEC-080）：改用方向中性词的建议**未被采纳**，代价是四处裸渲染点仍显英文或误义，三条出路推 S6（见 P1 概况 `PH-P1010`）。
  - **两个第三方中文化项目均不可作方案基线**（`Reference/` 下，P1-S2-R1 调研）：`saoxia/erpnext_china` 无任何财税本地化、只适配 v15、许可证矛盾、含 33727 个真实手机号；`zelin-tech/erpnext_china` 的 18297 条译文中仅 748 条覆盖官方，四条已知缺陷只解决一条，且自身有确定译错（`May`→`04`、`Work In Progress`→「进行中」、`Committed`→「已提交」、`Ledger`→「会计凭证」）。**译名上可当词汇素材，不可当方案。**（财税上另论：zelin 的科目表与税模板数据以并入式取用，胶水层重写，见 ADR-0007）
