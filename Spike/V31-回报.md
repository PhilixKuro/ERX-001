# V-31 回报 — 列头字串能否原样活到人眼：Desk datatable ／ XLSX ／ PDF 三条渲染路径实测

**命题**：报表的列头字串，能不能**原样活到人真正看见和收到的那一层** —— 屏幕上的 Desk datatable、导出的 XLSX、打印/PDF？还是说中间某一层会重新翻译、改写、截断或以其它方式改动它们？

**判定**：**`no-go`** —— 分路径讲：

| 路径 | 字串本身 | 人眼所见 |
|---|---|---|
| **Desk datatable（屏幕）** | ✅ 逐字原样，无 `__()` | ✅ 中文正常（宽度不够会视觉省略号截断，字串未变） |
| **XLSX ／ CSV 导出** | ✅ 逐字原样（实跑读回字节） | ✅ 正常 |
| **PDF ／ 打印** | ⚠️ 经 `__()`，本站中文恰好无碰撞 | ❌ **全部 CJK 画不出来** —— 24 个汉字在容器内**零字体覆盖**，页面对每个汉字发的是 GID 0（`.notdef`） |

判 `no-go`的唯一理由是 **PDF**：字串活着，**字形死了**。屏幕与 XLSX 两条路径若单独判，是 `go`。

**这项代价落在两条设计路线上，不只是模板路线。** 见 §六。

**探针**：`Spike/V31-seg0-recon.py`（侦察）／`V31-render-layer.py`（主轴）／`V31-seg2-xlsx.py`／`V31-seg3-pdf.py`／`V31-seg4-truncation-and-glyphs.py`／`V31-seg5-glyph-proof.py`／`V31-seg9-verify.py`
**原始输出**：`Spike/V31-out/*.json`（另有实际导出的 xlsx／csv／pdf 及 PDF 内容流文本）
**站点**：`erx.localhost`，公司 `华东弹簧`，UI 语言 `zh`
**写入**：会计年度 2025 与各临时模板全在事务内建出、`finally` 里 `rollback()`，全程无 `commit()`

## 一、先摆清楚：翻译层碰不碰列头

这是整份回报的枢纽，因为**三条路径里有两个地方对列头套了翻译函数**：

| 位置 | 代码 | 对列头套 `_()`？ |
|---|---|---|
| **XLSX／CSV 表头** | `frappe/desk/query_report.py:692` `column_data.append(_(column.get("label")))` | **是** |
| **PDF／打印表头** | `frappe/public/js/frappe/views/reports/print_grid.html` `{{ __(col.name) }}` | **是** |
| **Desk datatable** | `query_report.js:1434` `name: is_query_generated_report ? __(column.label) : column.label` | **否**（本报表 `query` 为 `null`，实测 `therefore_is_query_generated_report: false`） |
| `query_report.run` 服务端返回 | `generate_report_result` 无 label 翻译 | 否 |
| 报表自身两个 JS | `custom_financial_statement.js` ／ `erpnext/public/js/financial_statements.js` | 否（实测两文件 `column.label`／`col.label` 出现次数均为 **0**） |

`_()` 的语义（`frappe/utils/translations.py`，实测源码入 JSON）：**查不到就原样返回**，查到就替换。所以「中文列头没被改」有两种完全不同的读法 ——
**(a)** 渲染层不翻译列头；**(b)** 渲染层**确实**翻译，只是这个中文串刚好在词典里没有对应条目。

项目已知 747 处翻译键碰撞，(b) 不是理论风险。所以本探针没有只跑一组中文，而是设了**能区分这两种情况的四格**。

### 判据能不能分辨：阳性对照给了答案

实测 `zh` 词典 **14440 条，含 CJK 的键 0 条**（`zh_dict_shape.keys_with_cjk: 0`）。所以中文列头查不到、原样透传 —— 这是**词典内容**的事实，不是「中文免疫」。

阳性对照（`POS` 格）把 `Column Break.display_name` 填成词典里**真有条目**的英文键，runtime 从活词典里挑（不硬编码，免得词典变了对照悄悄失效）：

**同一个 XLSX 文件里出现了两种结果**（`XLSX_HEADER_DIFFS_POS_translated_key_hidden0`，`discriminates: true`）：

| 列 | 引擎 label | 落到 XLSX | 变了？ |
|---|---|---|---|
| `seg_0_account` | `Assets` | **`资产`** | ✅ 被替换 |
| `seg_0_dec_2025` | `Assets - 2025` | `Assets - 2025` | 未变（`Assets - 2025` 不是键） |
| `seg_1_account` | `Liabilities` | **`负债`** | ✅ 被替换 |
| `seg_1_dec_2026` | `Liabilities - 2026` | `Liabilities - 2026` | 未变 |

**⇒ 判据确实能看见替换。** 中文那一组的「零差异」因此是真结果，不是探针瞎。

### 反向再钉一遍：给中文注入条目，它就被换掉

`CJK` 格在**本进程内**给 `get_all_translations` 打补丁，注入 `年初余额 → 被翻译层替换了`（不写 Translation 表、不写 redis，`finally` 撤销）：

```
seg_0_account   年初余额        → 被翻译层替换了   changed: true
seg_1_dec_2026  期末余额 - 2026 → 被翻译层替换了   changed: true
```

**⇒ `_()` 会毫不犹豫地替换一个中文列头。** 挡着它的只是「出厂 `zh` 词典没有 CJK 键」这一条，而这条**不是我们控制的** —— 任何人在 `Translation` doctype 里建一条 `source_text=年初余额` 的记录，或将来 `zh` 词典收进 CJK msgid，PDF 与 XLSX 的表头就会被改。实测当前 `Translation` 表 **0 行**。

**另有一个已经在发生的替换**：隐藏列的英文 label 本来就被换成中文了 —— `Account Name → 科目名称`、`Account Number → 科目代码`、`Currency → 货币`（`RUN_PAYLOAD_COLUMNS_*`）。这**不是**渲染层干的，是引擎自己：`financial_statements.py:670-700` 的 `get_columns` 用 `_("Account Name")` 构造 base column。V-29 说「中文没有传到隐藏列」是因为它在 `lang=en` 的探针进程里跑；真实会话 `lang=zh`，这三列是中文。**对 V-29 该条的一处修正**。

> ⚠ 语言这件事本身是个坑：python 探针进程的 `frappe.local.lang` 默认 `en`，而真实 Desk 会话解析出的是 `zh`（`get_user_lang(Administrator) == "zh"`，`User.language = zh`，`System Settings.language = zh`）。本探针所有渲染层测试都**显式设成 `zh`**，并保留 `en` 作对照格。若不设，结论会偏乐观。

## 二、Desk datatable（屏幕）

**字串：逐字原样。** `query_report.run` 返回的 `columns` payload（实跑，非读码）：

```
年初余额 | 年初余额 - 2025 | 年初余额 - 2026 | 期末余额 | 期末余额 - 2025 | 期末余额 - 2026
```

`RUN_PAYLOAD_CHARDUMP_NEG` 给了逐字码位，与 V-29 完全一致：

| label | 码位 | 前后空白 |
|---|---|---|
| `年初余额` | `U+5E74 U+521D U+4F59 U+989D` | 无 |
| `年初余额 - 2025` | `…U+989D` **`U+0020 U+002D U+0020`** `U+0032 U+0030 U+0032 U+0035` | 无 |
| `负债和所有者权益 - 2026` | `U+8D1F U+503A U+548C U+6240 U+6709 U+8005 U+6743 U+76CA` **`U+0020 U+002D U+0020`** `…2026` | 无 |

分隔符仍是 ` - `（空格＋ASCII 连字符 `U+002D` ＋空格），非全角、非 `U+00A0`。`V29_REPRODUCTION_CHECK.matches_V29: true`。

**客户端那一段是读码得出的，不是实跑。** 依据链：`query_report.js:1380-1383` 算出 `is_query_generated_report`（本报表 `Report.query` 为 `null` ⇒ `false`）→ `:1434` 走 `column.label` 分支，**不套 `__()`**。代码注释自己写着「label 应已在后端翻译过，再翻会出意外行为」。两个报表 JS 都不碰 label。**未用 CDP 实跑浏览器**（`Spike/V16-cdp-*.js` 的先例我没动）—— 理由见 §七。

## 三、XLSX ／ CSV 导出：实跑并读回字节

**这是实跑。** 调的是 Desk「导出」按钮走的同一个函数 `frappe.desk.query_report._export_query`，把返回的字节写进 `V31-out/`，再用 **openpyxl**（独立读取器，不是 frappe 自己的代码）读回首行。

`xlsx-NEG_statutory_chinese_hidden0.xlsx` 首行逐字：

```
年初余额 | 年初余额 - 2025 | 年初余额 - 2026 | 期末余额 | 期末余额 - 2025 | 期末余额 - 2026
```

`byte_identical_to_engine: true`，`XLSX_HEADER_DIFFS_*.count: 0`。长标签组同样 `true`：

```
资产 | 资产 - 2025 | 资产 - 2026 | 负债和所有者权益 | 负债和所有者权益 - 2025 | 负债和所有者权益 - 2026
```

**数字是真的**，列头不挂在死列上：`资产合计` 行 2026 列 `719.5`，与 V-29 一致。`include_hidden_columns=1` 时 12 列全出，隐藏列头是中文 `科目名称／科目代码／货币`。

## 四、PDF ／ 打印：字串活着，字形死了

### 4.1 字串层：多一道 `__()`，本站中文恰好无碰撞

报表 PDF 是**客户端**生成的：`query_report.js` 渲染 `print_grid` 微模板，把 HTML POST 给 `frappe.utils.print_format.report_to_pdf`。而 `print_grid.html` 的表头单元格是 `{{ __(col.name) }}` ——
**打印路径比屏幕多一道翻译**（屏幕在 `:1434` 跳过了 `__()`）。

我用浏览器拿到的**同一本词典**复现了这个变换（`frappe.boot.__messages` == `get_messages_for_boot()` == `get_all_translations("zh")`，实测 `identical_to_get_all_translations: true`，14440 条、CJK 键 0 条）：

- 中文组：12 列 `print_differs_from_screen` **全 false** —— 字串不变
- 阳性对照组：`Assets → 资产`、`Liabilities → 负债`，`changed: ["seg_0_account", "seg_1_account"]` —— **变换是活的**

**⇒ 打印路径对中文列头无碰撞（当前词典下），但它确实带着一道屏幕没有的翻译步骤。** 这是**读码＋用真实词典复现**，不是端到端实跑打印（原因见下）。

### 4.2 字形层：24 个汉字，零字体覆盖，页面画 `.notdef`

**这才是判 `no-go` 的那一条，而且是实跑。**

渲染用 `frappe.utils.pdf.get_pdf` —— `report_to_pdf` 内部真正干活的那个函数（`print_format.py:268`），HTML 里嵌入真实列头加一个 ASCII 对照串 `ZZASCIICONTROL`，出来的 PDF 用 **pypdf** 抽文字：

```
extracted_text: "\u0000\u0000\u0000\u0000\u0000\u0000\u0000\u0000 - 2025…\nZZASCIICONTROL\n…"
ascii_control_present: true
cjk_headers_found: 0 / 12
```

ASCII 对照串干净出来，12 个中文列头**一个都没出来**，全变 NUL。为免这只是抽取器/CMap 的假象（那种情况下页面其实画得好、只是复制粘贴坏），我用两条互相独立的方式钉到字形层：

**(A) 字体覆盖。** 用 fontTools 遍历 fontconfig 报告的**全部 11 个字体文件**的 cmap：

```
installed: Cantarell ×5, DejaVuSans/Serif/Mono ×6
chars_covered_by_NO_installed_font:
  U+5E74 年  U+521D 初  U+4F59 余  U+989D 额  U+671F 期  U+672B 末
  U+8D44 资  U+4EA7 产  U+8D1F 负  U+503A 债  U+548C 和  U+6240 所
  U+6709 有  U+8005 者  U+6743 权  U+76CA 益  U+79D1 科  U+76EE 目
  U+540D 名  U+79F0 称  U+4EE3 代  U+7801 码  U+8D27 货  U+5E01 币
count_uncovered: 24 / count_tested: 24
```

**24 个全部零覆盖。** `fc-match sans-serif:lang=zh-cn` 退到 `DejaVuSans.ttf`。

**(B) 页面自己发的字形号。** PDF 用 `/Identity-H`，`Tj` 操作数里是**裸 GID**，而 GID 0 按定义就是 `.notdef`（「没有这个字形」槽）。解出内容流（184 个 `Tj`）：

- 中文那些 run：`<0000>` —— **全 GID 0**
- 同一页的 ASCII run：`<0001> <0002> <0003> <0004> <0005>` —— 真实非零 GID

**⇒ 页面的绘图指令本身在命令渲染器为每个汉字画「缺字形」。** ASCII 在同一流里拿到真 GID，说明解码没错、零不是解析 bug。

第三个对照：显式写上 `font-family: "Noto Sans CJK SC", "WenQuanYi Zen Hei", …` 的 PDF 与不写的**字节数完全相同**（6453 vs 6453，ASCII 版 7335）—— **点名 CJK 字族没有用，因为一个都没装**。

**人眼所见**：法定字样位置是空白或豆腐块。字串一路完好，最后一步画不出来。

> **我没有调 `report_to_pdf`，这是刻意的，也是一处观察边界。** 事前扫描发现 `print_format.py:266` 有 `make_access_log(...)` → `Document.deferred_insert()`（`document.py:1985`）→ `frappe.cache.rpush` 进 `insert_queue_for_Access Log`，而 `deferred_insert.py:save_to_db()` 之后会**插入并 commit** —— 那是我的事务管不着的 redis 写＋后续提交，`rollback()` 撤不掉。所以我直接调它委派渲染的 `get_pdf`（实测 `db.commit`／`enqueue`／`save_file`／`make_access_log` 计数**全 0**）。**渲染是真的，围绕它的 access-log 记账被跳过了。**

## 六、自建报表路线是否同样吃这份成本

**是，几乎全额同样吃。** 这不是模板路线的专属代价：

1. **PDF 字形问题与报表实现完全无关。** 缺的是**容器里的字体**。自建报表的列头照样是中文，照样经 `print_grid.html` 的 `{{ __(col.name) }}`，照样交给同一个 wkhtmltopdf，照样得到 GID 0。**自建报表一行代码也躲不开。**
2. **XLSX／CSV 表头的 `_()` 是框架层的。** `query_report.py:692` 在 `build_xlsx_data` 里，所有 Script Report 的导出都过这里。自建报表只要返回 `columns`，表头就被 `_()` 过一遍 —— 翻译碰撞风险同在。
3. **datatable 的 `__()` 跳过条件也是框架层的。** `is_query_generated_report` 看的是 `Report.query` 字段；自建的 Script Report 同样 `query` 为空，同样走 `column.label` 不翻译分支。**这一条对两条路线都是好消息。**
4. **自建报表能省下的，只有引擎那部分** —— 即 V-29／V-26 记的「` - {期间}` 尾巴关不掉」「段标签被复用到项目列头」「两个项目列而非一个」。那些是 `MultiSegmentFormatter` 的约束，自写 `execute()` 自然绕开。

**一句话**：自建报表能修好**列的形状和文字构造**，修不好**字体缺失**，也躲不开**导出与打印路径上的 `_()`**。PDF 这一条若不装 CJK 字体，两条路线都出不了能给人看的打印件。

## 八、复核建议

1. **最该先看的：`no-go` 卡在字体，不卡在字串。** 这两件在决策上完全不同 ——
   - 字串层（引擎→payload→XLSX/CSV）**已经是干净的**，`go`；
   - 字形层（PDF）是**环境缺陷**，装一个 CJK 字体（Noto Sans CJK / WenQuanYi）大概就能解，属可修，**但本探针没有验证「装了就好」** —— 我没装字体、没重跑。若 B 步只摘 `no-go` 而不摘「卡在字体」，会被读成「中文列头做不到」，那是错的。
   查法：读 `V31-out/seg5-glyph-proof.json` 的 `FONT_CMAP_COVERAGE_per_char`（24/24 零覆盖）与 `PDF_EMITTED_GLYPH_IDS`（GID 0 vs 非零对照）。

2. **哪些是实跑、哪些是读码**（这条界线请照抄，不要糊）：

   | 结论 | 来源 |
   |---|---|
   | 引擎 12 列 label、复现 V-29 | **实跑** |
   | `run()` 返回的 `columns` payload | **实跑** |
   | `_()` 对各 label 的作用（zh／en 双语） | **实跑**（调真 `_()`，真词典） |
   | 中文注入后被替换 | **实跑**（进程内打补丁） |
   | XLSX／CSV 表头字节 | **实跑**（真导出，openpyxl 读回） |
   | PDF 字形失败 | **实跑**（真渲染，pypdf＋fontTools＋内容流） |
