# V-30 回报 — `Custom API` 的返回值契约，以及它到底能不能碰列

## 一、命题

`Financial Report Row` 的 `data_source` 取 `Custom API` 时，被引用的那个 whitelisted GET 方法的**返回值是否必然是「一个按期间排序的扁平数值列表」**——亦即 `Custom API` 是否**确实没有任何入口去改列的数量与列的名字**？

背景：R1 讨论把 `Custom API` 记成「解决列头合规问题的那个出口」。V-25 从读码否证了这一点（`financial_report_engine.py:1185` 把 `frappe.call(...)` 的返回值绑给 `values`，一个按期间排的扁平列表），但 V-25 自己声明过：**「我只读了 `:1185` 的调用签名，没有真写一个 Custom API 方法跑一遍。」** 本探针就是去补那一跑。

## 二、判定

**`go`** —— V-25 的结论**成立**：`Custom API` 是行级取数出口，**其返回值改不了列的数量，也改不了列的名字**。这一条现在有实跑撑着，不再只是读码推论。

但要交代两处 V-25 没看到、且会影响下游怎么写判据的事实：

1. **「必然是扁平数值列表」是引擎的一个未校验的假设，不是它强制的契约。** 引擎既不校验也不转换返回值：返回字符串它就把字符串塞进单元格，返回 `dict` 它会在**更晚**的地方崩掉。所以「必然」二字，在「引擎会保证」这个意义上**不成立**；在「只有这个形状才работ得对」这个意义上成立。
2. **「没有任何入口」这个绝对形式被我证伪了。** 返回值这条通道确实动不了列，但 `:1185` 把 `periods=self.period_list` **按引用**传进方法，而列是**之后**才由同一个对象生成的——**在方法里原地改这个 list，列的数量和名字都会跟着变**，我实跑到了 17 列、6 列、以及把列头改成自定义文本。这是一条非契约的副作用通道，见 §五。

**给下游用的一句话**：可以写「`Custom API` 的**返回值**只能供给行内各期间的数值，无法控制列」；**不要**写成「`Custom API` 完全无法影响列」——后者会被下一个人用 15 行代码证伪。

## 三、各子问题的实测

站点 `erx.localhost`，公司 `华东弹簧`（唯一一家），`filter_based_on=Fiscal Year`、`2026`、`periodicity=Monthly`、`selected_view=Report`。基线 12 个期间、16 列。

> 为何是 16 列而不是 17：`filters` 里没有 `accumulated_values`，取到 `None`，`financial_statements.py:712-722` 的 `if not accumulated_values` 因此为假，**不追加 `Total` 列**；同理 `:1662` 的 `total` 累加也不发生，所以实测各行 `total` 恒为 0。这与 V-25 §四记载的「FRT 路径不传 `accumulated_values`」一致。

### (a) 正常的扁平数值返回 — `V30-custom-api.py`

方法按索引返回**互不相同**的哨兵值 `1001, 1002, … 1012`（不用同一个值，否则「对得上」无法区分「真按位置映射」与「恰好都一样」）：

| 期间列 | `jan_2026` | `feb_2026` | … | `nov_2026` | `dec_2026` |
|---|---|---|---|---|---|
| 交付值 | `1001.0` | `1002.0` | … | `1011.0` | `1012.0` |

- `sentinel_to_column_mapping_exact: true`，`mismatches: {}` ⇒ **返回值是按期间下标定位的**，第 i 个元素进第 i 个期间列。
- 方法实际收到的三个 kwargs：`filters` 是 `_dict`（8 个键，`company=华东弹簧`、`periodicity=Monthly`）；`periods` 是 12 个 `_dict` 的 `list`，带 `key`/`label`（`jan_2026`…`dec_2026` / `Jan 2026`…`Dec 2026`）；`row` 是 `FinancialReportRow` 文档对象。
- `reverse_sign=1` 的行取到 `-1001.0 … -1012.0` ⇒ `:1187-1188` 生效。
- `Calculated Amount` 能引用 Custom API 行的 `reference_code`：`API_FLAT * 2` 得 `2002 … 2024` ⇒ `:1196-1197` 把值写进了 `row_values`。
- 列头是引擎自己的 `Jan 2026 … Dec 2026`，**返回值没有泄漏到任何 label 或 fieldname**（`return_value_leaked_into_columns: []`）。
- 同一方法被两行引用 ⇒ 被调用 **2 次**（每行各一次，无缓存）。

**校验路径实测**（`financial_report_validation.py:18-30`，五种情形全打）：

| 情形 | 结果 |
|---|---|
| `@frappe.whitelist(methods=["GET"])` | **通过**，`allowed_http_methods = ["GET"]` |
| 只 `methods=["POST"]` | `PermissionError`：`Method ... must permit GET requests` |
| 未 whitelist 的普通函数 | `PermissionError`：`Function ... is not whitelisted.` |
| 模块里不存在的属性 | `AttributeError` |

⇒ **任何 app 的 `@frappe.whitelist(methods=["GET"])` 方法都能被直接引用，不需要改上游**，这条确认。解析靠 `frappe.get_attr`（`frappe/__init__.py:1129-1137`，走 `importlib.import_module`）。

13 种形状，**全部 13 种都没有触发静默归零**（`error_log_delta` 恒为 0），**全部 13 种都没有改动列**（16 列、label 逐字相同）：

### (c) 在方法里抛异常：静默归零**确认为真** — `V30-seg3-silent-zero.py`

`:1192-1194` 确实存在且确实生效。五种抛法**全部被吞**，`execute()` **一次都没有抛**，报表照常返回：

| 方法内行为 | `execute()` 抛? | Error Log +1? | 12 格值 | 用户可见消息 |
|---|---|---|---|---|
| 合法地返回全 0（对照组）| 否 | **否** | 全 `0.0` | 0 条 |
| 合法地返回全 42 | 否 | 否 | 全 `42.0` | 0 条 |
| `raise Exception(...)` | **否** | **是** | **全 `0.0`** | **0 条** |
| `1/0` | **否** | 是 | 全 `0.0` | 0 条 |
| `frappe.throw(...)` | **否** | 是 | 全 `0.0` | **1 条** |
| `raise frappe.PermissionError` | **否** | 是 | 全 `0.0` | 0 条 |
| `KeyError` | **否** | 是 | 全 `0.0` | 0 条 |

Error Log 里落的正是 `:1193` 那句：`Custom API Error: erpnext.zz_v30_raise_inj.maybe_raise - V30 deliberate generic failure inside Custom API`。

**抗歧义设计（本探针的关键）**：单看「格子是 0」无法区分「失败被吞」和「就是合法的 0」。所以我加了一个**合法地返回全 0** 的对照组，把两者交付到报表的行**逐格对比**：

```
legit_zero  cells: {jan_2026: 0.0, feb_2026: 0.0, ... dec_2026: 0.0}
raise_generic cells: {jan_2026: 0.0, feb_2026: 0.0, ... dec_2026: 0.0}
swallowed_failure_INDISTINGUISHABLE_from_legit_zero: true
any_user_facing_message_on_failure: 0
```

⇒ **「没报错」不等于「跑通了」**，这一条成立。一个 Custom API 方法可以彻底失败，而报表上呈现的东西与「该科目本期确实为零」**在交付数据层面完全无法区分**，且默认不给用户任何提示。唯一的痕迹在 Error Log 里——一个用户不会去看的地方。

一处例外值得记：`frappe.throw` 那次 `message_log` 里留了 1 条。`frappe.throw` 会先 `msgprint` 再 raise，所以消息先落进了 log 才被 `:1192` 吞掉异常。**只有 `frappe.throw` 这一种抛法有部分可见性**；裸 `raise` / `1/0` / `KeyError` / `PermissionError` 全是 0 条。我**没有**验证这 1 条消息在真实 UI 上是否真的弹出来。

### (d) 能不能影响列的数量与名字 — `V30-seg4-columns.py`（核心）

命题要求分清「机制做不到」与「我这次的返回形状恰好没做到」。所以本段跑**两条通道**，并带一个**阳性对照**来标定仪器灵敏度。

**返回值通道（`Custom API` 的正式契约）：**

| 尝试 | 列数 | 结果 |
|---|---|---|
| 基线（扁平）| 16 | — |
| 返回 `{"columns":[{label...}],"values":[...]}` | — | **`KeyError: 0` 抛出**，并没有据此定义列 |
| 只返回 2 个值（想要 2 列）| **16** | 列一个没少 |

`return_value_ever_changed_columns: **false**`

**变异通道（阳性对照，非契约路径）：**

| 方法里做的事 | 列数 | 列头变化 |
|---|---|---|
| 改 `periods[0]["label"]` / `[1]` | 16 | **`Jan 2026`→`NIANCHU YUE E`、`Feb 2026`→`QIMO YUE E`** |
| `periods.append(...)` | **17** | 末尾多出 `EXTRA COLUMN` |
| `del periods[2:]` | **6** | 只剩 `Jan 2026`、`Feb 2026` |
| 改 `filters["periodicity"]="Yearly"` | 16 | 无变化（`period_list` 早已建好）|
| 改 `row.display_name` | 16 | 无变化 |

`mutation_channel_moved_columns: **true**` ⇒ `harness_can_detect_column_changes: **true**`

**这就是我能回答「究竟确立了哪一件事」的依据**：我的观测装置**被证明对列的变化是敏感的**（它抓到了 17 列、6 列、改掉的列头）。因此「返回值通道下列从未变化」是一个**真实的否定结论**，而不是「仪器瞎了」。我确立的是**前者**（机制做不到），不是后者（恰好没做到）。

### (e) 附带：路径写错是响的，不是静默的 — `V30-seg5-badpath.py`

`get_valid_api_method` 在 `:1181`，**在 `:1183` 那个 `try` 之外**，且保存时 `_validate_custom_api`（`financial_report_validation.py:525-552`）也会再校一遍。实测**六种坏路径全部在保存阶段就被 `ValidationError` 拦下**，根本存不进去：

- 只 POST / 未 whitelist → `Row 1: [API Method Path] Method '...' must be whitelisted and permit GET requests`
- 属性不存在 → `Row 1: Could not validate API Method Path: module '...' has no attribute '...'`
- app 未安装 → `Row 1: Could not validate API Method Path: App no_such_app is not installed`
- 没有点号 → `Row 1: API Method Path should be in format: app.module.method`

⇒ **配置错误是响的，运行时异常是静默的。** 这条区分决定了「Custom API 失败长什么样」。

三点串起来就是全部答案：

1. **返回值只流向单元格。** `values` 只被 `:1673` 按下标取用，`RowData.values` 从不参与 `:1414-1422` 的列构造。列的唯一来源是 `period_list` ＋ `filters`（`periodicity`/`accumulated_values`/`company`），**没有一处读返回值**。这就是返回值改不了列的机制性原因。
2. **`Financial Report Row` 的 21 个字段里没有任何 `label`/`header` 字段**（与 V-25 §二一致），所以模板层也没有列名入口。
3. **但 `:1185` 传的是引用，不是副本**，而 `:221` 早于 `:222`——方法拿到的 `periods` 正是 `:1417` 稍后要读的同一个 list 对象。原地改它，列就跟着变。这条通道在代码里没有任何注释或防护，它是实现细节的外泄，不是设计出来的入口。

## 五、静默归零对「能不能信这个出口」的意义

静默归零**是真的**（§三(c) 实测）。它的影响面要说准：

- **只有「方法内部抛异常」这一种失败会被吞。** 路径配错在保存期就被拦（§三(e)）；返回形状错会在格式化阶段裸崩（§三(b)）。这两类都是响的。
- **被吞的那一类，后果最重**：报表正常出，列正常，数字全 0，默认零提示，且与「合法的 0」在交付数据上**逐格无法区分**。财务报表里「0」是一个合法且常见的答案，这使得该失败模式**天然伪装成正确结果**。
- **唯一痕迹是 Error Log。** 而且——见 §六——本站 `tabError Log` 是 MyISAM。

⇒ 若将来真要用 `Custom API` 取数，**不能依赖「没报错」作为通过判据**。要么方法内部自己不允许异常逃逸（自己捕获并以可辨识的方式表达失败，例如返回一个明显不可能的哨兵值），要么在方法外另设核对（与独立算出的数对账）。把「跑出来没红字」当成验收标准，在这个出口上是不成立的。

## 七、复核建议

1. **最该先看的：判定是 `go`，但「绝对形式」被证伪了。** 若 B 步照抄成「`Custom API` 无法影响列」，下一个人用 15 行代码（在方法里 `periods.append(...)`）就能推翻它。准确写法是「**返回值**无法控制列」。查法：读 `V30-out/d-column-control.json` 的 `DECISIVE_d_return_value_channel`（三种返回形状列数恒 16）与 `DECISIVE_d_mutation_channel`（17 列 / 6 列 / 改掉的列头）两键，再看 `HARNESS_CALIBRATION` 确认仪器不是瞎的。
2. **变异通道我只证明了「能」，完全没评估「该不该」。** 它依赖 `:1185` 传引用 ＋ `:221` 早于 `:222` 这两个未文档化的实现细节，上游一次重构就可能失效，且没有任何测试保护它。**「要不要用它拿合规列头」是判断题，不是事实题，不在本探针射程内。** 我的事实贡献仅止于：这条路存在，且真能改列数与列名。
3. **观察范围（未验的部分）**：
   - 只跑**单段**模板（无 `Column Break`）。Custom API 行处在**多段**模板里时，`MultiSegmentFormatter.get_columns`（`:1713-1729`）会给期间列加 `段标签 - ` 前缀（V-25 §二），**变异通道在多段下的表现我没跑**。
   - 只跑 `Monthly` ＋ `Fiscal Year 2026` ＋ `selected_view=Report`。未验 `Yearly`/`Quarterly`/`Date Range`，也**未验 `Growth` 视图**（`GrowthViewTransformer` 会另加列，与 Custom API 的交互未知）。
   - **全部在进程内直调 `FinancialReportEngine().execute()`**，未经 HTTP／`query_report` 真实请求路径，也未跑图表路径（`generate_chart_data`，`:226`）。
   - **未验并发／跨请求污染**：变异通道改的是 `period_list`，实测 `get_period_list` 每次调用新建 dict（无缓存），故我这几轮之间不串；但**真实 worker 下会不会跨请求泄漏，我没测**。若有人真打算用变异通道，这一条必须先补。
   - 第三方 app 只验到机制层（`frappe.get_attr` → `importlib`，且未安装的 app 会被 `AppNotInstalledError` 拦）。**没有真建一个独立 app** 来放方法。
4. **我做的选择**：探针 (b)–(e) 的方法用 `sys.modules` 注入而非落盘，为的是零文件系统痕迹。代价是**注入不是生产形态**——生产里方法住在某个已安装 app 的磁盘模块里。我用探针 (a) 落盘跑了一次真实磁盘模块来覆盖这个差异，两者经 `get_valid_api_method` 解析结果一致（同一个 importlib 模块注册表）。如果要更贴近生产，值得在一个真 app 里补一次。
5. **拿不准处**：`frappe.throw` 那一次在 `message_log` 里留了 1 条消息，其余四种抛法留 0 条。**这 1 条在真实 UI 上是否真会弹给用户，我没验**——若它确实可见，那么「用 `frappe.throw` 表达失败」就是这个出口里唯一半可见的失败方式，对「怎么安全地用它」有实际意义，值得单独补一跑。
6. **环境事实，建议记进项目常识**：**`tabError Log` 是 MyISAM，非事务性，`frappe.db.rollback()` 对它无效**；业务表都是 InnoDB。后续任何会触发 `frappe.log_error` 的探针都不能靠回滚自清，必须正向限定地按主键删自己造的行。我为此付了一次代价（§六）。
