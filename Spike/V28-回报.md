# V-28 回报 — 多月有账时 `Closing Balance` 列是否逐月正确递增

**命题**：几个月都有账时，`Closing Balance` 列**是否逐月正确递增**？即 V-26 观察到的累计语义在**多月场景下算术上真成立**，而不只是在「只有一个月有账」这个退化情形里**看起来**成立。

**判定：`go`** —— **累计语义在多月场景下算术上成立，逐位吻合裸 GL。**

**探针**：`V28-multimonth-cumulative.py`（主）／`V28-seg0-recon.py`（只读侦察）
**原始输出**：`V28-out/multimonth-cumulative.json`／`V28-out/seg0-recon.json`
**站点**：`erx.localhost`，公司 `华东弹簧`，FY2026（`2026-01-01`…`2026-12-31`）

---

## 一、为什么 V-26 答不了这一问

V-26 的证伪实验建立在「损益类 GL 全在 2026-09」这一事实上：累计列在 10 月之后**保持** 719.5、单月列**掉回** 0.0。该实验对「两列能否并存」有效，但**对本命题无判别力**——因为一个**只是把上一个值重复下去**的列，同样能通过那个测试。V-26 自己的复核建议第 3 条已把这点列为未验：「多月有账时逐月累计值是否正确递增（站点只有一个月有账，验不了）」。

**本探针先用只读侦察确认了这个前提仍然成立**（`V28-out/seg0-recon.json`）：全站 14 条有效 GL **全部落在 2026-09**，`distinct_posting_months` = `["2026-09"]`，**`accounts_with_postings_in_2plus_months_count` = 0**。故必须**造出第二、第三个月**才能测。

## 二、怎么造第二个月的账（最小侵入）

引擎**直接读 `GL Entry` 表**（`financial_report_engine.py:642` `_get_gl_movements`），不经任何凭证对象，所以**裸 GL 行足够**。因此用 `db_insert()` 写入 8 条 GL 行：它执行一条朴素 INSERT，**不触发任何 controller、不跑 validate、不跑 on_submit**，比提交 Journal Entry 严格更轻。并显式指定 `name`（`ZZPROBE-V28-001`…`008`），连 `tabSeries` 命名计数器都不碰。

注入的金额**刻意每月不同**，这是判据有判别力的关键：

| 月份 | 收入（贷） | 成本（借） | 该月损益 |
|---|---|---|---|
| 2026-09（站点原有，未动） | 1045.0 | 325.5 | 719.5 |
| 2026-10（注入） | 200.0 | 80.0 | 120.0 |
| 2026-11（注入） | 500.0 | 30.0 | 470.0 |

每月借贷自平（10 月 280/280、11 月 530/530，见 `inject_is_balanced_per_month`），现金科目承担配平腿。

### 两个「另有解释」已被明确排除

判据必须能区分它声称区分的两种情形，故专设两条反向断言：

2. **`REFUTED_column_is_grand_total_repeated` = true**——「累计列其实是全年总额铺满每一列」被排除：全年总额是 1309.5，而 9 月报 719.5、10 月报 839.5，**都不等于总额**。

## 四、机制（file:line）

累计不是某个开关算出来的，而是 `_calculate_running_balances()` 逐期滚动的**天然产物**（`financial_report_engine.py:679-703`）：

```python
for period in self.periods:
    movement = gl_movement.get(period_key, 0.0)
    closing_balance = current_balance + movement          # :699
    account_data.add_period(PeriodValue(period_key, current_balance, closing_balance, movement))  # :701
    current_balance = closing_balance                      # :703
```

`:703` 把本期 `closing` 结转成下期 `opening`，于是 **`closing` 是滚动累计、`movement` 是本期发生额，两个数同时存放在同一个 `PeriodValue` 上**。取哪个由 `PeriodValue.get_value()` 按 `balance_type` 三选一（`:60-66`），而 `balance_type` 是**行级字段**——这正是 V-26 两列并存的成因，本探针进一步证明滚动出来的那一串数**算术正确**。

`accumulated_values` 这个报表级开关在 FRT 路径上恒为 `None`（`accumulated_values_in_filters` = false），命中 `_handle_balance_accumulation():711-715` 的 `continue` 分支，两个值都**不被改写**：

```python
if accumulated_values is None:
    # respect user setting if not in filters
    # closing = accumulated
    # movement = unaccumulated
    continue
```

期初口径：站点 **PCV 0 条、`Account Closing Balance` 0 行**（`opening_balance_path_preconditions` 已记录），故走 `_get_opening_balances_from_gl()` 分支、以 `1900-01-01` 为起点——与 V-26 seg2 的结论一致。

## 六、复核建议

1. **最该先看的：本条判定把 V-26 留下的最后一个替代解释关掉了，但它只增强 V-26、不改变 V-26 的前提约束。** 查法：读 `V28-out/multimonth-cumulative.json` 的 `DECISIVE`（十二项布尔）与 `chain_identity_cum_prev_plus_monthly`，再对 `raw_gl_pl_movement_by_month`（`{"2026-09":-719.5,"2026-10":-120.0,"2026-11":-470.0}`）确认引擎数与裸 GL 一致。**要留意**：`cumulative_strictly_increases` 之所以有判别力，全靠我把三个月的金额设成互不相同；若有人重跑时改成等额，这条断言就退化成没意义了。

2. **第二该看的：本探针证明的是「单一会计年度内、逐月滚动算术正确」，不是「等于法定本年累计额」。** V-26 seg2 已证 `Closing Balance` 是**从有账以来的滚动余额**；本探针的三个月恰好全在 FY2026 之内，且**上一年度无任何账**，所以滚动值与本年累计值在这里**碰巧相等**。**跨年是否仍对，本探针没验**——那依赖年结 PCV（代码路径 `:536-547`），而建 PCV 是真写入。这一条仍是 V-26 复核建议第 3 条①留下的缺口，**未被本探针填上**。

3. **观察范围的边界**：单站点、单公司、**单会计年度**、`periodicity=Monthly`、`report_type=Profit and Loss Statement`、损益两个科目（`销售 - HDS`／`销货成本 - HDS`）。**未验**：① 跨会计年度；② `Quarterly`／`Yearly`／`Half-Yearly` 下累计是否同样正确；③ 资产负债类科目的累计（本探针只测损益段，虽然 `_calculate_running_balances` 对两类科目是同一段代码）；④ 有期初分录（`is_opening='Yes'`）时的行为——注入的 8 条全是 `is_opening='No'`；⑤ 存在已提交 PCV 时的重定基准路径。

4. **拿不准处 / 我的选择**：
   - **用 `db_insert()` 写裸 GL 行，而不是提交 Journal Entry**。这是我选的，理由是引擎只读 `GL Entry` 表、裸行已足够，且 `db_insert()` 不跑任何 hook，侵入面最小。**代价**：这些行**没有对应的 Journal Entry 凭证**，即它们不是「一笔真实业务在真实提交路径上产生的 GL」。就本命题（引擎对 GL 表的逐期归集算术）而言这不影响结论，但**若要验的是凭证侧行为（如 PCV、重过账、对账），本方法不适用**。
   - **注入的金额与日期（10-15 / 11-20，200/80 与 500/30）是我随手取的**，只保证借贷自平、每月互不相同、落在 FY2026 内。金额本身无业务含义。
   - 现金科目（`现金 - HDS`）被我选作配平腿。它是资产类，故不进损益段，对本命题的两列取数无影响——但**这意味着站点的现金余额在事务内被改过**（已随 rollback 一并撤销）。
