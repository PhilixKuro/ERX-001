# V-22 探针回报：中文列名银行对账单导入 + 自动核销

**判定：`go`（有附加条件）**

(a) 与 (b) 都成立，且都是在**未改动任何 erpnext / frappe 源码**的前提下实测通过的。
但通过路径**不是**命题所设想的那一条：`Bank Transaction Mapping` 子表完全没有参与，
它填的中文 `file_field` 从头到尾没被读过一次。下面逐条给证据。

- 站点 `erx.localhost`，公司 `华东弹簧`（HDS），容器 `erx001-frappe-1`
- 探针日期 2026-09-26，全部通过 `bench` 环境内 python 直接执行
- 留档数据：`Spike/V22-out/seg0..seg17-*.json`

## 1. 结论（两半）

| 半 | 结果 | 依据 |
|---|---|---|
| (a) 中文列名 xlsx/csv 能否导入 `Bank Transaction` | **能** | seg10（xlsx）status=`Success`，2 行；seg11（utf-8 csv）status=`Success`，2 行 |
| (b) `auto_reconcile_vouchers()` 能否自动核销至少一笔 | **能** | seg10：`ACC-BTN-2026-00007` → `Reconciled`，`ACC-PAY-2026-00009` 拿到 `clearance_date=2026-09-28` |

**但必须同时满足两个条件，否则静默失败**（不是报错，是"报成功但什么都没干"）：

1. **文件本身必须带一列字面量表头 `Bank Account`**，且该列的值是真实的 Bank Account 名。
2. **列映射必须以"列序号"为键**（`"0"`, `"1"`, ...）写进 `template_options`，
   即 desk 的 Map Columns 弹窗那条路；`Bank` 上配的中文 `file_field` 无效。

## 2. 实测到的四个缺陷

### 缺陷 1：`Bank Transaction Mapping` 的键与读取端不匹配（致命）

- 写入端 `bank_statement_import.py:68-70`：
  `column_to_field_map[i.file_field] = i.bank_transaction_field` → **键是表头字符串**（中文）
- 读取端 `importer.py:879`：
  `map_to_field = column_to_field_map.get(str(j))` → **键是 0 基列序号**

seg3 做了同数据、同文件的对照实验，结论无歧义：

| 映射键形式 | 成功映射字段数 |
|---|---|
| A 按表头（出厂行为） | **0 / 7** |
| B 按列序号（假设） | **7 / 7** |
| C 完全不给映射 | 0 / 7 |

所以在 `Bank` 上认真填中文列名映射，**一行也不会生效**，且界面不报错。

### 缺陷 2：`Bank Account` 列的门禁在添加该列之前就检查

`bank_statement_import.py:84-85` 要求预览列里出现字面量 `Bank Account` 才放行，
但真正补这一列的 `add_bank_account()`（:327-341）在 `start_import` 里、门禁之后才跑。
seg2 实测抛出：

```
frappe.exceptions.ValidationError: Please add the Bank Account column
```

### 缺陷 3：把真实列挪去凑门禁会静默毒化导入

seg5 曾判断"映射一列到 `bank_account` 即可过门禁"——**这个判断在实践中是错的**，
seg9 推翻了它。把 `余额` 映射到 `bank_account` 后，Link 校验拿余额数字去对 Bank Account 名：

```
{'col': 5, 'message': 'The following values do not exist for Bank Account: 10694.18, 10689.18',
 'type': 'warning'}
```

`importer.py:85-92` 对任何 `type != "info"` 的告警直接 `return`——不抛异常、不写日志、
不建单，`status` 停在 `Pending`。这正是本项目写过的那类静默失败。

### 缺陷 4：每次导入都会污染 `Bank` 的映射表，且污染有粘性

`update_mapping_db()`（:315-324）先删光 `bank_transaction_mapping` 全部行，
再用 `template_options` 的键重建 `file_field`。seg5-F1 实测：

```
导入前：交易日期 / 摘要 / 贷方发生额 / 借方发生额 / 对方户名 / 交易流水号 / 币种
导入后：0 / 1 / 2 / 3 / 5 / 6 / 7          ← 中文映射被彻底冲掉
```

更麻烦的是**粘性**：下一次建单时 `validate()` 又从这张被污染的表重建 `template_options`，
把上一轮的陈旧 `"4": "bank_account"` 悄悄塞回来。seg9 就是这样失败的，seg10 必须先洗表才通过。

## 3. 走通的那条路（seg10 / seg11，未改源码）

```
文件：8 个中文表头 + 1 个字面量 Bank Account 列（值为真实 Bank Account 名）
      交易日期 摘要 借方发生额 贷方发生额 余额 对方户名 交易流水号 币种 | Bank Account
映射：以列序号为键的 8 条，余额 故意不映射（Bank Transaction 没有余额字段，
      映到任何 Link 字段都会触发缺陷 3）
      {"0":date,"1":description,"2":withdrawal,"3":deposit,
       "5":bank_party_name,"6":reference_number,"7":currency,"8":bank_account}
前提：先把 Bank 的映射表洗回干净（缺陷 4）
```

seg10 结果：

```
bsi_status = Success，template_warnings 空
ACC-BTN-2026-00007  2026-09-28  deposit 8888.00  description 货款收入   bank_party_name 江南机械
ACC-BTN-2026-00008  2026-09-28  withdrawal 5.00  description 手续费
Data Import Log：2 条 success=1，exception 均为 None
```

中文摘要、中文对方户名都正确落库，无乱码。

自动核销（`auto_reconcile_vouchers`，同进程直调）：

```
消息：1笔交易已对账
ACC-BTN-2026-00007  status=Reconciled  allocated 8888.0  unallocated 0.0
Bank Transaction Payments：ACC-BTN-2026-00007 → Payment Entry ACC-PAY-2026-00009  8888.0
ACC-PAY-2026-00009   clearance_date = 2026-09-28     ← (b) 的正面证据
```

**自动核销的硬前提**：`get_pe_matching_query:1381-1382` 在
`frappe.flags.auto_reconcile_vouchers is True` 时追加 `.where(pe.reference_no == transaction.reference_number)`。
即凭证的 `reference_no` 必须与流水的 `reference_number` **完全相等**才可能自动匹配——
金额、日期、往来单位全对也不行。6 笔里只核销 1 笔正是这个原因（另 5 笔没有对应凭证）。

## 5. 映射配置工时（用户关心的 0.5-1 人日估算依据）

- 字段数：**8 个**（date / description / withdrawal / deposit / bank_party_name /
  reference_number / currency / bank_account），`余额` 必须留空
- 脚本内配置耗时：**0.45 秒**（seg10 `mapping_setup_seconds`），人工在 desk 弹窗里点选
  8 个下拉，量级是**分钟，不是小时**
- 借贷方向需人工判断一次：站在存款人视角，`借方发生额`=出账=`withdrawal`，
  `贷方发生额`=入账=`deposit`（与银行自身账簿视角相反，这里容易配反且不会报错）

**真正的工时不在配映射，而在缺陷 1-4 的绕行**：每张对账单导入前要脚本预处理
（补 `Bank Account` 列、必要时转码 UTF-8），且 `Bank` 映射表要在每次导入后复位。
把这些做成一个稳定的前置脚本，才是这个 Stage 里实际要花的钱。

## 6. 路径说明（同步 vs 队列）

- 本容器**没有 queue worker**，只有 `bench serve`；`is_scheduler_inactive()` = `True`
- 但 `frappe.conf.developer_mode = 1`，`start_import` 的 `run_now = frappe.in_test or developer_mode` 为真，
  于是 `enqueue(..., now=True)` 走 `frappe.call()` **同进程执行**
- 所以我调的是**出厂 `start_import()` 本身**，不是手工拼的替代流程；只是它同步跑完了
- 生产环境 worker 常驻时走的是同一段代码，但异常会落到后台任务里，静默失败更难发现

## 9. 复核建议

**结论里最弱的部分**

- 只测了**一种银行版式**（8 列、招行/工行式常见列名），行数只有 2-6 行。
  真实招行/工行/建行导出常带多行表头、合计行、账号抬头块、合并单元格，这些一律未测。
- **只测单币种 CNY**。`Bank Transaction.validate_currency`（bank_transaction.py:63-80）
  要求流水币种与 Bank Account 科目币种一致，外币户（USD 账户收美元）未验。
- **只核销 Payment Entry 一种凭证**。Journal Entry / Sales Invoice 分支只读了代码
  （`get_je_matching_query` 同样在 auto 模式下强制 `cheque_no` 相等），未实跑。
- **未测 `Bank Transaction Rule`** 自动分类，也未测 `Bank Reconciliation Tool` 的界面。
- 自动核销的 6 笔里只有 1 笔有匹配凭证，**没有测过"多笔候选如何排序"**；
  4 因子 rank（:1287-1303）在只有一个候选时体现不出来。
- 演示库 `developer_mode=1` 掩盖了调度器问题。**生产若 worker 没起、developer_mode=0，
  `start_import` 会直接抛 `Scheduler is inactive`**（:91-92），这一分支我没在真实
  worker 环境验证过。

**不确定的地方**

- 缺陷 1 我判定为上游 bug（键形式不一致），但没去查 frappe/erpnext issue 确认是否已知、
  是否有补丁分支。下判断前值得查一下版本演进。
- GBK 那条我确认了乱码落库，但**没有验证 `use_csv_sniffer` 开关是否能救**——
  `Bank Statement Import` 有这个字段，我没试。这可能把 GBK 问题降级。
- seg5 的 F2 结论（"映射即可过门禁"）被 seg9 推翻，seg12 里我又误判过一次
  GBK 行的 `bank_account` 为空（实际是正确填上的，`add_bank_account` 会覆盖该列）。
  这两处以 seg9 / seg12 的实测数据为准，**留档里我已改正，但 json 原文仍保留了错误表述**。

**清理残留**

- **无残留。** 10 个 DocType 计数全部与基线逐一相等（见第 7 节），演示数据的
  `clearance_date` 仍为 None，`Error Log` 未新增。
- 站点上唯一的不可逆动作是：删掉了基线本不存在的 `ACC-BTN-2026-` 序列行
  （删前已断言 Bank Transaction 计数为 0），以及删掉 12 条父凭证已不存在的孤儿
  GL Entry（删前逐行断言 `frappe.db.exists(voucher_type, voucher_no)` 为假）。
- 主机侧留下 `Spike/V22-*` 探针与样本文件，以及 `Spike/V22-out/*.json`，供复核。
