## (a) 钩子机制

### 结论（全部来自运行输出，非读码）

注入三个方法 `erpnext.v33_fake_{one,two,three}`，一次调用后：

```json
{"execution_order": ["one", "two", "three"], "ran_count": 3,
 "all_three_ran": true, "only_last_ran": false,
 "gl_dict_after": {"company": "SENTINEL", "debit": 0,
                   "v33_one": 1, "v33_two": 2, "v33_three": 3}}
```

三个都跑了，按注册顺序跑，三个键都落进了 gl_dict。**不取 `[-1]`，实测坐实。**

分发体本身（`accounts_controller.py:4481-4483`）：

```python
def update_gl_dict_with_app_based_fields(doc, gl_dict):
	for method in frappe.get_hooks("update_gl_dict_with_app_based_fields", default=[]):
		frappe.get_attr(method)(doc, gl_dict)
```

### 无地区门禁

同一组注册，把 `frappe.flags.country` 依次设成 China / United Arab Emirates / India / France，四次结果**完全一致**（`identical_across_regions: true`），三个方法每次都跑。没有任何国家过滤。

### 不占让位槽——并且给了阴性对照

| 观察 | app-based 钩子 | 隔壁的 regional 孪生函数 |
|---|---|---|
| 被 `allow_regional` 包装（有 `__wrapped__`） | `false` | `true` |
| 出现在 `regional_overrides` 的槽位名里 | `false` | 是（`validate_regional` 等） |

**阴性对照（让本次否定结论可信的关键）**：往 regional 孪生函数 `update_gl_dict_with_regional_fields` 的槽里注册**两个**实现，实测：

```json
{"registered": ["erpnext.v33_reg_one.impl", "erpnext.v33_reg_two.impl"],
 "execution_order": ["reg-two"], "ran_count": 1, "only_last_ran": true}
```

只跑最后一个。两套机制在同一次运行里表现相反 —— 说明仪器分得清「遍历全部」和「只取最后一个」这两种情况，(a) 的肯定结论不是仪器瞎了。

机制出处：`erpnext/__init__.py:145-152`，`overrides[function_path][-1]`，注释原文就写着 `# Priority given to last installed app`。

### 内部使用者：一个都没有 ⚠

- 站点实际注册数：`frappe.get_hooks("update_gl_dict_with_app_based_fields")` → `[]`（空）
- 全 bench 深度 grep（含 node_modules，跑满 120s）该钩子名**只有 3 处命中**：调用点 `:1447`、定义 `:4481`、`get_hooks` 那行 `:4482`
- `frappe/hooks.py` 与 `erpnext/hooks.py` 里各 0 处注册

**这条修正了前次调查的提问前提。** 前次问「内部使用者是谁」，答案是：没有。这个钩子上游无人使用、无既有先例、无回归测试覆盖它的多 app 叠加行为。它干净，是因为它没被用过。

### 顺带两个实现期会踩的事实

1. **`get_attr` 有 app 名门禁**（`frappe/__init__.py:1130-1133`）：方法串第一段必须是已装 app，否则抛 `AppNotInstalledError`。本探针第一版用 `v33_fake_app_one.gl` 就是这么挂的，改挂到 `erpnext.*` 命名空间才通。含义：中国本地化必须是**真正装上的 app**，不能靠野命名空间注册。
2. **该钩子在 `temporary_flag("company")` 块之外**。`:1444-1445` 把 regional 孪生函数包在 `with temporary_flag("company", self.company)` 里，而 `:1447` 的 app-based 调用在块**外**。钩子内实测 `frappe.local.flags.company` 为 `null`，`erpnext.get_region()` 回退到 System Settings 拿到 `China`。含义：app-based 钩子里**不能靠 `get_region()` 判断当前单据的国别**，要判得用传进来的 `doc.company` 自己查。

## (b) ⭐ gl_dict 同键覆盖关系

### 先立阳性对照，再谈否定

`remarks` 在基础字面量里设于 `:1425`，早于钩子 `:1447`，且不在 `args` 里。钩子改它：

```json
{"key": "remarks", "core_value_before_hook": "V33 core remark",
 "value_after": "V33 OVERWRITTEN BY HOOK", "overwrite_succeeded": true}
```

**覆盖成功。** 仪器能看见覆盖发生，所以下面「某些键覆盖不了」不是瞎了。

### 两个方法写同一个键：后写覆盖，静默

| 注册顺序 | 最终值 | 第二个方法进来时看到的值 |
|---|---|---|
| c1 → c2 | `FROM_C2` | — |
| c2 → c1 | `FROM_C1` | `FROM_C2` |

- 无异常（`raised: false`），无合并，无告警
- 两个方法各自的独占键都保住了（`both_keys_present: true`）
- 反转顺序结果就反转 → **后写者赢，纯 `dict` 赋值语义**
- 第二个方法进来时**看得见**第一个写的值（`second_saw_first_value: "FROM_C2"`）→ 是同一个 dict 被顺序改写，不是各写各的副本再合

### 顺序规则，以及怎么定的

规则：**钩子列表顺序 == `get_installed_apps()` 顺序**，即 app 安装顺序。

- 机制：`_load_app_hooks`（`frappe/__init__.py:962-985`）按 `get_installed_apps()` 顺序遍历 app，逐个 `append_hook`；`append_hook`（`:1017-1035`）用 `target[key].extend(value)` 往后接。先装的 app 排前面，**后装的 app 最后写，因此赢**。
- 实证（不只读码）：扫出 7 个 frappe 与 erpnext 都注册了的钩子，`frappe` 全部排在 `erpnext` 之前，与 `get_installed_apps() == ["frappe", "erpnext"]` 一致。例：`after_install → ["frappe.utils.install.after_install", "erpnext.setup.install.after_install"]`。

与 `regional_overrides` 的 `[-1]` 语义方向一致（都是后装的 app 优先），但后果不同：这里是**都跑、后写覆盖**，那里是**只跑最后一个**。

### 能覆盖核心键吗：分情况，界线是调用点位置

| gl_dict 键 | 钩子写入是否存活 | 原因 |
|---|---|---|
| `remarks` | ✅ 存活 | 字面量段 `:1425`，在钩子之前 |
| `fiscal_year` | ✅ 存活 | 同上 |
| `voucher_subtype` | ✅ 存活 | 同上 |
| `is_opening` | ✅ 存活 | 同上 |
| `project` | ✅ 存活 | 同上 |
| `account` | ❌ 被冲掉 | 走 `args`，`gl_dict.update(args)` 在 `:1461`，**晚于**钩子 |
| `cost_center` | ❌ 被冲掉 | 同上 |
| `debit` | ❌ 被冲掉 | 同上 |
| `debit_in_account_currency` | ❌ 被冲掉 | `set_balance_in_account_currency` 在 `:1485` 之后重算 |

钩子进来时看到的 `account` 是 `null`、`debit` 是 `0` —— 因为 `args` 还没合进来。**所以：钩子改不了科目和金额，能改的是基础字面量里那批元数据字段。**

### 新键、异常、持久化

- 任意新键都能塞进 dict（`v33_custom_vat_side`、`v33_unknown_col` 都在）
- 但 `GL Entry` 只有 47 个字段、当前**零个自定义字段** → 想落库必须先建真的 Custom Field
- **分发体没有 try/except**：一个钩子抛 `ValueError`，异常直接穿出去，它后面的钩子不跑（`later_hook_skipped: true`），整个 GL 组装挂掉。一个坏 app 能弄停全站记账。

### UAE 确实用该机制追加分录 —— 但实现体对中国站点无效

读码（标注：CODE READING）—— `erpnext/regional/united_arab_emirates/utils.py:162-183`，`make_gl_entry` 里确实是：

```python
gl_entries.append(
    doc.get_gl_dict({...}, account_currency, item=tax)
```

`appends_via_list_append: true`、`builds_entry_with_get_gl_dict: true`、`returns_the_list: true`。调用方 `purchase_invoice.py:959` 写的是 `gl_entries = make_regional_gl_entries(gl_entries, self)`，接回返回值。链路 `hooks.py:613` → `regional/united_arab_emirates/utils.py:146-159` 坐实。

**修正一处**（运行所得，非读码）：UAE 实现体是**双重设卡**的。除了 `hooks.py:613` 把它挂在 `"United Arab Emirates"` 这个国家键下，`utils.py:148-151` 自己又查一遍 `Company.country`，不是 UAE 就原样返回。拿 `华东弹簧` 跑它：

```json
{"input_len": 1, "output_len": 1, "returned_unchanged": true}
```

**原样返回，什么都没追加。** 所以 UAE 那段代码不可直接复用，可复用的是**机制**。

### 机制对中国可用 —— 实测跑通

把一个中国实现挂进真的 `purchase_invoice.make_regional_gl_entries` 槽，经真的 `allow_regional` 分发：

```json
{"impl_ran": true, "input_len": 1, "output_len": 3,
 "core_entry_preserved": true,

              {"account": "V33-INPUT-VAT",  "debit": 13,  "v33_vat_side": "INPUT"}]}
```

进项/销项两条分录追加成功，核心原有分录保住。**追加 GL 分录这条路，对中国是通的。**

### 但它是 L4，不是 L3：槽位独占，实测

两个 app 抢同一个槽：

```json
{"registered": ["erpnext.v33_cn.impl", "erpnext.v33_cn2.impl"],
 "who_ran": ["other-app"], "only_last_ran": true,
 "first_app_silently_dropped": true, "resulting_accounts": ["OTHER-APP"]}
```

第一个 app **被静默丢掉**，没有报错、没有告警。出处 `erpnext/__init__.py:152`。这就是 L4 的代价，实测确认，不是推测。

一个缓和事实：`regional_overrides` 全表**只有 6 条、覆盖 4 个国家**（France / Italy / Saudi Arabia / UAE），**没有 China 键**。所以 18 是「可占的槽位」而非「已占的注册」；今天占中国的槽，跟现存任何 app 都不冲突。独占风险只对**将来第二个中国 app** 成立。

### ⚠ LG-132 没提、但直接决定 CR-006 做法的一件事：`merge_similar_entries`

`erpnext/accounts/general_ledger.py:331-348` 的合并键是固定 12 项 + 会计维度：

```
account, cost_center, party, party_type, voucher_detail_no, against_voucher,
against_voucher_type, project, finance_book, voucher_no,
advance_voucher_type, advance_voucher_no
```

**不含任何自定义字段**（`includes_custom_vat_key: false`）。实测：同一科目、同维度、仅自定义标记不同的两条分录 ——

```json
{"input_count": 2, "output_count": 1, "collapsed": true,
 "surviving": [{"account": "VAT - HDS", "debit": 130.0, "v33_vat_side": "INPUT"}]}
```

**被静默合并**：100 + 30 = 130 一条，`OUTPUT` 那条的标记随行一起消失。

阳性对照（保证这不是仪器把什么都合掉）：把第二条换成另一个科目 `重估盈余 - HDS` → `output_count: 2`，**不合**。按**科目**分是站得住的。

逃生口：`_skip_merge=1` 时两条都留（`output_count: 2`，出处 `general_ledger.py:281-283`）。

时序：采购发票 `:959` 先调 regional 追加，`:961` 才 `merge_similar_entries` —— **合并在追加之后**，所以追加出来的分录逃不过这一刀。

含义（事实陈述，不含方案取舍）：进项销项若靠「同科目 + 自定义标记」区分，会被核心合并抹掉；靠**不同科目**区分则天然分得开。

## LG-132 逐条：坐实了哪些、推翻了哪些

### 坐实（CONFIRMED）

1. `update_gl_dict_with_app_based_fields` 遍历**全部**注册方法，不取 `[-1]` —— 运行坐实
2. 无国家/地区隔离 —— 四国对比运行坐实
3. 不占用 `regional_overrides` 让位槽 —— 带阴性对照坐实
4. 18 个让位点中**正好 5 个**在 GL 组装期 —— AST 计数坐实
5. UAE 反向征税确实经 `hooks.py:613` → `utils.py:146-159` 用 `gl_entries.append` 追加分录 —— 读码 + 机制运行坐实
6. `@allow_regional` 生产计数为 **18**（不是 20）—— 自查坐实，且查清了 20 的来源

### 推翻或需要修正（OVERTURNED / CORRECTED）

1. **「内部使用者」问题的前提错了**：该钩子上游**零注册**。全 bench 仅 3 处命中，全是自身定义与调用。它不是「已被多方稳定使用的扩展点」，而是一个**从未被用过**的扩展点 —— 干净是因为空置。多 app 叠加行为无上游先例、无回归测试兜底。
2. **「UAE 这一模式对中国现成可用」不成立**：UAE 实现体自己二次校验 `Company.country`，拿中国公司跑它原样返回。可迁移的是机制，不是代码。
3. **「存在加法式 L3 的增值税路径」只能分层成立**：
   - **字段级**（往既有 gl_dict 加/改字段）：`update_gl_dict_with_app_based_fields` 确为 L3，不占槽、可共存。
   - **分录级**（新增 GL 分录行）：该钩子**做不到** —— 它一次只拿到一个 gl_dict，签名里没有分录列表，无处 append。新增分录只能走 GL 组装期那 5 个让位点，而它们**独占、`[-1]`、抢槽者静默失败**，即 L4。
   - 所以「CR-006 可以纯加法实现」按分录级理解**不成立**。
4. **漏了 `merge_similar_entries` 这一关**：自定义标记不是合并键，同科目分录会被静默并掉。这一条 LG-132 完全没提，却直接约束进项销项分离的落地形态。
5. **`regional_overrides` 的 6 与 18 不是一回事**：全表仅 6 条注册、4 个国家、无 China。18 是可占槽位数。把两者混谈会高估「已被占用」的程度。

- **不能证明**：真实多 app 场景下**列表内容本身**如何生成 —— 即 `_load_app_hooks` 遍历真实多 app 时的实际顺序、`client_cache` 缓存失效时机、`bench install-app` 之后顺序是否如预期。顺序规则我是靠**读 `_load_app_hooks`/`append_hook` 源码 + 用现有 frappe/erpnext 两 app 的 7 个共注册钩子实证**推出来的，**没有真装第三个 app 验证**。本站只有 2 个 app，三 app 及以上的顺序未实测。

## 复核建议

### 没有验证的

1. **三个及以上真实 app 的钩子顺序**。顺序规则来自源码 + 两 app 实证，未真装第三个 app 检验。若将来中国本地化与另一个第三方会计 app 共存，建议真装后复测 `get_hooks` 列表顺序。
2. **完整的提交-过账全链路**。为站点安全只做到 `get_gl_dict()` / `make_regional_gl_entries()` 层面，**没有真 submit 过任何单据**，因此没观察到分录真正写入 `tabGL Entry` 的结果。自定义键在 `GL Entry.insert()` 时是被忽略还是报错 —— **未实测**（只确认了 schema 里没有对应字段）。这一步需要可抛弃的测试站点。
3. **`update_gl_dict_with_app_based_fields` 在 v16 的稳定性**。它上游零使用，没有回归测试覆盖多 app 叠加。零使用的钩子被上游改签名或删掉的风险，我无法评估。
4. **`Payment Entry` 的 `add_regional_gl_entries` 语义差异**。它的桩是 `return`（返回 None）而非 `return gl_entries`，调用点 `payment_entry.py:1327` 也不接返回值 —— 即靠**原地改列表**生效。我只读了码，**没跑**。这与另外两个 `make_regional_gl_entries` 的契约不同，实现时容易写错。
5. **会计维度对合并键的影响**。`get_merge_properties(dimensions)` 会把会计维度接进合并键，我是用 `None` 调的。若本站启用了会计维度，合并行为可能与本次观察不同 —— 未测。
6. **`_skip_merge` 的下游后果**。只验证了它能保住两条同科目分录不被合并，**没有验证**打了这个标记的分录在试算平衡、结账、报表侧是否被正常对待。

### 心里没底的

- `merge_similar_entries` 那条是本次最要紧的意外发现，但我只在**单元层面**喂了手造 dict 给它。真实链路里分录还带 `voucher_detail_no` 等字段，合并键更细，实际是否照样并掉，值得在真链路上再验一次。
- (a) 那些「干净」的结论我有阴性对照撑着，比较放心。但**「内部使用者为零」这个判断依赖 grep 的完备性** —— 我扫了全 bench 含 node_modules 只有 3 处命中，另外单独扫了两个 `hooks.py`。如果存在动态构造钩子名的写法（拼字符串注册），grep 看不见。我没有专门找这种写法。
- 站点只有 `frappe` + `erpnext`，**没有任何第三方 app 在场**。真实部署里第三方 app 可能已经占了某些让位槽，本次的「China 键为空、无人竞争」结论只对当前这个装配成立。
