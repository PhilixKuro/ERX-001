## 第 3 批：断言 C 的核心机制（已核实，关键发现）

### 3.1 中国科目表为什么在下拉框里选不到

文件：`erpnext/accounts/doctype/account/chart_of_accounts/chart_of_accounts.py`

`get_charts_for_country()`（第 135-167 行）的扫描逻辑：

```python
country_code = frappe.get_cached_value("Country", country, "code")   # 第146行
if country_code:
    folders = ("verified",)                                          # 第148行
    if frappe.local.flags.allow_unverified_charts:                   # 第149行
        folders = ("verified", "unverified")                         # 第150行
```

**默认只扫 `verified/`。要扫到 `unverified/`，必须 `frappe.local.flags.allow_unverified_charts` 为真。**

### 3.2 决定性发现：那个开关**全仓没有任何地方去打开它**

在 `erpnext` 与 `frappe` 两个 app 全文（含 .py/.js/.json/.md/.txt/.cfg）搜 `allow_unverified_charts`，命中仅 5 处，全在 2 个文件里，**全部是「读」，没有一处是「写/赋值」**：

- `erpnext/accounts/doctype/account/account.py:108` —— 读
- `chart_of_accounts.py:58` —— 读
- `chart_of_accounts.py:121` —— 读
- `chart_of_accounts.py:143` —— 读
- `chart_of_accounts.py:149` —— 读

搜赋值式 `allow_unverified_charts\s*=` → **零命中**。

**结论：`unverified/` 目录下 24 份科目表（含中国那份）在原生 ERPNext 里是一段死代码（dead path）—— 没有 UI、没有配置项、没有 bench 命令去打开这个开关。中国科目表被放进仓库了，但没有任何官方途径能用上它。**

> 白话：ERPNext 代码里有一道门，门后放着中国的会计科目表。但整套软件里**没有任何一把钥匙**——没有设置项、没有按钮、没有命令能打开这道门。中国科目表在仓库里躺着，实际上用不了。要用，只能自己写程序硬把这个开关拨开（这正是本项目在做的事，也正是「炸」的来源之一）。

### 3.3 中国那份科目表的实际质量（已核实）

文件：`unverified/cn_l10n_chart_china.json`（8218 字节）

- `country_code`: `"cn"`
- `name`: `"China - 中国会计科目表  （财会[2006]3号《企业会计准则》)"` —— 依据是 **2006 年**的文件
- `root_type` 出现 82 次，**82 次全部是空字符串 `""`**
- 全部 82 个节点**平铺**在 `tree` 下，无任何层级嵌套
- 无 `disabled` 字段（故若门被打开，它能通过 `disabled` 那道检查，第143行）

**用户给的「已知」第二条（82 个节点全部平铺、root_type 全为空）—— 核实为真。**

> 白话：这份中国科目表是 2006 年标准，而且做得很糙：82 个科目像一份没分类的清单全摊在一起（正常应该是「资产 → 流动资产 → 银行存款」这样的树状层次），而且每个科目都**没标明自己属于资产、负债、收入还是费用**。而这个标记是财务报表取数的唯一依据——没有它，资产负债表和利润表拿不到任何数。

| `china` / `chinese` / `prc.gaap`（py 文件） | 仅 1 处，且在 `frappe/frappe/tests/test_search.py:884` —— 是单元测试里的假数据 `["USA","India","Russia","China"]`，与功能无关 |

### 4.2 三条否定判据（按规范要求逐条满足）

1. **多个同义关键词都 grep 过** —— 见上表，中英文共 8 组关键词。
2. **看过目录清单，不只 grep** ——
   - `erpnext/regional/` 实有目录：`australia`、`italy`、`south_africa`、`turkey`、`united_arab_emirates`、`united_states`。**无 `china`**。
   - `erpnext/accounts/doctype/` 全量清单（约 190 个 DocType）已列，其中与地区税务相关的只有 `south_africa_vat_account` 一个，**无任何中国/发票/税控相关 DocType**。
3. **为什么不可能在别的模块** —— 地区功能的唯一装载入口是 `company.py:858 install_country_fixtures()`：
   ```python
   module_name = f"erpnext.regional.{frappe.scrub(country)}.setup.setup"
   frappe.get_attr(module_name)(company, False)
   except ImportError: pass
   ```
   它按国家名拼出 `erpnext.regional.<国家>.setup.setup` 这个路径去导入。中国对应的路径是 `erpnext.regional.china.setup.setup`，该目录不存在 ⇒ 抛 `ImportError` ⇒ **被 `pass` 静默吞掉**。也就是说：建中国公司时，这一步什么都不做，而且**不报错、不提示**。

**断言 A 判定：不成立。**

> 白话：「金税」是中国开增值税发票必须走的国家系统。ERPNext 里**一行相关代码都没有**——不是做得不好，是完全没有。而且软件的设计是：你把公司国家选成「中国」，它去找「中国专用设置」这个文件夹，找不到就**默默跳过，连一句提示都不给**，你会以为一切正常。
>
> 对比之下，意大利的电子发票是真有代码的（`regional/italy/`），所以这不是「ERPNext 不做这类事」，而是「唯独没做中国」。

## 第 5 批：断言 C 的报表部分 —— v16 有重大变化（已核实，需修正预设）

### 5.1 v16 新增了「财务报表模板」引擎

这是**本次调查最重要的意外发现**，与「中国格式报表原生没有」的直觉预设**部分冲突**，须如实记下。

- 新 DocType：`accounts/doctype/financial_report_template/`（含 `financial_report_engine.py`、`financial_report_validation.py`）
- 新子表：`accounts/doctype/financial_report_row/`
- 新 DocType：`accounts/doctype/account_category/`
- `balance_sheet.py:31-33`、`cash_flow.py:32-33` 都已改成：
  ```python
  if filters and filters.report_template:
      return FinancialReportEngine().execute(filters)
  ```
  即报表可以**完全由模板驱动**，不再只走硬编码逻辑。

### 5.2 原生已随附 6 个模板

路径 `erpnext/accounts/financial_report_template/`：

| 模板 | 类型 |
|---|---|
| `Standard Balance Sheet (IFRS)` | 资产负债表（国际准则，竖排） |
| `Standard Profit and Loss (IFRS)` | 利润表 |
| `Standard Cash Flow Statement (IFRS)` | 现金流量表 |
| **`Horizontal Balance Sheet (Columnar)`** | **左右双栏资产负债表** |
| `Horizontal Profit and Loss (Columnar)` | 横排利润表 |
| `Financial Ratios Analysis` | 财务比率 |

**`Horizontal Balance Sheet (Columnar)` 的结构已实读**（26923 字节，64 行）：含 `data_source: "Column Break"`、右栏标题 `"Equity & Liabilities"` —— **这确实是中国式「左资产／右负债及所有者权益」的双栏排版**。

> 白话：中国的资产负债表是左右两栏（左边资产，右边负债和股东权益），而国际通行的是从上到下一竖排。原先以为 ERPNext 只能做竖排。**实测发现 v16 已经自带了「左右双栏」这个模板**，排版形式上是够的。
>
> 但**排版对 ≠ 科目对**：模板里的行项目名称还是 `Share Capital`、`Reserves & Surplus` 这些国际口径，不是中国财政部规定的行次和项目名（如「货币资金」「应收票据及应收账款」「合同负债」）。

### 5.3 模板引擎怎么取数 —— 这是真正的卡点

`financial_report_row` 的 `data_source` 可选值：`Account Data` / `Calculated Amount` / `Custom API` / `Blank Line` / `Column Break` / `Section Break`。

取数靠 `calculation_formula`，实例（横排资产负债表首几行）：

```
["account_category", "=", "Share Capital"]
{"and":[["account_category","=","Reserves and Surplus"],["account_name","not like","%Retained Earnings%"]]}
```

**⇒ 模板取数主要依赖 `account_category`（科目类别）这个字段。**

而 `Account Category` 原生只随附 **29 个类别**（`accounts/financial_report_template/account_categories.json`），全是 IFRS 口径：`Cash and Cash Equivalents`、`Cost of Goods Sold`、`Long-term Borrowings`…… **没有一个是中国特有的**（如「应交税费」下的进项/销项细分）。

且 `Account` DocType 确有 `account_category` 字段（`account.json` 字段清单末位），但**中国那份科目表 JSON 里 82 个节点一个都没写 `account_category`**（该文件仅有 `root_type` 键，全为空）。

**⇒ 即便把中国科目表建起来，模板引擎也取不到数：它按 `account_category` 找科目，而中国科目表的科目身上这个标签是空的。**

> 白话：v16 这套新报表模板像一个「填空表格」：表格上写着「这一行去把所有贴着『现金及现金等价物』标签的科目加起来」。中国那份科目表的 82 个科目**一个标签都没贴**。所以模板再好，也全是空行。要能出数，得先给每个中国科目贴上标签，还得先定义一批中国特有的标签——这些都得自己做。

### 5.4 好消息：有官方扩展口

`financial_report_template.py:131-153` 的 `sync_financial_report_templates()`：

- 遍历**所有已安装 app**（`frappe.get_installed_apps()`），扫每个 app 下 `<module>/financial_report_template/` 目录，自动导入其中的模板 JSON（`_sync_templates_for`，第156-196行）
- 还支持在科目表 JSON 里写 `disable_default_financial_report_template: true`，**让地区模板完全顶掉 ERPNext 自带模板**（第141-151行）
- 同时会 `import_account_categories(template_path)`（第168行）—— 即**自定义 app 可以自带自己的科目类别**

已核实：现有任何科目表 JSON 都**没有**声明 `disable_default_financial_report_template`（grep 零命中），即这个能力目前无人使用，是留给下游的。

> 白话：这是这次调查里对本项目**最有利**的发现。v16 官方留了一个正规接口：你自己做一个「中国财税」插件，把中国格式的报表模板和中国特有的科目标签放进去，系统装上就会自动认。不用去改 ERPNext 自己的代码——这意味着以后 ERPNext 升级，你的东西不会被冲掉。这比「改源码」的路子稳得多。

## 第 6 批：断言 B（增值税）（已核实）

### 6.1 能表达的（用户「已知」第①条 —— 核实为真）

`Sales Taxes and Charges` 子表字段（已实读 `sales_taxes_and_charges.json`）：

- `charge_type` 可选值：`Actual` / `On Net Total` / `On Previous Row Amount` / `On Previous Row Total` / `On Item Quantity`
- **`included_in_print_rate`（Check）** —— 这就是**价税分离**的开关：标价含税，系统反算出不含税金额与税额
- `account_head`（Link → Account）—— 税额进哪个科目，可指定
- `Item Tax Template` + `Item Tax Template Detail`（`tax_type` → Account，`tax_rate` → Float）—— **按物料指定不同税率**，即**多档税率**（13%/9%/6%/3%）的表达方式

**⇒ 价税分离、多档税率：原生能表达。核实为真。**

> 白话：开票时「标价 113 元，其中货款 100、税 13」这种拆分，以及不同商品适用不同税率（13%、9%、6%），ERPNext 原生就能做。这部分官网说得不算错。

### 6.2 不能表达的：月末结转（用户「已知」第②条 —— 核实为真，且找到结构性原因）

`Period Closing Voucher`（期末结账凭证）实读源码：

`period_closing_voucher.py:318`：

    pl_account_balances = self.get_account_balances_based_on_dimensions(report_type="Profit and Loss")

`period_closing_voucher.py:132-137`：

    closing_account_type = frappe.get_cached_value("Account", self.closing_account_head, "root_type")
    if closing_account_type not in ["Liability", "Equity"]:
        frappe.throw(_("Closing Account {0} must be of type Liability / Equity"))

且 `validate_start_and_end_date()`（第62行起）强制 `period_end_date` 不得超过 `fiscal_year` 的 `year_end_date`，`fiscal_year` 为必填 Link。

**⇒ PCV 做的是：把「利润表类」科目（收入、费用）余额清零，转入一个权益/负债类的「本年利润」科目。这是会计上的「损益结转」。**

**⇒ 而增值税科目（应交税费—应交增值税—进项税额/销项税额）的 `report_type` 是 `Balance Sheet`（负债类），PCV 的取数条件 `report_type="Profit and Loss"` 从结构上就取不到它们。**

**断言 B 判定：部分成立。**

- 成立部分：价税分离、多档税率、税额入指定科目
- 不成立部分：**增值税月末结转（进项税额转出、转出未交增值税、未交增值税三步）原生无任何功能**。

按三条否定判据核实：

1. 关键词 `input_tax` / `output_tax` / `input vat` / `output vat` / `month.end clos` / `monthly clos` / `vat.clos` / `tax.transfer` 全扫，在 erpnext 核心代码中零命中（仅泰国 `th_chart.json`、奥地利 `at_austria_chart_template.json` 的**科目表 JSON** 里出现 `Input VAT` / `Output VAT` 字样 —— 那只是科目名称，不是功能）
2. `accounts/doctype/` 约 190 个 DocType 清单已看全，唯一地区性增值税 DocType 是 `south_africa_vat_account`；`regional/report/` 清单为 `electronic_invoice_register`、`irs_1099`、`uae_vat_201`、`vat_audit_report` —— 分别属意大利、美国、阿联酋，**无中国**
3. 不可能在别处：地区功能唯一入口是 `install_country_fixtures()`，中国无对应目录

**⇒ 月末结转只能靠手工 Journal Entry 或自写逻辑。核实为真。**

> 白话：`Period Closing Voucher`（期末结账）名字听着像「月末结转」，但它干的是**完全不同的另一件事**——年末把收入和费用清零、结出利润。中国增值税的月末结转是每月都要做的一套三步转账（进项税额转出 → 转出未交增值税 → 未交增值税），动的是负债类科目。这个功能从取数条件上就**只看收入费用类科目，根本看不到增值税科目**。两件事名字像，实际毫不相干，靠它做不了月结。

### 6.3 专票与普票区别

原生**无「发票种类」概念**（专用发票/普通发票）。`Sales Invoice` 无此字段（已看全 `regional/` 目录与 `accounts/doctype/` 清单）。专票关系到购买方能否抵扣进项税，是中国增值税的核心区分 —— 原生完全不表达。

## 第 7 批：为什么这件事难（针对用户两个疑问）（已核实）

### 7.1 科目表是不是「一张简单表格」？—— 不是，它是一棵带冗余索引的树

`account.json` 已实读：

- **`"is_tree": 1`（第204行）**、**`"nsm_parent_field": "parent_account"`（第210行）** —— Account 是树形 DocType
- 字段含 **`lft` / `rgt`（Int）** —— 即 **nested set model（嵌套集合模型）**：树结构不只存在「父指针」里，还**冗余地编码成每个节点的一对数字区间**，子节点 `[lft, rgt]` 必须严格落在父节点区间内
- `parent_account` 是 **`reqd: 1`（必填）**
- 四个分类字段，各管不同的事：

| 字段 | 可选值 | 管什么 |
|---|---|---|
| `root_type` | `Asset`/`Liability`/`Income`/`Expense`/`Equity` | 会计大类。**报表取数的总开关** |
| `report_type` | `Balance Sheet`/`Profit and Loss` | 进资产负债表还是利润表。**也是 PCV 结转的筛选条件** |
| `account_type` | 32 个值（`Bank`/`Cash`/`Receivable`/`Payable`/`Stock`/`Tax`/`Cost of Goods Sold`…） | **业务行为**：哪些科目能被选作「收款账户」「库存科目」「默认应收」等 |
| `account_category` | Link → Account Category（29 个） | **v16 新报表模板引擎的取数依据** |

**一个科目建错会连带影响什么（已核实的连带链）：**

1. **`root_type` 错 → 报表取数全错**。`balance_sheet.py:51` 起按 `get_data(company, "Asset", "Debit", ...)` 取数，`root_type` 是筛选键。空值（如中国那份科目表的 82 个空 `root_type`）⇒ 报表这一块直接是空的。
2. **`root_type` 改一个组科目 → 一条裸 SQL 批量改掉所有后代**。`account.py:175-187`：

        if cint(self.is_group):
            db_value = self.get_doc_before_save()
            if db_value:
                if self.root_type != db_value.root_type:
                    frappe.db.sql(
                        "update `tabAccount` set root_type=%s where lft > %s and rgt < %s",
                        (self.root_type, self.lft, self.rgt))

   注意它用 `lft`/`rgt` 区间定位后代 —— **若 `lft`/`rgt` 因批量插入而尚未重建，这条 SQL 会改错一批科目，且不经任何校验、不留痕迹。**
3. **`account_type` 错 → 业务单据报错或走错账**。`validate_receivable_payable_account_type()`、`validate_stock_account_type_change()` 都在 `validate()` 里。
4. **`parent_account` 指向错 → 树断裂**，`rebuild_tree` 时该分支整体挂到错误位置。

> 白话：科目表**不是一张 Excel 表格，是一棵家谱树**，而且这棵树的结构被存了两遍：一遍是「我爸是谁」，另一遍是给每个科目编一对数字（像图书馆书架编号），保证「儿子的编号区间必须在爸爸的区间里面」。两遍必须严丝合缝对上，对不上系统就开始算错数。
>
> 更麻烦的是每个科目身上有**四个**分类标签，各管一件事：一个决定它进哪张报表、一个决定它算资产还是负债、一个决定它能不能被当成「银行账户」来收钱、还有一个是新版报表引擎认的标签。**填错任何一个，症状都不是「这一个科目不对」，而是「整张报表的数不对」或者「录单据时莫名报错」。**
>
> 还有个真正危险的地方：你改一个上级科目的分类，系统会用一条**直接改数据库的命令**把它下面所有科目一起改掉，不做任何检查。如果此时那对「书架编号」还没算好，它就会**改错一批科目，而且不报错、不留记录**。

### 7.2 UI 一个个建 vs 程序批量建，差别在哪？

**这是本次调查能从源码直接印证用户那个「炸」的地方。**

**差别一：flag（开关）的生命周期**

`frappe/frappe/app.py:139` → `init_request()` → `frappe.init(site, force=True, is_request=True)`（第217行），而 `frappe/__init__.py:169` 的 `init()` 里 **`local.flags = _dict({...})` 是整体重建的**。

⇒ **UI 上每点一次「保存」都是一个独立 HTTP 请求，`frappe.local.flags` 从头新建。上一次留下的脏开关自动消失。**

⇒ **批量脚本在同一个进程、同一个 `frappe.local` 里跑完全程，开关一旦被置上就一直在，直到进程结束。**

**差别二：已核实的两个「有设无复位」的开关**

| 开关 | 设置处 | 复位处 |
|---|---|---|
| `frappe.local.flags.ignore_root_company_validation` | `company.py:422`（`create_default_accounts` 开头）、`chart_of_accounts_importer.py:104` | **erpnext 生产代码中零处复位**。仅 `test_account.py` 有 4 处 `frappe.local.flags.pop(...)`（第131/160/202/248行）—— 即**官方自己的测试代码知道必须手工清，生产代码不清** |
| `frappe.local.flags.allow_unverified_charts` | **全仓零处设置** | 不适用 |

`company.py:422-423`：

    frappe.local.flags.ignore_root_company_validation = True
    create_charts(self.name, self.chart_of_accounts, self.existing_company)

设了就走，**函数返回后不复位**。

**差别三：`ignore_chart_of_accounts` —— 与用户描述的「原生建账分支被永久跳过」完全对应**

`company.py:346` 与 `company.py:362`：

    if not frappe.local.flags.ignore_chart_of_accounts:      # 346
        frappe.flags.country_change = True
        sync_financial_report_templates(...)
        self.create_default_accounts()                       # 原生建账在这里
        self.create_default_warehouses()
    ...
    if not frappe.local.flags.ignore_chart_of_accounts:      # 362
        self.set_default_accounts()

已核实：`ignore_chart_of_accounts` 在两个 app 全仓**只有这 2 处，都是「读」，零处「设置」、零处「复位」**。

⇒ **它是留给下游（自定义 app / 脚本）去设的**。一旦某段脚本把它设成 1 想跳过第一家公司的原生建账，**这个进程内后面建的每一家公司都会被永久跳过建账**（无任何复位点），且 `set_default_accounts()` 一并被跳过 ⇒ 公司没有默认应收/应付科目 ⇒ 后续任何单据都会失败。

**用户「已知」第三条（某 flag 被置 1 后全仓无复位点，导致同进程内建第二家公司时原生建账分支被永久跳过）—— 核实为真，机制定位到 `company.py:346` 与 `company.py:362` 的 `ignore_chart_of_accounts`。**

**差别四：批量插入时 nested set 被刻意关掉，且无 try/finally**

`chart_of_accounts.py:71-74`：

    frappe.local.flags.ignore_update_nsm = True
    _import_accounts(chart, None, None, root_account=True)
    rebuild_tree("Account")
    frappe.local.flags.ignore_update_nsm = False

**这个开关有复位（第74行）—— 但只在正常返回时复位。若 `_import_accounts` 或 `rebuild_tree` 中途抛异常，第74行不执行**（无 try/finally）⇒ `ignore_update_nsm` 留在 True ⇒ 同进程内后续所有树操作都不再维护 `lft`/`rgt`。

且 `rebuild_tree` 里 `frappe.db.auto_commit_on_many_writes = 1`（`nestedset.py:196`）—— **重建树期间会自动提交事务**，意味着**出错回滚也回不干净**。

> 白话：这是「为什么 UI 上点一百次没事、脚本跑一次就炸」的真正原因。
>
> 你在界面上建科目，每建一个都是一次独立的「上门服务」——师傅来了、干完活、走了，把工具都带走。下一次来的是全新的师傅，带全新的工具。
>
> 而脚本是**一个师傅一口气干完所有活**。ERPNext 代码里有好几个「临时把安全检查关掉」的开关，本意是建账时图快。问题是这些开关**关了之后没人负责再打开**：
>
> - 有一个开关（跳过原生建账）**整个软件里没有任何一处会把它复位**。脚本一关，这个进程里之后建的每一家公司都不会建科目表了 —— 这正好就是你遇到的「建第二家公司时崩」。
> - 另一个开关（暂停维护书架编号）虽然写了复位，但**只在一切顺利时才复位**。中途一报错，它就永远留在「关」的状态，之后所有树操作都在悄悄算错。
> - 而且重建树的时候，系统会**自动把改动落盘**。所以「出错了整体撤销」这条退路也被堵了一半 —— 撤不干净。
>
> 官方自己也知道这个问题：他们的**测试代码**里专门写了几行手工清理开关的代码（`test_account.py` 里 4 处）。但**生产代码里没有**。这个坑是官方留给下游自己填的。

### 10.4 那句话唯一的「逃生门」

> 白话：这句话里藏了一个很轻的限定词「通过专门的本地化解决方案」。用软件行业的读法，它其实是在说「配上额外的中国插件之后能合规」。但这个限定词被塞在句子中间，加上「完全符合」四个字的冲击力，普通读者只会读成「买了就能用」。
>
> 说白了：这句话在法律上大概挑不出毛病，但在沟通上会让人产生完全错误的预期。

## 第 11 批：中国二次开发可用的官方扩展口清单（已核实）

这是**建设性结论**：断言 A/B/C 虽多不成立，但 ERPNext 留了几个正规接入点，走它们可以免改上游源码（升级不被冲掉）。

| 扩展口 | 位置 | 现状 | 对中国可用性 |
|---|---|---|---|
| `install_country_fixtures()` | `company.py:858-870` | 按 `erpnext.regional.<国家>.setup.setup` 动态导入 | **可用**：自定义 app 可提供该模块。注意原生对不存在的国家是 `except ImportError: pass` 静默跳过 |
| `regional_overrides` | `hooks.py:609-622` | 现有条目：France、United Arab Emirates、Saudi Arabia、Italy。**无 China** | **可用**：自定义 app 在自己的 hooks.py 里加 `"China": {...}`，可替换 `update_itemised_tax_data`、`make_regional_gl_entries`、`validate_regional` 等函数 |
| `make_regional_gl_entries(gl_entries, doc)` | `purchase_invoice.py:2093`、`sales_invoice.py:2655` | 原生是空钩子，阿联酋在 `regional/united_arab_emirates/utils.py:146` 实现了 | **可用**：这是**给发票追加自定义会计分录**的正规口 —— 进项/销项税分离可从此切入 |
| `validate_regional(doc)` | `accounts_controller.py:4467` | 空钩子，意大利覆写了 | **可用**：可加中国特有校验（如专票必填项） |
| `sync_financial_report_templates()` | `financial_report_template.py:131-153` | 遍历**所有已安装 app** 的 `<module>/financial_report_template/` 目录自动导入 | **可用**：中国格式三大报表模板可由自有 app 提供，系统自动认 |
| `import_account_categories()` | `account_category.py:59-68` | 由上面那个函数在每个 app 的模板目录下找 `account_categories.json` | **可用**：中国特有科目类别（如进项税额、销项税额）可自带 |
| `disable_default_financial_report_template` | `financial_report_template.py:141-151` | 写在科目表 JSON 里，可让地区模板**完全顶掉** ERPNext 自带模板。**现无任何科目表使用** | **可用但未验证**：全仓零使用，属未走过的路 |
| `allow_unverified_charts` | `chart_of_accounts.py:121/143/149`、`account.py:108` | **全仓零处设置** | **死路**：无官方途径打开。且 `account.py:113-114` 一旦打开会让 `validate()` **整体 return**，跳过全部校验（含 `set_root_and_report_type()`）—— 代价是科目建出来但分类字段不被补全 |

**⚠ 重要警示（已核实）**：`account.py:112-114`

    def validate(self):
        if frappe.local.flags.allow_unverified_charts:
            return

打开这个开关不是「放宽某一条校验」，而是**把 Account 的全部 14 项校验整体跳过**，包括 `set_root_and_report_type()`（负责从父科目继承 `root_type`/`report_type`）。**⇒ 用这个开关导入中国科目表，会得到一批 `root_type` 和 `report_type` 全空的科目，报表一个数都出不来。** 这与「82 个 root_type 为空」的现象互相叠加。

> 白话：原本以为「打开那个隐藏开关」是条捷径。实测发现这个开关的作用不是「少查一项」，而是**把科目的所有 14 项检查全部关掉**，其中包括「自动从上级科目继承分类标签」这一步。所以就算硬撬开这道门把中国科目表导进去，导进来的也是一批**没有任何分类标签的空壳科目**，报表还是出不了数。这条路不是捷径，是陷阱。
>
> 真正该走的是另外六个正规接口（上表标「可用」的）：自己做一个「中国财税」插件，通过这些接口把中国的科目、报表模板、发票分录规则挂进去。ERPNext 官方对意大利、阿联酋就是这么做的——有现成的范例可抄。

## 第 12 批：最终判定

| 断言 | 判定 | 缺的具体是什么 |
|---|---|---|
| **A 完全符合中国金税要求** | **不成立** | 零代码。无 `regional/china/` 目录、无金税/发票/税控任何关键词命中、无相关 DocType。`install_country_fixtures()` 对中国静默跳过 |
| **B 符合增值税（VAT）合规要求** | **部分成立** | 成立：价税分离（`included_in_print_rate`）、多档税率（`Item Tax Template`）、税额入指定科目。不成立：增值税月末结转三步（PCV 只取 `report_type="Profit and Loss"`，取不到负债类的增值税科目）、专票/普票区分、进项销项自动分离与申报 |
| **C 支持中国企业会计准则（PRC GAAP）** | **部分成立（偏弱）** | 成立：v16 自带 `Horizontal Balance Sheet (Columnar)` 左右双栏排版 + `Financial Report Template` 模板引擎 + 正规扩展口。不成立：中国科目表在 `unverified/` 且开关无人设置（死路）、82 节点全平铺、`root_type` 与 `account_category` 全空、29 个 `Account Category` 全 IFRS 口径、6 个自带模板行次全国际口径（`Share Capital`/`Reserves & Surplus` 而非「货币资金」「合同负债」）、现金流量表仅 IFRS 版（官网另称有「中国现金流量表（直接法）」—— **未在代码中找到，判为不成立**） |

### 一句话总结

**这句宣传语把「有基础能力 + 有扩展接口」说成了「完全符合」。** 准确的表述应是：ERPNext 提供了做中国合规所需的**框架与接入点**，但中国本地化内容本身**基本为零**（金税完全没有，增值税月结没有，科目表有但装不进去且内容残缺），须由二次开发补齐。这句话在官网 30 多个国家页里是**套模板批量生成的**（泰国页句式完全相同，而泰国科目表同样在 `unverified/` 里用不了），因此不宜当作技术承诺看待。

### 对「还有必要二次开发吗」的回答

**必要，且这不是「加一点东西」，而是要造一个完整的地区化插件。** 但好消息是：v16 的扩展接口比预想的完备（六个可用口，意大利/阿联酋有现成范例），**不需要改 ERPNext 源码**，升级安全性可控。
