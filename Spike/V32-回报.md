## 1. 子项 (a)：自定义 `charge_type` 落库 —— **no-go**，但 G3 的覆盖面不够

G3 自评这是「本次调查里最像 `Bank Transaction Mapping` 的一条」（`S4-G3:106`），也是它自己点名最可能误判的一条。实跑结论：**这次 G3 没有重犯那个错误，核心断言成立**；但它把结论说成「存不下来」，而实测显示**有两条路能存下来**，这是它漏掉的。

### 1.1 实测观察（`V32-out/a-chargetype.json`）

用载体 `Sales Taxes and Charges Template`（其子表就是持有 `charge_type` 的 `Sales Taxes and Charges`），写入越界值 `On Gross Value`：

| 路径 | 是否报错 | 库里实际值 | 结论 |
|---|---|---|---|
| A. 普通 ORM `insert()` | **ValidationError** | 无行 | **拦死** |
| A-对照. 同样 insert 但用 `On Net Total` | 不报错 | `On Net Total` | 对照有效（证明 A 的失败不是别的原因） |
| B. `frappe.flags.in_import = True` 下 ORM insert | **不报错** | `On Gross Value` | **存进去了，逐字保留** |
| C. 直接 `update ... set charge_type=...` 裸 SQL | 不报错 | `On Gross Value` | **存进去了**，且 ORM 读回来也是 `On Gross Value` |
| D. 对 C 种下的值再走一次普通 ORM `save()` | **ValidationError** | 旧值仍在库 | **一改就炸**：库里留得住，但谁碰谁报错 |
| F. erpnext 自己的 `validate_taxes_and_charges` | 不报错 | — | **erpnext 层面不反对**自定义 charge_type |
| G. 直接调 `_validate_selects()` | **ValidationError** | — | 闸门定位确认在此 |

A 与 D 的报错原文逐字一致：

```
Row #1: Type cannot be "On Gross Value". It should be one of "", "Actual",
"On Net Total", "On Previous Row Amount", "On Previous Row Total", "On Item Quantity"
```

### 1.2 下游消费者是否认（phase E）

关键设计：解析器故意返回 `item.amount * 3`（=3000），而 fallback 是 `flt(item.net_amount)`（=1000）。**两者税额不同（300 vs 100），判据因此可区分**——若两边都返回 1000，「税额=100」就无法分辨「解析器跑了」与「fallback 跑了」，判据等于没判。

- 挂 `erpnext_taxable_base_resolvers` 解析器：`resolver_call_count=1`，`tax_amount=300.0`，`net_total=1000.0`，`grand_total=1300.0` → **解析器确实被调用，计算走的是自定义 base**
- 不挂解析器：`tax_amount=100.0` → 落到 `taxes_and_totals.py:677` 的 `return flt(item.net_amount)` fallback，**不报错、静默按净额计税**

所以计税段对自定义 `charge_type` 是**完全支持**的（`taxes_and_totals.py:638-642` 的 `else` 分支、`:649-678` `get_item_taxable_base`）。断链**只在落库校验那一道**。

### 1.3 机制（file:line，均已在容器内逐行核对）

- `frappe/model/document.py:830`（父）、`:843`（遍历 `get_all_children()`，子表逐行）调 `_validate_selects`
- `frappe/model/base_document.py:1101` 定义；`:1102-1103` `if frappe.flags.in_import: return` ← **这就是 B 路能过的原因**
- `base_document.py:1119` `if value not in options and not (frappe.in_test and value.startswith("_T-"))` → `:1125-1128` `frappe.throw`
- `sales_taxes_and_charges.json` `charge_type`：`fieldtype=Select`，`reqd=1`，`options` 为 `"\nActual\nOn Net Total\nOn Previous Row Amount\nOn Previous Row Total\nOn Item Quantity"`（实测逐字确认）
- erpnext 4 个测试全部 `do_not_save=True`（`controllers/tests/test_taxes_and_totals.py:35`/`:49`/`:93`/`:134`）——**G3 这条属实，已在源码逐字复核**

### 1.4 对 G3 的增补

G3 说法是「自定义 charge_type 能存下来从未被测过」，隐含结论是「存不下来」。**更准确的说法是**：普通 ORM 路存不下来；`in_import` 与裸 SQL 两条路存得下来但**属于「带炸弹的持久化」**——D 步证明，这种行落库后任何一次正常 ORM 保存都会抛错。这不是可用方案，但它是一个**与「完全存不下来」不同的事实**，而且正是「静默失败自成一类」这条守则要求区分的情形。

## 2. 子项 (b)：Property Setter 直插扩 Select options —— **go，G3 的「不可行」被推翻**

G3 在 `:155` 自己说：「这一条直接决定 §4 那个『不可行』是否可翻案，值得单独一次实测。」现在实测了：**可翻案。**

### 2.1 三条判据全部成立（`V32-out/b-propertysetter.json`）

「插入没报错」**不是**判据——Property Setter 行存在而什么也不改变是完全可能的。故设三条独立判据，全部须成立：

| 判据 | 观察 | 结果 |
|---|---|---|
| **C1 meta 认** | 未缓存 meta 与已缓存 meta 的 `options` **都**变成 `...\nOn Item Quantity\nOn Gross Value`，且 5 个标准值一个没丢 | ✅ |
| **C2 落库认** | 与 (a) phase A **完全相同**的那个 insert，这次 `raised=false`，库里读回 `On Gross Value`，ORM 也读回 `On Gross Value` | ✅ |
| **C3 下游认** | `calculate_taxes_and_totals` 得 `tax_amount=300.0`、`grand_total=1300.0`、`resolver_call_count=1`；且整张 **Sales Order 真的 insert 成功**（`SAL-ORD-2026-00007`），库里 `charge_type='On Gross Value'`、`tax_amount=300.0` | ✅ |

### 2.2 因果由负对照锁定（这是本子项最要紧的一步）

光看「装了 PS 之后能存了」不足以断定是 PS 起的作用。故：

- **phase 1（前置基线）**：未插 PS 时，同一 insert → `ValidationError`
- **phase 5（装 PS 后）**：同一 insert → 成功
- **phaseZ（回滚后负对照）**：PS 已随回滚消失，**同一 insert 又变回 `ValidationError`**，报错原文与 phase 1 逐字一致

三点连起来才构成「是 PS 造成的差异」，而非环境漂移。

### 2.3 G3 担心的第二道闸门不存在

G3 在 `:155` 猜测 `PropertySetter.on_update` 调 `validate_fields_for_doctype` 时「那里是否另有 Select 校验我没查」。已查并实测：

- `property_setter.py:54-61` `on_update` → `doctype.py:1280` `validate_fields_for_doctype` → `:1225` `validate_links_table_fieldnames` + `:1287` `validate_fields`
- 通读 `validate_fields`（`:1287-1815`）：与 Select 相关的只有两处，**都不是 options 白名单校验**——`check_illegal_default` 只管「默认值须在 options 内」，`scrub_options_in_select` 只做去空格。**没有任何一处比对 `ALLOWED_OPTIONS_CHANGE`**
- 实测插入 `raised=false`，直接证实无第二道闸门

### 2.4 `ALLOWED_OPTIONS_CHANGE` 守的到底是什么（G3 这半句属实）

实测 `phase0_ALLOWED_OPTIONS_CHANGE = ["Read Only", "HTML", "Data"]`，`Select` 不在其中——**G3 引的常量内容与行号全部准确**（`customize_form.py:852`）。且直接调 `CustomizeForm.allow_property_change("options", ...)`（`customize_form.py:329`，`:394` 是那道判断）实测返回 **`False`**，并 msgprint `"You can't set 'Options' for field Type"`。

**所以准确的机制是**：那道守卫只长在 **Customize Form 这一条 UI 路径**上，是**界面层面的限制，不是数据层面的约束**。`property_setter.py` 全文 170 行（已通读）不引用该常量；`frappe/model/meta.py:428` `apply_property_setters` 在 `:446-450` 对 `doctype_or_field == "DocField"` 的行无条件 `d.set(ps.property, cast(ps.property_type, ps.value))`——**它不问这个 property 是否在任何白名单里**。绕过成立的根因就在这里。

### 2.5 两条插入路都行

- 自建 doc + `insert()`：成功，PS 名 `Sales Taxes and Charges-charge_type-options`
- `frappe.make_property_setter(...)` 官方助手：也成功，`helper_route_also_works=true`，且经此路后 insert 同样成功（`save_via_helper_route.persisted_verbatim=true`）

证明绕过不是我这个探针构造 doc 的方式造成的假象。

> 顺带一处上游事实：`frappe.make_property_setter`（`frappe/__init__.py:1193-1245`）**没有 return 语句**，永远返回 `None`。第一版探针读它的 `.name` 因此报 `AttributeError`，已改。与本命题无关，但调用方要注意。

### 2.6 一个不该忽略的旁证

`customize_form.py:688` `reset_customization` 的过滤条件里写着 `"property": ["!=", "options"]`——**上游自己在「重置定制」时刻意跳过 `options` 类 Property Setter**。这说明上游知道 options 型 PS 存在且不打算在重置时动它。对「靠 PS 扩 options」这条路的稳定性是正面信号，但也意味着**它不会被 reset_customization 清掉**，装上就得自己负责卸载。

## 3. 子项 (c)：per-doc 缓存是否跨单据泄漏 —— **G3 的说法对了一半**

G3 两处表述：`:80`「`:896` 缓存是 **per-doc** 的，同一单据生命周期内改设置不生效（**不是进程级陷阱**）」；`:157` 自承「是 per-doc 还是会跨单据泄漏……**未验**」。

实测结论：**它命名的那一层（L1）确实是 per-instance、不跨单据；但它断言的「不是进程级陷阱」不成立——另有两层缓存会让陈旧值到达新单据与跨请求。**

### 3.1 三层缓存，逐层实测（`V32-out/c-stockexpense-cache.json`）

被测代码 `erpnext/controllers/stock_controller.py:896-902`：

```python
def book_stock_expense_enabled(self):
    if not hasattr(self, "_book_stock_expense_enabled"):
        self._book_stock_expense_enabled = cint(
            frappe.db.get_single_value("Accounts Settings", "book_stock_expense_gl_entries"))
    return self._book_stock_expense_enabled
```

**L1：`self._book_stock_expense_enabled`（实例级）→ G3 属实**

- 新实例上属性不存在（`attr_present_on_brand_new_instance=false`），首次调用后出现，**懒建**
- 同一实例：翻设置 0→1 后，DB 读到 1，实例仍返回 **0** → `L1_same_instance_is_stale=true`。**G3 这条完全属实**
- **另一个单据**：新 `Purchase Receipt` 实例返回 **1**（当前 DB 值），属性调用前不存在；已保存单据 `MAT-PRE-2026-00002` 同样返回 1；`class_level_attr_present=false` → **`L1_leaks_across_documents=false`，不跨单据**
- 只有删掉属性（或换实例）能清 L1：`delattr_clears_L1=true`；`reload()` **不清**（`reload_clears_the_cache=false`）

**L2：`get_single_value` 自己的 `value_cache`（连接级=进程级）→ G3 的「不是进程级陷阱」被推翻**

`frappe/database/database.py:900` 命中即返回、`:926` 填充，仅在 `commit()`（`:1193`）／`rollback()`（`:1200`/`:1209`/`:1214`）与 `clear_document_cache`（`document.py:2321`）时清空。实测：

- 用裸 SQL 把 `tabSingles` 改成 0（绕过 `set_single_value` 的失效逻辑）
- 裸读 DB = `0`；`get_single_value(...)` 仍返回 **1**；`get_single_value(..., cache=False)` 返回 **0** → `L2_get_single_value_is_stale_after_raw_write=true`
- **全新 `Purchase Receipt` 实例返回 1** → `L2_leaks_into_brand_new_document=true`。**这是真正的跨单据泄漏**，且发生在 L1 完全洁净的情况下
- 更要紧：`buying_controller.py:345` 那个**根本没有 `self._` 缓存**的直读点，同样返回 1 → `L2_affects_uncached_reader_too=true`。**「去掉 per-doc 缓存就没事」是错的**

**重要限定（诚实边界）**：L2 泄漏需要 `tabSingles` 被**不经 `set_single_value` 的路径**改写。正常走 `frappe.db.set_single_value`（`database.py:843-872`，末行调 `clear_document_cache`）时不会泄漏——phase 2/3 即是此情形，新单据立刻看到新值。所以 L2 是**条件性**陷阱，不是无条件的。

**L3：redis 文档缓存（跨请求）→ G3 完全没看到这一层**

- 把已 warm 属性的 doc 放进文档缓存，只清进程内 `frappe.local.cache` 条目、保留 redis 载荷，再取回
- `revived_is_distinct_object=true`（确实是 pickle 反序列化出的新对象，不是同一对象）
- `L3_stale_attr_survives_serialized_cache=true`，`L3_revived_attr_value=1` → **`_book_stock_expense_enabled` 被 pickle 进了 redis 载荷，陈旧值跨请求存活**
- 属性**不在** `as_dict()`／`get_valid_dict()` 里（都 false），所以它不是 DB 字段——但 pickle 序列化 `__dict__`，照样带走

这比 G3 描述的「同一单据生命周期内」严重一档：**同一单据、不同请求**也可能拿到陈旧值。

> 判据自查：此 phase 第一版得出 `revived_is_distinct_object=false`（同一对象），那等于什么都没证明。根因是 `frappe.local.cache` 的键经 `redis_wrapper.py:55-62` `make_key` 加了库名前缀并编码，我 pop 的是原始键，**没清掉任何东西**。改用 `frappe.cache.make_key(ckey)` 后判据才真正可区分。同理 phase 5 第一版拿 warm 值 0 去比对目标值 0，「相等」与「陈旧」不可分辨，已改为**把 DB 驱到 warm 值的反面**（`criterion_is_distinguishing=true`）再比。

### 3.2 (c) 的判决

- 「L1 是 per-doc、不跨单据」→ **go，G3 属实**
- 「不是进程级陷阱」→ **no-go，被推翻**。L2 是连接级，条件成立时跨单据；L3 跨请求
- 未验：**关掉开关后实际少了哪些 GL 分录**。该验证须提交 Purchase Receipt，而 `repost_item_valuation.py:397`、`:465` 有 `frappe.db.commit()`、`:646`／`:658` 有 `frappe.enqueue`，不可回滚，按规则禁跑。本子项**只回答被问的缓存语义问题，不声称任何关于产出分录的结论**

4. erpnext 4 个计税测试全部 `do_not_save=True`、从不落库 —— 源码逐字确认
5. `ALLOWED_OPTIONS_CHANGE = ("Read Only", "HTML", "Data")` 不含 Select，`customize_form.py:394` 会 msgprint 拒绝 —— 确认，且**实调 `allow_property_change` 返回 `False`**

### 5.2 本次实跑**推翻**的 G3 断言

1. **【主要推翻】§4「Property Setter 直插扩 Select options 不可行」→ 可行。** meta 认、落库认、下游认，负对照锁定因果。连带使 §4 整条「自定义 `charge_type` 作为价税分离抓手不可行」的判定**失去依据**——那条「不可行」的唯一支点就是「扩不了 options」
2. **`:80`「不是进程级陷阱」→ 不成立。** `get_single_value` 的 `value_cache` 是连接级（`database.py:900`/`:926`），条件成立时陈旧值会到达全新单据；且影响 `buying_controller.py:345` 那个无 `self._` 缓存的直读点
3. **G3 未发现的第三层：** `_book_stock_expense_enabled` 会被 pickle 进 redis 文档缓存，**陈旧值跨请求存活**，比 G3 描述的「同一单据生命周期内」更严重
4. **「自定义 charge_type 存不下来」这个隐含结论过强。** `frappe.flags.in_import`（`base_document.py:1102-1103`）与裸 SQL 两条路都能逐字存进去；只是存进去之后任何一次正常 ORM 保存都会抛错（D 步实测）

### 5.3 对「Property Setter 不能扩 Select options」这个判定的明确答复

**该判定被推翻。** 不是「看起来可能可以」，而是三条独立判据（meta／落库／下游计算）全部由打印输出证实，并有回滚后的负对照证明因果归属。机制根因已定位到 `frappe/model/meta.py:446-450`：`apply_property_setters` 对 DocField 的 property 无条件 `d.set(...)`，不查任何白名单；`ALLOWED_OPTIONS_CHANGE` 只是 Customize Form 这条 UI 路径上的门禁（`customize_form.py:394`），不是数据层约束。

### 7.3 方法上值得记下的两处

本次有**两个判据在第一版是不可区分的**，都靠「先自问这个判据能不能分辨它声称分辨的两种情形」发现并修掉：

1. (a)/(b) phase E/C3 原设计里解析器与 fallback **都返回 1000**，税额同为 100 → 无法分辨「解析器跑了」和「fallback 跑了」。改成解析器返回 3 倍（300 vs 100）后才可判
2. (c) phase 6 原本 pop 了错误的缓存键（`frappe.local.cache` 经 `redis_wrapper.py:55-62` `make_key` 加库名前缀），**什么也没清掉**，于是拿回同一个对象却被误读成「属性存活」；phase 5 原本拿 warm 值 0 比对目标值 0，「相等」与「陈旧」不可分辨

两处都印证 LG-131 那条守则的实际价值：**判据必须能分辨它声称分辨的情形，「没报错」和「值对了」都不是「生效了」。** 这两个缺陷不是读码读漏，而是**判据设计**本身的缺陷——即便全程实跑也会得出错结论，值得作为独立教训记下。
