# V-26 回报 — 同一张报表里能否一列「本年累计」一列「本月」

**命题**：`accumulated_values` 是报表级开关、非列级 ⇒ 同表内**做不到**一列累计一列单月（《小企业会计准则》利润表法定的「本年累计金额／本月金额」两栏）。

**判定**：**`no-go`** —— **命题被证伪。实测两列并存成功。**

**探针**：`V26-accumulated-vs-monthly.py` ／ 原始输出 `V26-out/accumulated-vs-monthly.json`
**站点**：`erx.localhost`，公司 `华东弹簧`
**写入**：无。临时模板在事务内 `insert`、`finally` 里 `rollback()`，全程无 `commit()`。已验：`template_exists_after_rollback` = `false`、`stray_exported_files` = `[]`、FRT 计数回到 6

**⚠ 一处刻意的探针设计，写明**：临时模板的 `module` **故意留空**。因为 `FinancialReportTemplate.on_update()` → `_export_template()` 在 `module` 有值时会把模板 json **写进 erpnext 源码树**，那是 `rollback()` 撤不掉的文件系统副作用。留空即绕开该分支。

## 一、判据：用一个「只有一个月有账」的站点做可证伪实验

`华东弹簧` 的损益类 GL **全部落在 2026-09**（独立算得 `{"2026-09": -719.5}`，未经引擎）。于是两种归集方式在 10 月之后必然分岔：

- 累计列 → 9 月的值**保持住**
- 单月列 → **掉回 0**

## 二、实测结果

建一张两段模板，两段**选同一批科目**，**只有 `balance_type` 不同**：

| 段 | `Column Break.display_name` | `balance_type` |
|---|---|---|
| seg_0 | `本年累计金额` | `Closing Balance` |
| seg_1 | `本月金额` | `Period Movement (Debits - Credits)` |

`periodicity=Monthly`、FY2026，跑真引擎。净利润行：

| 月份 | `本年累计金额` 列 | `本月金额` 列 |
|---|---|---|
| Aug 2026 | 0.0 | 0.0 |
| **Sep 2026** | **719.5** | **719.5** |
| **Oct 2026** | **719.5** | **0.0** |
| **Dec 2026** | **719.5** | **0.0** |

三项断言全部成立：`cumulative_holds_after_sep`=true／`monthly_drops_after_sep`=true／`two_columns_differ_in_oct`=true。营业收入（1045.0）与营业成本（325.5）两行同型，且 `1045.0 - 325.5 = 719.5` 与独立算得的裸 GL 合计 **逐位吻合**。

## 三、为什么做得到 —— 机制

**关键是 `accumulated_values` 这个 filter 在本报表上压根不存在。** 实测三份 js 的出现次数：

| 文件 | `accumulated_values` 出现次数 |
|---|---|
| `custom_financial_statement.js`（FRT 报表） | **0** |
| `financial_statements.js`（共享基座） | **0** |
| `balance_sheet.js`（旧报表） | 1 |

于是引擎里 `filters.get("accumulated_values")` 恒为 `None`，命中 `_handle_balance_accumulation():711-715` 的 **`continue` 分支**：

```python
if accumulated_values is None:
    # respect user setting if not in filters
    # closing = accumulated
    # movement = unaccumulated
    continue
```

注释就是答案：**`closing` 天然累计、`movement` 天然单月，两者在 `PeriodValue` 上并存**（`:60-66` 的 `get_value` 按 `balance_type` 三选一）。而 `balance_type` 是**行级字段**。

**⇒ 那个「报表级开关」只在被显式传入时才拉平全表**（旧的 `balance_sheet.py` 会传）。FRT 路径不传，故累计与单月是**同时可取的两个值**，按行各取所需即可。R1 判据里「`accumulated_values` 是报表级开关」这句**代码上没错**，但推不出「同表做不到两列」——**推理跳了一步**。

## 四、代价（事实，不是建议）

列集实际长这样：`本年累计金额`／`本年累计金额 - Jan 2026`…`- Dec 2026`／`本月金额`／`本月金额 - Jan 2026`…`- Dec 2026`，**共 26 个可见列**。即：

1. 每段带出自己的期间全轴（12 个月 × 2 段），不是法定的两列；
2. 段与段之间插入一个**重复的项目列**（`seg_1_account`）;
3. 列头仍是 `段标签 - 期间标签` 拼接（与 V-25 同一机制）。

法定利润表要的是「项目 ｜ 本年累计金额 ｜ 本月金额」三列。**引擎给的是 26 列**（`periodicity=Monthly`）。`Yearly` 下每段只剩 1 列（seg2 已验，见下），但那时 `Period Movement` 就是全年发生额、不是本月。

**⇒ 两个数确实能在一次运行里同时拿到**（`Monthly` 下读当月的 `seg_0_{月}` 与 `seg_1_{月}`），但它们**嵌在 24 个期间列里**，要成法定三列形态须隐藏其余 22 列。

## 四·补 seg2 — `Closing Balance` 是不是「本年累计」（原复核建议第 2②／第 3 条，已验）

**探针**：`V26-seg2-crossperiod.py` ／ 输出 `V26-out/seg2-crossperiod.json`。同样事务内建模板、`rollback`，已验 `template_exists_after_rollback`=false、FRT 计数回 6、GL 仍 22。

**判定：`Closing Balance` 是从有账以来的滚动余额，不是本年累计额。**

把报表区间起点挪到**所有 GL 之后**（`Date Range` 2026-10-01…12-31，而全部损益类 GL 在 2026-09-21）：

| | Oct | Nov | Dec |
|---|---|---|---|
| `Closing Balance`（收入） | **1045.0** | **1045.0** | **1045.0** |
| `Period Movement`（收入） | 0.0 | 0.0 | 0.0 |

**区间内一笔账都没有，`Closing Balance` 仍报 1045.0** ⇒ 它把区间之前的发生额全带进来了。

**机制已读码坐实**（三个函数源码留在 json 里）：`_get_opening_balances()` 先找 `period_end_date < 区间起点` 的**已提交 `Period Closing Voucher`**；找到则从 `Account Closing Balance` 重定基准；**找不到就走 `_get_opening_balances_from_gl()`——以 `1900-01-01` 为起点**，再由 `_rebase_closing_balances()` 把 `1900-01-01` 到区间起点之间的全部 GL 算成期初。本站点 **PCV 0 条、`Account Closing Balance` 0 行**，故走的正是后一条。

**⇒ 对损益类科目，`Closing Balance` 只在两种情况下等于「本年累计金额」**：① 上一年度**没有**损益发生额（本站点恰好如此，故 seg1 那次实测通过）；② 上年末**做过年结 PCV** 把损益科目结平。**第 ② 条的代码路径存在（`:536-547`），但本探针未验**——站点只有一个会计年度，且建 PCV 是真写入。

**一条跨议题事实**：年结 PCV 正是 **CR-007 的「月末结转」范围内的东西**。即「配模板」这条路要成立，**依赖本 Stage 自己要做的那块结转**先做对。

**顺带验到**：`periodicity=Yearly` 时每段**恰好 1 个期间列**（`yearly_column_count_per_segment`=1）。

## 五、复核建议

1. **最该先看的：`no-go` 这个判定直接推翻 R1「BS＋PL 自写」的一半判据，代价最大。** 查法：读 `V26-out/accumulated-vs-monthly.json` 的 `DECISIVE` 键（四个布尔 ＋ 两组按月数值），再对照 `raw_gl_pl_movement_by_month`（`{"2026-09": -719.5}`）确认引擎数与裸 GL 一致。若要重跑，改 `watch` 列表里的月份即可。
2. **第二该看的：`no-go` 成立，但「能用」比 `no-go` 这两个字窄得多。** seg2 已证 `Closing Balance` 是滚动余额 ⇒ 它等于「本年累计金额」**有前提**（上年无损益发生额，或上年末做过年结 PCV）。**故本条的准确表述是**：「一列累计一列单月」在引擎里**可并存**（原命题证伪），但**要在第二个会计年度以后仍正确，须依赖年结 PCV**——而那属 CR-007 自己要做的月末结转。查法：读 `V26-out/seg2-crossperiod.json` 的 `DECISIVE_seg2`（Oct 无账却报 1045.0）与 `get_opening_balances_source`（`1900-01-01` 那条回退路径）。
3. **观察范围的边界**：单站点、单公司、单会计年度、**损益 GL 仅 3 条且全在 2026-09-21**。**仍未验两件事**：① **年结 PCV 真能否把损益科目结平并让累计列从本年起算**（代码路径在 `:536-547`，但建 PCV 是真写入，本探针不碰）；② 多月有账时逐月累计值是否正确递增（站点只有一个月有账，验不了）。**第 ① 条是「配模板」这条路的最后一块拼图**。
4. **拿不准处**：我拿 `Closing Balance` 映射「本年累计」、`Period Movement` 映射「本月」。**这个映射是我选的，不是上游命名的**——上游没有任何字段叫「本年累计」。seg2 已把这个选择的代价查清（滚动余额、依赖年结），但**是否接受这个代价是判断题**，属 B 步与用户，不在本探针射程内。
